> **v0.9 仓库容量与邮件（本文已同步）——先说结论：ρ / M̄ / D̄ / B / σ / `headline` / 归因算法全部不受仓库与邮件影响。**
>
> 上游给每个实例加了**落点** `location ∈ {warehouse, mail}`，并给仓库加了**容量**（`warehouse_capacity`、`ItemDef.size`；放不下的产出进邮件——核心 §4.7 / §14.2 铁律 9）。
> **而本系统的每一个数字都只依赖概率分布（`probs` + `void_prob`）与 `ItemDef.value`——不依赖持有形态，更不依赖持有位置。** 一盒开出什么、值多少 TVU，与那件东西**落在仓库还是邮件里**无关；`σ` 同理，它的求和范围是**分布**，不是货架。
> **因此：公式、三个因子、量纲校验、方差公式、归因顺序、缓存与共享求值路径一律不变**（核心 §16.4："C1–C6、P1–P7、D1–D14、ρ 公式一律不变"）。**后来者请勿据此改动任何公式，也不要为 `location` 或仓库容量新增失效依据。**
>
> **但有一条间接影响必须写清（它不改公式）**：核心 §4.7 / §14.2 铁律 9 明确 **`count()` 只统计 `location == warehouse` 的实例，邮件里的物品不可用于交付 / 装配 / 镶嵌 / 转化**。
> 于是当仓库满、产出持续进邮件时，**玩家实际能交付的物品少于模型假设**——**"仓库满"会降低*实际可达*的 ρ，但不改 ρ 的公式**。这是模型**外**的**可达性**约束（输入被卡住），不是 ρ 的定义变化：**它不进入 `attribution`**（它不是模块 / 装置 / 任务结构 / 损耗任一项的贡献，§5.5 的固定归因链一行不动）。口径区分见 §2 与 §5.2。
> **裁决 15（v0.9 追加，本文新增 §5.6）**：仓库满时产出可能**整批进邮件**，而邮件实例**不可交付**——因此**任务生成侧的守门量不能再按总产出计**（否则会生成"算得出来却永远交不了"的需求）。本文给出守门口径 **`expected_deliverable(t)`（可交付产出的保守下界）**，见 **§5.6**。**注意：M̄ 本身不变**，变的只是**守门用的那个量**。
> **裁决 12（v0.9，本文只确认、不改公式）**：权威守恒等式是 **`total_granted − total_consumed == Σ 全部实例（含邮件）`**；**`count()` 只是带 `location` 过滤的查询，不是守恒量**。本文**不引用、也不得引入任何"仓库内 Σcount == 差值"之类的等式**（§5.2）。
> **裁决 13（v0.9，本文只确认）**：**不承诺跨系统原子性**——`transact()` 只覆盖物品侧，Box 发放与解锁靠各自幂等键 + 重放。**本系统本来就是纯只读的**，不参与任何事务（§7）。
>
> 本文只有六处**引用性**调整：①§2 边界与 §3 术语新增 `warehouse` / `mail` / `location` 三个**只读引用**（归属 02，**不进入任何公式**）；②§5.2 增加"位置无关"的排除性说明与"可达 ρ ≠ ρ"的口径区分；③§7 流程明确 `location` 与容量变化**不是**缓存失效条件；④§8 接口表增补 02 侧仓位 / 容量接口的**只读、不消费**说明；⑤§10.2 的 **T12 由"实例化无关性"扩展为"持有形态与位置无关性"**；⑥**新增 §5.6 守门口径 `expected_deliverable(t)`**（裁决 15——**只定义口径，不计算**：仓库余量不是本系统的输入）。

## 1. 这个系统负责什么

1. **概率求值路径**——本作唯一的一条。`EvalService` 与 `GachaService` 必须共用它（README §2.2 铁律）。
2. **ρ 的定义与计算**：`ρ = (M̄ / D̄) × B`
3. **M̄ / D̄ / B 的口径**：把物品、任务、装置、池子编辑折算成同一单位
4. **σ（方差）**：第二轴的显式数值
5. **`headline`**：盲盒默认层那两个数字的**产出方**（渲染归 08）
6. **归因**：把 ρ 的变化逐项分解到模块 / 装置 / 任务结构 / 损耗
7. **缓存与失效**：UI 高频调用下的性能保证
8. **守门量的口径（v0.9 新增 / 裁决 15）**：**`expected_deliverable(t)`**——任务生成侧"可交付产出"的**保守下界**（§5.6）。**只定义口径**：仓库余量 `F` 由 02 提供只读输入、求解与使用归 03（本系统**不计算它**，也不放进 `EvalResult`）。

## 3. 核心概念与术语

| 术语 | 代码名 | 说明 |
|---|---|---|
| 任务价值点 | `TVU` (Task Value Unit) | **本作的统一计价单位**。物品、需求、产出全部折算成 TVU |
| 单盒期望产出 | `m_bar` | 开 1 盒平均产出多少 TVU |
| 单任务平均消耗 | `d_bar` | 完成 1 个任务平均消耗多少 TVU |
| 单任务奖励盒数 | `b` | 完成 1 个任务平均奖励多少个盲盒 |
| 闭环收益率 | `rho` | `(m_bar / d_bar) × b`，无量纲 |
| 方差 | `sigma` | 单盒产出（TVU）的标准差 |
| 封面数据 | `headline` | `{best_item, best_item_prob, ev}` |
| 空洞 | `void` | 排除损耗产生的零价值结果（见 §5.4） |
| 归因 | `attribution` | ρ 变化的逐项分解 |
| 基线 | `baseline` | 无任何模块 / 装置的原始池 + 基础任务结构 |
| 常规物品数 | `regular_count` | 该套系常规物品的数量（由套系品质决定，核心 §4.1.1）；C6 与 `headline` 候选集依赖它 |
| 物品实例 | `ItemInstance` | 玩家实际持有的**一个**物品（核心 §4.2.1）。**归属 02**；本系统**只读**——不创建、不销毁、不计数（v0.8） |
| 实例 id | `instance_id` | **UUIDv4，全局唯一**，兼作幂等键（核心 §4.2.1）。**归属 02**；本系统既不生成也不消费它——**ρ 与实例身份无关**（v0.8） |
| 持有量 | `count` | **派生值**：按 `(category, quality)` 由实例列表数出并缓存，**不是存储字段**（v0.8）；**v0.9：只统计 `location == warehouse` 的实例**。**归属 02**，仅供任务匹配与 UI（§8）；**不进入 ρ / M̄ / D̄ / σ / `headline` 的任何公式** |
| 仓库 | `warehouse` | 落点之一（`location == warehouse`），也是 `count()` 唯一统计的集合（核心 §4.7）。**归属 02**；本系统**只读引用、不消费**——不进入任何公式（v0.9） |
| 邮件 | `mail` | 落点之二：仓库放不下的产出进邮件，无上限、不过期；**邮件实例不可用于交付 / 装配 / 镶嵌 / 转化**（核心 §4.7 / §14.2 铁律 9），**因此会压低"实际可达的 ρ"，但不改 ρ 的公式**（§5.2）。**归属 02**；本系统**只读引用、不消费** |
| 落点 | `location` | `warehouse` / `mail`，实例的位置属性（核心 §4.2.1 / §4.7）。**归属 02**；**ρ / M̄ / D̄ / B / σ / `headline` 与归因都不读它**（v0.9） |
| 套系品质 | `series_quality` | 该套系的品质等级，决定 `regular_count` / `socket_count` 与物品品质区间。**与物品品质 `quality` 不是同一个概念** |

> **v0.8 术语纪律**：`ItemInstance` / `instance_id` / `count` 三项**都是 02 的术语**（README §5），本文**只引用、只读**，不复述其字段定义（见 `02-item.md`）。
>
> **v0.9 术语纪律**：`warehouse` / `mail` / `location`（以及 `warehouse_capacity` / `ItemDef.size`）同样**归属 02**，本文**只读引用**——**它们不出现在任何公式、任何 `EvalResult` 字段与任何归因条目里**（§5.2）。**"只统计仓库内实例"的 `count` 口径本身也不进入本系统**（§2）。

> **⚠️ 术语纪律（v0.6）："品质"有两个含义，本系统内不得混用。**
> - **物品品质 `quality`**（1–5 序数，`ItemDef.quality`，**字段定义归 02**，见 `02-item.md`）：本系统中 **`v_i`（物品的 TVU 价值）涉及的是它**；
> - **套系品质 `series_quality`**（1–4，核心 §4.1.1）：决定该套系的 `regular_count` 与 `socket_count`，由里程碑任务解锁。
>
> 两者**没有任何换算关系**：`v_i` 的高低不改变 `regular_count`，`series_quality` 也不直接进入 `v_i` 的定义（它只通过"高品质套系提供更高品质区间的物品"间接影响 `v_i` 的分布）。

### 3.1 为什么需要 TVU

物品有类别与品质两个维度（见 `02-item.md`），任务需求也是向量，两者无法直接比较。**TVU 是把它们压成一个标量的桥。**

- 物品 `i` 的价值 `v_i` 取自 `ItemDef.value`（**字段归属 02**，见 `02-item.md` 与 §8 接口表），定义为：**它能贡献的 TVU 数**
- 任务需求的 TVU = 需求向量中各项折算之和
- 于是 M̄ 与 D̄ 可以相除

**TVU 是本作唯一允许出现的"通用价值"单位。** 任何系统不得引入第二套计价。

## 4. 数据结构

```gdscript
# res://autoload/eval_service.gd
class_name EvalService

## 单池求值结果——EvalService 与 GachaService 共用的唯一数据契约
class PoolEvaluation:
    var probs: PackedFloat32Array      # 每个 Item 的最终概率，length = series.items.size()
    var void_prob: float               # 空洞概率（排除损耗产生，见 §5.4）
    var is_normalized: bool            # 是否满足 probs.sum() + void_prob == 1.0
    var revision: int                  # 求值时的 pool_state.revision，用于缓存校验

## ρ 的完整分解
class EvalResult:
    var rho: float
    var m_bar: float
    var d_bar: float
    var b: float
    var sigma: float
    var headline: Headline
    var attribution: Array[AttributionEntry]
    var distribution: PackedFloat32Array
    var void_prob: float
    var revision: int

class Headline:
    var best_item_id: StringName        # 当前池中价值最高的"可产出"物品
    var best_item_prob: float           # 其最终概率（受池子编辑影响）
    var ev: float                       # = m_bar，单位 TVU

class AttributionEntry:
    var source_kind: int                # MODULE / DEVICE / TASK_STRUCTURE / LOSS / BASELINE
    var source_id: StringName           # 模块或装置的 id
    var delta_rho: float
    var delta_m_bar: float
    var delta_d_bar: float
    var delta_b: float
    var delta_void_prob: float = 0.0    # 该项贡献的 void 概率增量
    var void_breakdown: Dictionary = {} # item_id -> 该物品被排除所贡献的 void 分量（LOSS 条目专用）
    var note: String                    # 人类可读，如「排除 3 个物品」
```

> `[补充]` `delta_void_prob` 与 `void_breakdown` 是按 `08-ui-panels.md` §11 的 **U9** 契约请求新增的：08 的直方图与"空洞来源"行需要逐个物品分解，若让 UI 层自行按 40% 换算，即违反"单一数据源"（跨系统铁律 3）。**因此分解必须在 `EvalService` 内完成**。08 侧对应的实现要求见其 §5 R-10/R-11 与 §9。

```gdscript
## 只读依赖：本系统读取但不修改
class_name PoolState:
    var series_id: StringName
    var revision: int                   # ★ 每次 PoolService 写入时 +1，缓存与失效的唯一依据
    var banned: Array[StringName]
    var boosted: Dictionary             # item_id -> multiplier
    var socket_count: int               # 该套系的常量（由套系品质决定），从 SeriesDef.socket_count 拷贝，运行时不可变（C4）
    var regular_count: int              # 该套系的常规物品数（由套系品质决定），从 SeriesDef 拷贝；C6 与 headline 候选集依赖它
    var socketed_modules: Array[StringName]
```

> `[补充]` `regular_count` 随 `socket_count` 一起在 `PoolService` 建档时从 `SeriesDef` 拷入 `PoolState`，理由是让求值与缓存**只依赖 `PoolState` 一个输入**（`revision` 驱动），避免求值路径回头读 `SeriesDef` 造成两份事实来源。

## 5. 规则与公式

### 5.1 概率求值（唯一路径）

```
evaluate_pool(pool_state, series):
  1. w[i] = series.base_weight[i]
  2. 隐藏物品：w[hidden] 固定，不允许被 3~6 步影响（C3）
  3. 未拥有物品加权：w[i] *= 1.5        （规则归 01，此处执行）
  4. 排除：w[banned] = 0，释放质量 m = Σ series.base_weight[banned]
  5. 提升：w[boosted[i]] *= multiplier
  6. 损耗：释放质量中仅 0.6 可回收，0.4 记为 void_mass
  7. 归一化：probs = w / Σw  （在 regular_count 个常规物品之间，不假设物品数），隐藏物品独立占 2%
  8. void_prob = void_mass（见 §5.4）
```

> `[补充]` 步骤顺序被固定（加权 → 排除 → 提升 → 损耗 → 归一化），因为顺序会影响结果。固定顺序使求值可复现，也让归因可对账。

### 5.2 三个因子

```
m_bar = Σ (probs[i] × v_i)        # v_i 取自 ItemDef.value（**字段归属 02**，见 §8 接口表）；void 的 v = 0，不贡献
d_bar = 任务需求向量的 TVU 折算（含装置修正）
b     = 任务奖励盒数（含装置修正）

rho = (m_bar / d_bar) × b
```

量纲校验：
```
(TVU / 盒) / (TVU / 任务) × (盒 / 任务) = 任务 / 盒 × 盒 / 任务 = 无量纲 ✓
```
ρ 的含义即"**每投入 1 个盲盒，最终回收多少个盲盒**"。

> `[补充]` 核心设计书 §2.3 写作 `M̄ = Σ(pᵢ × vᵢ) × 池子修正`。此处把"池子修正"**显式展开为编辑后的 `pᵢ`**，因为池子编辑的全部效果就体现在 `pᵢ` 上，不存在独立的修正乘数。这是表述澄清，不是机制改动。

> **v0.8（实例化不在公式里——这是本节最容易被误改的一点）**：`m_bar` 与 `sigma` 的求和范围是**概率分布**，不是持有量。因此 **`count`（派生值）、`instance_id`、`serial`、`source` 都不出现在任何公式中**：玩家把同一件物品记成"计数 3"还是"3 个实例"，`Σ (probs[i] × v_i)` 的结果逐位相同。
> **实例化只改持有模型，不改期望**——ρ / M̄ / D̄ / B / σ / `headline` / 归因算法**全部不变**（核心 §16.3）。本文不因此新增任何输入、参数或公式项。

> **v0.9（仓库与邮件同样不在公式里——本条与上一条是一对，结论同样是"公式一行都不改"）**：`location`、`warehouse_capacity`、`ItemDef.size`、邮件条目**都不出现在任何公式中**：`Σ (probs[i] × v_i)` 的求和范围是**概率分布**，不是货架；给定同一份 `probs` 与 `ItemDef.value`，物品**落在仓库还是邮件里**，`m_bar` / `sigma` / `headline` 逐位相同。
> **因此"持有形态与位置无关性"是同一条不变量**（§10.2 T12）：v0.8 守护"计数 vs 实例"，v0.9 追补"**仓库 vs 邮件**（含把仓库容量改到 0 或无限）"。
>
> **"ρ"与"实际可达的 ρ"是两个量（v0.9 必须分清，否则一定有人来改公式）**：
>
> | 量 | 定义 | 受仓库容量 / 溢出影响吗 |
> |---|---|---|
> | **ρ（本系统的口径）** | `(m_bar / d_bar) × b`——**模型值**：在"产出可用于交付"这一前提下算出的闭环收益率 | **不受影响**。公式、三个因子、σ、归因一律不变 |
> | **实际可达的 ρ** | 玩家**真正能跑到**的收益率：它额外要求产出物**在仓库里**（邮件里的实例不可交付 / 装配 / 镶嵌 / 转化，核心 §4.7） | **受影响**：仓库满 → 可交付物变少 → **实际可达 ρ 低于模型值** |
>
> **结论：容量满会压低"实际可达的 ρ"，但不改 ρ 的公式。** 这张表的右列就是这条区别的答案——**变的是可达性，不是定义**。三条推论（都必须遵守）：
> ① `EvalResult` **不新增字段**，`attribution` **不新增条目**——外部可达性不是模块 / 装置 / 任务结构 / 损耗任一项的贡献，**§5.5 的固定归因链与可加性公式一行不动**；
> ② 本系统**不实现**任何"因容量而对 ρ 打折"的修正项，也**不把 `location` 当输入**；全绿前提不变：P7 / C1–C6 / ρ 公式均与本改动无关（核心 §16.4）；
> ③ 切片**不产出**这个"可达 ρ"的数：若将来要在 UI 上提示这一折损，**必须先在本文定义口径**（§11 E7），再由 08 呈现——**不得由 UI 私自换算**（跨系统铁律 3）。

> **裁决 12（守恒等式只按全部实例，v0.9 确认，不改公式）**：权威守恒式是 **`total_granted − total_consumed == Σ 全部实例（含邮件）`**，而 **`count()` 只是带 `location` 过滤的查询、不是守恒量**。因此本文**不引用、也不得引入**任何形如"**仓库内 Σcount == 差值**"或"`count` 之和 == 累计产出"的等式——在 v0.9 下这类等式**必然不成立**（产出可以整批进邮件）。
> **本系统不参与守恒校验**（归 02 / 03），也不消费 `total_granted` / `total_consumed`；本文的任何数字都来自**分布**与 `ItemDef.value`，与实例账本无关（§5.2 上一条）。**后来者请勿用守恒等式去推导 ρ 的任何量。**

**`regular_count` 进入公式的位置（v0.6）：** 核心 §4.1.1 起，常规物品数由**套系品质**决定（品质 1/2 = 8 个物品，品质 3/4 = 12 个物品），**不再是常量 8**——所以本系统内部不得再假设"8 个常规物品"：

| 量 | 与 `regular_count` 的关系 |
|---|---|
| `m_bar` | **无关**。只依赖最终分布 `probs`（含 `void`），求和范围是**实际存在的物品**，8 或 12 都不进入公式 |
| `sigma` | **无关**，理由同上（§5.3） |
| `headline.best_item` | **依赖**。头奖候选集 = 该套系全部常规物品 ∪ 隐藏物品中**可产出**者，取 `v` 最高；物品数变了候选集就变了（核心 §6.1） |
| C6 判定 | **依赖**。排除上限 = `regular_count − 3`，即可产出常规物品数 ≥ 3（§10.1 T7） |

> 因此 `probs` 的长度、归一化范围、C6 校验一律以 `pool_state.regular_count` 为准，**不得写死 8**。

### 5.3 方差

```
sigma = sqrt( Σ probs[i] × (v_i - m_bar)² )     # void 以 v = 0 参与
```

求和范围同样是**实际存在的物品**（含 `void`），**与 `regular_count` 无关**——物品数变化不改变方差公式本身，只改变分布的取值集合。

**σ 是一等公民数值**（核心设计书 §7）：必须显示，且直方图必须同时呈现编辑前后的形状。

### 5.4 空洞（`void`）——一处必须解决的内部矛盾

**核心设计书存在一处内部矛盾：**

| 条目 | 原文 |
|---|---|
| C1 | 常规物品概率之和**恒为 98%** |
| C2 | 排除释放的概率仅 60% 可回收，**40% 蒸发** |

若 40% 真的消失且 Σp 仍需为 1，则抽取分布不成立。**本系统采用如下解法：**

> **蒸发的概率不消失，而是落为一个显式的零价值结果 `void`。**
> 于是：`Σ probs(常规物品) + void_prob + 0.02(隐藏物品) = 1.0`

设计上的好处：
- 损耗**可见**（直方图上多出一根柱子），玩家能亲眼看到"我把池子凿出了一个洞"；
- 损耗**可计价**（`void` 的 `v = 0`，直接压低 `m_bar`），符合 P2 可归因；
- 不需要"归一化抹掉损耗"这种让损耗失效的做法。

**代价**：C1 的措辞需要从"恒为 98%"调整为"**常规物品概率之和 ≤ 98%，差额即为 void_prob**"。

⚠️ **此项需要在核心设计书中同步修订，已记入 §11 与 `README.md` 待定项汇总。**

> **v0.6：`void` 从"损耗"升格为"自限机制"（核心 §5.3）。定义完全不变**——仍是 `Σ probs(常规) + void_prob + 0.02 == 1.0`，`void` 的 `v = 0`，上面那套口径**一字不改**。
> 变的是它在设计里的**角色**：v0.5 靠"镶嵌位数固定为常数"抑制 R2；v0.6 位子随**套系品质**变多，
> 于是**防止"位子变多导致池子被收敛"的主要机制就是这里的 40% 损耗**——每排除一个物品就永久损失 40% 质量，
> 排得越狠池子越"漏"，`m_bar` 塌陷、ρ 下降，**过度排除自我惩罚**。
> 本系统因此把 `void` 对 ρ 的压制作用确认为 **R2 的头号对策**（核心 §5.3 / R2）。

### 5.5 归因算法

采用**顺序分解（sequential decomposition）**，固定顺序：

```
baseline → +模块 → +装置 → +任务结构 → +损耗 = 当前 ρ
```

- 每一步的增量记为一条 `AttributionEntry`
- **满足可加性**：`Σ delta_rho == rho_current − rho_baseline`（玩家能对账，这是 P2 的硬要求）

> `[补充]` 备选方案是 leave-one-out（逐项移除求差），更直观但**不满足可加性**，玩家会发现各项之和与总变化对不上。因此选顺序分解，并把"顺序依赖"作为已知代价接受——固定顺序使其稳定可预期。
> 可选：在展开层额外提供 leave-one-out 的"独立贡献"视图作为补充，但**默认视图必须是可加性的顺序分解**。

### 5.6 守门口径：`expected_deliverable(t)`（v0.9 新增 / 裁决 15）

**背景**：`03-task.md` §5.5 用 **`solvency_cap`**（单任务需求 ≤ 该档 `expected_output(t)` 的 35%）守门，防止生成"算不出来"的需求。
**v0.9 下这条守门会失效**：开盒产出**可能整批进邮件**，而**邮件实例不可交付 / 装配 / 镶嵌 / 转化**（核心 §4.7）。若 `expected_output(t)` 仍按**总产出**计，守门就会**高估可用量**，生成"**算得出来却永远交不了**"的需求。

> **裁决：守门用的量不是 `expected_output(t)`，而是 `expected_deliverable(t)`——"可交付产出"的保守下界。**

```
# 口径归本文；求值归 03（F 由 02 提供只读输入）——本文不计算它
k(t)         该档一个循环周期内可兑现的盒数（囤积 + 任务回流的产物）
p_void(t)    该档池当前的 void_prob（07 的求值产物，随池子编辑而变）
F_min(t)     该周期内仓库**剩余空间的下界**（保守取周期内最小值；归 02，只读）

m_bar(t)   = Σ probs[i] × v_i                       # 不变（§5.2）
expected_output(t)       = k(t) × m_bar(t)          # 原量，**不变**

n_void(t)  = floor( k(t) × (1 − p_void(t)) )        # 期望非空产出件数（下取整）
size_max(t)= 该档池内**可产出**物品（含隐藏物品）的**最大** ItemDef.size
n_cap(t)   = floor( F_min(t) / size_max(t) )        # 仓库余量**保证**能容下的件数（与 01 §5.7 同一条论证）
n_deliv(t) = min( n_void(t), n_cap(t) )             # 可交付件数的保守下界
v_min(t)   = 该档池内**可产出**物品（含隐藏物品）的**最小** ItemDef.value
                                                     # void 的 v = 0 **不参与**（它不是物品）

expected_deliverable(t) = n_deliv(t) × v_min(t)      # ★ 守门用这个
需求(t) ≤ 0.35 × expected_deliverable(t)            # solvency_cap 的判据（35% 系数归 03 §5.5）
```

**为什么两层都取"保守"（方向是有意选的）：**

| 层 | 取法 | 为什么保守 |
|---|---|---|
| **件数** | `n_cap = floor(F_min ÷ size_max)` | 每件 `size ≤ size_max` ⇒ 这 `n_cap` 件**无论开出什么都放得下**，因此它们**一定在仓库里**、一定可交付；`void` 只让件数更少，不会突破它 |
| **件数** | 再与 `n_void` 取小 | 防止"期望件数本就少于 `n_cap`"时把件数算多 |
| **价值** | `v_min`（池内最不值钱的**可产出**物品） | 每件按**最低价值**计价 ⇒ **最坏组合也不会低于它** |

**结论：这条守门是"保证可交付"的**——只要 `需求 ≤ 35% × expected_deliverable(t)`，该需求**一定能被仓库里的物品偿付**，**不依赖运气，也不依赖玩家是否愿意领取邮件**。

**三个必须写明的边界：**

1. **`F_min = 0`（仓库满）⇒ `n_cap = 0` ⇒ `expected_deliverable(t) = 0` ⇒ `solvency_cap = 0` ⇒ 不再生成新需求。** 这正是裁决 15 想要的行为：**宁可暂时不生成，也不生成交不了的需求**。恢复途径是内容侧的 **D15（容量里程碑解锁）** 与**把邮件领回仓库**（02）；**不是**放宽 35% 系数、也**不是**改 ρ 的公式。
2. **库内既有物品不受影响**：守门只管**生成**侧；玩家仓库里**已经持有**的物品仍可正常交付（`count()` 只看仓库，归 02 / 03）。本条款**不改任何需求匹配规则**。
3. **`v_min` 只看"当前可产出"集合**：被 `ban` 掉的低价值物品不再参与 ⇒ 排除垃圾之后守门量**略微上升**（池子更值钱了），与池子编辑的联动方向正确。

**与 M̄ 的关系（本次裁决最容易被误读的一点）：**

| 量 | 受仓库 / 邮件影响吗 | 用途 |
|---|---|---|
| **`m_bar`（M̄）** | **不受影响**——它是**池子分布**的属性（§5.2），不扣邮件、不打折 | ρ 的三个因子之一；`headline.ev` |
| **`expected_output(t) = k(t) × m_bar`** | **公式不变**（仍按总产出） | 经济口径 / 归因 / 平衡分析 |
| **`expected_deliverable(t)`** | **受影响**（受 `F_min` 与 `p_void` 约束） | **只用于 `solvency_cap` 守门**（03 §5.5） |

> **一句话**：**M̄ 不变，ρ 不变，变的只是"守门时用的那个量"。**
> 因此本次裁决**不新增任何 `EvalResult` 字段、不改任何公式、不加任何归因条目**——`expected_deliverable(t)` **不是 ρ 的因子**，它是一份**给 03 生成侧的公式**（口径归本文，`F` 归 02，求解归 03，§8）。

   ├── 实例落点变化（location: warehouse ↔ mail）？ ──否──▶ **不失效**（v0.9）
   ├── 仓库容量变化（里程碑解锁 / 邮件领取）？      ──否──▶ **不失效**（v0.9）

   │
   ├─ evaluate_pool()  ← 与 GachaService 共用

**本系统是纯只读的。** 它不产生任何状态变更，也不发出任何会改变游戏状态的事件。

> **v0.8：持有形态不是失效条件。** 实例的增删（`ItemService.grant` / `consume`、转化产生新实例、任务挑选实例销毁）**不改变本系统的缓存**——因为 `EvalResult` 的每个字段都与实例无关（§5.2）。**不要**为持有量再引入一个 `inventory_revision` 之类的新失效依据：它只会带来无谓的重算，并且会让读者误以为 ρ 依赖持有量。
>
> **v0.9：持有位置与仓库容量同样不是失效条件。** 实例落点变化（`warehouse ↔ mail`，含领取）、仓库容量变化（里程碑解锁 D15）、`ItemDef.size` 调整、邮件里堆积任意多条目，**都不得触发重算**——`EvalResult` 的每个字段都与它们无关（§5.2）。**不要**新增 `location_revision` / `warehouse_revision` 之类的依据：理由是同一个（会让人误以为 ρ 依赖持有位置），**且会掩盖一个真问题**——"仓库满导致可交付物变少"是**可达性**问题，它在样本统计里体现，**不可能**由一个缓存失效修好（§5.2 的 ρ vs 可达 ρ）。
>
> **v0.9（裁决 13）：本系统不参与任何事务，因此不存在任何跨系统原子性承诺。** `transact()` 的语义只覆盖物品侧（归 02）；本文**既不发 Box、也不解锁内容、也不改任何状态**——它唯一需要的是"**读到一份一致的快照**"（`PoolState.revision` 就是这个快照的锚点）。**不要**为本系统设计事务边界或补偿逻辑。
>
> **v0.9（裁决 15）：守门量 `expected_deliverable(t)` 也不在本文的流程里求值。** 它需要仓库余量 `F`（02 的输入），因此**由 03 在生成需求时求解**（§5.6）；本文只提供 `m_bar` / `p_void` / `v_min` / `size_max` 这几个**口径**。**它的变化同样不构成本系统的缓存失效条件**。

### 8.1 共享求值路径的保证方式

> **`evaluate_pool()` 是唯一实现。** `EvalService` 与 `GachaService` 都只能调用它。
> - `GachaService.roll()` 从 `PoolEvaluation.probs` + `void_prob` 依 `seed` 抽样，**不得重新计算权重**；
> - 任何地方出现第二份权重计算逻辑即为严重缺陷；
> - 守护测试见 §10.1。

- 归因各项**必须能对账**（合计 = 相对基线的总变化）。

### 10.2 功能测试

|---|---|---|
| T8 | 纯函数性 | 同 `(state, series, seed)` 两次调用，`EvalResult` 逐字段相等 |

### 10.3 验收信号（切片）

- ✅ 测试者能在 2 分钟内说出自己 ρ 的主要贡献来源（P2 达成）
- ✅ 测试者能理解 `void` 的含义，并据此决定是否继续排除
- ✅ **测试者不再问"为什么位子会变"**——开始问"怎么拿到更高品质的套系"即算通过（说明**品质 → 镶嵌位**的关系被理解了，核心 §4.1.1 / P7）
- ❌ **测试者认为"显示的期望"与实际开出的东西不符** → 共享路径失效，头号缺陷，立即停止其他工作排查
- ❌ **测试者发现归因各项之和对不上总变化** → 归因算法回归，P2 失效
- ⚠️ **测试者说"我算出来的 ρ 打不到"**（仓库满、东西堆在邮件里交付不了）→ **不是本系统回归**：这是 §5.2 的**可达性**折损（ρ 的公式没错，能落到仓库里的产出变少了）。**处置是 01 / 02 / 08 侧的事**（开盒前预告 §5.7、容量解锁 D15、邮件领取），**绝不允许**回头去改 ρ 的公式或往 `attribution` 里加条目
