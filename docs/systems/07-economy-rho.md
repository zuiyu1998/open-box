> **v0.8 物品实例化（本文已同步）——先说结论：本系统的公式与算法一行都不用改。**

>

> **v0.9 仓库容量与邮件（本文已同步）——先说结论：ρ / M̄ / D̄ / B / σ / `headline` / 归因算法全部不受仓库与邮件影响。**
>
> 上游给每个实例加了**落点** `location ∈ {warehouse, mail}`，并给仓库加了**容量**（`warehouse_capacity`、`ItemDef.size`；放不下的产出进邮件——核心 §4.7 / §14.2 铁律 9）。
> **而本系统的每一个数字都只依赖概率分布（`probs` + `void_prob`）与 `ItemDef.value`——不依赖持有形态，更不依赖持有位置。** 一盒开出什么、值多少 TVU，与那件东西**落在仓库还是邮件里**无关；`σ` 同理，它的求和范围是**分布**，不是货架。
> **因此：公式、三个因子、量纲校验、方差公式、归因顺序、缓存与共享求值路径一律不变**（核心 §16.4："C1–C6、P1–P7、D1–D14、ρ 公式一律不变"）。**后来者请勿据此改动任何公式，也不要为 `location` 或仓库容量新增失效依据。**
>
> **但有一条间接影响必须写清（它不改公式）**：核心 §4.7 / §14.2 铁律 9 明确 **`count()` 只统计 `location == warehouse` 的实例，邮件里的物品不可用于交付 / 装配 / 镶嵌 / 转化**。
> 于是当仓库满、产出持续进邮件时，**玩家实际能交付的物品少于模型假设**——**"仓库满"会降低*实际可达*的 ρ，但不改 ρ 的公式**。这是模型**外**的**可达性**约束（输入被卡住），不是 ρ 的定义变化：**它不进入 `attribution`**（它不是模块 / 装置 / 任务结构 / 损耗任一项的贡献，§5.5 的固定归因链一行不动）。口径区分见 §2 与 §5.2。
> **裁决 15（v0.9 追加，本文新增 §5.6）**：仓库满时产出可能**整批进邮件**，而邮件实例**不可交付**——因此**任务生成侧的守门量不能再按总产出计**（否则会生成"算得出来却永远交不了"的需求）。本文给出守门口径 **`expected_deliverable(t)`（可交付产出的保守下界）**，见 **§5.6**。**注意：M̄ 本身不变**，变的只是**守门用的那个量**。
> **裁决 12（v0.9，本文只确认、不改公式）**：权威守恒等式是 **`total_granted − total_consumed == Σ 全部实例（含邮件）`**；**`count()` 只是带 `location` 过滤的查询，不是守恒量**。本文**不引用、也不得引入任何"仓库内 Σcount == 差值"之类的等式**（§5.2）。
> **裁决 13（v0.9，本文只确认）**：**不承诺跨系统原子性**——`transact()` 只覆盖物品侧，Box 发放与解锁靠各自幂等键 + 重放。**本系统本来就是纯只读的**，不参与任何事务（§7）。
>
> 本文只有六处**引用性**调整：①§2 边界与 §3 术语新增 `warehouse` / `mail` / `location` 三个**只读引用**（归属 02，**不进入任何公式**）；②§5.2 增加"位置无关"的排除性说明与"可达 ρ ≠ ρ"的口径区分；③§7 流程明确 `location` 与容量变化**不是**缓存失效条件；④§8 接口表增补 02 侧仓位 / 容量接口的**只读、不消费**说明；⑤§10.2 的 **T12 由"实例化无关性"扩展为"持有形态与位置无关性"**；⑥**新增 §5.6 守门口径 `expected_deliverable(t)`**（裁决 15——**只定义口径，不计算**：仓库余量不是本系统的输入）。

> **v0.11 去除保底系统（本文已同步）——结论：本文的公式与算法"零变更"，因为本系统从未依赖保底。** 上游删掉"连续 8 次未出新物品则硬保底"与整个保底计数器（`pity_counters` 不存在、不入档；`void` 不推进任何计数器；`roll(evaluation, seed)`——核心 §9 铁律 1 / §16.6）。**本系统只改引用、不改任何量**：`M̄` 是**期望**，而保底是**抽取侧的单次条件覆盖**——它**从未进入** `m_bar` / `sigma` / `ρ` / `headline`、也**从未进入** `attribution`（§5.5 的固定归因链只有模块 / 装置 / 任务结构 / 损耗 / 基线五项）。因此**没有一条公式、没有一个归因条目依赖保底**，删除它**不影响本文任何一个数字**。
> **已同步的三处引用**：§2 边界行 / §5.1 的 `roll` 签名 / §8 的 01 行。**尾部风险不是本系统的账**：v0.11 时的尾部风险集中在"隐藏物品恒 2%、期望 50 抽、无兜底"，记在核心 **§12 R15** 与 **§15 D18**；**v0.13 删除隐藏款后 R15 已大幅缓解**——不再有"最难且无法被编辑影响"的那一款，**残留风险 = "抬缺口很贵"**（见下方 v0.13 说明，与核心 §12 R15 的 v0.13 修订）；**07 不引入任何替代机制**（不得以"隐式必出"复活保底——那会破坏 P1 的严格性）。

> **v0.10 池子随盒子走（本文已同步）——先说结论：`ρ` / `M̄` / `D̄` / `B` / `σ` 的公式一律不变，变的是它们的参照物。**
>
> 上游把**池子从"套系共享状态"改成"盒子的属性"**：每个 `Box` 各持有一份 `PoolState`，模块镶嵌进具体的盒子并锁定在那里（核心 §4.1.2 / §16.5）。**结构澄清**：`Box` 下面是**两个并列字段**——`item_pool`（物品池，生成数据的凭证）与 `modules`（模块列表，唯一作用方式是更改 `item_pool` 的状态），**模块不折进池子**；池子的当前状态是二者的**函数**（§4 / §8）。
> **公式一个字都没动**（`ρ = (M̄ / D̄) × B`、`m_bar = Σ(probs[i] × v_i)`、`sigma`、`d_bar` / `b` 的折算、归因算法、共享求值路径全部原样）；**变的是"参照物"**：这些量过去隐含地"以某个**套系**为准"，现在**一律以"某一个盒子的池子"为准**——
>
> | 项 | v0.9（参照物 = 套系） | v0.10（参照物 = 盒子） |
> |---|---|---|
> | `evaluate_pool(pool_state, series)` | 池子天然唯一（每套系一份） | **签名与实现都不变**——它本来就只收一个 `PoolState`；现在收到的是**某个盒子**的那一份 |
> | `EvalService.compute()` 入参 | 只需 `state` | **必须能指向"一个池子"**，即能定位到某个盒子的 `PoolState`（§4.1 / §5.2） |
> | `headline` | 该**套系**的期望 | **选中盒子的池子**的三个值（§5.2 / §10.2 T11）；同套系两盒可不同（这是正确行为） |
> | `ρ` | "这个套系的闭环率" | **"某个池子的闭环率"**；**不同批次可以有不同 ρ**（§5.2） |
> | 缓存键 | `revision` | **`(盒子标识, revision)`**——`revision` 现在是**每盒一个**（§7） |
> | "全局 ρ" | 不需要 | **若需要，它是各批次的加权 / 聚合**——属 08 的呈现问题；**07 不引入第二个 ρ 口径**（§11 E9） |
>
> 本文的调整集中在**六处**（**没有一处改公式**）：①§1 / §2 / §3 补盒子的口径与术语；②§4 的入参与缓存键能指向**一个池子**；③**§5.2 新增"ρ 的参照物"裁决**（本文唯一的语义变更）；④§6 / §7 明确"每盒一个 `revision`，缓存键必须含盒子标识"；⑤§8 接口按 `box_id` 取池子、§9 呈现以选中盒子为准；⑥**§10.2 新增 T14**、**§11 新增 E9**。**C1–C6、`void` 的定义与规格、归因算法、共享求值路径、全部数值一律不动**（核心 §16.5）。

> **v0.13 去除隐藏款（本文已同步）——结论：`ρ` / `M̄` / `D̄` / `B` / `σ` / `headline` 与归因算法的公式与算法一律不变；变的是"池子里不再有隐藏物品"带来的三条口径。**
> 上游删除了"每个套系 1 个隐藏物品"的设定（`ItemDef.is_hidden` / `ItemPool.hidden_item` / `HIDDEN_TOTAL_BP` 已删除；核心 §5.4 / §16.8）：**池中的全部物品都是常规物品，全部物品共分 100%**——`p_i = rarity_i / Σ rarity`（`rarity` 是**权重**：越大越常见、**≥ 1**；全部相等时退化为均等）。

## 1. 这个系统负责什么

1. **概率求值路径**——本作唯一的一条。`EvalService` 与 `GachaService` 必须共用它（README §2.2 铁律）。
2. **ρ 的定义与计算**：`ρ = (M̄ / D̄) × B`——**参照物是"某一个盒子的池子"**（v0.10，核心 §4.1.2；见 §5.2）
3. **M̄ / D̄ / B 的口径**：把物品、任务、装置、池子编辑折算成同一单位
4. **σ（方差）**：第二轴的显式数值
5. **`headline`**：盲盒默认层那两个数字的**产出方**（渲染归 08）。**v0.10：它是"选中盒子的池子"的 `{best_item, best_item_prob, ev}`**——同套系的两个盒子配置不同 ⇒ `headline` 不同，**这是正确行为**（核心 §4.1.2 / §6.1）
6. **归因**：把 ρ 的变化逐项分解到模块 / 装置 / 任务结构 / 损耗
7. **缓存与失效**：UI 高频调用下的性能保证
8. **守门量的口径（v0.9 新增 / 裁决 15）**：**`expected_deliverable(t)`**——任务生成侧"可交付产出"的**保守下界**（§5.6）。**只定义口径**：仓库余量 `F` 由 02 提供只读输入、求解与使用归 03（本系统**不计算它**，也不放进 `EvalResult`）。

>
> **v0.8 补充**：`EvalService` 也**不读、不缓存、不改编物品实例列表**——`count` 是**派生值**（由实例列表数出并缓存，属 02），**本系统的任何公式都不使用它**（§5.2）。持有形态变化（`grant` / `consume` / 转化产生新实例）**不构成本系统的缓存失效条件**（§7）。
>
> **v0.9 补充**：`EvalService` 同样**不读 `location`、不读 `warehouse_capacity`、不统计"仓库剩余空间"、不做任何"能不能装下"的判断**——**持有位置与容量都不是本系统的输入**，也**不是缓存失效条件**（§7）。`count()` 的"只统计仓库内实例"是 **02 的口径**，而本系统**连 `count()` 都不消费**（§5.2 / §8）。仓库与邮件在本文中的身份只有一个：**一个会压低"实际可达 ρ"的外部可达性约束**（§5.2），**不是公式项**。
>

> **⚠️ 术语纪律（v0.6）："品质"有两个含义，本系统内不得混用。**
> - **物品品质 `quality`**（1–5 序数，`ItemDef.quality`，**字段定义归 02**，见 `02-item.md`）：本系统中 **`v_i`（物品的 TVU 价值）涉及的是它**；
> - **套系品质 `series_quality`**（1–4，核心 §4.1.1）：决定该套系的 `regular_count` 与 `socket_count`，由里程碑任务解锁。
>
> 两者**没有任何换算关系**：`v_i` 的高低不改变 `regular_count`，`series_quality` 也不直接进入 `v_i` 的定义（它只通过"高品质套系提供更高品质区间的物品"间接影响 `v_i` 的分布）。

### 3.1 为什么需要 TVU

物品有类别与品质两个维度（见 `02-item.md`），任务需求也是向量，两者无法直接比较。**TVU 是把它们压成一个标量的桥。**

- 物品 `i` 的价值 `v_i` 取自 `ItemDef.value`（**字段归属 02**，见 `02-item.md` 与 §8 接口表），定义为：**它能贡献的 TVU 数**
- 任务需求的 TVU = 需求向量中各项折算之和
- 于是 M̄ 与 D̄ 可以相除

**TVU 是本作唯一允许出现的"通用价值"单位。** 任何系统不得引入第二套计价。

## 5. 规则与公式

### 5.1 概率求值（唯一路径）

> **v0.10 职责切分（本节已按裁决改写，不是改规则，是修正"共享求值路径"的表述）：** **编辑算术（排除 / 提升 / 40% 损耗 / 零和）只归 05 的 `_rebuild()`**——它由「该盒 `item_pool` + `modules`」推出 **`weights_bp` + `void_mass_bp`**（整数万分比，`Σ weights_bp + void_mass_bp == 10000`，C1 的零和等式因此在**整数**上精确成立）；**07 从 `weights_bp` 出发，只做「归一化 + 统计量」**。**07 绝不再应用一次排除 / 提升 / 损耗**——那会**双重应用**，且结果是**静默错**（算出来仍然"看起来合理"，核心 §4.1.2 的裁决 ②）。

```
evaluate_pool(pool_state, series):
  1. w[i] = pool_state.weights_bp[i]      # ★ 输入是 05 已推出的**当前权重**（整数万分比，`i` 即 `item_id`）；编辑算术已完成，禁止在此重算
  2. 未拥有物品加权：w[i] *= 1.5           # 规则归 01；"未拥有"是**收藏口径、随进度变**，故只能在求值时执行
  3. 归一化：probs = w / Σw                # ★ **全流程唯一的浮点入口**：`weights_bp`（整数）在此一次性变成浮点 `probs`；此后不再出现第二份浮点权重（**全部物品一起归一化**——v0.13 无隐藏款，不再有"独立占 2%、不参与归一化"的那一项；不依赖 `regular_count`）
  4. void_prob = pool_state.void_mass_bp / 10000    # 40% 损耗的产物，由 05 产出，07 只读数（§5.4）
```

> `[补充]` **两条固定顺序，别混**：①**编辑侧的顺序固定在 05 的 `_rebuild()` 内**（排除 → 提升 → 损耗 → 零和，05 §5.1）；②**求值侧的顺序固定为本节的 1 → 3**（读权重 → 未拥有加权 → 归一化），`void_prob` 只是读数。顺序固定使求值可复现、也让归因可对账。**`banned` / `boosted` 这两个概念在 07 侧已删除**——它们已经烘进 `weights_bp`，其数据来源是该盒的 `Box.modules`（归 01 / 05，§2 / §4）。**本系统不读 `Box.modules`、不应用模块、不做编辑算术。** **（`evaluate_pool()` 的第二个入参 `series` **保留**：它只用于"**物品清单（`probs` 的长度与顺序）的对齐**"，**不再用于读取任何基础权重**。）** **规范表示是整数**：`weights_bp` / `void_mass_bp` **一律是整数万分比**（**只有整数才能让 C1 的零和等式被精确断言**，也让存档往返字节级稳定）；**浮点 `probs` 只在本节第 3 步出现一次**——**这是本文档中唯一允许把权重变成浮点的地方**，不得在别处另算一份浮点权重。 本条产出的 `PoolEvaluation`（`probs` + `void_prob`）就是 `GachaService.roll(evaluation, seed)` 的入参（核心 §9 铁律 1；**v0.11：入参里没有 `pity_counter`——保底已删除，抽取无状态**）——**"显示的分布"与"实际抽取用的分布"因此必然是同一份**（核心 §9 铁律 4）。

### 5.2 三个因子

```
m_bar = Σ (probs[i] × v_i)        # v_i 取自 ItemDef.value（**字段归属 02**，见 §8 接口表）；void 的 v = 0，不贡献
d_bar = 任务需求向量的 TVU 折算（含装置修正）
b     = 任务奖励盒数（含装置修正）

rho = (m_bar / d_bar) × b
```

量纲校验：
```
(TVU / 盒) / (TVU / 任务) × (盒 / 任务) = 任务 / 盒 × 盒 / 任务 = 无量纲 ✓
```
ρ 的含义即"**每投入 1 个盲盒，最终回收多少个盲盒**"。

> `[补充]` 核心设计书 §2.3 写作 `M̄ = Σ(pᵢ × vᵢ) × 池子修正`。此处把"池子修正"**显式展开为编辑后的 `pᵢ`**，因为池子编辑的全部效果就体现在 `pᵢ` 上，不存在独立的修正乘数。这是表述澄清，不是机制改动。

> **v0.8（实例化不在公式里——这是本节最容易被误改的一点）**：`m_bar` 与 `sigma` 的求和范围是**概率分布**，不是持有量。因此 **`count`（派生值）、`instance_id`、`serial`、`source` 都不出现在任何公式中**：玩家把同一件物品记成"计数 3"还是"3 个实例"，`Σ (probs[i] × v_i)` 的结果逐位相同。
> **实例化只改持有模型，不改期望**——ρ / M̄ / D̄ / B / σ / `headline` / 归因算法**全部不变**（核心 §16.3）。本文不因此新增任何输入、参数或公式项。

> **v0.9（仓库与邮件同样不在公式里——本条与上一条是一对，结论同样是"公式一行都不改"）**：`location`、`warehouse_capacity`、`ItemDef.size`、邮件条目**都不出现在任何公式中**：`Σ (probs[i] × v_i)` 的求和范围是**概率分布**，不是货架；给定同一份 `probs` 与 `ItemDef.value`，物品**落在仓库还是邮件里**，`m_bar` / `sigma` / `headline` 逐位相同。
> **因此"持有形态与位置无关性"是同一条不变量**（§10.2 T12）：v0.8 守护"计数 vs 实例"，v0.9 追补"**仓库 vs 邮件**（含把仓库容量改到 0 或无限）"。
>
> **"ρ"与"实际可达的 ρ"是两个量（v0.9 必须分清，否则一定有人来改公式）**：
>
> | 量 | 定义 | 受仓库容量 / 溢出影响吗 |
> |---|---|---|
> | **ρ（本系统的口径）** | `(m_bar / d_bar) × b`——**模型值**：在"产出可用于交付"这一前提下算出的闭环收益率 | **不受影响**。公式、三个因子、σ、归因一律不变 |
> | **实际可达的 ρ** | 玩家**真正能跑到**的收益率：它额外要求产出物**在仓库里**（邮件里的实例不可交付 / 装配 / 镶嵌 / 转化，核心 §4.7） | **受影响**：仓库满 → 可交付物变少 → **实际可达 ρ 低于模型值** |
>
> **结论：容量满会压低"实际可达的 ρ"，但不改 ρ 的公式。** 这张表的右列就是这条区别的答案——**变的是可达性，不是定义**。三条推论（都必须遵守）：
> ① `EvalResult` **不新增字段**，`attribution` **不新增条目**——外部可达性不是模块 / 装置 / 任务结构 / 损耗任一项的贡献，**§5.5 的固定归因链与可加性公式一行不动**；
> ② 本系统**不实现**任何"因容量而对 ρ 打折"的修正项，也**不把 `location` 当输入**；全绿前提不变：P7 / C1–C6 / ρ 公式均与本改动无关（核心 §16.4）；
> ③ 切片**不产出**这个"可达 ρ"的数：若将来要在 UI 上提示这一折损，**必须先在本文定义口径**（§11 E7），再由 08 呈现——**不得由 UI 私自换算**（跨系统铁律 3）。

> **裁决 12（守恒等式只按全部实例，v0.9 确认，不改公式）**：权威守恒式是 **`total_granted − total_consumed == Σ 全部实例（含邮件）`**，而 **`count()` 只是带 `location` 过滤的查询、不是守恒量**。因此本文**不引用、也不得引入**任何形如"**仓库内 Σcount == 差值**"或"`count` 之和 == 累计产出"的等式——在 v0.9 下这类等式**必然不成立**（产出可以整批进邮件）。
> **本系统不参与守恒校验**（归 02 / 03），也不消费 `total_granted` / `total_consumed`；本文的任何数字都来自**分布**与 `ItemDef.value`，与实例账本无关（§5.2 上一条）。**后来者请勿用守恒等式去推导 ρ 的任何量。**

> **v0.10：ρ 的参照物 = 一个池子（本节唯一的语义变更，公式一个字都没动）**
>
> **裁决一 · `EvalService.compute()` 的入参必须能指向"一个池子"，而不是"一个套系"。** 池子随盒子走之后，"这个套系的分布"不再是单数的东西——同套系的两个盒子有**两份不同的 `PoolState`**。因此求值入口必须携带**盒子标识**（§4.1 的 `compute(state, box_id)`）；`[补充]` 具体形参名是落地细节（也可传 `pool_state` 与 `box_id` 的二元组），**"必须能区分盒子"是契约级的**。`evaluate_pool(pool_state, series)` **签名与实现都不改**——它本来就只认一个 `PoolState`，这正是 v0.10 所依赖的性质。
>
> **裁决二 · ρ 是"以该池子为准的闭环率"。** **"该池子"= 该盒 `item_pool` 经其 `modules` 求值后的那份分布**（05 **推导权重** → 07 **求值成概率 / EV / ρ**；§4 / §8）——**ρ 的参照物既不是套系，也不是"某个 `item_pool` 这份数据本身"，而是"某个盒子那一刻的池子状态"**。
> - ①`rho` / `m_bar` / `d_bar` / `b` / `sigma` / `headline` / `attribution` **全部是某盒那份池子当前状态的属性**；②**不同批次（同套系的不同盒子）可以有不同 ρ**——这正是核心 §4.1.2"分批"的经济含义，**不是 bug、也不是需要被抹平的方差**；**同一个 `item_pool` 配上不同 `modules`，ρ 也必然不同**（"模块更改池子状态"的直接后果）；③**不存在"这套系的 ρ"这种量**——要比较两个盒子，就分别对两个 `box_id` 求值，再在**呈现层**比较（渲染归 08）。
>
> **裁决三 · 若需要"全局的 ρ"，它是各批次的加权 / 聚合，不是第二个口径。** 聚合口径（按盒数加权？按这批盒子的兑现进度加权？只算已配置的盒子？）**是呈现问题，归 08**；**07 不引入第二个 ρ**（不加"全局 ρ"字段、不加聚合函数、不加第二种归因）——本系统只回答"**这一个池子**的 ρ 是多少"，想知道总体就把若干个 `EvalResult` 交给 08 去合。★ **聚合不得反写公式**：不得因此让 `compute()` 支持"一次算多个池子"，也不得往 `EvalResult` 里加多池字段；且注意 **ρ 是比值**——只有当各池的 `d̄` / `b` 相同时，"按盒数加权平均 ρ"才等于"先按盒数合并分布再算一次 ρ"，两者是否一致**由 08 在聚合时说明**，**07 不下定义**。
>
> ✓ **与 v0.9 的"实际可达的 ρ"是两件事，不要混**：上面那条讲的是**同一个池子**的模型值 vs 可达性（仓库溢出），本条讲的是**"哪个池子的 ρ"**（参照物）。两者可以同时出现在一处读数里（"**选中的这个盒子的池子**，在当前仓库余量下"），但**都不改 ρ 的公式**。

**`regular_count` 进入公式的位置（v0.6）：** 核心 §4.1.1 起，常规物品数由**套系品质**决定（品质 1/2 = 8 个物品，品质 3/4 = 12 个物品），**不再是常量 8**——所以本系统内部不得再假设"8 个常规物品"：

| 量 | 与 `regular_count` 的关系 |
|---|---|
| `m_bar` | **无关**。只依赖最终分布 `probs`（含 `void`），求和范围是**实际存在的物品**，8 或 12 都不进入公式 |
| `sigma` | **无关**，理由同上（§5.3） |
| `headline.best_item` | **依赖**。头奖候选集 = **该盒池中仍可产出的全部物品**（v0.13：无隐藏款，即"该套系的 `regular_count` 个物品"减去被排除项），取 `v` 最高；物品数变了候选集就变了，**同一套系的两个盒子也可以有不同的 `best_item`**（某盒排除了原本的头奖）→ v0.10，核心 §6.1 |
| C6 判定 | **依赖**。排除上限 = `regular_count − 3`，即可产出常规物品数 ≥ 3（§10.1 T7） |

> 因此 `probs` 的长度、归一化范围、C6 校验一律以 `pool_state.regular_count` 为准，**不得写死 8**。

### 5.3 方差

```
sigma = sqrt( Σ probs[i] × (v_i - m_bar)² )     # void 以 v = 0 参与
```

求和范围同样是**实际存在的物品**（含 `void`），**与 `regular_count` 无关**——物品数变化不改变方差公式本身，只改变分布的取值集合。

**σ 是一等公民数值**（核心设计书 §7）：必须显示，且直方图必须同时呈现编辑前后的形状。

### 5.4 空洞（`void`）——一处必须解决的内部矛盾

**核心设计书曾存在一处内部矛盾（本节是 v0.6 的历史记录；**v0.13 起 C1 已是 100%**，见文首 v0.13 说明）：**

| 条目 | 当时的原文（v0.6 之前） |
|---|---|
| C1 | 常规物品概率之和**恒为 98%** |
| C2 | 排除释放的概率仅 60% 可回收，**40% 蒸发** |

若 40% 真的消失且 Σp 仍需为 1，则抽取分布不成立。**本系统采用如下解法：**

> **蒸发的概率不消失，而是落为一个显式的零价值结果 `void`。**
> 于是：`Σ probs(全部物品) + void_prob == 1.0`　　# v0.13：无隐藏款，不再有那独立的 2%

设计上的好处：
- 损耗**可见**（直方图上多出一根柱子），玩家能亲眼看到"我把池子凿出了一个洞"；
- 损耗**可计价**（`void` 的 `v = 0`，直接压低 `m_bar`），符合 P2 可归因；
- 不需要"归一化抹掉损耗"这种让损耗失效的做法。

> **代价**：C1 的措辞需要从"恒为 98%"调整为"**常规物品概率之和 ≤ 98%，差额即为 void_prob**"。（**v0.13 已随之收口**：全部物品共分 100%，见下条与文首 v0.13 说明。）

✅ **已回改上游（核心 v0.6）**：C1 已修订为"常规物品概率之和 + `void_prob` 恒为 98%"（**v0.13 修订：现为"物品概率之和 + `void_prob` 恒为 100%"**——隐藏款已删除，那 2% 已并入全部物品的归一化，见文首 v0.13 说明），核心 **§5.6「空洞 void」** 也已正式补入定义。**本条不再需要任何上游动作**——下方文字与 §11 的 E1 保留作该缺陷的历史记录与论证（`README.md` §6.1 有同一记录）。

> **v0.6：`void` 从"损耗"升格为"自限机制"（核心 §5.3）。定义完全不变**——仍是 `Σ probs(全部物品) + void_prob == 1.0`（**v0.13：隐藏款已删除，不再有那 0.02**），`void` 的 `v = 0`，上面那套口径**一字不改**。
> 变的是它在设计里的**角色**：v0.5 靠"镶嵌位数固定为常数"抑制 R2；v0.6 位子随**套系品质**变多，
> 于是**防止"位子变多导致池子被收敛"的主要机制就是这里的 40% 损耗**——每排除一个物品就永久损失 40% 质量，
> 排得越狠池子越"漏"，`m_bar` 塌陷、ρ 下降，**过度排除自我惩罚**。
> 本系统因此把 `void` 对 ρ 的压制作用确认为 **R2 的头号对策**（核心 §5.3 / R2）。

### 5.5 归因算法

采用**顺序分解（sequential decomposition）**，固定顺序：

```
baseline → +模块 → +装置 → +任务结构 → +损耗 = 当前 ρ
```

- 每一步的增量记为一条 `AttributionEntry`
- **满足可加性**：`Σ delta_rho == rho_current − rho_baseline`（玩家能对账，这是 P2 的硬要求）

> `[补充]` 备选方案是 leave-one-out（逐项移除求差），更直观但**不满足可加性**，玩家会发现各项之和与总变化对不上。因此选顺序分解，并把"顺序依赖"作为已知代价接受——固定顺序使其稳定可预期。
> 可选：在展开层额外提供 leave-one-out 的"独立贡献"视图作为补充，但**默认视图必须是可加性的顺序分解**。

### 5.6 守门口径：`expected_deliverable(t)`（v0.9 新增 / 裁决 15）

**背景**：`03-task.md` §5.5 用 **`solvency_cap`**（单任务需求 ≤ 该档 `expected_output(t)` 的 35%）守门，防止生成"算不出来"的需求。
**v0.9 下这条守门会失效**：开盒产出**可能整批进邮件**，而**邮件实例不可交付 / 装配 / 镶嵌 / 转化**（核心 §4.7）。若 `expected_output(t)` 仍按**总产出**计，守门就会**高估可用量**，生成"**算得出来却永远交不了**"的需求。

> **裁决：守门用的量不是 `expected_output(t)`，而是 `expected_deliverable(t)`——"可交付产出"的保守下界。**

```
# 口径归本文；求值归 03（F 由 02 提供只读输入）——本文不计算它。★ v0.10 批量口径（池子每盒一份）：`m_bar` **按各盒各自求和**。
# ★ 取法原则（唯一的一条）：**三个保守量必须同向——一律"低估可交付量"**（`solvency_cap` 是**任务生成**的守门：高估会生成"算得出来却永远交不了"的任务，**宁可低估、任务偏简单**）——
#   `p_void` 取各盒**最大** ⇒ `(1 − p_void)` 最小 ⇒ 到手件数最少；`size_max` 取各盒**最大** ⇒ 每件最占地方 ⇒ `n_cap` 最小；`v_min` 取各盒**最小** ⇒ 每件最不值钱。
# ★ 反面做法（**错**）：按各盒分别算 `n_void` 再相加 —— 那是把每盒的乐观值相加，得到的是**高估**的下界，与守门目的相反。
k(t)         该档一个循环周期内可兑现的盒数（囤积 + 任务回流的产物）
p_void(t)    该档各盒池子的 void_prob（v0.10：按每盒各自取值，批量时取**最大**；07 的求值产物，随池子编辑而变）
F_min(t)     该周期内仓库**剩余空间的下界**（保守取周期内最小值；归 02，只读）

m_bar(t)   = Σ probs[i] × v_i                       # 不变（§5.2）
expected_output(t)       = k(t) × m_bar(t)          # 原量，**不变**

n_void(t)  = floor( k(t) × (1 − p_void(t)) )        # 期望**非空**（**会产出物品**）的抽取件数（下取整）——⚠️ **名实相反**，见块下方命名警告
size_max(t)= **该盒池子**的**可产出集合**（v0.13：= 该套系**全部物品**减去被排除项，无隐藏款）里的**最大** ItemDef.size
              # ★ v0.10：按**每个盒子各自的池子**分别取；本档批量兑现 k(t) 盒时**必须取这 k 个盒子中的最大值**（否则"k ≤ N ⇒ 必然 0 件进邮件"的下界不成立；与 01 §5.7 同一论证）
n_cap(t)   = floor( F_min(t) / size_max(t) )        # 仓库余量**保证**能容下的件数（`size_max` 已按上一条取"各盒最大值"）
n_deliv(t) = min( n_void(t), n_cap(t) )             # 可交付件数的保守下界
v_min(t)   = 该盒池子**可产出集合**（同上，v0.13：无隐藏款）里的**最小** ItemDef.value（批量时按各盒分别取、再取最小；`void` 的 v = 0 **不参与**——它不是物品）

expected_deliverable(t) = n_deliv(t) × v_min(t)      # ★ 守门用这个
需求(t) ≤ 0.35 × expected_deliverable(t)            # solvency_cap 的判据（35% 系数归 03 §5.5）
```

> ⚠️ **命名警告（不得改名、更不得用反）**：`n_void` 这个名字与它的含义**相反**——它数的是「**会产出物品**的抽取件数」（`k × (1 − p_void)`），**不是空洞数**（空洞数/期望次数的方向与它互补）。**03 已引用此名，故不得改名**（改名会牵动 03）；但读它的人必须先知道这一点——数值守门里一个名字与语义相反的变量，是最容易被后来者用反的地方。

**为什么两层都取"保守"（方向是有意选的）：**

| 层 | 取法 | 为什么保守 |
|---|---|---|
| **件数** | `n_cap = floor(F_min ÷ size_max)`，再与 `n_void` 取小 | 每件 `size ≤ size_max` ⇒ 这 `n_cap` 件**无论开出什么都放得下**，因此它们**一定在仓库里**、一定可交付；`void` 只让件数更少，不会突破它。**v0.10：批量兑现时 `size_max` 取"这 k 个盒子各自的最大值"，该论证对每一个盒子都成立**。再与 `n_void` 取小是为了防止"期望件数本就少于 `n_cap`"时把件数算多 |
| **价值** | `v_min`（**该盒池子**的可产出集合里最不值钱的物品；批量时再取各盒最小） | 每件按**最低价值**计价 ⇒ **最坏组合也不会低于它** |

**结论：这条守门是"保证可交付"的**——只要 `需求 ≤ 35% × expected_deliverable(t)`，该需求**一定能被仓库里的物品偿付**，**不依赖运气，也不依赖玩家是否愿意领取邮件**。

**三个必须写明的边界：**

1. **`F_min = 0`（仓库满）⇒ `n_cap = 0` ⇒ `expected_deliverable(t) = 0` ⇒ `solvency_cap = 0` ⇒ 不再生成新需求。** 这正是裁决 15 想要的行为：**宁可暂时不生成，也不生成交不了的需求**。恢复途径是内容侧的 **D15（容量里程碑解锁）** 与**把邮件领回仓库**（02）；**不是**放宽 35% 系数、也**不是**改 ρ 的公式。
2. **库内既有物品不受影响**：守门只管**生成**侧；玩家仓库里**已经持有**的物品仍可正常交付（`count()` 只看仓库，归 02 / 03）。本条款**不改任何需求匹配规则**。
3. **`v_min` 与 `size_max` 都只看"当前可产出"集合**（v0.10：**该盒池子**的当前可产出集合；**按每盒分别计算、批量取最值**）：被 `ban` 掉的低价值物品不再参与 ⇒ 排除垃圾之后守门量**略微上升**（池子更值钱了），与池子编辑的联动方向正确。★ **由此推出的更正（v0.10）：`size_max` 会随池子编辑而变**——把池子里最大的那件 `ban` 掉之后，**可产出集合里不再有那个 `size`**，`size_max` 变小、`n_cap` 变大、提示里的 `N` 随之变大。**正确表述是"N 只随容量与该盒池子的可产出集合变化"**；旧文"`N` 不因池子编辑而变"**是错的，不得沿用**（01 §5.7 已改正）。

**与 M̄ 的关系（本次裁决最容易被误读的一点）：**

| 量 | 受仓库 / 邮件影响吗 | 用途 |
|---|---|---|
| **`m_bar`（M̄）** | **不受影响**——它是**池子分布**的属性（§5.2），不扣邮件、不打折 | ρ 的三个因子之一；`headline.ev` |
| **`expected_output(t) = k(t) × m_bar`** | **公式不变**（仍按总产出） | 经济口径 / 归因 / 平衡分析 |
| **`expected_deliverable(t)`** | **受影响**（受 `F_min` 与 `p_void` 约束） | **只用于 `solvency_cap` 守门**（03 §5.5） |

> **一句话**：**M̄ 不变，ρ 不变，变的只是"守门时用的那个量"。**
> 因此本次裁决**不新增任何 `EvalResult` 字段、不改任何公式、不加任何归因条目**——`expected_deliverable(t)` **不是 ρ 的因子**，它是一份**给 03 生成侧的公式**（口径归本文，`F` 归 02，求解归 03，§8）。

| 未拥有物品加权 | `new_item_mult` | 1.5 | 规则归 01 |
| 提升强度上限 | `boost_cap` | ×3 | 核心文档 D7 🔧 |
| 缓存失效依据 | `revision` | — | **每个盒子各有一个** `PoolState.revision`（v0.10）；**缓存键 = `(box_id, revision)`**，缺了盒子标识必然串味（§7） |

## 7. 流程

```
GameState 变化
   │
   ├── **某个盒子**的 PoolState.revision 变化？ ──是──▶ **该盒**的缓存失效（**只失效这一盒**，v0.10）
   ├── 装置变更？               ──是──▶ 缓存失效
   ├── 任务结构变更？           ──是──▶ 缓存失效
   ├── 物品实例增删（grant / consume / 转化）？ ──否──▶ **不失效**（v0.8，见下）
   ├── 实例落点变化（location: warehouse ↔ mail）？ ──否──▶ **不失效**（v0.9）
   ├── 仓库容量变化（里程碑解锁 / 邮件领取）？      ──否──▶ **不失效**（v0.9）
   ├── 选了另一个盒子（selected_box 变化）？       ──否──▶ **不失效**——**是换输入**，不是旧值失效（v0.10）
   │
   ▼
EvalService.compute(state, box_id)
   │
   ├─ evaluate_pool()  ← 与 GachaService 共用（收的是**该盒的** PoolState）
   ├─ m_bar / d_bar / b / sigma
   ├─ headline
   └─ attribution（顺序分解）
   │
   ▼
EvalResult（按 **(box_id, revision)** 缓存）
   │
   ├──▶ 08 六面板渲染（**全部以"选中的那个盒子"为准**）
   ├──▶ 08 试算预览
   ├──▶ 09 兑现对照
   └──▶ 11? 无（本系统不驱动任何写入）
```

**本系统是纯只读的。** 它不产生任何状态变更，也不发出任何会改变游戏状态的事件。

> **v0.10：缓存失效依据仍是 `revision`，但它现在是"每个盒子各有一个"——缓存键必须包含盒子标识。**
> `[补充]` 落地形态可取 `Dictionary[box_id] -> {revision, EvalResult}`（名称是落地细节，"键里必须有盒子"是契约级的）。三条必须写清：
> 1. **键里不含 `box_id` 必然串味**：两个盒子的 `revision` 是**独立计数器、可以取相同数值**（初始都是 0）。A 盒编辑后 `revision` 0 → 1，B 盒的 0 或 1 会被当成"已命中"，于是**B 盒显示 A 盒的数字**——而且是**静默**的，正是 P1 最害怕的那种错（核心 §6.4 / R4）。
> 2. **A 盒的编辑不得使 B 盒的缓存失效**（正确行为是零工作）；B 盒的编辑同样只失效 B 盒。**不要**按 `series_id` 建"套系级"缓存条目——那正是 v0.10 废除的东西。
> 3. **切换选中盒子不是"失效"，而是"换输入"**：`selected_box` 变化时**无需**让任何缓存失效（各盒结果本就分别缓存），UI 只是改读另一份 `EvalResult`（"无残留"是 08 的呈现要求，见 `08-ui-panels.md` §10 T22）。盒子被**兑现消耗**后其派生状态与缓存条目一并释放——那是**生命周期清理**，不是失效逻辑。**v0.9 的结论仍然成立**：实例增删 / `location` / 仓库容量**都不是**失效依据（下三条）——**唯一新增的是"缓存键要连盒子一起"**。

> **v0.8：持有形态不是失效条件。** 实例的增删（`ItemService.grant` / `consume`、转化产生新实例、任务挑选实例销毁）**不改变本系统的缓存**——因为 `EvalResult` 的每个字段都与实例无关（§5.2）。**不要**为持有量再引入一个 `inventory_revision` 之类的新失效依据：它只会带来无谓的重算，并且会让读者误以为 ρ 依赖持有量。
>
> **v0.9：持有位置与仓库容量同样不是失效条件。** 实例落点变化（`warehouse ↔ mail`，含领取）、仓库容量变化（里程碑解锁 D15）、`ItemDef.size` 调整、邮件里堆积任意多条目，**都不得触发重算**——`EvalResult` 的每个字段都与它们无关（§5.2）。**不要**新增 `location_revision` / `warehouse_revision` 之类的依据：理由是同一个（会让人误以为 ρ 依赖持有位置），**且会掩盖一个真问题**——"仓库满导致可交付物变少"是**可达性**问题，它在样本统计里体现，**不可能**由一个缓存失效修好（§5.2 的 ρ vs 可达 ρ）。
>
> **v0.9（裁决 13）：本系统不参与任何事务，因此不存在任何跨系统原子性承诺。** `transact()` 的语义只覆盖物品侧（归 02）；本文**既不发 Box、也不解锁内容、也不改任何状态**——它唯一需要的是"**读到一份一致的快照**"（`PoolState.revision` 就是这个快照的锚点）。**不要**为本系统设计事务边界或补偿逻辑。
>
> **v0.9（裁决 15）：守门量 `expected_deliverable(t)` 也不在本文的流程里求值。** 它需要仓库余量 `F`（02 的输入），因此**由 03 在生成需求时求解**（§5.6）；本文只提供 `m_bar` / `p_void` / `v_min` / `size_max` 这几个**口径**。**它的变化同样不构成本系统的缓存失效条件**。

本系统**产出数据不产出界面**，但下列呈现由本系统的口径决定：

| 试算预览 | 08 | `compute()` 的假设态结果 |
| 兑现对照（预期 vs 实际） | 09 | `m_bar` / `sigma` |

**v0.9：本系统的呈现清单不因仓库 / 邮件增加任何一行。** 容量占用、邮件条目、开盒前预告（`01-gacha.md` §5.7 的"剩余空间还能放 N 件"）**都不是本系统的数据**——容量查询归 02、渲染归 08；"实际可达的 ρ"切片**不做**（§5.2 / §11 E7），因此 08 **不得**在 UI 层自行从 ρ 折算出任何"因仓库满而打折"的数字（跨系统铁律 3）。

**必须满足（P2 / P6）**：
- `headline` 与展开层的分布数字**必须同源**——都来自**同一次、同一个 `box_id`** 的 `compute()`；
- **v0.10：08 不得把两个盒子的数字合并或取平均**——"两个盒子的 ρ / EV 平均一下"是**违规**的呈现（§5.2 裁决三；要聚合只能按 08 自己的口径做加权，且**必须标注它是聚合值**）；
- 试算必须展示 `void_prob` 的变化，否则玩家无法理解 40% 损耗；
- 归因各项**必须能对账**（合计 = 相对基线的总变化）。

| T11 | `headline` 一致性 | `headline.ev == m_bar`；`headline.best_item_prob == probs[best_item]`；候选集取自**该盒池中仍可产出的全部物品**（v0.13：无隐藏款 = 该套系的 `regular_count` 个物品减去被排除项）。**v0.10**：`headline` 随 `box_id` 变——**同套系两盒配置不同 ⇒ `headline` 必须不同，相等即为缺陷** |
| T12 | **持有形态与位置无关性（v0.8 新增，v0.9 扩展）** | 固定 `(PoolState, SeriesDef, ItemDef.value)` 不动，只改变**持有形态与位置**——①把某物品的持有量从"计数 n"换成"n 个 `ItemInstance`"；②改 `serial` / `source` / `instance_id`；③**把全部同种实例改到 `location = mail`**（含分半：一部分在仓库、一部分在邮件）；④**把 `warehouse_capacity` 改成 0、改成恰好放不下一件、改成无限大**；⑤**模拟领取**（`mail → warehouse`）与**制造溢出**（产出无处可放）；⑥清空实例列表——以上任一步之后，`EvalResult` 与 `PoolEvaluation` **必须逐字段相等**（含 `m_bar` / `sigma` / `headline` / `attribution` / `rho`）。**等价判据**：`compute()` 的输入里**不出现** `count` / `instance_id` / `location` / `warehouse_capacity` / `ItemDef.size`；实现中出现即失败 |
| T13 | **守门量不侵入 ρ（v0.9 新增 / 裁决 15）** | 把仓库余量 `F` 从"充裕"改到 0（`expected_deliverable(t)` 随之降到 0）、并让 03 的 `solvency_cap` 判定结果翻转——`EvalResult`（`rho` / `m_bar` / `d_bar` / `b` / `sigma` / `headline` / `attribution` / `distribution`）**逐字段不变**。**等价判据**：`expected_deliverable` / `solvency_cap` **不出现在 `EvalResult` / `PoolEvaluation` 的任何字段里**；实现中对它求值即失败——它是**生成侧**的量，不是 ρ 的因子（§5.6） |
| T14 | **池子归属无关性（v0.10 新增；与 T12 同族：T12 守"计数 vs 实例 / 仓库 vs 邮件"两条，本条守"池子归谁"这第三条）** | 取同套系的**两个盒子 A / B**（`box_id` 不同、`socket_count` / `regular_count` 相同），**把 A 的池子编辑成与 B 不同**（如 A 排除物品 1、提升物品 2；B 不动）后：①`compute(state, A)` **只反映 A 的编辑**——其 `probs` / `void_prob` / `m_bar` / `headline` 与"只用 A 的那份 `PoolState` 单独求值"**逐字段相等**，且与 B 的编辑**无关**；②`compute(state, B)` 同理只反映 B（在本例中等于**基础池**：`void_prob == 0`、无 `ban` / `boost`）；③**A 的编辑不得使 B 的缓存失效**——断言编辑 A 前后 `compute(state, B)` 的结果**逐字段不变**，且 B 的缓存条目**未被重建**（计数器 / 调用次数可观测；反过来 B 的编辑只失效 B）；④**A ≠ B 是正确行为**：断言两盒的 `headline` / `rho` 在该编辑下**必须不同**，**相等即视为"池子被套系共享"的回归**（核心 §4.1.2 / §16.5）。⑤**同一个 `item_pool` 配不同 `modules` ⇒ 求值结果必须不同**（v0.10 结构澄清的直接验证："模块的唯一作用方式就是更改 `item_pool` 的状态"）：固定一份**相同的基础池 `item_pool`**、只让两盒的 `modules` 不同，断言 `probs` / `void_prob` / `m_bar` / `headline` / `rho` **逐字段不同**，且两盒的 `Box.modules` **逐项不同**（模块列表是**独立数据、不被折进 `weights_bp`**；**定长数组、按 `slot` 下标对齐比较**——"不同"指**占用项不同**，**不是长度不同**）；再把两盒 `modules` 都置空 ⇒ 二者**必须逐字段相等**（都回到基础池）。**等价判据**：`evaluate_pool()` 的入参里**只出现一个 `PoolState`**（**已含 05 推导好的权重**，本系统不得再应用一遍模块），且该 `PoolState` 的 `box_id` 与调用方给的 `box_id` 一致；实现中若出现"按 `series_id` 取池子"、**"按 `series_id` 缓存一份池子再复用"**或"套系级缓存键"，即失败 |

### 10.3 验收信号（切片）

- ✅ 测试者能在 2 分钟内说出自己 ρ 的主要贡献来源（P2 达成）
- ✅ 测试者能理解 `void` 的含义，并据此决定是否继续排除
- ✅ **测试者不再问"为什么位子会变"**——开始问"怎么拿到更高品质的套系"即算通过（说明**品质 → 镶嵌位**的关系被理解了，核心 §4.1.1 / P7）
- ❌ **测试者认为"显示的期望"与实际开出的东西不符** → 共享路径失效，头号缺陷，立即停止其他工作排查
- ❌ **测试者发现归因各项之和对不上总变化** → 归因算法回归，P2 失效
- ⚠️ **测试者说"我算出来的 ρ 打不到"**（仓库满、东西堆在邮件里交付不了）→ **不是本系统回归**：这是 §5.2 的**可达性**折损（ρ 的公式没错，能落到仓库里的产出变少了）。**处置是 01 / 02 / 08 侧的事**（开盒前预告 §5.7、容量解锁 D15、邮件领取），**绝不允许**回头去改 ρ 的公式或往 `attribution` 里加条目
