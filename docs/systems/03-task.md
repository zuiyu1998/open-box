# 03 · 任务系统

- 上游：`../core-design.md` **v0.9** ／ `README.md`
- 依赖系统：02 物品（**物品实例列表、派生计数、实例位置、`ItemService` 唯一写入**）、01 盲盒（发放未兑现 `Box`）、04 装置（转化端修正）、07 数值与期望（D̄ / B / ρ 口径、预期产出）
- 被依赖：08 界面与信息呈现（任务面板）、10 收集与进度（里程碑解锁落地、存档）

> **v0.8 说明（物品实例化）**：上游已把持有模型从"计数"改为"**实例**"（核心 §4.2 / §4.2.1–4.2.3）。本系统受影响的只有**一件事**——**需求匹配的落地方式**：
> 1. 需求匹配不再是"扣 `count -= 3`"，而是**挑选 N 个合格实例并销毁**（§5.2 / §5.4）；
> 2. 挑选顺序沿用本文件原有精神（**最低合格品质优先**，把高品质留给引擎），**同品质内按 `acquired_at` 升序**（先入先出）（§5.4）；
> 3. 一次交付的多个需求项**全有或全无**——任一实例不存在或已被消耗则整体失败，**不产生部分销毁**（§5.3 / §7）；
> 4. §5.2 的最大流仍按 `(category, quality)` 建模，但供应量改为**由实例聚合出的派生计数**；**匹配成功后必须回落到具体 `instance_id` 才能销毁**。
>
> **需求向量的口径不变**：仍是「类别 × 品质下限 × 数量」，只是"数量"现在的含义是**要销毁的实例个数**（§5.1）。
> 本系统的其它规则与**全部数值一律不变**（C1–C6、P1–P7、D1–D13 均不受影响）。

> **v0.9 说明（仓库容量与邮件）**：上游 v0.9 给实例加了**位置**（核心 §4.7 / §14.2 铁律 9 / §16.4）。本系统受影响三件事：
> 1. **交付的可用性口径**：**只有 `location == warehouse` 的实例可被交付**。`count()` **只统计仓库内实例**（核心 §4.7 边界 1），因此**邮件里的物品不能交付**——即使类别、品质都匹配、数量也够。§5.2 步骤 1 的 `supply` 与 §9 的"持有"一列都只认仓库内实例。
> 2. **交付走单次事务原语**：多需求项交付的全部需求项合并为**一次 `ItemService.transact(ops)` 调用**（上游裁决 2），**不再逐项 / 多次 `consume` 拼合**（§5.2 步骤 3 / §7 第 4 步）。
> 3. **交付不检查空间**：交付是**纯消耗类主动操作**（只消耗、不产出），**永不因仓库空间不足而失败**（核心 §4.7 边界 2）。**03 不做溢出判定、不碰仓库、不移动实例、不领取邮件**。
>
> **必须写明的后果**：**仓库满（且邮件里有货）时，玩家可能无法交付任务。** 这是 v0.9 的**设计要求**而非 bug——仓库容量正是"燃料还是引擎"取舍压力的来源（核心 §4.7）。但它给 08 增加了一条硬性 UI 义务：**必须让玩家看得出"邮件里有货、领不出来是因为仓库满"**，见 §9 第 6 条。
>
> **⚠️ 但这不是死局（上游裁决 16）**：核心 §4.7 **边界 4** 规定了**主动丢弃**路径——玩家可主动销毁仓库内任意实例腾出空间；**丢弃是主动行为，不违反 P5**（P5 管的是**被动**产出不得丢失）。因此"仓库满"永远有出路：**交付 / 装配 / 镶嵌 / 主动丢弃**（全部是主动操作）。`[v0.9]` "领不出来"也已被削弱：**领取是部分成功语义**——按 `acquired_at` 升序**尽可能多领**并返回实际领取清单（02 §5.10），不是"要么全领要么全不领"。**因此 §9 第 6 条的提示必须给出这些出路，而不是只报"缺口 N"。**
>
> **口径风险（已裁决，记录以免重提）**：02 的 `find_unstocked_items` 是"**当前仓库内无持有**"口径，**不得**用于 01 的"未拥有物品权重 ×1.5"——否则玩家把某 `item_id` 的实例全部压在邮件里，就能**长期白吃 ×1.5**（邮件物品虽不可用，权重加成照拿）。**×1.5 必须用收藏口径**（读 10 的 `collected`），核心与 `02-item.md` §8 已定。**03 不使用 `find_unstocked_items`**：本系统的"持有"一律指**仓库内实例的派生计数**。
>
> **需求向量的口径（§5.1）、最大流三步（§5.2）、挑选顺序（§5.4）、全部数值与红线（C1–C6、P1–P7、D1–D13）一律不变。**

## 1. 这个系统负责什么

任务 = **需求向量 + 奖励**，是循环里「完成任务」这一步的全部内容，也是**盲盒回流的主要来源**（核心 §4.3）。

| 职责 | 说明 |
|---|---|
| **`TaskDef` 定义** | 需求向量（若干「`category` × `quality` × 数量」）与奖励（`Box` / 套系券 / 位次） |
| **常规任务 `regular`** | 可重复、循环引擎；每次交付后重生成需求并回到队列。**盲盒回流的主要来源** |
| **里程碑任务 `milestone`** | 一次性；解锁新套系 / 新物品类别 / 更强模块的产出权限（D13） |
| **需求匹配** | 需求向量 vs **仓库内实例的 `(category, quality)` 派生计数**的可行性与缺口计算（§5.2）。**邮件实例不计入**（核心 §4.7 边界 1） |
| **奖励结算** | 原子交付：**一次 `transact()` 调用挑选并销毁 N 个仓库内实例** → 发奖励（**发放的是未兑现的 `Box`，进入囤积**） |
| **需求随进度变宽** | 长期压力的**唯一合法来源**（核心 §10.3 / D10） |
| **任务队列与刷新** | 队列容量、补位、放弃、批量交付 |

**宪法约束**：本系统**不得**引入任何形式的概率调整。压力只能来自需求结构（见 §5.6 与 §10 的守护性测试）。

## 3. 核心概念与术语

- **需求向量 `requirements`**：`Array[TaskRequirement]`，每项是一个「类别 × 品质下限 × 数量」三元组。**口径不变**（§5.1）。`[v0.8]` 其中「数量」现在的含义是**要销毁的实例个数**，不再是某个计数键上的扣减量。
- **持有向量（实例版）**：当前持有的一批**物品实例**（`ItemInstance`），由 02 的 `ItemService` 提供**只读快照**（见 `02-item.md`）。v0.7 的"持有向量"至此只是这份实例列表的**投影**。
- **可用实例数 `supply(category, quality)`**：某个 `(category, quality)` 分组内**仓库内实例（`location == warehouse`）的个数**。`count` 在 v0.8 是**派生值**（数实例并缓存，核心 §4.2.2），**不是存储字段**，由 02 的 `ItemService.count(category, quality, location = &"warehouse")`（`count_index` 缓存）给出——`[v0.9]` 该接口是**带 `location` 过滤的查询**（**裁决 12 / 裁决 14**，核心 §4.7 边界 3），默认口径正是本系统需要的"只数仓库"（核心 §4.7 边界 1）；§5.2 的最大流只用这个聚合量做**判定**，销毁则必须落到实例（§5.2 步骤 3）。
- **持有总量 ≠ `count()`（裁决 12）**：守恒等式以**全部实例（含 `location == mail`）**为准——`total_granted − total_consumed == Σ 全部实例`（核心 §4.7 边界 3）。**03 不得拿 `count()` 当持有总量做对账**（§10 E 第 19 条）。
- **挑选 `pick`**：在一次交付中按 §5.4 的顺序从合格实例里选出恰好 `amount` 个实例的动作；输出是 `Array[String]`（被选中的 `instance_id`）。**只读**，由 02 的 `ItemService.query(category, quality_floor)` 提供（按 §5.4 顺序返回合格实例 id）。
- **实例身份 `instance_id`**：**UUIDv4，全局唯一**，兼作发放幂等键（核心 §4.2.1 / §14.2 铁律 8）。**同一实例不得被两个需求项重复计入或重复销毁**（§5.2 / §10 E）。
- **位置 `location`（v0.9）**：每个实例的位置属性，取值 `warehouse`（仓库）/ `mail`（邮件）（核心 §4.7 / §14.2 铁律 9）。**可交付的只有 `warehouse` 实例**；邮件实例不进 `count()`，**不可用于交付 / 装配 / 镶嵌 / 转化**（口径归 02，本文档只依赖）。**领取只改 `location`**——不创建实例、不重分配 `serial`、不重跑幂等判定（归 02）。
- **有效品质下限 `effective_floor`**：需求项的品质下限经 04 的装置修正后的值。
- **可行性 `feasible`**：存在一种**实例分配**——把互不相同的实例指派给各需求项——使每一项需求都被满足。`[v0.8]` 判定的对象是**实例**（不是计数），只是用聚合计数来算（§5.2）。
- **缺口报告 `MatchReport`**：不可行时逐项缺多少、以及最小割给出的"最紧约束类别"。
- **需求变宽 `widening`**：随 `progress_tier` 上升，需求项更多、品质下限更高、类别更分散。
- **进度档位 `progress_tier`**：需求变宽的唯一输入，只在**刷新时**读取。
- **冻结**：任务实例一经生成，其 `requirements` 逐字段不再变化。
- **"品质"的两个含义（术语纪律）**：本文档出现的"品质"（`quality` / `quality_floor` / `品质下限`）一律指**物品品质**，归 `02-item.md`；**套系品质 `series_quality`**（决定常规物品数 `regular_count`、镶嵌位数、装置槽位数，归核心 §4.1.1）与本系统无关——本系统既不读写 `series_quality`，也不得把二者混用。

## 4. 数据结构（GDScript Resource 字段定义）

**选择：嵌套 `Resource`，不用 `Dictionary`。** 理由：① 需求向量必须**可在 Inspector 里结构化编辑**——R11 要求内容纯配置产出，`Dictionary` 没有字段校验、键名靠约定，配错不报错；② 存档要稳定 schema（见 `10-progression.md`），`Dictionary` 的键易漂移；③ 同一组类型可复用为运行时缺口报告对象。
> `[补充]` Godot 4.5 中把嵌套 `Resource` 用作 `@export` 元素类型需要独立脚本文件与 `class_name`，故拆为 4 个文件（`task_requirement.gd` / `reward_entry.gd` / `task_widening_profile.gd` / `task_def.gd`），理由是不拆则 Inspector 无法展开编辑，违背 R11 的数据驱动目标。

```gdscript
# res://data/defs/task_requirement.gd
class_name TaskRequirement
extends Resource
## 一条需求项：「类别 × 品质 × 数量」三元组。
@export var category: StringName = &""   ## 见 `02-item.md` 的 `ItemDef.category`
@export var quality_floor: int = 1       ## 品质下限：仅 quality >= 该值的物品可计入
@export var amount: int = 1              ## 需求量（物理单位数，非加权贡献点；[v0.8] = 要销毁的实例个数）
```

## 5. 规则与公式

### 5.1 品质在需求中的口径（明确选择）

**品质只决定"资格下限"，不做加权贡献度**：需求量 `amount` 以**物理单位数**计，**1 个合格实例 = 1 点满足度**。

`[v0.8]` 唯一的口径澄清：`amount` 计的是**要销毁的实例个数**——v0.7 计的是某个 `(category, quality)` 计数键上的扣减量，二者**在数值上完全等价**（因为计数本来就是数实例数出来的，核心 §4.2.2），因此本节的结论、§5.3 的全有或全无、§5.5 的变宽公式与 §6 的全部参数**一字未改**。

对核心 §4.2「品质决定任务贡献度」的落地口径：**品质决定该物品能否计入某一档需求**（高品质可顶替低品质，反之不行），并继续由 §4.2 的另一半——"作为装置/模块素材时的强度"——承担品质的强度语义。
`[补充]` 不采用"贡献度 = 品质"的加权口径，理由：① `D̄` 的"单位物品"口径必须唯一且确定，否则 ρ 不可归因（P2、`07-economy-rho.md`）；② 加权会让"烧高品质当燃料更省单位"成为隐藏最优解，与 §1.2「完成任务是执行、不是决策」冲突；③ P6 要求心算友好。该口径是否成立列入 §11 待定项。

### 5.2 匹配算法（两步：先聚合，再回落实例）

> **v0.8 要害**：最大流的**判定**建立在**聚合量**上，但**销毁必须落到实例**。
> 计数不再是存储字段（核心 §4.2.2），所以"够不够"要由实例聚合出来，"销毁"也只能按 `instance_id` 执行。
> **只动计数、不碰实例的实现不是合法实现**——那是在改派生值，而不是在改事实来源。

**步骤 1 · 聚合（派生计数）**

```
supply(c, q) = |{ i ∈ 持有实例 : i.item_id.category == c ∧ i.item_id.quality == q }|
```

- `supply` 即 v0.7 的"持有量"，由 02 的 `ItemService.count(c, q)`（其 `count_index` = `"<category>:<quality>" → int` 派生缓存）读出（随实例增删在**同一次调用内**更新，核心 §4.2.2）。**它只能读，不能写**。
- **02 是实例列表的唯一写入方**：03 只读这份聚合量，**不自行维护任何持有量副本**（README §3.2 / §3.8）；`count` 在 v0.8 不是存储字段，**任何"直接写 `count`"的路径都是改派生值而非改事实来源**（核心 §14.2 铁律 8）。

**步骤 2 · 最大流（判定，只用聚合量）**

```
有效下限  effective_floor(r) = max(1, r.quality_floor + mods.quality_floor_delta)   # mods 来自 04
合格判定  ok(g, r) ⟺ g.category == r.category ∧ g.quality >= effective_floor(r)
组        g = (category, quality)，其供应量 = supply(g)
可行性    maxflow = Σ amount_r  ⟺  存在整数分配 x(g,r) ≥ 0，使
            ∀g: Σ_r x(g,r) ≤ supply(g)      （一个实例只能满足一个需求项）
            ∀r: Σ_g x(g,r) = r.amount
```

- 建模为**运输问题**，用整数最大流判定（源→**实例组 `g`** 容量 `supply(g)`，组→需求项 容量 `supply(g)`（仅合格边），需求项→汇 容量 `amount`）。
- **"同一实例不得被两个需求项重复计入"在判定层的表达就是 `∀g: Σ_r x(g,r) ≤ supply(g)`。** 注意它只保证**聚合层面**不重复计数，**不保证挑选层面互斥**——因此步骤 3 必须显式去重（§5.4 / §10 E 第 20 条）。
- **禁止用贪心近似判定**：贪心会产生"明明够却判不够"的假缺口，直接破坏 P1 的可信度。`[补充]` 核心文档未规定判定算法，此处补足为最大流并禁止贪心，理由同上。

**步骤 3 · 回落到实例（销毁）**

```
对每个需求项 r、每个合格组 g（x(g,r) > 0）：
  # ① 挑选（只读）：02 的 query() 按 §5.4 顺序返回该组全部合格实例 id，取前 x(g,r) 个
  pick_g = ItemService.query(g.category, effective_floor(r))[0 : x(g,r)]

汇总所有 pick_g → 本次交付的销毁清单 dest_ids
  # 要求：跨需求项互斥、无重复、长度 == Σ amount_r

  # ② 销毁（唯一写入）：**全部需求项合并为一次事务调用**（上游裁决 2）
  res = ItemService.transact([
    { op = &"consume", instance_ids = dest_ids, tag = &"fuel" },   # 一条 op 承载全部需求项
  ])                                                              # -> { ok, reason, consumed, granted, mailed }
  # ok == true 时 consumed 即被销毁的 instance_id 列表，且必须与 dest_ids 逐位一致
  # 注意：交付的 transact 里**没有 grant op**（奖励是 01 的 Box，不是物品），因此**不涉及任何容量判定**
```

- **`transact(ops)` 是 02 提供的单次事务原语（上游裁决 2）：一次调用 = 一次提交。** 一个交付的**全部**需求项必须装进**同一次** `transact()` 调用里，**不得**把需求项拆成多次调用再"拼起来"——拆开就等于放弃了跨需求项的原子性（§5.3 规则 3 / §10 E 第 24 条）。`[v0.9]` `ops` 只含**一条 `consume` op**（`tag = &"fuel"`，供 02 的 R-M9 出口归因）：**交付不判定仓库空间**——交付只消耗、不产出，**事务内没有任何 `grant` op，因此不存在容量判定**（核心 §4.7 边界 2；`transact` 的签名与 `{ ok, reason, consumed, granted, mailed }` 返回形状见 `02-item.md` §5.11）。

- **`consume_by_filter(category, quality_floor, n) -> Array[String]`** 是同一语义的接口（挑选顺序同 §5.4，返回被销毁的 `instance_id` 列表）。⚠️ **它在一次交付里单独使用会破坏跨需求项原子性**——它**每次调用即提交**，逐项调用时"第 2 项失败"会留下第 1 项已被销毁的部分销毁；且它**不接受出口标签**（02 的 R-M9 归因需要 `fuel` 标签）。因此：
  - **`[v0.9]` 交付一律走 `transact()`（含单需求项）**：上游裁决 2 已把它定为唯一写入原语，把 `{ op = &"consume", instance_ids = dest_ids, tag = &"fuel" }` 放进**同一次**事务调用，**天然满足 §5.3 的全有或全无**。
  - 若确实要用 `consume_by_filter` 的挑选语义，只允许把它当**只读挑选**（不提交），提交仍在 `transact()` 内完成。**02 的签名不由本文档改**（§11 T9 已由裁决 2 关闭）。
- **挑选顺序**由 §5.4 规定，**落地定义在 02**（`02-item.md` §5.5：quality 升序 → `acquired_at` 升序 → `instance_id` 字典序）；03 只依赖该顺序，不自己排序，也不遍历实例列表。`[v0.9]` `query()` 只返回**仓库内**合格实例——**邮件实例不可被挑选、不可被销毁**（核心 §4.7 边界 1）。
- **必须核对返回值**：长度 == `Σ x(g,r)`、**无重复**、且 `res.ok == true`；任一不成立即整笔交付失败并回滚（§5.3 规则 3–4、§7）。`[补充]` 核对的必要性：挑选与销毁之间可能被其它出口（`engine` / `convert`）插入消耗，此时事务调用会返回 `ok == false`（`reason == &"missing_instance"`）——这正是"失败面变大"的具体形态。
- **缺口报告 `MatchReport`** 由最大流残余 + **最小割**生成：逐项缺口 = `amount_r − flow_r`，并给出最紧约束的 `(category, quality_floor)` 档，供 §9 缺口高亮使用。口径不变，只是 v0.7 的"物品组"在此改称"**实例组**"。

### 5.3 部分满足如何结算（明确规则）

> **全有或全无（all-or-nothing）。不存在部分奖励，不做暂存槽，不存在部分销毁。**

1. 匹配是**只读查询**（`TaskService.evaluate(task_instance, held_instances) -> MatchReport`），不冻结、不预留、不销毁任何实例。`[v0.8]` 形参名用 `task_instance`，以免与物品的 `instance_id` 混淆（§3）。
2. 只有当**每一需求项都满足**时才能交付；交付时**一次性销毁全部需求实例**。
3. `[v0.8]` **销毁的原子性（跨需求项）**：一次交付的**全部**需求项要销毁的实例必须在**一次提交**中销毁。`[v0.9]` 这次提交**由 `ItemService.transact(ops)` 的单次调用承载**（上游裁决 2，§5.2 步骤 3）：**任一实例不存在、已被其它需求项占用、或已被消耗 → 整个交付失败，不产生任何部分销毁**（对齐 02 的 R-M6「原子销毁、禁止部分销毁」，`02-item.md` §5.7）。
4. `[v0.8]` **每个实例最多被销毁一次**：多需求项的挑选结果必须**互斥**；两个需求项选中同一个 `instance_id` 即为致命 bug（§10 E 第 20 条）。
5. **不引入暂存槽**：允许把物品预存进任务会使燃料取舍变成"可后悔操作"，削弱 §3 的永久代价，且与 §1.2 冲突。
6. **不按比例发放奖励**：按比例奖励会让"永远差一点"也无限回流 `Box`，摧毁 ρ 的可计算性（`07-economy-rho.md`）与"燃料有代价"（核心 §3）。
7. **超额不消耗**：交付只销毁足以满足需求的实例数，多余实例**一个不动**。

### 5.4 挑选顺序（v0.8：从"扣减顺序"改为"挑选并销毁哪些实例"）

**挑选顺序（唯一规则）：**

1. **物品品质由低到高优先**——只在**合格实例**（`quality >= effective_floor(r)`）中挑选，先挑最低合格品质，把高品质留到最后。
2. **同品质内按 `acquired_at` 升序**（**先入先出**）；`acquired_at` 相同时按 `instance_id` 字典序兜底，保证顺序确定、可复现（§5.5 的 `generated_seed` 精神）。
3. **不跨类别**：挑选始终限定在该需求项自己的 `category` 内。

`[补充]` **规则 1 沿用 v0.7 的"最低合格品质优先"精神**（原为 `[补充]`：核心文档未规定扣减顺序），理由一字未改：① 交付是执行（§1.2），必须有一条确定规则；② 高品质物品同时是最好的**引擎**素材（核心 §4.2），该规则把高品质留给"使用物品"这个唯一决策点。**规则导致的 D̄ 变化必须可由归因面板读到（P2）**。v0.8 只把机制从"扣减计数"换成"挑选实例"，**结论与理由均不重写**。

`[补充]` **规则 2（同品质内 FIFO）是 v0.8 新增的上游裁决**（核心 §4.2.3）。理由：同品质实例在功能上**完全等价**（价值 `v` 只由 `quality` 决定，核心 §4.2；02 的持有量层本就不区分具体物品），因此这个顺序**不影响任何数值**，只影响**留下的是哪些个体**——FIFO 让玩家保留较新开出的实例（`serial` 更大），与核心 §4.2.1 的收藏叙事一致；`acquired_at` 单调又让顺序天然确定、可重放。`instance_id` 字典序兜底是 `[补充]`，只为消解同一秒开出多个实例时的平局。

### 5.5 需求生成与冻结

```
n_req   = clamp(base.size() + floor(t / tier_per_extra_requirement), base.size(), max_requirements)
t       = min(progress_tier, widening.max_tier)
floor   = min(max(base_floor) + floor(t / tier_per_quality_step), max_quality_floor)
amount_i= ceil(base_amount_i × (1 + amount_growth_per_tier × t))
类别     = 从 (category_pool ∩ 已解锁类别) 中按权重抽 n_req 个不重复类别
权重(c)  = (1 − rarity_bias) + rarity_bias × (1 − base_output_share(c))
```

- `base_output_share(c)` **只读 `SeriesDef` 基础权重表**（见 `01-gacha.md`），**绝不读 `PoolState`**。若需求读取玩家编辑后的池子，等于对镶嵌行为施加隐性惩罚，破坏 P1 与 P7 的承诺。
- **可满足性守门**：若 `Σ amount > solvency_cap × expected_output(t)`，先按比例回退 `amount`，再回退 `n_req`；`n_req ≤ |category_pool ∩ 已解锁类别|`。
  `[v0.9]` **`expected_output(t)` 必须改用「可交付产出的保守下界」（上游裁决 15）**：v0.9 下产出可能落进邮件而**不可交付**（核心 §4.7 边界 1），若守门仍按"产出总量"计，会生成"**算得出来却永远交不了**"的需求。**该口径由 `07-economy-rho.md` 定义**（核心 §4.7 接口约定）；07 落地前本项**标注为待定（§11 T11）**，实现**不得**沿用 v0.8 的"产出总量"口径。
- **数量轴只做温和线性补偿**：核心 §10.3 点名的压力主轴是"更分散、更稀有的类别"，数量轴**不得**成为主要压力源（否则退化成数值墙，R7）。`[补充]` 核心只点名宽度与稀有度两轴，此处限定第三轴的从属地位。
- **冻结**：生成即冻结，`progress_tier` 上升**不得回溯修改**已生成任务的需求。`[补充]` 这是 P1（不得暗改）在任务侧的必然推论，明确写死以防实现时"顺手刷新"。
- **可复现**：`generated_seed = hash(save_seed, task_id, completed_count)`，同一存档的刷新结果完全确定（进存档，见 `10-progression.md`）。

### 5.6 进度档位与"压力只能来自需求结构"

```
progress_tier = 常规任务交付总次数 + milestone_tier_weight × 已完成里程碑数
```

**硬规则（本系统的宪法条款）：**

1. 需求变宽是**唯一的长期压力来源**；`progress_tier` **只能**作为需求生成（§5.5）的输入。
2. **任何以 `progress_tier` / 完成数 / 游戏时间为输入去修改 `SeriesDef` 基础权重、隐藏物品概率、保底参数或 `PoolState` 的实现，一律否决**（P1 + §3.7 跨系统铁律 7）。
3. 需求变宽**必须可预告**：任务面板要显示"下一档位的需求结构变化"（如"下档位起需求将要求第 3 类类别、品质下限 +1"）。`[补充]` 长期压力若不可预告，玩家会怀疑系统暗改（R12 同类风险），这是 P1 的要求在任务侧的落地。
4. 变宽造成的 ρ 下滑必须**逐项可归因**到需求结构项（宽度 / 品质下限 / 数量），归因口径见 `07-economy-rho.md`。

### 5.7 队列、刷新与可接数量

- 队列容量常量 `QUEUE_CAPACITY = 3`，**恒满**：交付或放弃后立刻补位，队列中不出现空位。
- **可接数量 = 队列容量**，不设第二层"接取"动作。`[补充]` 切片内"接取"不产生决策只增加点击；任务面板直接标明可交付 / 不可交付即可。
- **无手动刷新**。`[补充]` 本作没有刷新资源，免费刷新会退化成"刷到好任务为止"的最优解（D12 精神、R1）。
- **放弃不惩罚**：不可满足或暂时不想做可放弃，当次不消耗任何资源，放弃计数只进入刷新种子。`[补充]` 施加惩罚会诱导玩家"不敢放弃"而回避任务分配这个唯一的决策点（与 R10 同理）。
- 里程碑任务独立展示，**不占队列位**。

### 5.8 批量交付（可选）

`TaskService.deliver_batch(task_instance_ids)`：**按玩家选择顺序逐个判定**，不可行者跳过并报告原因，不阻塞其余任务；**不做跨任务的全局最优分配**。`[补充]` 核心 D12「不提供一键最优配置」在任务侧的直接体现。
`[v0.8]` 形参由 `instance_ids` 改名为 `task_instance_ids`：**这是任务实例，不是物品实例**——v0.8 引入物品 `instance_id` 后原名会与 02 的实例身份混淆（§3）。仅改名，规则未变。**每个任务仍各自独立挑选并销毁自己的实例**，跨任务不做实例层面的全局分配（同上）。
**不做自动交付**：自动化会把唯一的决策点（燃料/引擎与任务分配，§1.2 / P3）自动化掉，违反 R1 对策。

## 7. 流程 / 状态机

```
任务实例状态： QUEUED ──交付成功──▶ DELIVERED
                 │                     ├─ 常规：completed_count+1 → 重新生成需求（tier 已更新）→ QUEUED
                 │                     └─ 里程碑：COMPLETED（终结）
                 └──玩家放弃──▶ ABANDONED（移除并补位）
```

**结算序列（一次交付）**：`[补充]` 核心文档未规定结算原子性，此处明确为**物品侧单一事务 + 跨系统幂等重放**（`[v0.9]` 按上游裁决 13 修订），理由：扣减与发放若中途失败会产生"物品没了但盒子没到"的不可解释状态，直接摧毁 P1 可信度。**物品侧的"没了一半"由 `transact()` 杜绝；跨系统的重复发放由幂等键杜绝**——两条分别守各自的边界，不做跨系统两阶段提交（核心 §4.7 边界 5）。
`[v0.8]` **失败面变大**：v0.7 的交付只改一个计数键，v0.8 要"挑选实例 → 销毁 → 核对返回"，**挑选结果可能因期间消耗而失效**，且跨需求项存在重复计入风险。因此第 2 步的互斥校验与第 4 步的返回值核对都是**必须**的，不是可选优化。
`[v0.9]` **提交收敛为一次 `transact()` 调用**（上游裁决 2）：跨需求项的原子性由 02 的事务原语承载，**03 不再自行拼接多次 `consume`**；同时**交付不检查仓库空间**（只消耗、不产出，核心 §4.7 边界 2）——"仓库满"既不会让交付失败，也不会让交付"部分成功"。

1. 重算可行性（§5.2 步骤 1–2），不可行即中止并返回缺口报告；
2. 生成挑选清单（§5.4）：确定**每个需求项要销毁的实例集合**，并校验清单内 `instance_id` **互斥且无重复**、总长 == `Σ amount_r`；
3. 计算经 04 修正后的消耗量、经 04 修正后的 B；
4. 提交（**单事务**）：`ItemService.transact([{ op = &"consume", instance_ids = dest_ids, tag = &"fuel" }])` **一次调用销毁全部需求实例**（上游裁决 2；返回 `{ok, reason, consumed, granted, mailed}`，`ok == true` 且 `consumed` 与 `dest_ids` 逐位一致）→ `01` 发放未兑现 `Box` → `10` 落地 `unlock_ids` 与位次 → 更新任务实例状态与 `progress_tier`；
   `[v0.9]` **交付路径不得出现任何空间检查**：不读 `warehouse_capacity` / `ItemDef.size`、不写 `location`、不生成或领取邮件条目（核心 §4.7 边界 2）。交付的事务里**只有 `consume` op**（没有 `grant`），因此**根本不存在容量判定**。
5. **失败处理分两层（上游裁决 13，核心 §4.7 边界 5）**：
   - **① 物品侧**：`transact()` **只覆盖物品侧**，且**一次调用 = 一次提交**——失败即整体回滚，**源实例一个都不销毁**，`instances` / `count_index` / `warehouse_used` / 三个计数器逐项回到事务前（02 §5.11）；
   - **② 跨系统侧**：`transact()` **不承诺跨系统原子性**——01 的 `Box` 发放与 10 的解锁落地**不参与该事务**，它们各靠**自己的幂等键**（核心 §14.2 铁律 8：`instance_id` 作幂等键）保证"**重放不会重复发放**"，失败后由**幂等重放**恢复：重放时必须**复用同一批 `dest_ids` 与同一组奖励载荷**，**不得二次挑选**（下方 ⚠️ 第 5 条）。
   **单人游戏不需要分布式事务，幂等重放更简单也更可靠**——因此 §7 不追求"全部步骤一起回滚"。任务实例状态与 `progress_tier` 只在**全部步骤成功之后**推进。
6. 记录结算事件 `task_delivered(task_id, tier, consumed, rewards, mods)`。`[v0.8]` `consumed` 记**被销毁的 `instance_id` 列表**（而非计数）——这样归因（P2）与数量对账都能回落到具体个体，与 02 的 `total_consumed` 记账一致。

## 9. UI 需求

面板规格归 `08-ui-panels.md`，本系统只提供数据：

1. **需求向量 vs 仓库内持有向量对照**（核心 §8.1 任务面板）：逐项显示"需要 / 持有 / 缺口"，缺口高亮取自 §5.2 的 `MatchReport`。`[v0.8]` "持有"一列显示的是**实例聚合出的派生计数**（`supply`）——UI 上的数字不变，只是它的来源从存储字段变成了数实例（核心 §4.2.2）。**面板不得缓存该数字**，它必须随实例增删失效重算。`[v0.9]` 该列**只统计仓库内实例**（`count()` 口径）：**邮件里的同类物品不计入"持有"**，因为**它们不可交付**（核心 §4.7 边界 1）。
2. **可交付状态**：可行 = 可点击；不可行 = 缺口高亮 + 最小割给出的最紧约束档。
3. **奖励预告**：显示装置修正后的实际发放 `Box` 数，而非 `TaskDef` 原值（P2）。
4. **变宽预告**：显示下一档位的需求结构变化（§5.6 规则 3）。
5. **批量交付多选**（可选）：多选后一次确认，逐个结算并回报被跳过的任务。
6. **`[v0.9]` "邮件里有货、领不出来是因为仓库满"必须让玩家一眼看出（硬性义务，转交 08）**：当仓库已满（`Σ size` 接近 `warehouse_capacity`）且邮件里存在**满足当前任务需求**的同类实例时，"不可交付"状态**不得**只显示"缺口 N"——它必须同时点明：**缺口物品正在邮件里，而邮件物品不可交付**，并给出可执行提示（"仓库已满 x/y → 先腾出空间：**交付其它任务 / 装配 / 镶嵌 / 主动丢弃**（核心 §4.7 边界 4），或按 D15 扩容后领取"）。理由：**"交不了任务"是 v0.9 的设计要求而非缺陷**（见文首 v0.9 说明），但玩家若看不出原因是仓库满，它会被读成 bug 或暗改概率（P1 / R12 / R14 同型风险）。**呈现规格归 08**；03 只提供数据：`MatchReport` + **邮件侧同类实例计数**（`count(c, q, &"mail")` / `mail_instances()`，**上游裁决 14：02 已提供该接口**）+ 仓库占用占比。`[v0.9]` 提示里**必须出现"主动丢弃"**这一条出路——否则玩家会以为系统锁死了（核心 §4.7 边界 4 的理由就是防这个死局）。

## 10. 测试点与验收标准

**A. 奖励守恒**

1. 交付 N 次 → 囤积清单中该套系 `Box` 增量 == `Σ rewards.count × N + B 修正量`，无凭空产生、无重复发放。
2. **销毁清单总量 == `requirements` 总量**（不可行时**零销毁**）；`[v0.8]` 清单由 `instance_id` 构成，长度与互斥性见 E 第 18 / 20 条。
3. 里程碑任务**只能完成一次**，第二次交付被拒绝且不销毁任何实例、不发奖励。
4. 结算任一步注入失败 → 物品、`Box`、`progress_tier` 全部回到交付前（回滚测试）。

**B. 需求匹配边界情况**

5. 恰好满足 / 超出一单位（不扣多余）/ 持有为空 / 品质全部低于下限。
6. 同一**实例**不得同时计入两个需求项（防止重复计数；实例版用例见 E 第 20 条）。
7. 混合品质：低品质优先**挑选**顺序正确（§5.4）。`[v0.8]` 原"扣减顺序"的用例改为断言**被销毁的 `instance_id` 集合**，见 E 第 17 条。
8. **假缺口反例（禁止贪心）**：构造"按需求项顺序贪心会失败、但实际可行"的用例，断言判定为可行。
9. 04 的"需求品质下限 −1"生效后，由不可行翻为可行。

**C. 冻结与可复现**

10. 交付后 `progress_tier` 上升，已刷新任务的需求**逐字段不变**。
11. 同一 `save_seed` 重放 → 刷新结果与 `generated_seed` 完全一致。

**D. 守护性测试：「压力只能来自需求结构，不能来自降低概率」★**

12. 对 `progress_tier = 0…50` 逐档快照 `SeriesDef` 基础权重表、隐藏物品参数、保底参数：**全档位哈希恒定**（配置层不随进度变化）。
13. 在**不执行任何 `PoolService` 写入**的前提下，逐档断言 `EvalService` 的 `pool_distribution` 恒定——运行时不因进度调权（P1）。
14. ρ 随档位下滑的归因项集合 ⊆ `{需求宽度, 品质下限, 需求数量}`，**不得出现任何池权重类归因项**。
15. 源码级扫描：池子权重写入路径唯一为 `PoolService`；**不存在**任何以 `progress_tier` / 完成数 / 游戏时间为输入的权重修改 API。
16. `SLOT_UNLOCK` 与任何奖励路径都不得改变**同一套系内**的 `socket_count` / 装置槽位常量（对齐 C4 回归测试）；跨套系取值不同（更高品质套系）是合法的（核心 §4.1.1）。

**E. 实例挑选与销毁（v0.8 新增，物品实例化的直接后果）★**

17. **挑选顺序正确（低品质先进先出）**：构造同类别、品质混合的实例集（如 `q1 × 2` / `q2 × 3`，两组 `acquired_at` 交错），需求 `quality_floor = 1, amount = 4` → 断言销毁的是 **2 个 `q1` 实例 + `acquired_at` 最早的 2 个 `q2` 实例**；再单独测**同品质内的 FIFO**（`acquired_at` 升序、平局按 `instance_id` 字典序）逐位正确。
18. **原子性（失败不留部分销毁）**：挑选清单已生成后，人为令其中**一个 `instance_id` 失效**（模拟期间被其它出口消耗）→ 断言整个交付**失败**，且 02 的实例列表与 `(category, quality)` 派生计数**逐位不变**（**零部分销毁**）；对齐 02 的 R-M6。另测多需求项用例：令**第 2 个**需求项必然失败 → 第 1 个需求项的实例**也不得被销毁**。
19. **销毁后派生 `count` 同步变化**：交付成功后，被销毁实例所在分组的**仓库 `count`（`count(c, q, &"warehouse")`）恰好减少请求量**，实例列表中**不再出现这些 `instance_id`**；且 **`total_granted − total_consumed == Σ 全部实例（含 `location == mail`）`**（**上游裁决 12**，核心 §4.7 边界 3 / 02 §4.3）。**任何"仓库 `count` 与仓库内实例数不一致"即为致命 bug**（核心 §14.2 铁律 8）——注意 `count()` 只是**带 `location` 过滤的查询**，它**本来就不等于实例总数**，因此对账必须走 `total_granted − total_consumed` 那条等式，**不得**用 `count()` 冒充持有总量。反向：**不存在**任何"只改 `count` 不改实例列表"的路径（静态检查）。
20. **同一实例不得被两个需求项重复计入**：① 边界用例 `ore ≥1 × 4` + `ore ≥2 × 1`，持有恰好 `1 个 q2 + 3 个 q1` → 最大流判**不可行**（`q2` 只能顶一个需求项）；② 持有 `1 个 q2 + 4 个 q1` → 可行，且两个需求项**销毁的 `instance_id` 集合互不相交**。断言挑选结果**无重复 ID**、`Σ` 长度 == `Σ amount_r`（§5.2 步骤 3 / §5.3 规则 4）。
21. **实例不变量守护**：交付路径**不得**出现任何绕过 `ItemService` 的实例增删或计数改写（静态检查，对齐 README §3.2 / §3.8 与 02 的 §10.3 单写入方测试）。

**E2. 仓库与邮件（v0.9 新增，仓库容量与邮件系统的直接后果）★**

22. **邮件实例不可交付**：构造"需求 `ore ≥1 × 3`，仓库内 0 个、**邮件里恰好 3 个**（类别、品质完全匹配，数量足够）"→ 断言 `MatchReport.feasible == false`、逐项缺口为 3、**交付被拒绝且零副作用**（实例列表逐位不变）；随后把邮件实例的 `location` 改为 `warehouse`（模拟领取）→ **同一断言翻为可行**。同时断言 `count(&"ore", 1) == 0`：**邮件实例不得计入 `supply`**（核心 §4.7 边界 1 / §14.2 铁律 9）。反向用例：把某实例的 `location` 置为 `mail` 后，它**不得**出现在 `query()` 的挑选结果里。
23. **交付不因空间不足而失败**：把仓库填满（`Σ size` 达到 `warehouse_capacity`，**不阻碍本次交付**的其它物品）后交付一个可行任务 → 断言**交付成功**、目标实例被销毁、仓库占用**下降**、`Box` 正常发放；交付过程中的任意时刻都**不产生邮件条目**、**不读写 `location`**（核心 §4.7 边界 2）。静态检查：03 的交付路径不含 `warehouse_capacity` / `ItemDef.size` / `location` 的**判定或写入**。
24. **事务原子性（一次 `transact()`）**：断言一次交付（含多需求项）**只发起一次 `ItemService.transact()` 调用**（运行期调用计数 == 1，静态检查无"按需求项循环提交"的形态）；在该调用内注入**第 2 个需求项**的失败 → 断言**第 1 个需求项的实例也不得被销毁**、实例列表与派生计数逐位不变。**本条是 E 第 18 条在事务原语下的对应版本，两条都要保留**（18 测"失败不留部分销毁"，本条测"只有一次提交"）。

**F. 切片失败信号（要正视）**

- 测试者感觉"任务越要越稀有"但**说不出这是需求变宽**，或怀疑系统暗改了概率 → 变宽预告与归因失效（P1 / R12）。
- 测试者在中后期仍只刷一个任务、从不看第二个 → 宽度轴太缓。
- 测试者把物品**全部**用掉、从不考虑装配 → 中心机制不成立（对齐核心 §13.4）。
- 测试者因需求变宽产生"被惩罚"感而非"要选更宽的库存"感 → `solvency_cap` 过低或变宽曲线过陡。
- 3 个常规任务对盲盒回流的贡献占比 < 90% → 与核心 §4.3「常规任务是回流主要来源」不符。
- `[v0.9]` **测试者说"东西明明就在邮件里，为什么交不了任务"，并认为这是 bug** → §9 第 6 条的提示缺失（"仓库满 + 邮件有货"的合成状态没有被呈现出来）。
