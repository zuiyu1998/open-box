# 05 · 模块与池子编辑系统 ★

- 上游：`../core-design.md` **v0.11** ／ `README.md`
- 依赖系统：`02-item.md`（模块素材）、`07-economy-rho.md`（求值路径）
- 被依赖：`01-gacha.md`（抽取消费池子状态）、`08-ui-panels.md`（池子面板）、`09-presentation.md`（演出过滤）
> **本文件已并入 `01-gacha.md`（模块与池子系统是盲盒下的子模块），内容以 `01-gacha.md` 为准。**

> **本系统是全作风险最高的系统。**
> 它同时承担三件事：玩家能动性的主载体、"盲盒期望可被施工"的实现、以及最大的平衡风险（R2）与最大的技术风险（R4）。
> 改动本系统前请通读 §5 与 §10.1。

> **v0.11 说明（去除保底系统——对本文档：零规则改动，只清措辞）**
> 1. **本系统的求值链本来与保底无关**：`ItemPool` / `Box.modules` / `PoolState` / `_rebuild()` 里**没有任何为保底预留的状态**（无计数器、无 streak、无"必出"覆盖）——当前状态**只**由「`item_pool` + 该盒 `modules`」决定（§4 / §5.1），因此**抽取无状态**，`roll(evaluation, seed)` 的入参里也没有计数器（核心 §9 铁律 1）。
> 2. **唯二的连带修改是措辞**：`void` 那句"计入保底推进"作废（v0.11 起"不产出物品 + 消耗一个盲盒，仅此而已"，§5.4）；§5.3 的"C6 保底 3 个物品"改述为"C6 保证至少保留 3 个可产出物品"（**C6 本身一字未改**）。**池子编辑的规则与数值全部不变**（C1/C2/C3/C6、40% 损耗、零和、25%–40%、`weights_bp`）——P1 因此**在每一次抽取上都严格成立**。

> **v0.10 说明（结构澄清：`Box` 下面是两个并列数据 + 池子随盒子走）**
> 1. **`Box` 下面挂着两个并列的数据**（核心 §4.1.2 / §16.5，**字段名固定**）：**`item_pool`（物品池）**——该盒的池子、**生成数据的凭证**（`roll()` 消费它）；
>    **`modules`（模块列表）**——镶嵌在**该盒**上的模块，**其唯一作用方式就是更改 `item_pool` 的状态**。
> 2. **模块不折进池子**：它与 `item_pool` **并列**，**池子的当前状态是二者的函数**（「`item_pool` 基础数据 + 该盒 `modules` 的编辑效果」）——由本系统的 `PoolService` **唯一求值/写入**，再由 07 的 `EvalService` 求值成概率 / EV / ρ。
>    核心**已明确否决 `PoolState.socketed` 这种"模块在池子里"的形状**；本文档 §4 已按此重构。"换掉一个模块" = 换掉**一项作用于该池的编辑**，而**不是**"在池子里挖掉一块再补上"。
> 3. **这份当前状态是派生值、不入档**：载入时**逐盒重建**——存档里**不存在"编辑后的权重"这第二个事实来源**。**模块列表可以独立于池子被查看、替换与拆卸**，而池子的状态**始终是它的函数**。
> 4. **模块镶嵌进具体的盒子并锁定在那里**：镶嵌后进入**该盒的 `modules` 列表**，**该盒施工台随之清空**；**配置下一个盒子需要新的模块**（模块由物品制造，是实体消耗品）。**不得把模块移到别的盒子。**
> 5. **镶嵌位数 = 该盒所属套系品质对应的位数**（2/3/4/5），**在同一池（盒）内恒定**——**C4 只改措辞，规则不变**。**拆卸从盒子上拆**（盒子未兑现时）；**兑现后盒子连同它的 `modules` 一同消耗**（不再返还）。
> 6. **P7 已改写**（核心 §7）：v0.9 的"功率不随重复劳动增长"**不再成立**（位子总数 = 盒数 × 每池位数，盒数无上限）；新锚点：**单池功率仍封顶于 N**（结构性）+ **跨池复制则由模块的物品成本约束（D17）**。**D17 = 单个模块的物品成本**，本版最关键数值，见 §11 **M9**。
> 7. **C1 / C2 / C3 / C6 与 `void` 自限全部不变**——它们本来就是**单池**约束。**归属与写入权是两件事**：`Box.item_pool` / `Box.modules` 的**数据归属是 01（那个盒子）**；本系统拥有**编辑规则与写入权**（`PoolService` 仍是**唯一写入方**）。

## 1. 这个系统负责什么

1. **某一个盒子的两份池子数据（`Box.item_pool` + `Box.modules`）的唯一写入方**——这两份数据的任何变更都只能经由 `PoolService`；**它们的归属是 01（那个盒子）**，本系统拥有的是**编辑规则与写入权**（README §2 / §2.1，v0.10）
2. **排除（`ban`）**：令指定物品概率归零，不再产出
3. **提升（`boost`）**：提高指定物品概率，增量从其他常规物品按比例扣除
4. **损耗（`loss`）**：排除释放的概率中 40% 不可回收，落为 `void`（详见 §5.4）
5. **隐藏物品免疫的执行**：保证隐藏物品概率恒为 2%（规则由 `01-gacha.md` 声明，执行在此）
6. **镶嵌位管理**：数量由**该盒所属套系品质**决定（品质1–4 → 2/3/4/5），**在同一池（即同一盒子）内恒定、运行时不可变**（C4 / P7）
7. **模块的镶嵌、替换与拆卸（全部针对"某一个盒子"）**——**镶嵌即写进该盒 `modules` 的第 `slot` 位并锁定在那个盒子**，**镶嵌后该盒施工台清空**（配置下一个盒子要新模块）；**拆卸只是把该盒 `modules` 的第 `slot` 位置空**（定长数组长度不变）——**不是"把模块从池子里挖出来"**（模块与池子并列，见 §4）；**拆卸只能从盒子上拆**（盒子未兑现时），**兑现后盒子连同它的 `modules` 一同消耗**；拆卸返还 50%。v0.9 起：制造消耗**销毁物品实例**（原子），拆卸返还**创建新实例**（新 UUID、`source = { kind = &"refund" }`；`serial = 0` 由 02 内部置位，**不是 `grant` 的参数**；见 §5.6 / §7.1）；替换是**一次 `transact()`**；**拆卸返还装不下则拒绝整个拆卸**（裁决 17：被动产出（开盒）才进邮件，主动操作不反噬）
8. **回收（`recover`）**：挽回部分 `void` 质量——**第二切片，本版仅定义接口**
9. **排除物品数上限（C6）**：排除物品数 ≤ 常规物品数 − 3，**任何池子至少保留 3 个可产出物品**
10. **池子当前状态的推导（v0.10）**——由「该盒 `item_pool` 的基础数据 + 该盒 `modules`」算出**当前权重与 `void_mass_bp`**（**整数万分比**，Σ == 10000），产出 §4 的**派生状态**；这份状态**不入档**，载入时**逐盒重建**

## 2. 不负责什么（边界）

| 不负责 | 归属 |
|---|---|
| 概率求值（把**派生状态**变成具体概率 / EV / ρ） | `07-economy-rho.md` |
| 抽取判定 `roll()` | `01-gacha.md` |
| 隐藏物品概率**数值**的声明（2%） | `01-gacha.md` |
| EV / ρ / `headline` 的计算 | `07-economy-rho.md` |
| 池子面板的渲染、以及**"哪个盒子被选中"的选中态** | `08-ui-panels.md`（`selected_box` 由 08 维护，见 §5.6） |
| 演出中被排除物品的过滤**呈现** | `09-presentation.md` |
| **`Box.item_pool` 与 `Box.modules` 这两份数据的归属** | **`01-gacha.md`（盒子）**——两个字段都挂在**那个盒子**上，池子是**那个盒子自己的属性**（核心 §4.1.2）。**05 只拥有编辑它们的规则与写入权**（`PoolService` 是唯一写入方）。**"归属"与"写入权"是两件事，不得混写**（README §2.1） |
| **"池子当前状态"这份派生值的去向** | **由 05 推导**，但它**不是一份存储的数据**：**任何系统都不得把它当第二个事实来源落盘**（载入时逐盒重建，核心 §4.1.2）；求值成概率 / EV / ρ 归 `07-economy-rho.md` |

> **关键边界**：本系统**只写数据、不算数字**。任何"想知道当前概率是多少"的需求，一律调 `EvalService`。
>
> **v0.10 补充边界**：本系统**也不拥有这两份数据本身**——它拥有的是**编辑某个盒子数据的规则与写入权**。
> 因此**每一次写入都必须显式指定目标盒子**（§4.1 的接口签名），本系统**不得**持有"当前套系的池子"这种全局单例状态，
> 也**不得**缓存"某个套系的一份池子"——两条都会让同套系的两个盒子被误合并成一份（v0.9 → v0.10 的核心隐患）。

## 3. 核心概念与术语

| 术语 | 代码名 | 说明 |
|---|---|---|
| 物品池 | `Box.item_pool` | **该盒的池子这份数据本身**（产出哪些物品、基础权重、隐藏物品）——**生成数据的凭证**，`roll()` 消费它。**每个 `Box` 各一份**；归属 01，写入权归本系统（核心 §4.1.2，v0.10） |
| 模块列表 | `Box.modules` | **定长** `Array[Module]`（长度恒 == `item_pool.socket_count`，**空位为空项**）——镶嵌在该盒上的模块，与 `item_pool` **并列**（**不是折进池子里的**）；**模块的唯一作用方式就是更改 `item_pool` 的状态**（核心 §4.1.2）。**槽位号＝数组下标**（**不另设 `slot` 字段**——不留第二事实来源）；**落盘由下标生成稀疏序列**（`index` + `module_id` + `quality` + `socketed_at`），归 10 |
| 池子状态 | `PoolState` | **派生状态**：由「`item_pool` 的基础数据 + 该盒 `modules`」求值出的**当前权重**（`weights_bp`，Σ == 10000）与 `void_mass_bp`（整数万分比，同单位同精度）。**不是一份存储数据、不入档**（载入时逐盒重建）；**不含模块列表**——`PoolState.socketed` 这种"模块在池子里"的形状**已被核心否决** |
| 修订号 | `revision` | 每次写入 +1；缓存与失效的唯一依据（**每盒一份**）。主副本在 `ItemPool`，派生状态只镜像它 |
| 模块（实例） | `Module` | **一个已镶嵌模块的实例**（`module_id` / `quality` / `socketed_at`）——挂在 `Box.modules` 上、**不在 `ItemPool` 里**；**不含 `slot`**（槽位＝它在数组里的下标）；与 `ModuleDef`（**定义**）**是两回事**；模块是**消耗品**（§5.6）。类型定义见 §4 |
| 模块定义 | `ModuleDef` | 一条作用在开盒端的**编辑规则蓝图**（`op_type` / `targets` / `magnitude` / `item_cost`…，见 §4 前两段）；`Module.module_id` 指向它 |
| 镶嵌 | `socket` | 把模块放进**某个盒子**的镶嵌位的动作——**即进入该盒的 `modules` 列表**；**放上即锁定进该盒**（v0.10） |
| 镶嵌位 | `socket_slot` | **数量由该盒所属套系品质决定**（品质1–4 → 2/3/4/5），落在该盒 `item_pool.socket_count` 上；**在同一池（盒）内恒定、运行时不可变**（C4；v0.10 只把口径从"同一套系"改为"同一池（盒）"） |
| 排除 | `ban` | 某个物品概率归零 |
| 提升 | `boost` | 某个物品概率 ×N |
| 释放质量 | `freed_mass` | 排除某个物品后从其基础权重中释放出的质量 |
| 回收率 | `recover_rate` | 释放质量中可重新分配的比例，**0.60** |
| 空洞 | `void` | 不可回收的那 40%，落为零价值结果（§5.4） |
| 重分配模式 | `redistribute_mode` | `AUTO`（按基础权重）／ `TARGETED`（指定目标物品） |
| 替换 | `replace` | 镶嵌位满时的唯一操作——**没有"再装一个"** |
| 物品实例 | `ItemInstance` | 模块制造时被**销毁**的那个物品个体；拆卸返还时**新建**（见 §5.6） |
| 实例 id | `instance_id` | **UUIDv4**；制造消耗按它指定，**返还实例的 UUID 全新**（原实例已销毁） |
| 收藏编号 | `serial` | **返还实例一律 `serial = 0`**——只有开盒产出才分配收藏编号；它是**实例字段**，**不是 `grant` 的参数**（第三位是幂等键 `instance_id`），由 02 内部置位 |
| 物品品质 | `quality` | 1–5 序数，物品的等级维度（见 `02-item.md`） |
| 套系品质 | `series_quality` | 该套系的规模等级（1–4）。**每个盒子按其所属套系的品质取得**常规物品数与镶嵌位数（核心设计书 §4.1.1 / §4.1.2，v0.10） |

> **术语纪律（v0.6 新增）**：本作的"品质"有**两个**含义——**物品品质 `quality`**（1–5，见 `02-item.md`）与**套系品质 `series_quality`**（核心设计书 §4.1.1）。
> 凡文中出现"品质"二字**必须可分辨是哪一个**：谈镶嵌位与物品数时指**套系品质**，谈物品价值与任务需求时指**物品品质**。
> （`ModuleDef.quality` 是**模块品质梯度**，属第三条独立轴，见 D13，不得与前两者混用。）

## 4. 数据结构

```gdscript
# res://src/gacha/pool/defs/module_cost.gd（v0.9 新增）
class_name ModuleCost
extends Resource

## 制造消耗条目 = **需求向量**（裁决 5）：与 04 的 `DeviceCost` **同一结构**，两文档消耗维度已统一。
##   制造 → 交 02 按 (category, quality) 挑选 amount 个实例并**销毁**（原子，全有或全无）；
##   拆卸 → 按本条目逐条 floor(amount × 0.5) **新建**实例（新 UUID；serial = 0 由 02 内部置位）。
##   [补充] 字段形状照 04 的 DeviceCost 落地（核心 §14.3 只列出 ModuleDef 含"成本"，未给形状）。
@export var category: StringName = &""
@export var quality: int = 1
@export_range(1, 99, 1) var amount: int = 1
```

```gdscript
# res://src/gacha/pool/defs/module_def.gd
class_name ModuleDef
extends Resource

enum OpType { BAN, BOOST, RECOVER }

@export var id: StringName
@export var display_name: String
@export var quality: int                       # 模块品质梯度（核心文档 D13）
@export var op_type: OpType
@export var targets: Array[StringName]         # 多目标；隐藏物品出现在此处即为非法配置
@export var magnitude: float = 1.0             # BOOST 的倍数；BAN/RECOVER 忽略
@export var redistribute_mode: int = 0         # 0 = AUTO, 1 = TARGETED
@export var redistribute_target: StringName    # TARGETED 时的目标物品
@export var item_cost: Array[ModuleCost] = []  # 制造消耗：**需求向量** `(category, quality, amount)`（v0.9 与 04 的 DeviceCost 统一，裁决 5）
@export var exclusive_tags: Array[StringName]  # 互斥标记
```

> `[补充]` **制造消耗的实例语义（v0.9：与 04 统一为需求向量）**：`item_cost` 是 `(category, quality, amount)` 的**需求向量数组**，与 04 的 `DeviceCost` **同一结构**（裁决 5）——v0.8 那句"两文档消耗维度**不对称**"**已删除**（不对称已由裁决消除，见 §11 / M8）。理由：盲盒产出随机，`item_id` 级要求会让玩家卡在"我需要星尘但只开出晶核"。
> - **制造（消耗）侧不需要反查**：需求是**向量级**，交 02 按 `(category, quality)` 挑选实例并原子销毁即可（`consume_by_filter` / `consume`）；
> - **拆卸（返还）侧需要反查**：返还必须落到具体 `item_id`，一律调 **`ItemService.resolve_item_id(category, quality)`**（裁决 9），05 **不得**自己构造 id 字符串；该映射的"唯一"由**配置校验器强制**（配置期即报错），不是"切片下碰巧唯一"的兜底；
> - **溢出处理按操作性质分叉（裁决 17）**：**被动产出（开盒）**放不下 → 进邮件（归 01 / 02）；**主动操作（转化 / 拆卸返还）**放不下 → **拒绝整个操作**。理由：主动操作会销毁源实例腾出空间，产出的新实例却进邮件，就是**净损失可用持有**，与"转化是燃料路径的预处理"直接冲突。**因此 05 对拆卸返还必须做空间预检**（见 §5.6）——这条不是"05 不判定"，而是"05 先查再动"。

```gdscript
#     @export var modules: Array[Module]           # 镶嵌在该盒上的模块：**定长**，长度恒 == item_pool.socket_count，空位为空项
#

#     （**顶层 `src/pool/` 已不存在**）。这与 §2 的"数据归属 01 / 唯一写入权归 05"是同一件事的两面：
#     `Box.item_pool` 是**盒子的数据**，而"编辑这份数据"的规则是**盒子下的一个子模块**。
class_name ItemPool
extends Resource

@export var box_id: String = ""                  # 属于哪个盒子（`Uuid.v4()`；与 01 的 `Box.box_id` 同一个值）
@export var series_id: StringName = &""          # **基础池的来源**：引用 01 的 `SeriesDef`（基础池模板）
@export var regular_count: int = 8               # ★ 冻结元数据：该盒所属套系的常规物品数（`ban_limit` 由其派生，C6）
@export var socket_count: int = 3                # ★ 冻结元数据：该盒所属套系品质对应的位数，运行时不可变（C4）
@export var revision: int = 0                    # ★ 元数据：**每次由 05 写入时 +1**（`regular_count`/`socket_count` 是冻结副本，本项不是）
@export var base_items: Array[StringName] = []   # [补充] **内存中的解析结果**（载入时从 `series_id` → `SeriesDef` 解析；**不逐盒落盘**）
@export var base_weights: Dictionary = {}        # [补充] 同上：基础权重（**未编辑**；整数万分比）——**不逐盒落盘**
# ★ **落盘子集 = `box_id` / `series_id` / `regular_count` / `socket_count` / `revision`**（在 `SeriesDef` 之外推不出的部分）；
#   `base_items` / `base_weights` 是**套系模板（`SeriesDef`）的东西**，盒子只持**引用**（见下方裁决与代价）。
# ★ **本类型不含 `modules`、不含任何"编辑后的权重"**——那正是被否决的 `socketed` 形状（模块在池子里）。

# ── 类型二：Module —— 一个**已镶嵌模块的实例**（挂在 `Box.modules` 上）────────
# res://src/gacha/pool/defs/module.gd
# ★ `Module`（**实例**）与 `ModuleDef`（**定义**，见本文档 §4 前两段）**是两回事**：前者回答"这个盒子的第几位装了什么"，
#   后者是"这类模块怎么编辑池子"的静态蓝图；运行期只存实例，蓝图按 `module_id` 查表。
class_name Module
extends Resource

@export var module_id: StringName = &""   # 指向 `ModuleDef`（编辑规则蓝图）
@export var quality: int = 1              # 模块品质梯度（D13；制造时从 `ModuleDef` 复制，供展示与排序）
@export var socketed_at: int = 0          # [补充] 镶嵌时刻（tick），供 UI 排序与回放；**不参与求值**
# ★ **本类型不含 `slot`**：**槽位号 = 它在 `Box.modules` 里的下标**（`unsocket(box, slot)` 的 `slot` 就是该下标）——
#   只留**一个**事实来源（数组下标）；再留一个 `slot` 字段就是两份副本，可能静默不一致。
# ★ **本类型挂在 `Box.modules` 上、不在 `ItemPool` 里**。模块是**消耗品**（§5.6 裁决）：
#   拆卸 = **把该位置空**（定长数组不变；只返还 50% 材料）；兑现 = 随盒子一同消失；**不存在"模块库存"**。
# ★ **落盘 = 由下标生成的稀疏序列**（`{index, module_id, quality, socketed_at}`，归 10）；运行期恒为**定长** `Array[Module]`。

# ── 派生状态（**不是第三个数据**）：由上面两者求值出的"池子的当前状态" ────────
# `PoolState` = f(`ItemPool` 的基础数据, `Box.modules`)；**派生值、不入档**，载入时由 `PoolService` **逐盒重建**（与 `count_index` 同类）。
class PoolState:
    var box_id: String              # 本状态属于**哪一个盒子**
    var revision: int = 0           # **镜像** `ItemPool.revision`（07 的缓存键 = (box_id, revision)）
    var socket_count: int = 3       # 从该盒 `item_pool` 冻结（C4）
    var regular_count: int = 8      # 从该盒 `item_pool` 冻结（C6 的依据）
    var weights_bp: Dictionary = {} # item_id -> **当前**权重（**整数万分比，Σ == 10000**；**只有整数才能让 C1 的零和等式被精确断言**，浮点 `probs` 只在 07 归一化时出现一次）
    var void_mass_bp: int = 0       # 当前不可回收质量（**同单位同精度**；本文 §5 叙述中的 `void_mass` 即该量；每个池子各自累积）
    # ★ 字段集**仅此**：`weights_bp` / `void_mass_bp` / `revision`（+ `box_id` / 规模副本）；**不含 `socketed`**。
```

> `[补充]` **`base_items` / `base_weights` 的口径与取值一律以 01 的 `SeriesDef` 为准**——05 只规定"`item_pool` 是该盒的一份基础池副本"，**不定义基础池的内容**（README §2：基础池模板归 01）。`regular_count` 与派生的 `ban_limit` 则是 C6 的落地字段：落在 `item_pool`（并被派生状态冻结）可让 V5 校验与 §10.1 T4b 有唯一数据源，**避免各处硬编码 5/8**（品质 3/4 是 12 个物品）。
>
> **★ 裁决（v0.10）：`base_items` / `base_weights` 不逐盒落盘。** 基础池是**套系模板**（`SeriesDef`）的东西，盒子只持**引用**；逐盒落盘会把同一份模板**复制 N 份**，并与 `SeriesDef` 形成**第二份副本**（配置一变两处就不一致）。载入时**从 `series_id` 解析**（与"派生状态不入档、逐盒重建"同一条思路）。**代价（明确写出，不是免费的）**：内容配置调整基础权重时，**所有存量盒子的基础池会一起变**——这是同一笔交易的必然结果，**不是 bug**（断言见 §10.2 **T17**）。
>
> **★ 裁决（v0.10）：`Box.box_id` 加为正式字段（归 01）。** 字段集定稿：`box_id : String` / `series_id : StringName` / `item_pool : ItemPool` / `modules : Array[Module]`（`01-gacha.md` §11 **G11 ✅**）。**生成方式 = `Uuid.v4()`（返回 `String`，与 `ItemInstance.instance_id` 同一套工具、同一类型）**——两个身份字段同源就必须同类型，**不得存在任何 `StringName(...)` 转换点**（早先的 `StringName(Uuid.v4())` 写法**已作废**；否则"同一身份逐位相等"的断言会被隐式转换破坏）。它**关闭了"盒子稳定身份悬空"这条待定项**，并给各接口的 `box_id` 入参提供来源（`pool_changed` 同样带它，§8）；**本系统只消费它、不定义它**（身份、不是输入——不参与权重与抽样）。

## 5. 规则与公式

### 5.1 重建流程（与 07 的 `evaluate_pool()` 步骤严格对应）

```
_rebuild(state, box_id):        # v0.10：**逐盒**重建——只算这一个盒子的"当前状态"
  0. 取两个**并列**输入：该盒的 `Box.item_pool`（基础数据）+ 该盒的 `Box.modules`（**定长**模块数组，空位为空项）
  1. revision += 1
  2. 校验 `modules` 的非空项（已镶嵌模块）的合法性（§5.5）
  3. freed_mass = Σ 被排除物品的基础权重（取自 `base_weights`）
  4. void_mass_bp = freed_mass × (1 - recover_rate)      # 40%（整数万分比）
  5. 可回收部分按 redistribute_mode 分配：
       AUTO     → 按基础权重分配给其余未被排除的常规物品
       TARGETED → 全部分配给 redistribute_target
  6. 提升：w[target] *= magnitude
  7. 隐藏物品权重全程不动（C3）
  8. 断言（C4：**两件事都要断言到**——只断言"数组长度"等于没断言）：
       a. **定长长度**：`modules.size() == item_pool.socket_count == SeriesDef(series_id).socket_count`（该盒所属套系品质对应的位数）
       b. **已占用位数**（= `modules` 的**非空项数**）`<= modules.size()`——**这才是真正的守护**：
          `modules.size()` 恒等于 `socket_count`（定长），单独断言它**恒真、C4 的守护会形同虚设**
  9. 断言：可产出常规物品数 ≥ 3（C6）
 10. 产出**派生状态** `PoolState`（`weights_bp` Σ == 10000 + `void_mass_bp`）——**不落盘**
```

> `[补充]` 步骤顺序被固定，与 `07-economy-rho.md` §5.1 一致。顺序影响结果，固定顺序是求值可复现与归因可对账的前提。
>
> **v0.10**：`box_id`（**`String`**）必须是**入参**，**不得**由 `series_id` 推导——同一套系可以同时存在多个盒子，
> `series_id` 已经**无法定位唯一池子**。重建只作用在 `box_id` 这一个盒子上，**绝不影响同套系的其他盒子**；**逐盒重建、绝不共用缓存**。
>
> **v0.10 结构澄清**：本流程的输入是**两个并列数据**（`item_pool` + `modules`），输出是一份**派生状态**（`PoolState`）。
> 这也解释了为什么"拆卸"不会在池子里留下坑：**把一位置空之后，池子的状态就是"少了那一项"的函数值**——
> 全部位为空时它**必然**等于基础池（`void_mass_bp == 0`），**不需要任何"补回来"的动作**（§7.1）。

### 5.2 硬约束（C1 / C4 / C6）

| # | 约束 | 理由 |
|---|---|---|
| **C1** | **零和**：常规物品概率之和 ≤ 98%（差额为 `void_prob`） | 提升必须从别处抢，取舍才真实 |
| **C4** ★ | **镶嵌位数由该盒所属套系品质决定；在同一池（即同一盒子）内恒定、运行时不可变** | 功率门控（P7）：**同一个池子内没有任何扩容路径**；跨池复制只能靠**新模块的新成本**（核心 §7） |
| **C6** ★ | **排除物品数上限 = 常规物品数 − 3**（任何池子至少保留 3 个可产出物品） | **防收敛下限** |

常规物品概率质量总量恒定。**提升某个物品必须从其他常规物品按比例扣除**——不存在"凭空增加概率"的模块。

代价因此是真实的：**你给某个物品加的概率，是从所有别的物品身上按比例抠出来的**，包括你正需要的那几个物品。

**C4 管"位子有多少"，C6 管"能排除多少"**：位子再多（最高品质套系也只有 5 个），池子也必须留下至少 3 个可产出物品——因此**永远收敛不到单个物品**。

> **v0.10 只改 C4 的措辞，规则一字未动**：v0.6 说的"同一**套系**内恒定"在 v0.9 等价于"同一池内恒定"（那时每套系只有一个池子）；
> 池子发给每个盒子之后，**唯一还正确的说法是"同一池（盒）内恒定"**——位子数仍取该盒所属套系品质的 2/3/4/5（核心 §5.2 / §16.5）。

### 5.3 `void` 即自限机制（v0.6 升格）

```
freed_mass = Σ base_weight[banned]
void_mass  = freed_mass × 0.4
```

v0.5 靠"C4 固定常数"抑制 R2（池子编辑过强）。**v0.6 位子随套系品质变多，因此抑制改由 C2 的 40% 损耗承担**：

| 玩家若…… | 会发生什么 |
|---|---|
| 排除 1 个物品 | 该物品释放质量的 **40% 永久变成 `void`** |
| 排除到只剩 3 个物品 | `void_mass` 已累积到可观比例，**`m_bar` 显著塌陷**，ρ 下降 |
| 想把池子收敛到必出某个物品 | 做不到（C6 保证**至少保留 3 个可产出物品**），且代价是循环效率大幅下滑 |

**排除越多 → `void_mass` 累积越多 → `m_bar` 塌得越狠 → ρ 越低。过度排除是自我惩罚的。**

这条机制的三条关键性质：

- **自限，不是封顶**：`void` 不阻止玩家排除，只让"排得越狠、循环越差"成为机制事实；收官阶段的玩法因此是"权衡逼近到什么程度为止"（核心设计书 §5.5）。
- **随品质自动扩展**：高品质套系给更多位子，但每一次排除的代价同样真实——**位子多 ≠ 收敛容易**，不需要为每档品质另设上限。
- **不新增参数**：抑制 R2 靠的是 C2 这条既有机制，而不是一个需要单独调平的常数。

损耗的可见性（`void` 的基本定义见 §5.4，本条只升级其地位）：
- **可见**：直方图多一根 `void` 柱；
- **可计价**：`void` 的 `v = 0`，直接压低 `m_bar`（P2 可归因）；
- **不可被归一化抹掉**：归一化会让损耗完全失效，D6 这个主旋钮就白设了。

**v0.10：本机制是单池的，池子跟着盒子走之后照旧生效——规则不动。**

`void_mass` 是**每个池子各自累积**的：在盒子 A 里排除物品凿出的洞**不会**带到盒子 B，
**每个池子各自漏各自的**。因此 `void` **不构成跨池的约束**（跨池由 **D17 的模块物品成本**约束），
它约束的始终是"**这一个池子被排得有多狠**"——与 v0.9 相比，这条机制的含义与强度**完全没变**。

### 5.4 `void` 的实现方式 ⚠️

**核心设计书存在一处内部矛盾**（C1 说"Σp 恒为 98%"，C2 说"40% 蒸发"），本系统采用如下解法：

> **蒸发的概率不消失，而是落为一个显式的零价值结果 `void`。**

```
Σ probs(常规物品) + void_prob + 0.02(隐藏) == 1.0
```

| 好处 | 说明 |
|---|---|
| 损耗**可见** | 直方图上多出一根柱子，玩家亲眼看到"我把池子凿出了一个洞" |
| 损耗**可计价** | `void` 的 `v = 0`，直接压低 `m_bar`，符合 P2 可归因 |
| 不需要归一化抹掉损耗 | 归一化会让损耗**完全失效**，D6 这个主旋钮就白设了 |

**代价**：C1 措辞需从"恒为 98%"改为"**≤ 98%，差额为 `void_prob`**"。
✅ **已回改上游（v0.6）**：核心 §5.2 的 C1 已修订为"常规物品概率之和 + `void_prob` 恒为 98%"，并新增 **§5.6「空洞 void」**正式定义（本节的论证过程保留为历史记录）。

### 5.5 合法性与冲突规则

| # | 规则 | 违反时 |
|---|---|---|
| V1 | `targets` 不得包含隐藏物品 | 配置期报错，拒绝加载 |
| V2 | 同一物品不得同时被排除与提升 | 拒绝镶嵌，UI 明确提示冲突源 |
| V3 | **已占用位数（= `modules` 的非空项数）≤ `item_pool.socket_count`**（定长长度恒等于它，故**要守的是"已镶嵌数 ≤ 位子数"**）；`socket(box, module, slot)` 要求第 `slot` 位**为空项**，且**玩家可指定任意空位** | 拒绝：占用位需**显式替换**（先 `unsocket(box, slot)`），**不做隐式覆盖** |
| V4 | `boost` 倍数不得超过 `boost_cap`（×3） | 配置期钳制并警告 |
| V5 | 常规物品被排除总数 ≤ `ban_limit`（**派生自 C6**：`ban_limit = regular_count − 3`；品质2 即 8 − 3 = 5） | 拒绝，保证至少 3 个可产出物品 |
| V6 | 互斥标记（`exclusive_tags`）冲突的模块不得共存 | 拒绝镶嵌 |
| V7 | **数组形状**：`modules.size() == item_pool.socket_count`、空位为空项、**非空项良构**（是合法 `Module`，其 `module_id` 能在 `ModuleDef` 注册表查到）。**"同一盒内唯一"无需检查**——定长数组"一个下标一项"，唯一性**结构上自动成立** | 拒绝，保证"位子"与"定位"自洽 |

> **所有非法操作必须"响亮地拒绝"，不做静默钳制。** 静默处理会让玩家以为自己成功了，从而对所有数字失去信任（P1）。

### 5.6 替换：本作最锋利的一层决策

**在这一个盒子的池子里**，镶嵌位恒定、不可扩容，所以**不存在"再装一个模块"这个选项**。这一条 v0.9 → v0.10 **未变**——变的只是参照物：从"套系的施工台"变成**"这个盒子的池子"**。

玩家每一次镶嵌都在回答：**我要把这个盒子里的谁换下来？**

> **v0.10 结构澄清下，这句话的确切含义是：**"换掉一个模块" = **换掉该盒 `modules` 列表里的**一项编辑，
> 而**不是**"在池子里挖掉一块再补上"——`modules` 与 `item_pool` **并列**，池子的状态**始终是二者的函数**（§4 / §5.1）。
> 因此**拆卸不会在池子里留下任何痕迹**：移除一项编辑，状态就是"少了那一项"的函数值；**全部移除时必然等于基础池**（`void_mass == 0`）。

> **v0.10 新增的前置一层：在问"换下谁"之前，先要问"这个盒子值不值得配置？"**
> 因为**模块镶嵌即锁定进这个盒子**（进入该盒 `modules` 列表、施工台随之清空），而**拆卸只能从盒子上拆、且只返还 50%**：

| 玩家的判断 | 后果 |
|---|---|
| **这个盒子值得配置** | 花掉 N 个模块的**物品成本**，换**这个盒子**（且只是这个盒子）的高质量产出 |
| **不值得配置** | 让它以**基础池**被兑现即可——**没有任何配置被浪费** |
| **配置了却先去开别的盒子** | 模块**留在原盒**（已锁定），不会消失，但**也不会跟着别的盒子走**：那个盒子的池子**依然必须是它自己配置的** |

> 这三行是 §3.3 那层替换决策在**盒子尺度**上的延伸，也是"分批"的真正来源（核心 §4.1.2 / §16.5）：
> **配置好的盒子先开，没配置的盒子按基础池开。**
> 这层取舍的代价由 **D17（单个模块的物品成本）** 标定——**它是 P7 的实际执行者**（见 §11 M9）。

配套要求：
- 镶嵌界面**必须显示将被换下的模块**及其效果损失（核心文档 R10）；
- 镶嵌界面**必须显示"正在配置的是哪个盒子"**（v0.10）：模块不可复用，玩家必须能看出**配置下一个盒子需要新模块**；
- **拆卸只能从盒子上拆**（v0.10）：即**把该盒 `modules` 的第 `slot` 位置空**（**定长数组长度不变**；只返还 50% 材料）；**盒子未兑现时**才可拆；**兑现后盒子连同它的 `modules` 一同消耗**，**没有拆卸路径、也没有返还**（核心 §4.1.2）；
- 拆卸返还 50%，使"换错"有代价但可承受；**v0.9：返还落地为新建实例**（新 UUID、`source = { kind = &"refund" }`；**`serial = 0` 由 02 内部置位——`serial` 不是 `grant` 的参数**），**原实例在制造时已被销毁、UUID 不可恢复**——"可逆"说的是**池子状态与物品数量**，不是**实例身份**（见 §7.1）；
- **★ 裁决（v0.10）：模块是消耗品——不存在"模块库存"。** 制造消耗物品（`item_cost`）；**拆卸只返还 50% 材料，模块本体不回到库存、也不可能被搬到别的盒子**（本系统**不提供**任何"模块仓库 / 回收再用"的接口）。**为什么必须写死**：若本体可回收再用，同一个模块就能在多个盒子上**轮流使用**——**D17 会被直接归零**（"配置 N 个盒子需要 N × 位数个模块"不再成立），P7 唯一的跨池锚点随之消失。因此"**配置下一个盒子需要新的模块**"是**字面意义**：每次镶嵌都要**重新支付**一份模块成本——这正是上面那张"值不值得配置"表的代价来源；
- **制造与拆卸必须在同一事务内完成**：任一 `item_cost` **需求向量条目**实例不足即整体失败（原子，全有或全无）；**替换 = 一次 `ItemService.transact()` 调用**（02 提供的单次事务原语），**不是多次调用拼起来**——一次替换叠加**多次实例销毁与创建**，失败面比计数模型更大，故任一失败必须**物品侧事务整体回滚**（含撤销本次已 `grant` 的返还新实例）；**不承诺跨系统原子性**（裁决 13）：`transact()` **只覆盖物品侧**，模块 / 镶嵌位等 05 侧状态不在其中，其后失败由 05 侧自行回退或自愈，不得要求物品侧回滚；
- **⚠️ 拆卸返还装不下 → 拒绝整个拆卸**（裁决 17）：`Σ(返还实例的 ItemDef.size) > 仓库剩余空间` ⇒ `unsocket` **返回失败**并给出可读错误（缺多少空间），**`PoolState` 与实例列表逐项不变**（该盒 `modules` 仍含那一项、原实例不销毁、不创建返还实例）。**空间预检必须在事务之前**（先查再动），**禁止**"先拆卸 / 先 `grant`，发现装不下再用回滚补救"。**制造侧不做空间预检**——它只消耗不产出，不因仓库满而失败；
- **可消耗的只有仓库内实例**：制造只挑 `location == warehouse` 的实例，**邮件实例不可用于镶嵌**（核心 §4.7 边界 1 / §14.2 铁律 9）；`count()` 只统计仓库实例，05 **不自行读 `location`、不自行统计**（否则会造出第二个事实来源）。**守恒口径以全部实例（含邮件）为准**（裁决 12）——`count()` 只是**带 `location` 过滤的查询**，**不得**写进任何守恒等式；
- **禁止提供任何增加镶嵌位的接口**，也**禁止任何"把已镶嵌模块移到别的盒子 / 复制到别的盒子"的接口**（P7 的代码层体现；v0.10：这是 P7 被改写后仅存的否决项，见 §10.1 T4 / §10.2 T13）。

### 7.1 状态机（**一个盒子**的池子生命周期，v0.10）

```
[盒子创建：item_pool = 基础池副本, modules = [null × socket_count]（定长全空位）]
        │
        ├──镶嵌（写进第 slot 位）──▶ [已配置：modules 有非空项] ──继续镶嵌──▶ [已配置]
        │                        │
        │                        └───拆卸（把第 slot 位置空）───┐
        │                                                        ▼
        └────────────────────────▶ [未配置：所有位皆空（已占用位数 = 0）]
                                    状态 = 基础池（void_mass_bp = 0）

[已配置] ──兑现──▶ [盒子连同它的 item_pool 与 modules 一同消耗]（终态：池子随盒消失，无返还）
```

**状态不是"存在池子里的东西"，而是 `item_pool` + `modules` 的函数**：全部拆卸后 `modules` **所有位皆空（已占用位数 = 0）**，状态**必然**回到基础池（`void_mass_bp = 0`）——
**注意：定长数组的"空"不是 `[]`**（长度永远 == `socket_count`，"空"= **每个下标都是空项**）；因此不需要任何"补回来"的动作，也不会出现"不可逆的污染"（§5.6 的可逆承诺是**结构性**的，不是靠约定）。
**v0.10：这个状态机是"每个盒子一份"的**——状态迁移只发生在**一个盒子内部**，不跨盒、不共享。

> **⚠️ v0.8 澄清（否则 T6 的措辞会与新模型矛盾）：** 这里的"**可逆**"指的是两件事——
> ① **派生状态回到基础态**（`void_mass_bp == 0`、该盒 `modules` **所有位皆空（已占用位数 = 0）**、`revision` 继续单调递增）；
> ② **物品实例数量回到拆卸前**（返还量仍按逐条 `floor(cost × 0.5)`，**数量规则不变**）。
> **它不指实例身份可逆**：原实例在制造时已被销毁，返还的是**新实例**，`instance_id` 是**新的 UUID**，`serial == 0`。
> **"完全可逆"是状态级与数量级的可逆，不是 UUID 级的可逆**——任何"拆卸后 UUID 集合与拆卸前完全相同"的断言都是错误断言（见 §10.1 T6）。

> **v0.10：位子数是该盒所属套系的属性，但池子不是。** `item_pool.socket_count` / `regular_count` 按**该盒所属套系品质**取值，`modules` 的**定长就是它**（C4）；**两个同套系的盒子位子数相同，池子内容却可以完全不同**——这正是"分批"的来源（核心 §4.1.2）。换到另一个盒子只是换了个池子，**已配置的那个盒子不会跟过来**；替换路径本身不变——位子满了仍然只能先换下谁。

### 8.1 依赖方向铁律

```
05 (写) ──▶ 07 (算) ──▶ 01 (抽) / 08 (显)
```

**任何反向依赖都是缺陷。**
特别地：`01` 虽然在 v0.10 起**持有** `Box.item_pool` 与 `Box.modules`（数据归属，见 §2），但**不得自行解读它们、更不得自行计算权重**——
**求值一律经 07**，01 只把该盒的池子**原样**交给求值路径。

**v0.10 裁决（写入方与求值方分离，二者不得混写）：**
- **`PoolService`（05）= 唯一写入方**：由该盒 `item_pool` + `modules` **推导**出池子的当前权重（`PoolState`）；
- **`EvalService`（07）= 唯一求值方**：把权重求值成概率 / EV / ρ / `headline`；
- **`get_pool_state()` 只交出状态、不做任何算术**（§4.1）；01 / 04 / 08 / 09 / 10 一律不得自行算概率。

### 10.3 切片验收信号

- ✅ 测试者主动讨论"这个要不要留"
- ✅ 测试者在被排除物品与缺口物品之间做出**有意识的取舍**
- ✅ 测试者表现出**"给哪些盒子配置好了，就先开哪些"**的分批行为（v0.10 的兑现时机口径：**决策从"何时开"变成"给哪些盒子配置"**，核心 §4.1.2 / §16.5）——**而不是**旧口径的"等我把池子编好再开这批盒子"
- ❌ **测试者在 10 分钟内就把池子编到接近必出** → C4 / C6 / C2 未生效，检查代码而非调参
- ❌ **测试者抱怨"想再装一个但位子不够"** → ⚠️ **这是设计意图，不是 bug**。但若玩家感到的是**挫败**而非**取舍**，应调低拆卸成本（50% → 更高返还），**而不是增加镶嵌位**
- ❌ **测试者完全忽略池子面板** → R3 成立，"燃料/引擎"被淹没，需要简化而非放弃本系统
- ❌ **测试者不理解 `void`** → §5.4 的可视化失败，直方图必须重做
- ❌ **测试者抱怨"高品质盒子位子多了但没什么用"** → **位子/池子比例失衡**（位子涨得比池子快），核对核心设计书 §4.1.1 的 25%–40% 区间，修正比例而**不是**加排除强度
