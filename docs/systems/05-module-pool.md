# 05 · 模块与池子编辑系统 ★

- 上游：`../core-design.md` **v0.9** ／ `README.md`
- 依赖系统：`02-item.md`（模块素材）、`07-economy-rho.md`（求值路径）
- 被依赖：`01-gacha.md`（抽取消费池子状态）、`08-ui-panels.md`（池子面板）、`09-presentation.md`（演出过滤）

> **本系统是全作风险最高的系统。**
> 它同时承担三件事：玩家能动性的主载体、"盲盒期望可被施工"的实现、以及最大的平衡风险（R2）与最大的技术风险（R4）。
> 改动本系统前请通读 §5 与 §10.1。

---

## 1. 这个系统负责什么

1. **`PoolState` 的唯一写入方**——池子状态的任何变更都只能经由 `PoolService`
2. **排除（`ban`）**：令指定物品概率归零，不再产出
3. **提升（`boost`）**：提高指定物品概率，增量从其他常规物品按比例扣除
4. **损耗（`loss`）**：排除释放的概率中 40% 不可回收，落为 `void`（详见 §5.4）
5. **隐藏物品免疫的执行**：保证隐藏物品概率恒为 2%（规则由 `01-gacha.md` 声明，执行在此）
6. **镶嵌位管理**：数量由**套系品质**决定（品质1–4 → 2/3/4/5），**同一套系内恒定、运行时不可变**（C4 / P7）
7. **模块的装配、替换与拆卸**（拆卸返还 50%）——v0.9 起：制造消耗**销毁物品实例**（原子），拆卸返还**创建新实例**（新 UUID、`source = { kind = &"refund" }`；`serial = 0` 由 02 内部置位，**不是 `grant` 的参数**；见 §5.6 / §7.1）；替换是**一次 `transact()`**；**拆卸返还装不下则拒绝整个拆卸**（裁决 17：被动产出（开盒）才进邮件，主动操作不反噬）
8. **回收（`recover`）**：挽回部分 `void` 质量——**第二切片，本版仅定义接口**
9. **排除物品数上限（C6）**：排除物品数 ≤ 常规物品数 − 3，**任何池子至少保留 3 个可产出物品**

## 3. 核心概念与术语

| 术语 | 代码名 | 说明 |
|---|---|---|
| 池子状态 | `PoolState` | 基础权重 + 全部编辑结果的**唯一权威表示** |
| 修订号 | `revision` | 每次写入 +1；缓存与失效的唯一依据 |
| 模块 | `Module` | 一条作用在开盒端的编辑规则 |
| 镶嵌 | `socket` | 把模块放入镶嵌位 |
| 镶嵌位 | `socket_slot` | **数量由套系品质决定**（品质1–4 → 2/3/4/5）；**同一套系内恒定、运行时不可变**（C4） |
| 排除 | `ban` | 某个物品概率归零 |
| 提升 | `boost` | 某个物品概率 ×N |
| 释放质量 | `freed_mass` | 排除某个物品后从其基础权重中释放出的质量 |
| 回收率 | `recover_rate` | 释放质量中可重新分配的比例，**0.60** |
| 空洞 | `void` | 不可回收的那 40%，落为零价值结果（§5.4） |
| 重分配模式 | `redistribute_mode` | `AUTO`（按基础权重）／ `TARGETED`（指定目标物品） |
| 替换 | `replace` | 镶嵌位满时的唯一操作——**没有"再装一个"** |
| 物品实例 | `ItemInstance` | 模块制造时被**销毁**的那个物品个体；拆卸返还时**新建**（见 §5.6） |
| 实例 id | `instance_id` | **UUIDv4**；制造消耗按它指定，**返还实例的 UUID 全新**（原实例已销毁） |
| 收藏编号 | `serial` | **返还实例一律 `serial = 0`**——只有开盒产出才分配收藏编号；它是**实例字段**，**不是 `grant` 的参数**（第三位是幂等键 `instance_id`），由 02 内部置位 |
| 物品品质 | `quality` | 1–5 序数，物品的等级维度（见 `02-item.md`） |
| 套系品质 | `series_quality` | 该套系的规模等级（1–4），决定其**常规物品数与镶嵌位数**（核心设计书 §4.1.1） |

> **术语纪律（v0.6 新增）**：本作的"品质"有**两个**含义——**物品品质 `quality`**（1–5，见 `02-item.md`）与**套系品质 `series_quality`**（核心设计书 §4.1.1）。
> 凡文中出现"品质"二字**必须可分辨是哪一个**：谈镶嵌位与物品数时指**套系品质**，谈物品价值与任务需求时指**物品品质**。
> （`ModuleDef.quality` 是**模块品质梯度**，属第三条独立轴，见 D13，不得与前两者混用。）

## 4. 数据结构

```gdscript
# res://src/pool/defs/module_cost.gd（v0.9 新增）
class_name ModuleCost
extends Resource

## 制造消耗条目 = **需求向量**（裁决 5）：与 04 的 `DeviceCost` **同一结构**，两文档消耗维度已统一。
##   制造 → 交 02 按 (category, quality) 挑选 amount 个实例并**销毁**（原子，全有或全无）；
##   拆卸 → 按本条目逐条 floor(amount × 0.5) **新建**实例（新 UUID；serial = 0 由 02 内部置位）。
##   [补充] 字段形状照 04 的 DeviceCost 落地（核心 §14.3 只列出 ModuleDef 含"成本"，未给形状）。
@export var category: StringName = &""
@export var quality: int = 1
@export_range(1, 99, 1) var amount: int = 1
```

```gdscript
# res://src/pool/defs/module_def.gd
class_name ModuleDef
extends Resource

enum OpType { BAN, BOOST, RECOVER }

@export var id: StringName
@export var display_name: String
@export var quality: int                       # 模块品质梯度（核心文档 D13）
@export var op_type: OpType
@export var targets: Array[StringName]         # 多目标；隐藏物品出现在此处即为非法配置
@export var magnitude: float = 1.0             # BOOST 的倍数；BAN/RECOVER 忽略
@export var redistribute_mode: int = 0         # 0 = AUTO, 1 = TARGETED
@export var redistribute_target: StringName    # TARGETED 时的目标物品
@export var item_cost: Array[ModuleCost] = []  # 制造消耗：**需求向量** `(category, quality, amount)`（v0.9 与 04 的 DeviceCost 统一，裁决 5）
@export var exclusive_tags: Array[StringName]  # 互斥标记
```

> `[补充]` **制造消耗的实例语义（v0.9：与 04 统一为需求向量）**：`item_cost` 是 `(category, quality, amount)` 的**需求向量数组**，与 04 的 `DeviceCost` **同一结构**（裁决 5）——v0.8 那句"两文档消耗维度**不对称**"**已删除**（不对称已由裁决消除，见 §11 / M8）。理由：盲盒产出随机，`item_id` 级要求会让玩家卡在"我需要星尘但只开出晶核"。
> - **制造（消耗）侧不需要反查**：需求是**向量级**，交 02 按 `(category, quality)` 挑选实例并原子销毁即可（`consume_by_filter` / `consume`）；
> - **拆卸（返还）侧需要反查**：返还必须落到具体 `item_id`，一律调 **`ItemService.resolve_item_id(category, quality)`**（裁决 9），05 **不得**自己构造 id 字符串；该映射的"唯一"由**配置校验器强制**（配置期即报错），不是"切片下碰巧唯一"的兜底；
> - **溢出处理按操作性质分叉（裁决 17）**：**被动产出（开盒）**放不下 → 进邮件（归 01 / 02）；**主动操作（转化 / 拆卸返还）**放不下 → **拒绝整个操作**。理由：主动操作会销毁源实例腾出空间，产出的新实例却进邮件，就是**净损失可用持有**，与"转化是燃料路径的预处理"直接冲突。**因此 05 对拆卸返还必须做空间预检**（见 §5.6）——这条不是"05 不判定"，而是"05 先查再动"。

```gdscript
# res://src/pool/pool_service.gd
class_name PoolService

class PoolState:
    var series_id: StringName
    var revision: int = 0
    var socketed: Array[StringName] = []       # 长度恒 == socket_count（C4）
    var socket_count: int = 3                  # ★ 该套系的常量，从 SeriesDef.socket_count 拷贝，运行时永不改变
    var regular_count: int = 8                 # ★ 该套系的常规物品数，从 SeriesDef 拷贝；ban_limit 由其派生（C6）
    var void_mass: float = 0.0                 # 当前不可回收质量
```

> `[补充]` `regular_count` 与由它派生的 `ban_limit` 是 C6 的落地字段：核心设计书只规定"至少保留 3 个可产出物品"，
> 把上限落成 `PoolState` 字段可让 V5 校验与 §10.1 T4b 断言有唯一数据源，**避免各处按 8 个物品硬编码 5/8**（品质 3/4 的池子是 12 个物品）。

### 4.1 唯一写入接口

```gdscript
## 镶嵌。槽位满时返回错误——不做隐式替换，强制玩家显式选择换下谁。
## v0.8：制造消耗 = ItemService.consume(instance_ids)，**销毁实例**，且**原子**（全有或全无）。
static func socket(state: GameState, module_id: StringName, slot: int) -> Result

## 拆卸。返还 50% 素材。
## v0.9：**返还的是新建实例**——ItemService.grant(item_id, { kind = &"refund" })，
## **新 UUID，不是把原实例改回来**（原实例在制造时已销毁）；数量规则仍是逐条 floor(cost × 0.5)，不变。
## ★ serial 不是 grant 的参数：grant(item_id, source, instance_id) 的第三位是**幂等键**；
##   返还实例的 serial = 0 由 02 内部按"非开盒来源"置位（02 §5.6）。把 serial 写进第三个位置参数
##   会让所有返还**共享同一个幂等键 0**——第二次返还起被幂等吞掉，直接吃掉玩家资产。
static func unsocket(state: GameState, slot: int) -> Result

## 试算通道：算出"若这样镶嵌"的候选 PoolState，但**不写入任何状态**、不推进 revision。
## 供 08 的实时预览与沙盒使用（P6）。返回的是副本，调用方不得回写。
static func preview_socket(state: GameState, slot: int, module_id: StringName) -> PoolState

## 内部：重建 PoolState（不对外暴露）
static func _rebuild(state: GameState) -> void
```

> **`preview_socket()` 是只读的**：它走与 `_rebuild()` 完全相同的计算路径（避免两套实现），但结果不落盘、不推进 `revision`、不触发缓存失效。09 的演出层不得调用它。
> **⚠️ v0.8 复核：实例化不触及本条。** `preview_socket()` 完全不读物品实例（它只读 `PoolState` 与 `ModuleDef.item_cost`），因此 **① 只读通道、② `PoolService` 对 `PoolState` 的单写入方地位、③ `revision` 单调**这三条**均不受影响**。实例列表的单写入方是 02 的 `ItemService`——两份状态各有唯一写入方，互不越界（README §2.1 / §3.2）。

> **`PoolState` 没有任何公开的 setter。** 所有字段只能由 `PoolService._rebuild()` 写入。
> 这是本作头号 bug 源（R4）的唯一防线。

## 5. 规则与公式

### 5.1 重建流程（与 07 的 `evaluate_pool()` 步骤严格对应）

```
_rebuild(state):
  1. revision += 1
  2. 校验全部已镶嵌模块的合法性（§5.5）
  3. freed_mass = Σ 被排除物品的基础权重
  4. void_mass   = freed_mass × (1 - recover_rate)      # 40%
  5. 可回收部分按 redistribute_mode 分配：
       AUTO     → 按基础权重分配给其余未被排除的常规物品
       TARGETED → 全部分配给 redistribute_target
  6. 提升：w[target] *= magnitude
  7. 隐藏物品权重全程不动（C3）
  8. 断言：socketed.size() == socket_count（C4）
  9. 断言：可产出常规物品数 ≥ 3（C6）
```

> `[补充]` 步骤顺序被固定，与 `07-economy-rho.md` §5.1 一致。顺序影响结果，固定顺序是求值可复现与归因可对账的前提。

### 5.2 硬约束（C1 / C4 / C6）

| # | 约束 | 理由 |
|---|---|---|
| **C1** | **零和**：常规物品概率之和 ≤ 98%（差额为 `void_prob`） | 提升必须从别处抢，取舍才真实 |
| **C4** ★ | **镶嵌位数由套系品质决定；在同一套系内恒定、运行时不可变** | 功率门控（P7）：**同一套系内没有任何扩容路径** |
| **C6** ★ | **排除物品数上限 = 常规物品数 − 3**（任何池子至少保留 3 个可产出物品） | **防收敛下限** |

常规物品概率质量总量恒定。**提升某个物品必须从其他常规物品按比例扣除**——不存在"凭空增加概率"的模块。

代价因此是真实的：**你给某个物品加的概率，是从所有别的物品身上按比例抠出来的**，包括你正需要的那几个物品。

**C4 管"位子有多少"，C6 管"能排除多少"**：位子再多（最高品质套系也只有 5 个），池子也必须留下至少 3 个可产出物品——因此**永远收敛不到单个物品**。

### 5.3 `void` 即自限机制（v0.6 升格）

```
freed_mass = Σ base_weight[banned]
void_mass  = freed_mass × 0.4
```

v0.5 靠"C4 固定常数"抑制 R2（池子编辑过强）。**v0.6 位子随套系品质变多，因此抑制改由 C2 的 40% 损耗承担**：

| 玩家若…… | 会发生什么 |
|---|---|
| 排除 1 个物品 | 该物品释放质量的 **40% 永久变成 `void`** |
| 排除到只剩 3 个物品 | `void_mass` 已累积到可观比例，**`m_bar` 显著塌陷**，ρ 下降 |
| 想把池子收敛到必出某个物品 | 做不到（C6 保底 3 个物品），且代价是循环效率大幅下滑 |

**排除越多 → `void_mass` 累积越多 → `m_bar` 塌得越狠 → ρ 越低。过度排除是自我惩罚的。**

这条机制的三条关键性质：

- **自限，不是封顶**：`void` 不阻止玩家排除，只让"排得越狠、循环越差"成为机制事实；收官阶段的玩法因此是"权衡逼近到什么程度为止"（核心设计书 §5.5）。
- **随品质自动扩展**：高品质套系给更多位子，但每一次排除的代价同样真实——**位子多 ≠ 收敛容易**，不需要为每档品质另设上限。
- **不新增参数**：抑制 R2 靠的是 C2 这条既有机制，而不是一个需要单独调平的常数。

损耗的可见性（`void` 的基本定义见 §5.4，本条只升级其地位）：
- **可见**：直方图多一根 `void` 柱；
- **可计价**：`void` 的 `v = 0`，直接压低 `m_bar`（P2 可归因）；
- **不可被归一化抹掉**：归一化会让损耗完全失效，D6 这个主旋钮就白设了。

### 5.4 `void` 的实现方式 ⚠️

**核心设计书存在一处内部矛盾**（C1 说"Σp 恒为 98%"，C2 说"40% 蒸发"），本系统采用如下解法：

> **蒸发的概率不消失，而是落为一个显式的零价值结果 `void`。**

```
Σ probs(常规物品) + void_prob + 0.02(隐藏) == 1.0
```

| 好处 | 说明 |
|---|---|
| 损耗**可见** | 直方图上多出一根柱子，玩家亲眼看到"我把池子凿出了一个洞" |
| 损耗**可计价** | `void` 的 `v = 0`，直接压低 `m_bar`，符合 P2 可归因 |
| 不需要归一化抹掉损耗 | 归一化会让损耗**完全失效**，D6 这个主旋钮就白设了 |

**代价**：C1 措辞需从"恒为 98%"改为"**≤ 98%，差额为 `void_prob`**"。
⚠️ **已同步记入 `07-economy-rho.md` §11 与 `README.md` 待定项汇总，需回改核心设计书。**

### 5.5 合法性与冲突规则

| # | 规则 | 违反时 |
|---|---|---|
| V1 | `targets` 不得包含隐藏物品 | 配置期报错，拒绝加载 |
| V2 | 同一物品不得同时被排除与提升 | 拒绝镶嵌，UI 明确提示冲突源 |
| V3 | `socketed.size() <= socket_count` | 拒绝，要求先拆卸 |
| V4 | `boost` 倍数不得超过 `boost_cap`（×3） | 配置期钳制并警告 |
| V5 | 常规物品被排除总数 ≤ `ban_limit`（**派生自 C6**：`ban_limit = regular_count − 3`；品质2 即 8 − 3 = 5） | 拒绝，保证至少 3 个可产出物品 |
| V6 | 互斥标记（`exclusive_tags`）冲突的模块不得共存 | 拒绝镶嵌 |

> **所有非法操作必须"响亮地拒绝"，不做静默钳制。** 静默处理会让玩家以为自己成功了，从而对所有数字失去信任（P1）。

### 5.6 替换：本作最锋利的一层决策

镶嵌位在**同一套系内恒定、不可扩容**，所以**不存在"再装一个模块"这个选项**——想要更多位子，只能去**更高品质的套系**（那是内容，不是扩容）。

玩家每一次镶嵌都在回答：**我要把谁换下来？**

配套要求：
- 镶嵌界面**必须显示将被换下的模块**及其效果损失（核心文档 R10）；
- 拆卸返还 50%，使"换错"有代价但可承受；**v0.9：返还落地为新建实例**（新 UUID、`source = { kind = &"refund" }`；**`serial = 0` 由 02 内部置位——`serial` 不是 `grant` 的参数**），**原实例在制造时已被销毁、UUID 不可恢复**——"可逆"说的是**池子状态与物品数量**，不是**实例身份**（见 §7.1）；
- **制造与拆卸必须在同一事务内完成**：任一 `item_cost` **需求向量条目**实例不足即整体失败（原子，全有或全无）；**替换 = 一次 `ItemService.transact()` 调用**（02 提供的单次事务原语），**不是多次调用拼起来**——一次替换叠加**多次实例销毁与创建**，失败面比计数模型更大，故任一失败必须**物品侧事务整体回滚**（含撤销本次已 `grant` 的返还新实例）；**不承诺跨系统原子性**（裁决 13）：`transact()` **只覆盖物品侧**，模块 / 镶嵌位等 05 侧状态不在其中，其后失败由 05 侧自行回退或自愈，不得要求物品侧回滚；
- **⚠️ 拆卸返还装不下 → 拒绝整个拆卸**（裁决 17）：`Σ(返还实例的 ItemDef.size) > 仓库剩余空间` ⇒ `unsocket` **返回失败**并给出可读错误（缺多少空间），**`PoolState` 与实例列表逐项不变**（槽位仍为已镶嵌、原实例不销毁、不创建返还实例）。**空间预检必须在事务之前**（先查再动），**禁止**"先拆卸 / 先 `grant`，发现装不下再用回滚补救"。**制造侧不做空间预检**——它只消耗不产出，不因仓库满而失败；
- **可消耗的只有仓库内实例**：制造只挑 `location == warehouse` 的实例，**邮件实例不可用于镶嵌**（核心 §4.7 边界 1 / §14.2 铁律 9）；`count()` 只统计仓库实例，05 **不自行读 `location`、不自行统计**（否则会造出第二个事实来源）。**守恒口径以全部实例（含邮件）为准**（裁决 12）——`count()` 只是**带 `location` 过滤的查询**，**不得**写进任何守恒等式；
- **禁止提供任何增加镶嵌位的接口**（P7 的代码层体现，见 §10.1 T4）。

                                ▼

### 7.1 状态机（池子生命周期）

```
[基础池] ──首次镶嵌──▶ [已编辑池] ──继续镶嵌──▶ [已编辑池]
                            │                        │
                            └────全部拆卸────────────┘
                                     ▼
                              [基础池]（void_mass 归零）
```

**拆卸必须完全恢复到基础池**（`void_mass = 0`），否则池子会被不可逆地污染，违背 §5.6 的可逆承诺。

> **⚠️ v0.8 澄清（否则 T6 的措辞会与新模型矛盾）：** 这里的"**可逆**"指的是两件事——
> ① **`PoolState` 回到基础态**（`void_mass == 0`、无已镶嵌模块、`revision` 继续单调递增）；
> ② **物品实例数量回到拆卸前**（返还量仍按逐条 `floor(cost × 0.5)`，**数量规则不变**）。
> **它不指实例身份可逆**：原实例在制造时已被销毁，返还的是**新实例**，`instance_id` 是**新的 UUID**，`serial == 0`。
> **"完全可逆"是状态级与数量级的可逆，不是 UUID 级的可逆**——任何"拆卸后 UUID 集合与拆卸前完全相同"的断言都是错误断言（见 §10.1 T6）。

> **位子数是该套系的属性**：`socket_count` 与 `regular_count` 随套系走，**切换套系会改变位子数与池子规模**；在同一套系内始终不变（C4）。替换路径本身不变——满位时仍然只能换下谁。

## 9. UI 需求

本系统**提供数据与操作，不实现面板**（面板归 `08-ui-panels.md`），但下列为硬要求：

| 要求 | 理由 |

| **`void` 必须有独立可视元素**（一根柱子） | §5.4：损耗必须可见，否则玩家不理解 40% 意味着什么 |

| **替换时必须显示被换下的模块及其损失** | R10：否则玩家会因害怕误操作而不敢决策 |
| **★ 拆卸空间不足必须前置提示**：`Σ(返还实例 size) > 仓库剩余空间` 时拆卸按钮置灰 / 前置拦截，并显示**还缺多少空间**（"需要腾出 N 单位"） | 裁决 17：**主动操作装不下就拒绝**，不能让玩家"先拆了才发现返还进邮件 / 失败"。界面必须与 §5.6 的空间预检同源，**不得**先执行再报错 |
| **非法操作必须指出冲突源**（"与槽位 2 的模块冲突"） | P1：静默拒绝等于欺骗 |
