# 08 · 界面与信息呈现系统

- 上游：`../core-design.md` **v0.14（盲盒添加使用次数）**；历史变更见核心 §16 ／ `README.md`（系统索引、所有权边界、术语表）
- 依赖系统：**07 数值与期望（`EvalService`）**、05 模块与池子（`PoolService`）、01 盲盒与概率、02 物品（**含仓库占用与邮件**）、03 任务、09 演出（入口）、10 收集与进度（入口）
- 被依赖：无。本系统是**叶子**：只消费 `EvalService` 的结果并渲染，不产出任何被计算的数值

> **单一数据源声明（本系统第一条铁律）**
> **盲盒默认层 / 循环面板 / 池子面板 / 归因面板 / 架上面板 / 任务面板，加上试算（沙盒）与兑现对照，全部从 `EvalService` 单一数据源取数。**
> 任何面板自行计算、各自缓存概率副本、或自带一套数字口径，一律视为缺陷（核心文档 §9 铁律 3/4；README §3.3）。
> **本系统不拥有任何数值公式。** 它只决定"哪些数字、在哪里、以什么格式、在什么时机出现"。
> **v0.9 追加同一条**：**仓库占用与邮件列表一律从 02 取数**（`warehouse_usage()` / 邮件清单），08 **不得**自己累加 `size`、不得自己判定溢出或可否领取。

> **v0.14 同步（盲盒的寿命预算：装模块与开盒共用同一份次数）——呈现侧只新增一条读数。**
> ①**`Box.uses_remaining: int` = 盒子的"总寿命预算"**（**每盒可变**，不是套系常量；**v0.10 的"两个并列字段"照旧，本版在其上再加第三个**）：**发放时按该盒所属套系品质初始化**——**品质 1→10、2→15、3→20、4→25**（存活范围 **10–25**）；**`0` = 归零 ⇒ 盒子立即被摧毁**。★ **别与位数混**：**镶嵌位数仍是 2/3/4/5**——**预算远大于位数**（用户口径："盲盒的使用次数**远远超过**镶嵌的次数"）⇒ **装满镶嵌位烧不光预算**。②**两个消耗点，共用同一计数器，各 −1**：**①镶嵌一个模块 ②兑现一次**——**没有第三个消耗点**（核心 v0.14 说明 2）。因此**兑现一次后条目仍在清单里**（**除非恰好归零**），玩家看到的是"寿命 −1"，**不是条目消失**。
> ③**归零 = 立即摧毁**：盒子连同它的 `item_pool` 与 `modules` **立即消失**——**不存在"用尽才消耗"这种缓冲语义**（核心 v0.14 说明 3）；**模块在该盒被摧毁前一直挂在它上面**（可编辑、可拆卸），v0.13 及以前的"**兑现后随盒子一同消耗**"**不再成立**，本文所有"淘汰 / 从清单消失"的口径一律改述为"**归零即被摧毁**"。④**"次数归零 ⇒ 摧毁"这条规则本身仍然成立，哪怕这个盒子从未兑现过**：归零**只能由"镶嵌（**含替换**）+ 兑现累计到 0"触发**——**不是**靠"装满位子"（预算 10–25 **远大于**位数 2/3/4/5，**装满镶嵌位烧不光预算**）。因此仍是**真实的决策风险**（玩家必须自己数着剩余次数；★ **替换使 `m` 不再受位数封顶**——**每替换一个位子额外 −1**、拆卸不退还，核心 §15 D20②），但**08 不得发明任何拦截规则**，也**不得把"装模块"呈现成毁盒风险**（预警形态见 §11 **U20**）。**两次使用之间可以继续编辑池子** ⇒ "**根据上一次的结果决定下一次怎么调**"成为新决策：界面必须让玩家看得出"**这个盒子还剩几次寿命、上次开了什么**"（R-30 / T23）。⑤**`pool_snapshot` 每次抽取各一份**（两次之间池子可能被改过）；**`draw_index` 每次抽取 +1**（全局兑现计数器，跨批次 / 跨套系 / 不重置）。⑥**批量口径的 `k` 改为"本次结算的使用次数"**（**不再等于盒子数**；核心 v0.14 说明 7；`01-gacha.md` §5.7 的「本次将结算 k 次使用」是**已知量、不是估计**）——**兑现入口显示的 `k` 与 R-20 的 `N` 都按此口径，且 `k` 必须在按下之前可见**（R-30）。★ **它是与"每盒初始寿命 `k`（10–25）"不同的量，两者不得混用**（`07-economy-rho.md` §5.6 / §11 E10 同一提醒）。**架上每个盒子条目除 R-27 的「已配置 x / N」外必须再显示剩余寿命**（R-30，建议形如「◆ 剩余 12 次（装模块 / 开盒共用）」）。**经济连带（仅登记一句，本文不展开）**：`N̄(box) = M̄(box) − C(box)/d`，其中 **`d = k − m`**、**定义式 `m + d == k`**（`k` = 该盒**初始寿命** 10–25；`m` = **花在"镶嵌模块"上的次数**（**受位数封顶 `≤ 2/3/4/5`**）；`d` = **实际开出的次数**，⇒ **摊薄倍数 `d = k − m` = 8–20**）——**`m = 0 ⇒ d = k`**（未配置的盒子能被开 `k` 次），一句话：**"每装一个模块，就少开一次盒"**；**`C/k` 只在 `m = 0` 时成立、是错的口径** ⇒ **D17 必须重新标定**（"一个配置好的盒子确实能开出多次"这条结论不变且更硬）、**P7 唯一的跨池锚点实质归零**（`C/d` 相比"预算 = 位数"的旧基线又降了约 5 倍）、**R2 / R15 被缓冲**（核心 v0.14 说明 8 / 说明 9；`07-economy-rho.md` §5.6 的 `N̄` 登记同此口径）。**不变**：单一数据源铁律、`void` 柱与柱数公式、默认层"两个数字"契约（R-1）、池子逐盒一份、`weights_bp` 整数口径、六面板契约。

> **v0.13 去除隐藏款（本文已同步）——呈现侧只有四类改动，全部是"删掉一个不存在的对象"。**
> 上游删除了"每个套系 1 个隐藏物品"的设定（核心 §5.4 / §16.8）：**池中全部物品都是常规物品，全部物品共分 100%**（`p_i = rarity_i / Σ rarity`）。因此：①**红线 C3（隐藏物品恒 2%、免疫一切池子编辑）作废**——本文**删除它的呈现项、保留编号**（R-8 标【v0.13 作废】、§2 删掉"隐藏物品免疫的执行"、§10 T8 注明 C3 已作废）；②**R-2 的 N 不再 +1**：`N = regular_count`（品质 1/2 = 8，品质 3/4 = 12），**全部物品都是常规物品**；③**柱数公式由 `regular_count + 2` 改为 `regular_count + 1`**（物品柱 + 1 个 `void` 独立槽位；品质 1/2 = 9，品质 3/4 = 13）——**全文所有出现处同步**；④**R-10 的 `void` 柱"三方区分"变两方**：`void` 柱位于物品区之外（**全部物品之后**），**只须与物品柱区分**，不再有"隐藏柱"这一比较对象。
> **U18（R15 的 UI 含义）随之改述**：v0.13 下 R15 **已大幅缓解**——每一款都能被池子编辑加速，**残留风险 = "抬缺口很贵"**；UI 侧观测对象从"某个套系的隐藏物品"改为"**最后缺的少数几款**"（§11 U18，四条硬约束一字不改）。
> **不变**：`void` 柱必须画出（R-11）、池子逐盒一份（R-25–R-29）、`weights_bp` 整数口径、默认层"两个数字"契约（R-1）、25%–40% 比例、单一数据源铁律。

> **v0.11 去除保底（本文已同步）**：①**删除保底计数的显示项**——§2 边界行、§3 术语表的 `pity` 行、§8 的 01 行、§9.3 展开层线框图的「保底 `pity_counter` 3 / 8」行**全部移除**；**P1 的可查项不再包含保底**（它已不存在，不是"暂不显示"）。②**`void` 的呈现只剩两项**（核心 §5.6 已重写）：**「盒已消耗」确认 + 池子损耗来源提示**（**v0.14：该确认的文字应为"本次已消耗一次使用"，旧字面串「盒已消耗」作废**，见 R-11）——**不得**再呈现"保底推进"（那条 P5 兑付路径已随保底删除）。③**R15（尾部无界）的 UI 侧含义**登记为待实测 **U18**：只给中性、可公布的呈现，**不得话术掩盖、不得给件数预测（P4）**。

> **v0.10 同步（池子随盒子走：UI 上多了一个"选中盒子"）**：①**新增"选中盒子"概念**——池子面板 / 盲盒默认层 / 归因面板**一律显示"当前选中的那个盒子"的数据**；**选择态归 08 拥有，其余系统只读**（README §2.1），规格见 **§9.8 / R-25**；②**盲盒默认层按其选中盒子渲染 `headline`**——**同套系的两个盒子可以显示不同的两个数字，UI 不得合并、不得取平均、不得显示"该套系的期望"**（R-26）；③**架上面板每个盒子条目必须显示"是否已配置"**（有无镶嵌模块）——这是 v0.10 新增的核心决策信息，玩家要在"给哪些盒子配置"上做决策（R-27）；④**池子面板的标题与所有读数都注明"当前选中盒子"**（R-28）；⑤新增验收测试 **T22**（切换无残留 / 来回切换无串味 / 未配置的盒子显示基础池）。**`void` 柱、直方图柱数公式、默认层"两个数字"契约、25%–40% 比例一律未动。**
> **一句提醒 + 结构澄清**：v0.10 起，"池子"在 UI 上**永远是某个盒子的池子**——**屏幕上不允许存在"套系级的池子视图"**（核心 §4.1.2 / §16.5）。**核心已澄清 `Box` 下面是两个并列字段**：`item_pool`（物品池）+ `modules`（模块列表），**模块不折进池子**——因此**模块列表在本系统里是一块独立数据**：池子面板必须单列一块「**当前模块列表**」区域（**R-29**），架上的「是否已配置」**直读 `Box.modules` 的已占用位数是否为 0**（**R-27**——定长数组，**不得**判 `size() == 0`，**无需触及池子**），两者都**不得从池子反推**。

> **v0.9 同步（仓库容量与邮件）**：①新增**仓库占用呈现**——容量是抽象单位，UI **一律换算为占比**（已用 ÷ 容量）并让玩家**一眼看出快满了**（R-16）；②新增**邮件（收件箱）抽屉**——裁决为**可折叠的次级面板，从架上面板进入**，**不新增第七个常驻面板**（§9.7）；③**核心 §4.7 的边界必须由界面兑现**：邮件条目的"用于"按钮**置灰 + 一句说明**，不让玩家点了才发现失败（R-18）；④**R14 对策③**：开盒前给出**基于剩余空间的保守提示**（**下界式文案，唯一字面串见 R-20 / `01-gacha.md` §5.7**），**不得给精确件数**（`void` 与稀有度是随机的，R-20）；⑤物品详情补 `size` 一行（§9.3b）；⑥`source.kind` 的迁移取值按核心 v0.9 裁决 4 为 **`&"migrate"`**（旧稿 `migration` 作废）；⑦**新增主动丢弃路径**（裁决 16，R-22 / §9.7）：仓库内实例可主动销毁（二次确认、不可逆、可批量），且**"仓库满"提示里直给丢弃入口**；⑧**主动操作（转化 / 拆卸返还）空间不足时会被拒绝**（裁决 17）——UI 必须**提前置灰 + 给原因**，与"邮件条目禁用态"同类（R-23）；⑨邮件持有量用**带 `location` 的 `count()`** 显示（裁决 14，R-24）。**R-1 的两个数字契约一字未改。**

> **v0.8 同步（物品实例化）**：①**所有"数量"展示一律读 02 的派生值** `ItemService.count(category, quality)`（v0.8 起 `count` 不是存储字段），**UI 不得自己维护计数副本**（R-14）；②新增**实例的收藏编号与溯源呈现**——`serial` / `acquired_at` / `source`，且 `serial == 0` 的实例必须可与开盒实例区分（R-15）；③**默认层的两个数字契约不变**（R-1 一字不改，核心 §6.1）。

|---|---|---|

| 展开层 | `expanded_layer` | 全部物品分布、标记、损耗、镶嵌位、σ、直方图（核心 §6.3）`[补充]` |

| 盒子 / 盒子标识 | `Box` / `box_id` | 可囤积、**尚未归零（未被摧毁）**的抽取机会（**v0.14：剩余寿命 `uses_remaining` 次——装模块与开盒共用，归零即摧毁**）；**v0.10 起它下面挂着两个并列字段 `item_pool` + `modules`**（核心 §4.1.2），**v0.14 再在其上增 `uses_remaining`**。清单与 `box_id` **由 01 提供**；08 **按 `box_id` 取数**，不缓存盒子的池子、也不缓存剩余寿命（R-30） |

`[补充]` `expanded_layer` / `sandbox` 的代码名：术语表只给了 `headline`，而核心 §6.3 / §8.2 要求展开层与试算必须落地为独立状态，故补两个标识符。`[补充]` `mail_drawer` 同理：核心 §4.7 只规定邮件的行为，未规定它的呈现形态，故补一个标识符（归属裁决见 §9.7）。

**术语纪律（v0.6 新增）：本系统里"品质"有两个含义，线框图与文案中两者都会出现，必须可分辨。**

| 含义 | 代码名 | 书写规范 | 例 |
|---|---|---|---|
| **套系品质** | `series_quality` | 数字 **+ 档位名**，恒带 ` · ` 间隔符 | `品质 3 · 稀有` |
| **物品品质** | `quality` | 只写数字或品质符号（**★ 的个数 = `quality`**），**不得带档位名** | `品质 3` ／ `★★★` |

理由：默认层、展开层与线框图里"品质 3"与"品质 3 · 稀有"会同时出现（一个是盒子的档次，一个是东西的好坏），不加区分则玩家与实现者都会误读。**"套系品质必带档位名"是一条机械可检的书写规则**：任何出现 `series_quality` 的文案若缺少档位名，一律视为缺陷。`[补充]`

## 5. 规则与公式

**本系统不定义任何游戏数值公式。** 以下是渲染规则（R）与一条纯排版公式。

| # | 规则 | 依据 |
|---|---|---|
| **R-1** | **默认层三行制**：`best_item`（含品质符号 ★ 与图，★ 的个数 = 该物品的 `quality`）、`best_item_prob`、`ev`。**不得追加第四项数值**。**v0.10（U17 裁决）：封面必须标出"这是哪个盒子"**（如「盒 #7」），位置在**套系名那一行**，属**零数字的文字项**（不占"5 秒能懂"的预算）；**明确否决**用颜色 / 立绘差异等**需要解读**的方式表达属主（玩家会读成"稀有度"之类的暗示） | 核心 §6.1（v0.10 补充）/ P1 |
| **R-2** | **总量提示常驻**：默认层固定显示"共有 N 个物品"，N = 池中物品总数 = **`regular_count` 个物品（v0.13：全部常规，不再 +1）**（品质 1/2 → **8 个物品**，品质 3/4 → **12 个物品**，随套系变化）。**被排除的物品仍计入 N**——玩家要知道总量，而不是可见量 | 核心 §6.5 / §4.1.1 |
| **R-3** | **展开入口显眼**：位于默认层内部、常驻可见、点击区 ≥ 48×48 dp；首次出现时脉冲提示一次 | 核心 §6.5 / R12 |
| **R-4** | **实时联动**：`PoolService` 变更信号到达后，默认层在同一帧末重取 `EvalService.compute(state, box_id)`（**v0.10：`box_id` = 当前选中盒子**）；**禁止任何 UI 侧的概率增减** | 核心 §6.4 |

## 7. 流程 / 状态机

### 7.1 展开层状态机

```
collapsed ──(点击展开入口)──▶ expanded
expanded  ──(点击折叠 / ESC)──▶ collapsed
expanded  ──(选中候补模块)──▶ sandbox_preview
sandbox_preview ──(改目标物品 / 改强度)──▶ sandbox_preview      # 每次改动重取 EvalService
sandbox_preview ──(取消)──▶ expanded                          # 状态零变更
sandbox_preview ──(确认镶嵌)──▶ replace_confirm
replace_confirm ──(确认)──▶ collapsed                          # 池子已改，默认层立即更新
replace_confirm ──(返回)──▶ sandbox_preview
```

**关键约束：** `sandbox_preview` 全程**只读**。默认层在预览中显示的是"镶嵌后"的数字（`after_snapshot`），但 `PoolState` 只有走 `PoolService.socket()` 才发生变更（核心 §9 铁律 5）。**v0.10 追加**：预览与确认**都作用在当前选中盒子上**——**切换选中盒子必须退出 `sandbox_preview`**（状态归 `collapsed`），否则会在错的盒子上确认（§9.8 第 4 条）。**★ v0.16 追加（D20② 已裁决）：`replace_confirm` 的文案必须写明「本次替换将从该盒寿命再扣 1 次，且拆卸不退还」**（`替换 = 拆卸 + 重新镶嵌`；该位子历史累计 2 次）；**替换与镶嵌一样只做提示、不做拦截**，预警形态仍走 **§11 U20 的低强度提示**。

### 7.2 沙盒流程（P6）

1. UI 取候选状态（只读，不入库）——**v0.10：候选状态由 `preview_socket(state, box_id, slot, module_id)` 给出，`box_id` = 当前选中盒子**。
2. 用候选状态调用 `EvalService.compute()`（**v0.10：参照物是同一个选中盒子的池子**）得到 `after_snapshot`。
3. 直方图并排显示编辑前 / 编辑后（共享纵轴含 `void`，物品序对齐）。
4. **显式展示编辑后 `void_prob` 的变化**（如「空洞 5.00% → 7.50%」），与前后两条分布同屏对比——这是玩家判断"要不要继续排除"的唯一依据（`07-economy-rho.md` §9）。
5. 默认层数字并排显示"现在 → 镶嵌后"，**包括它变差的情况**。
6. 显示 `void_prob` 的逐物品来源、被换下模块及其损失——**损耗的算法见 `05-module-pool.md`，UI 只渲染字段**。
7. 确认后写入（`socket(state, box_id, module_id, slot)`，**写入的是选中盒子**）→ 变更信号 → 默认层重取（R-4）。

### 7.3 导航与信息层级


> **裁决（§6.1 的 `void` 呈现）：默认层不显示 `void_prob` 数值。**
> 默认层仍是"头奖概率 + 数学期望"两项数字（R-1）。理由：默认层的全部价值就是 5 秒可懂（核心 §6.2），任何第三个数字都在花掉它。
> **但不允许损耗在默认层完全不可见。** 当 `void_prob` ≥ 警示阈值（推荐 10% 🔧）时，默认层出现一条**不含数字**的提示条「池子已有损耗 · 展开查看空洞」，点击即展开（R-12）。理由：核心 §6.4 要求编辑在头部留下痕迹——排除"最好的物品"会当场拉低 `ev`，同理，排除积累出的空洞也必须在头部留下痕迹，否则 P1 想防的"系统在背后动手脚"的感觉会重新出现（R12 同源）。

> **裁决（品质标识在默认层）：可以显示，但必须是"零数字项"的文字铭牌，且只对较高品质套系显示。**
> 核心 §6.1 规定默认层只有"最好物品 + 其概率 + EV"三项，**v0.6 没有改变这一点**，因此这条裁决必须在不新增数字的前提下成立：
> - **允许**在套系名后追加纯文字铭牌「品质 3 · 稀有」（档位名必带，§3 术语纪律）；
> - **禁止**因它追加任何统计数字（概率、EV、位子数、物品数等一律不许随标识新增）；
> - 铭牌里的"3"是**档位名的一部分**（等级标签），不是数值项——默认层仍是两个数字（`best_item_prob`、`ev`）；
> - **仅 `series_quality` ≥ 3 时出现**：品质 1/2 是默认档，标识只制造噪音（核心 §6.2 的"5 秒能懂"）。
>
> 理由：核心 §4.1.1 把品质做成了一条**玩家可主动追求的轴**（核心 §11 的 3 h+ 教学点），而默认层是唯一常驻画面（R-9）。铭牌是这条轴在头部留下的最小痕迹，成本为零数字项；反过来，**只要它带上数字，就会花掉"5 秒能懂"**（核心 §6.2 / T10）。
> 这条与核心 §6.1 的三项契约的正式对齐仍记为待定项 **U11**。**参考（v0.10）**：核心 §6.1 已接受**盒标识**作为"**零数字文字项**"出现在**套系名那一行**（U17 裁决），因此同类处理（品质铭牌）的阻力已明显降低；但**仍待核心对 §6.1"三件事"契约正式表态**。

### 9.5 信息密度与教学曲线（核心 §11）

| 教学阶段 | UI 上出现的东西 | 玩家此刻不需要理解 |
|---|---|---|
| 0–5 min | 默认层三行 + "共有 N 个物品"（N = `regular_count`，本例 **8**；v0.13：无隐藏款、不再 +1）+ 任务面板 + **仓库占用占比条**（v0.9，R-16；**不给数字以外的解释**） | **概率、分布、σ、损耗、品质标识**、邮件（未溢出前不必解释） |
| 5–15 min | 循环面板（`rho` / `m_bar` / `d_bar` / `b`） | 分布 |
| 15–30 min | 转化入口（见 `06-conversion.md`） | 池子编辑 |
| 30 min–1 h | 架上面板完整版（位次占用） | 损耗 |
| 1–2 h | 模块·排除 → 池子面板 + 展开层分布与标记（**`void` 柱同时出现**，但只标"空洞"，不解释 40%） | **损耗的算术概念** |
| 2–3 h | 提升 + `loss` 行与 40% 口径 + **`void` 来源分解** + 镶嵌位占用行（格数 = `socket_count`） | σ、直方图 |
| 3 h+ | **套系品质与更大的施工台**（品质标识 + R-13 的位子来源说明）、σ、直方图前后对比、多套系对比、**邮件抽屉首次展开（v0.9，仅在首次真正溢出后）** | — |

**硬要求：**
- **前 15 分钟不需要理解概率**——这段时间里唯一出现的概率数字就是"最好物品的当前概率"。
- §5.2 的 **C5（编辑全程可查）**优先于节奏：**一旦玩家做过第一次镶嵌，分布与标记就必须始终可展开查看**，不得因教学阶段而锁。
- **`void` 柱从"展开层分布首次出现"起就画出**，不随教学阶段延后。理由：**物品概率之和 + `void_prob` 恒为 100%**，必须随时可核对（P1 / R-9；**v0.13：无隐藏款，全部物品一起归一化**，隐藏款删除前此式写作"`Σ probs + void_prob + 隐藏物品 = 100%`"），若在 1–2 h 阶段把 `void` 藏起来，玩家加总概率会发现缺口，反而怀疑系统藏了东西。教学差异只体现在**解释文案的深度**（2–3 h 才讲 40%），不体现在"画不画"。
- 未解锁项**不出现**；已解锁项**永不隐藏**（R-9）。
- **v0.10："选中盒子"要在"配置它"之前被教**：当架上**首次出现两个以上盒子**时给一次选择器说明（"池子面板 / 封面数字显示的是**你选中的那一个盒子**"）。它与"高品质套系给更多位子"（3 h+）**不是同一个教学点**，**不得合并**——前者是"看哪一个"，后者是"位子从哪来"（核心 §4.1.2 / §11）。

### 9.6 直方图规格（本作最重要的单个 UI）

1. **必须同时呈现编辑前后的分布形状**，并排或叠加，不允许只画一条（核心 §13.1）。
2. 共享纵轴（R-6，共享域含 `void_prob`）、物品序对齐、被排除物品保留空位（R-7）——**"哪一根被削掉了"必须在 0.5 秒内看出来**。
3. 纵轴即概率，柱数 **`regular_count + 1` 槽位**（**全部物品柱** + 1 个空洞 `void` 独立槽位；v0.13：无隐藏款）：品质 1/2 = 9，品质 3/4 = 13，**随当前套系品质取值，不得写死**。
4. **`void` 柱必须画出，且与物品柱样式互不混淆**（R-10；**v0.13：原"与常规物品、隐藏物品三方互不混淆"降为两方**——池中已无隐藏柱）：独立槽位（位于物品区之外、**全部物品之后**）、无填充或斜纹底 + 虚线边框 + 独立分隔线。**理由：损耗必须可见**，否则玩家无法理解 40% 意味着什么，也无法据此判断"要不要继续排除"（`07-economy-rho.md` §5.4 / §9，`05-module-pool.md` §5.3）。
5. **沙盒预览中，`void_prob` 的变化必须与编辑前后两条分布同屏呈现**（`07-economy-rho.md` §9 的硬要求）；直方图**实时重绘**，与默认层数字同帧更新（P6 的"没有实时预览的池子编辑是不可用的"）。
6. 不做动画过渡掩盖形状变化：形状变化本身就是要看的东西。

### 9.7 仓库占用、主动丢弃与邮件抽屉（v0.9）

**裁决：邮件不新增第七个常驻面板，而是"架上面板内的可折叠次级面板"（`mail_drawer`）。**

理由（三条）：①**核心 §8.1 的六个面板是按"玩法"选出来的**（编辑台、决策现场、工作台……），而邮件**没有决策**——它能做的动作只有一个「领取」；把抬成与池子 / 架上面板同权重的常驻面板，只会让面板数量膨胀，而六面板契约正是"信息架构不许膨胀"的体现。②**它应当在正确时刻浮现**：邮件只在"产出放不下"之后才有内容，常驻时 99% 是一具空壳，反而稀释"快满了"的紧迫感——那个信号应当由**占用条的分档警示**（R-16）承担。③**P1 的可查性并不要求常驻**（R-9 禁的是"藏"，不是"收"）：入口**常驻在架上面板**、带**未领取徽标**、一次展开即达（§7.3 的 L1c），且占用条在 ≥ 90% 时直接给"放不下的会进邮件"的文案——**可查性由入口 + 徽标 + 文案三处共同保证**，不靠第七个面板。

6. **邮件侧不得出现"扩容"入口**：容量只能由里程碑解锁（核心 D15 / `10-progression.md` §5 第 14 条），UI **不得**提供任何"花代价换容量"的按钮或话术。
7. **主动丢弃（v0.9 裁决 16）**：三处入口缺一不可——**①"仓库满"提示内（R-16 的 ≥ 90% 档位起出现，见线框图 A）**、②物品详情（§9.3b）、③仓库实例列表多选。**二次确认**必须逐条列出将销毁的 `item_id` / `serial` / `source.kind` / `size` 与**回收的空间量**，默认焦点在「取消」；**批量丢弃**一次确认 + 可展开逐条核对；**不得**存在无确认的"一键全丢"路径。丢弃后**占用占比、`count()` 与邮件可用性立即刷新**。**邮件侧条目没有丢弃入口**（裁决 16 只针对仓库内实例；邮件不占仓库空间，丢弃它也不能腾出容量）。
8. **主动操作的空间预检（v0.9 裁决 17）**：转化 / 拆卸返还的入口在空间不足时**置灰 + 一句可读原因**「仓库空间不足」+ 下一跳指向丢弃（上一条）；预检结果取执行方（04 / 06），**08 不得自己算**（R-23 / §11 U15）。**★ v0.16 追加：本屏的兑现入口（「开盒」）还多一道设备门槛**——**无设备时置灰 + 「你需要一台设备」+ 获取路径**（`no_device`，`04-device.md` §5.7），**与空间预检同一套"点击之前就看得出来"的呈现纪律**。理由：主动操作一旦进邮件就会**反噬**（销毁源腾出空间、产出又进邮件 = 净损失可用持有），所以它必须**拒绝**；而"拒绝"只有在**点击之前**就看得出来时才是约束，否则只是一次失败。

### 9.8 "选中盒子"与选择器（v0.10）

**归属裁决：选择态归 08，其余系统只读**（README §2.1）——08 只持有"**选了哪个盒子**"（`selected_box_id`），**不持有任何盒子的池子**：`Box` 清单与 `box_id` 来自 01，池子与读数来自 05 / 07（R-25）。理由：v0.10 之后"池子面板显示什么"**不再是一个套系能回答的问题**（同套系两盒不同，核心 §4.1.2），必须有人回答"现在看的是哪一个盒子"；而这个状态**不属于任何玩法系统**（它不改变任何玩法数据，只决定**读哪一份只读数据**），正是 08 的职责边界。

2. **位置与范围**：选择器**常驻于架上面板顶部**（那正是"我有哪些盒子"的地方）。**选择 ≠ 开盒**——它只改选中态，兑现仍走兑现入口（09）。**唯一的隐式选中**是"从某盒条目的深链进入池子面板"；其余入口一律**沿用当前选中态**，**不得**按套系重新挑一个盒子，也**不得**同时选中两个。
3. **回退规则**：`selected_box_id == ""`（首次进入）或**选中的盒子归零被摧毁（`uses_remaining` 归 0、立即离开清单）后** → 取 01 清单的**首个盒子**（**v0.14：兑现一次 / 镶嵌一次（寿命各 −1）不触发回退**——盒子还在清单里，**除非恰好归零**；R-30）；**架为空** → 池子面板显示**基础池** + 文案「架上还没有盒子」，**不得**沿用上一个盒子的任何读数（§6 参数表 / T22 ①）。
4. **沙盒只作用于选中盒子**：预览与"确认镶嵌"的写入对象都是**当前选中盒子**（`preview_socket(state, box_id, slot, module_id)` 与 `socket(state, box_id, module_id, slot)`，签名归 05）；**切换盒子必须取消进行中的沙盒预览**，否则会在错的盒子上确认。**位次由玩家选（核心 §4.1.2 的槽位语义）**：`modules` 是**长度恒为 `item_pool.socket_count` 的定长数组、下标即镶嵌位** ⇒ **任意空位都可被指定**；**往已占用位放必须走显式替换**（确认框显示"被换下来的是什么、损失多少"，核心 §3.3 / R-10），**不做隐式覆盖**——因此 UI **不得**把"只能追加到第一个空位"当作规则实现。
5. **不因选择器改变的东西**：`void` 柱（R-10）、直方图柱数公式（`regular_count + 1`）、默认层"两个数字"契约（R-1）、R-13 的位子来源说明、`25%–40%` 比例——**一律不动**（这是 v0.10 的硬约束：本版只改"看哪一个池子"，不改"池子长什么样"）。
