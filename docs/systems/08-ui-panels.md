# 08 · 界面与信息呈现系统

- 上游：`../core-design.md` **v0.9** ／ `README.md`（系统索引、所有权边界、术语表）
- 依赖系统：**07 数值与期望（`EvalService`）**、05 模块与池子（`PoolService`）、01 盲盒与概率、02 物品（**含仓库占用与邮件**）、03 任务、09 演出（入口）、10 收集与进度（入口）
- 被依赖：无。本系统是**叶子**：只消费 `EvalService` 的结果并渲染，不产出任何被计算的数值

> **单一数据源声明（本系统第一条铁律）**
> **盲盒默认层 / 循环面板 / 池子面板 / 归因面板 / 架上面板 / 任务面板，加上试算（沙盒）与兑现对照，全部从 `EvalService` 单一数据源取数。**
> 任何面板自行计算、各自缓存概率副本、或自带一套数字口径，一律视为缺陷（核心文档 §9 铁律 3/4；README §3.3）。
> **本系统不拥有任何数值公式。** 它只决定"哪些数字、在哪里、以什么格式、在什么时机出现"。
> **v0.9 追加同一条**：**仓库占用与邮件列表一律从 02 取数**（`warehouse_usage()` / 邮件清单），08 **不得**自己累加 `size`、不得自己判定溢出或可否领取。

> **v0.9 同步（仓库容量与邮件）**：①新增**仓库占用呈现**——容量是抽象单位，UI **一律换算为占比**（已用 ÷ 容量）并让玩家**一眼看出快满了**（R-16）；②新增**邮件（收件箱）抽屉**——裁决为**可折叠的次级面板，从架上面板进入**，**不新增第七个常驻面板**（§9.7）；③**核心 §4.7 的边界必须由界面兑现**：邮件条目的"用于"按钮**置灰 + 一句说明**，不让玩家点了才发现失败（R-18）；④**R14 对策③**：开盒前给出**基于剩余空间的保守提示**（"剩余空间至少还能放 N 件"），**不得给精确件数**（`void` 与稀有度是随机的，R-20）；⑤物品详情补 `size` 一行（§9.3b）；⑥`source.kind` 的迁移取值按核心 v0.9 裁决 4 为 **`&"migrate"`**（旧稿 `migration` 作废）；⑦**新增主动丢弃路径**（裁决 16，R-22 / §9.7）：仓库内实例可主动销毁（二次确认、不可逆、可批量），且**"仓库满"提示里直给丢弃入口**；⑧**主动操作（转化 / 拆卸返还）空间不足时会被拒绝**（裁决 17）——UI 必须**提前置灰 + 给原因**，与"邮件条目禁用态"同类（R-23）；⑨邮件持有量用**带 `location` 的 `count()`** 显示（裁决 14，R-24）。**R-1 的两个数字契约一字未改。**

> **v0.8 同步（物品实例化）**：①**所有"数量"展示一律读 02 的派生值** `ItemService.count(category, quality)`（v0.8 起 `count` 不是存储字段），**UI 不得自己维护计数副本**（R-14）；②新增**实例的收藏编号与溯源呈现**——`serial` / `acquired_at` / `source`，且 `serial == 0` 的实例必须可与开盒实例区分（R-15）；③**默认层的两个数字契约不变**（R-1 一字不改，核心 §6.1）。

| 装置装配规则与 50% 返还 | 见 `04-device.md` |
| **空洞概率 `void_prob` 的计算与口径**（`void_mass = freed_mass × 0.4`） | 见 `07-economy-rho.md` §5.4 / `05-module-pool.md` §5.4。**08 只渲染字段，不得在 UI 层换算 40% 损耗** |
| 仓库容量与占用（`warehouse_capacity` / `warehouse_usage()`）、`ItemDef.size`、邮件清单、领取动作、**产出溢出判定**（哪个实例进邮件）、**主动丢弃的销毁动作**（裁决 16，销毁归 02）、**主动操作（转化 / 拆卸返还）的空间拒绝判定**（裁决 17，判定归 06 / 04、执行归 02） | 见 `02-item.md`（核心 §4.7）。**08 只渲染**：不得自己累加 `size`、不得自己判断"还能放几件"、不得自己判断某条能否领取、不得自己判断某次转化 / 拆卸能否执行、不得在 UI 层改变任何实例的 `location` 或销毁任何实例 |

## 3. 核心概念与术语

沿用 README §5 术语表（中文名 + 代码名），本系统只新增呈现层标识符。

| 中文名 | 代码名 | 在本系统的含义 |
|---|---|---|
| 封面层 / 默认层 | `headline` | 盲盒封面：最好物品 + 其概率 + 期望（核心 §6.1） |
| 展开层 | `expanded_layer` | 全部物品分布、标记、损耗、镶嵌位、σ、直方图（核心 §6.3）`[补充]` |
| 池子 | `Pool` | 某套系当前的概率分布状态 |
| 池子状态 | `PoolState` | 基础权重 + 模块编辑结果（只读消费，见 `05-module-pool.md`） |
| 物品 | `Item` | 池中单个可产出物，**同时也是玩家积累的资源**（池中的物品就是你得到的物品）；默认层取材是其中价值最高者 |
| 套系 | `Series` | 一个独立概率池：`regular_count` 个常规物品 + 1 个隐藏物品（品质 1/2 = 8 个常规物品，品质 3/4 = 12 个，核心 §4.1.1） |
| 排除 / 提升 / 损耗 | `ban` / `boost` / `loss` | 展开层要展示的**标记**；规则见 `05-module-pool.md` |
| 隐藏物品 | `hidden` | 展开层中以"免疫编辑"视觉语言标注 |
| 镶嵌位 | `socket_slot` | **格数由套系品质决定**（= `SeriesDef.socket_count`，v0.6 起不再固定为 3）；同一套系内恒定，展开层与池子面板**按该值动态渲染格子，不得写死** |
| 期望 | `ev` | 默认层的第二个数字（`best_item_prob` 之后） |
| 闭环收益率 | `rho` | 归因面板与循环面板的主体 |
| 保底 | `pity` | 展开层的可查项（P1） |
| 试算 / 沙盒 | `sandbox` | 镶嵌前的实时预览态（核心 §8.2）`[补充]` |
| 空洞 | `void` | 排除损耗产生的**零价值结果**；在分布中占一个显式位置，**但它不是一个物品**（不计入 N） |
| 套系品质 | `series_quality` | 决定该套系的常规物品数、镶嵌位数、装置槽位数与物品品质区间（README §5，核心 §4.1.1）。**08 只直读渲染品质标识与位子说明，不参与任何计算** |
| 物品品质 | `quality` | 物品的 1–5 等级（取自 `ItemDef.quality`），与 `series_quality` **不是同一维度**（见下） |
| 物品实例 | `ItemInstance` | 玩家实际持有的**一个**物品：`instance_id` + `item_id` + `acquired_at` + `source` + `serial`（核心 §4.2.1）。**08 只读渲染** |
| 实例 id | `instance_id` | UUIDv4，全局唯一并兼作幂等键；**不给玩家看**（内部身份），仅调试视图可见 `[补充]` |
| 收藏编号 | `serial` | **该玩家开出的第 N 个此物品**（"这是你的第 187 个星尘"）；`serial == 0` = **非开盒来源**（转化 / 返还 / 解锁发放，核心 §4.2.3），**不可显示成"第 0 个"** |
| 溯源 | `source` | 实例来自哪个盒子：`{ kind, series_id, box_seed, draw_index }`（键名与取值域归 02 §4.2，核心 v0.9 裁决 4：`gacha` / `convert` / `refund` / `mail` / **`migrate`** / `unlock`）；`kind != &"gacha"` 时**无盒子可指**，显示来源类型文案而非空盒子 |
| 持有量 | `count` | **派生值**（由实例列表数出并缓存）：`count(category, quality)`。**不是存储字段**，08 不得缓存副本（v0.8）。**v0.9：只统计 `location == warehouse`**——邮件侧实例不计入，界面上必须能看出"它还没进仓库" |
| 仓库 | `warehouse` | 实例的一个**位置**（`location == &"warehouse"`），在容量内；只有这里的实例可被使用（核心 §4.7） |
| 仓库容量 / 占用 | `warehouse_capacity` / `warehouse_usage()` | 容量的**抽象单位**上限（示意 1000；**UI 一律换算为占比**，不把原值当主读数，R-16）与 02 的占用查询（已用 = Σ 仓库侧实例的 `size`）。08 只渲染，**不得自己累加 `size` 或相除**（§2） |
| 物品大小 | `ItemDef.size` | 单个实例占用的容量（**同种物品大小相同**）。**08 只直读渲染**（R-21） |
| 邮件 / 领取 | `mail` / `claim` | 邮件（`location == &"mail"`）是放不下产出的**兜底容器**：无上限、不过期，**不是第二个仓库**（条目不可用于交付 / 装配 / 镶嵌 / 转化，核心 §4.7），呈现为**可折叠抽屉**（R-17）；领取是把实例搬回仓库的**唯一**动作，**只改 `location`**，UI **不得**在本地改数量或编号（R-19） |
| 主动丢弃 | `discard` | v0.9（裁决 16）：玩家**主动销毁**仓库内任意实例的动作，**不可逆**、需二次确认（R-22）。**销毁归 02**，08 只发动作；**它不是产出，也不给任何回报** |
| 邮件抽屉 | `mail_drawer` | 邮件的呈现形态：**架上面板内的可折叠次级面板**（不是第七个常驻面板）`[补充]` |

`[补充]` `expanded_layer` / `sandbox` 的代码名：术语表只给了 `headline`，而核心 §6.3 / §8.2 要求展开层与试算必须落地为独立状态，故补两个标识符。`[补充]` `mail_drawer` 同理：核心 §4.7 只规定邮件的行为，未规定它的呈现形态，故补一个标识符（归属裁决见 §9.7）。

**术语纪律（v0.6 新增）：本系统里"品质"有两个含义，线框图与文案中两者都会出现，必须可分辨。**

| 含义 | 代码名 | 书写规范 | 例 |
|---|---|---|---|
| **套系品质** | `series_quality` | 数字 **+ 档位名**，恒带 ` · ` 间隔符 | `品质 3 · 稀有` |
| **物品品质** | `quality` | 只写数字或品质符号（**★ 的个数 = `quality`**），**不得带档位名** | `品质 3` ／ `★★★` |

理由：默认层、展开层与线框图里"品质 3"与"品质 3 · 稀有"会同时出现（一个是盒子的档次，一个是东西的好坏），不加区分则玩家与实现者都会误读。**"套系品质必带档位名"是一条机械可检的书写规则**：任何出现 `series_quality` 的文案若缺少档位名，一律视为缺陷。`[补充]`

## 4. 数据结构（GDScript Resource 字段定义）

```gdscript
# res://src/ui/scenes/panels/panel_def.gd
class_name PanelDef
extends Resource

enum PanelId { HEADLINE, LOOP, POOL, ATTRIBUTION, SHELF, TASK }

@export var panel_id: PanelId = PanelId.HEADLINE
@export var title_cn: String = ""
@export var unlock_step: int = 0                  # 教学曲线步骤（核心 §11）
@export var eval_fields: PackedStringArray = []   # 允许读取的 EvalResult 字段白名单
@export var is_expandable: bool = false           # 仅 HEADLINE / POOL 为 true
```

`[补充]` `PanelDef` 与 `eval_fields`：核心 §8.1 只规定面板内容，未规定配置形态。"字段白名单"是落地所需，同时是**单一数据源**的机械保证——面板读不到自己不该算的字段。

```gdscript
# res://src/ui/scenes/panels/panel_view_state.gd
class_name PanelViewState
extends Resource

@export var expanded: bool = false              # 展开层状态（核心 §6.3）
@export var sandbox_active: bool = false         # 沙盒预览中（核心 §8.2 / P6）
@export var before_snapshot: RefCounted          # 编辑前的 EvalResult 只读快照
@export var after_snapshot: RefCounted           # 编辑后的 EvalResult（来自 EvalService）
@export var highlighted_item_id: StringName = &""
@export var pulse_shown: bool = false            # 展开入口首见脉冲，一次性（R12 对策）
@export var mail_drawer_open: bool = false       # v0.9：邮件抽屉展开态（§9.7）；**默认收起**，只在架上面板内
```

`[补充]` `EvalResult` 类型由 07 定义（见 `07-economy-rho.md`）；`before_snapshot` 是**呈现层缓存**，只服务"编辑前后对比"，不参与任何求解，也不得被任何面板当作数据源。

**本系统不定义任何游戏数值公式。** 以下是渲染规则（R）与一条纯排版公式。

`[补充]` **R-16 的分档阈值与 R-20 的 N 取值**：核心 §4.7 只规定"容量用抽象单位、UI 换算为占比显示"，R14 对策③只规定"开盒前预告"，两者的具体形态与阈值是实现细节。落到"占比 + 分档 + 保守下界"三条，是为了同时满足 R14 的两个相互拉扯的目标：**②让"满了"是阶段性挑战**（可见、可预期）与**③把意外变成可预期**（提示必须**可信**，所以只给下界、不给精确数）。**N 只给下界是刻意的**：一旦给出精确件数，玩家会在容量边界处发现"显示还能放但实际放不下"，该提示的全部信任当场归零（T20）。**✅ 跨文档已对齐（v0.9 收尾）**：核心 §12 R14 对策③、`01-gacha.md` §5.7、`02-item.md` §9 三处**均已为保守下界口径**，无任何件数预测。**"只给下界"不只是措辞问题**：一旦给出精确件数，玩家会在容量边界处发现"显示还能放但实际放不下"，该提示的全部信任当场归零（T20）；更严重的是**精确件数会泄露单次悬念**（"3 件进邮件"直接暴露"这次没抽到 `void`"），**违反 P4**。

`[补充]` **R-12 的警示阈值**：核心文档 §6.1 只规定默认层"只有三样东西"，未规定损耗在默认层的可见性。为使"排除积累出的空洞"不在头部完全消失（§6.4 的精神：编辑必须在默认层留下痕迹），补一条阈值触发的提示条——它不新增数字，只增强展开入口（R-3 / R12）。

`[补充]` **R-13 的呈现位置与文案**：核心 §4.1.1 规定"位子由品质决定"，P1 只要求"可查"，未规定查在哪里。落到展开层的**镶嵌位状态行**与架上面板的**位次占用行**各加一行来源说明即可（一行字 + 一处深链），不新增页面层级、不新增默认层数字项。理由：v0.6 把品质变成玩家可主动追求的轴（核心 §11 的 3 h+ 教学点），若界面只显示"3 格"而不说"为什么是 3 格、哪里能拿到更多"，这条轴在 UI 上等于不存在。

排版公式（**仅布局，不含玩法语义**）：

```
柱高 hᵢ = clamp(pᵢ / max_j(p_j, void_prob), 0, 1)   # pᵢ 取自 EvalResult.distribution，void_prob 取自 EvalResult.void_prob（07 §4）
柱数   = regular_count + 2 个独立槽位               # 常规物品数 + 1 隐藏物品 + 1 空洞 void
       # regular_count 取自 SeriesDef（核心 §4.1.1），不得写死：
       #   品质 1 / 2 → 8 + 2 = 10 槽位　｜　品质 3 / 4 → 12 + 2 = 14 槽位
编辑前后两组柱使用同一个 max_j(p_j, void_prob)
```

## 7. 流程 / 状态机

### 7.1 展开层状态机

```
collapsed ──(点击展开入口)──▶ expanded
expanded  ──(点击折叠 / ESC)──▶ collapsed
expanded  ──(选中候补模块)──▶ sandbox_preview
sandbox_preview ──(改目标物品 / 改强度)──▶ sandbox_preview      # 每次改动重取 EvalService
sandbox_preview ──(取消)──▶ expanded                          # 状态零变更
sandbox_preview ──(确认镶嵌)──▶ replace_confirm
replace_confirm ──(确认)──▶ collapsed                          # 池子已改，默认层立即更新
replace_confirm ──(返回)──▶ sandbox_preview
```

**关键约束：** `sandbox_preview` 全程**只读**。默认层在预览中显示的是"镶嵌后"的数字（`after_snapshot`），但 `PoolState` 只有走 `PoolService.socket()` 才发生变更（核心 §9 铁律 5）。

### 7.2 沙盒流程（P6）

1. UI 取候选状态（只读，不入库）。
2. 用候选状态调用 `EvalService.compute(candidate)` 得到 `after_snapshot`。
3. 直方图并排显示编辑前 / 编辑后（共享纵轴含 `void`，物品序对齐）。
4. **显式展示编辑后 `void_prob` 的变化**（如「空洞 4.90% → 7.35%」），与前后两条分布同屏对比——这是玩家判断"要不要继续排除"的唯一依据（`07-economy-rho.md` §9）。
5. 默认层数字并排显示"现在 → 镶嵌后"，**包括它变差的情况**。
6. 显示 `void_prob` 的逐物品来源、被换下模块及其损失——**损耗的算法见 `05-module-pool.md`，UI 只渲染字段**。
7. 确认后写入 → 变更信号 → 默认层重取（R-4）。

### 7.3 导航与信息层级

```
L0  盲盒封面（默认层）—— 1 屏，**两个数字** + `best_item` 行 + "共有 N 个物品" + 展开入口（+ 品质标识，见 §9.2 裁决）
      │
      ├──▶ L1a 展开层（同屏内联展开）—— 全部物品分布 / 标记 / 损耗 / 镶嵌位 / σ / 直方图
      └──▶ L1b 底部导航：循环 · 池子 · 归因 · 架上 · 任务
L1  池子 ⇄ 归因  双向深链（编辑现场 ↔ 编辑依据）
    架上 ──▶ 兑现（见 `09-presentation.md`）／ 图鉴与套系进度（见 `10-progression.md`）／ **邮件抽屉 `mail_drawer`（v0.9）**
L1c **邮件抽屉（v0.9）**：在架上面板内**展开的次级面板**（默认收起，R-17）。**它不是第七个面板**——不常驻、不占底部导航位；条目 → 物品详情（§9.3b，含 `size`）；条目上方的「用于」入口一律置灰（R-18）
    任务 ──▶ 缺口物品 ──▶ 转化 / 装配
L2  沙盒预览与替换确认（模态覆盖，不新增页面层级）
```
**v0.9 层级原则不变**：邮件在**深度**上很浅（一次展开即达），但在**常驻性**上不属于面板——因为它的内容只在"放不下"之后才有意义，**入口常驻（架上面板 + 徽标）已经满足 P1 的可查性**（R-9：已解锁的信息永不隐藏，指的是"不得藏"，不是"必须常驻一屏"）。

**层级原则：** 深度按需下沉，但**入口在浅层**（R-3 / R-9）。层级越深的信息，入口必须越显眼。

**只有三件事**：最好的物品、它的当前实际概率、数学期望。加上 R12 要求的总量提示与展开入口——**其余一律下沉到展开层**。本图主体按**品质 2 · 精良**绘制（物品数 9）；品质标识是**占位示例**，与品质 2 不同时出现——它只出现于品质 ≥ 3 的套系，且**不占数字项**（三件事的数值契约不变）。

> **裁决（§6.1 的 `void` 呈现）：默认层不显示 `void_prob` 数值。**
> 默认层仍是"头奖概率 + 数学期望"两项数字（R-1）。理由：默认层的全部价值就是 5 秒可懂（核心 §6.2），任何第三个数字都在花掉它。
> **但不允许损耗在默认层完全不可见。** 当 `void_prob` ≥ 警示阈值（推荐 10% 🔧）时，默认层出现一条**不含数字**的提示条「池子已有损耗 · 展开查看空洞」，点击即展开（R-12）。理由：核心 §6.4 要求编辑在头部留下痕迹——排除"最好的物品"会当场拉低 `ev`，同理，排除积累出的空洞也必须在头部留下痕迹，否则 P1 想防的"系统在背后动手脚"的感觉会重新出现（R12 同源）。

> **裁决（品质标识在默认层）：可以显示，但必须是"零数字项"的文字铭牌，且只对较高品质套系显示。**
> 核心 §6.1 规定默认层只有"最好物品 + 其概率 + EV"三项，**v0.6 没有改变这一点**，因此这条裁决必须在不新增数字的前提下成立：
> - **允许**在套系名后追加纯文字铭牌「品质 3 · 稀有」（档位名必带，§3 术语纪律）；
> - **禁止**因它追加任何统计数字（概率、EV、位子数、物品数等一律不许随标识新增）；
> - 铭牌里的"3"是**档位名的一部分**（等级标签），不是数值项——默认层仍是两个数字（`best_item_prob`、`ev`）；
> - **仅 `series_quality` ≥ 3 时出现**：品质 1/2 是默认档，标识只制造噪音（核心 §6.2 的"5 秒能懂"）。
>
> 理由：核心 §4.1.1 把品质做成了一条**玩家可主动追求的轴**（核心 §11 的 3 h+ 教学点），而默认层是唯一常驻画面（R-9）。铭牌是这条轴在头部留下的最小痕迹，成本为零数字项；反过来，**只要它带上数字，就会花掉"5 秒能懂"**（核心 §6.2 / T10）。
> 这条与核心 §6.1 的三项契约的正式对齐仍记为待定项 **U11**。

### 9.5 信息密度与教学曲线（核心 §11）

| 教学阶段 | UI 上出现的东西 | 玩家此刻不需要理解 |
|---|---|---|
| 0–5 min | 默认层三行 + "共有 N 个物品"（N = `regular_count` + 1，本例 9）+ 任务面板 + **仓库占用占比条**（v0.9，R-16；**不给数字以外的解释**） | **概率、分布、σ、损耗、品质标识**、邮件（未溢出前不必解释） |
| 5–15 min | 循环面板（`rho` / `m_bar` / `d_bar` / `b`） | 分布 |
| 15–30 min | 转化入口（见 `06-conversion.md`） | 池子编辑 |
| 30 min–1 h | 架上面板完整版（位次占用） | 损耗 |
| 1–2 h | 模块·排除 → 池子面板 + 展开层分布与标记（**`void` 柱同时出现**，但只标"空洞"，不解释 40%） | **损耗的算术概念** |
| 2–3 h | 提升 + `loss` 行与 40% 口径 + **`void` 来源分解** + 镶嵌位占用行（格数 = `socket_count`） | σ、直方图 |
| 3 h+ | **套系品质与更大的施工台**（品质标识 + R-13 的位子来源说明）、σ、直方图前后对比、多套系对比、**邮件抽屉首次展开（v0.9，仅在首次真正溢出后）** | — |

**硬要求：**
- **前 15 分钟不需要理解概率**——这段时间里唯一出现的概率数字就是"最好物品的当前概率"。
- §5.2 的 **C5（编辑全程可查）**优先于节奏：**一旦玩家做过第一次镶嵌，分布与标记就必须始终可展开查看**，不得因教学阶段而锁。
- **`void` 柱从"展开层分布首次出现"起就画出**，不随教学阶段延后。理由：`Σ probs + void_prob + 隐藏物品 = 100%` 必须随时可核对（P1 / R-9），若在 1–2 h 阶段把 `void` 藏起来，玩家加总概率会发现缺口，反而怀疑系统藏了东西。教学差异只体现在**解释文案的深度**（2–3 h 才讲 40%），不体现在"画不画"。
- 未解锁项**不出现**；已解锁项**永不隐藏**（R-9）。
- 展开层默认收起——**但入口必须显眼**（R-3）。默认层是门面，不是牢笼。

### 9.6 直方图规格（本作最重要的单个 UI）

1. **必须同时呈现编辑前后的分布形状**，并排或叠加，不允许只画一条（核心 §13.1）。
2. 共享纵轴（R-6，共享域含 `void_prob`）、物品序对齐、被排除物品保留空位（R-7）——**"哪一根被削掉了"必须在 0.5 秒内看出来**。
3. 纵轴即概率，柱数 **`regular_count + 2` 槽位**（常规物品数 + 1 个隐藏物品 + 1 空洞 `void`）：品质 1/2 = 10，品质 3/4 = 14，**随当前套系品质取值，不得写死**。
4. **`void` 柱必须画出，且与常规物品、隐藏物品三方样式互不混淆**（R-10）：独立槽位（位于物品区之外）、无填充或斜纹底 + 虚线边框 + 独立分隔线。**理由：损耗必须可见**，否则玩家无法理解 40% 意味着什么，也无法据此判断"要不要继续排除"（`07-economy-rho.md` §5.4 / §9，`05-module-pool.md` §5.3）。
5. **沙盒预览中，`void_prob` 的变化必须与编辑前后两条分布同屏呈现**（`07-economy-rho.md` §9 的硬要求）；直方图**实时重绘**，与默认层数字同帧更新（P6 的"没有实时预览的池子编辑是不可用的"）。
6. 不做动画过渡掩盖形状变化：形状变化本身就是要看的东西。

### 9.7 仓库占用、主动丢弃与邮件抽屉（v0.9）

**裁决：邮件不新增第七个常驻面板，而是"架上面板内的可折叠次级面板"（`mail_drawer`）。**

理由（三条）：①**核心 §8.1 的六个面板是按"玩法"选出来的**（编辑台、决策现场、工作台……），而邮件**没有决策**——它能做的动作只有一个「领取」；把抬成与池子 / 架上面板同权重的常驻面板，只会让面板数量膨胀，而六面板契约正是"信息架构不许膨胀"的体现。②**它应当在正确时刻浮现**：邮件只在"产出放不下"之后才有内容，常驻时 99% 是一具空壳，反而稀释"快满了"的紧迫感——那个信号应当由**占用条的分档警示**（R-16）承担。③**P1 的可查性并不要求常驻**（R-9 禁的是"藏"，不是"收"）：入口**常驻在架上面板**、带**未领取徽标**、一次展开即达（§7.3 的 L1c），且占用条在 ≥ 90% 时直接给"放不下的会进邮件"的文案——**可查性由入口 + 徽标 + 文案三处共同保证**，不靠第七个面板。

**规格（逐条）：**
1. **数据源**：条目 = 02 的 `mail_instances()`；徽标数 = 该清单长度；`size` 直读 `ItemDef.size`。**08 不缓存副本、不做加减**（R-14 / R-19 ②）。
2. **禁用态必须在点击之前可见**（R-18）：邮件侧四个"用于"入口**一律禁用**并给出同一句原因；**不得**先允许点击、失败后再弹错误——核心 §4.7 的边界不能只活在报错里。
3. **领取**：逐条 + 一键；按 `acquired_at` 升序逐件尝试，**空间不足时是"部分成功"**（02 §5.10）——放不下的留在邮件，界面**必须回报「已领取 M / 还剩 K 件」**，「一键领取」**不得**表述为"一键领完"（R-19）。**不得丢弃、不得覆盖、不得自动转换**。领取后**只**刷新 `location` 相关呈现（占用条与清单）——**数量与编号读数不因领取而变化**。
4. **排序**沿用 R-15 的实例序（`acquired_at` 升序、同刻 `instance_id` 字典序）；`≥ 3000` 条目同样走虚拟滚动 / 分页（T17）。
5. **首次溢出的一次性说明**：首次真正产生 `location == &"mail"` 的实例时，抽屉入口脉冲一次 + 一行说明「仓库满了，这件已存入邮件，不会丢失」；与 `09-presentation.md` §5.9 的演出提示**同源**——两处可同时出现，**但不得互相矛盾**。
6. **邮件侧不得出现"扩容"入口**：容量只能由里程碑解锁（核心 D15 / `10-progression.md` §5 第 14 条），UI **不得**提供任何"花代价换容量"的按钮或话术。
7. **主动丢弃（v0.9 裁决 16）**：三处入口缺一不可——**①"仓库满"提示内（R-16 的 ≥ 90% 档位起出现，见线框图 A）**、②物品详情（§9.3b）、③仓库实例列表多选。**二次确认**必须逐条列出将销毁的 `item_id` / `serial` / `source.kind` / `size` 与**回收的空间量**，默认焦点在「取消」；**批量丢弃**一次确认 + 可展开逐条核对；**不得**存在无确认的"一键全丢"路径。丢弃后**占用占比、`count()` 与邮件可用性立即刷新**。**邮件侧条目没有丢弃入口**（裁决 16 只针对仓库内实例；邮件不占仓库空间，丢弃它也不能腾出容量）。
8. **主动操作的空间预检（v0.9 裁决 17）**：转化 / 拆卸返还的入口在空间不足时**置灰 + 一句可读原因**「仓库空间不足」+ 下一跳指向丢弃（上一条）；预检结果取执行方（04 / 06），**08 不得自己算**（R-23 / §11 U15）。理由：主动操作一旦进邮件就会**反噬**（销毁源腾出空间、产出又进邮件 = 净损失可用持有），所以它必须**拒绝**；而"拒绝"只有在**点击之前**就看得出来时才是约束，否则只是一次失败。

| **T16 编号与溯源呈现（含 `serial == 0`，v0.8 验收）** | ①开盒实例显示 `serial ≥ 1` 且文案为"第 N 个"；②转化 / 返还 / 解锁产出（`serial == 0`）**不得**渲染成"第 0 个"——断言其走"非开盒来源"分支，且与开盒实例视觉可分；③迁移实例（`source.kind == &"migrate"`）有编号但**来源行不得显示盒子**；④`acquired_at` / `source` 两行存在且与 02 的实例字段**逐位相同**；⑤列表顺序 = 本 `item_id` 内 `acquired_at` 升序、同刻 `instance_id` 字典序 | 收藏叙事不得产生假编号 / 假溯源（R-15 / 核心 §4.2.3） |
| **T17 大实例量渲染预算（v0.8 验收）** | 构造 **≥ 3000** 个实例（同一 `item_id` ≥ 1000 个）：①详情 / 列表一屏渲染 ≤ 1 帧（上限 100 ms）；②断言走**虚拟滚动或分页**——实例化条目数 ≤ 一屏可见数 + 缓冲，且**不随实例总数线性增长**；③断言每次渲染对 `count()` 的调用不随实例总数线性增长（派生索引由 02 缓存） | 每实例一条目会让 UI 随存档体积线性劣化（核心 §4.2.2 第 4 条的体积代价） |

| **T19 邮件条目禁用态与不构成持有（v0.9 验收）** | ①邮件侧每个条目的「交付 / 装配 / 镶嵌 / 转化」控件处于**禁用态**，禁用原因**非空且可读**（如「先领取到仓库才能使用」），并断言**一次点击也不会发出动作**（不得"先尝试后报错"）；②条目被领取（`location == warehouse`）后这四项目**在同一刷新周期内变为可用**；③**邮件条目不计入任何持有量读数**：构造「仓库 0 件 + 邮件 3 件」的存档，断言任务面板持有向量为零、显示缺口高亮（`count()` 只统计仓库侧）；④断言**邮件不是第七个常驻面板**——底部导航仍为五个入口（循环 / 池子 / 归因 / 架上 / 任务），邮件入口只出现在架上面板内（R-17） | 核心 §4.7 的边界必须由界面兑现，而不是让玩家点了才发现失败 |
| **T20 容量边界提示可信（v0.9 验收）** | 构造「剩余容量 == 某物品 `size`」「剩余容量 == `size` − 1」「剩余容量 == 0」三个临界存档：①断言 R-20 的提示 `N == floor(剩余容量 ÷ 池中最大 size)`；**当 N ≥ 1 时，连续 N 次 `grant()` 的结果必须全部落在 `warehouse`**——**不得出现"显示还能放但实际放不下"**（本条为硬断言）；②`N` 恒为**下界**（实际入库件数 ≥ N）——它是**承诺**，不是预测；③`N == 0` 时**不显示数字**，文案含「放不下的会自动存入邮件，不会丢失」；④断言该提示**不引用任何池子分布或随机量**（`void` / 稀有度 / 概率一律不可用），静态检查确认它只依赖 02 的占用查询与 `ItemDef.size` | R14 对策③的价值全部建立在"提示可信"上；给精确件数会当场摧毁它 |
| **T21 丢弃路径与主动操作被拒的提前告知（v0.9 验收）** | ①**入口存在性**：占用 ≥ 90% 时提示内出现「丢弃…」，物品详情与仓库列表同样可达，**邮件侧条目无任何丢弃入口**；②**不可逆必须二次确认**：确认弹窗逐条列出 `item_id` / `serial` / `size` 与回收空间，默认焦点在「取消」，**取消后零变更**；批量丢弃可展开逐条核对；③断言**不存在**无确认的"一键全丢"路径（静态检查：丢弃动作只经确认流程发出）；④丢弃后：实例数 −N、`total_consumed` +N、占用占比与 `count()` **立即刷新**，且**无任何回报**（无新实例、无券）；⑤**主动操作预检**：构造转化 / 拆卸返还在空间不足的状态，断言两者入口**禁用且原因可读**（「仓库空间不足」），**一次点击也不发出动作**；丢弃或交付腾出空间后**同一刷新周期内变为可用**（R-23） | 约束必须**可见**，不能变成一次失败（裁决 17）；没有丢弃路径，"仓库满"会变死局（裁决 16） |

**切片期必采指标：** 展开层打开率、人均展开次数、首次镶嵌到首次展开的时长、"共有 N 个物品"的点击率、**`void` 来源行的查看率**。展开率过低即触发 T11 ①。
**v0.9 新增必采指标**：**占用条警示档（≥ 90%）的到达率与停留时长**、**邮件抽屉展开率与一次性说明的命中率**、**一键领取的使用率**、**"仓库快满"出现后单次会话的开盒次数变化**（这一项直接观测核心 R14：**若开盒次数显著下降，即为核心 R14 命中**，处置见 `10-progression.md` §10 的失败信号）。
