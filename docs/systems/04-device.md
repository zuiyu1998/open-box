## 1. 这个系统负责什么

**设备系统是盲盒的入口工具**：**没有设备，既不能开盒也不能装模块**。它是核心循环的第一步，不是可选修正层。原"作用于转化端"的职能已取消（`06` 已解耦、D9 已固定为 30%）。

装置是**开启盲盒与给盲盒添加模块的前置条件**（`engine` 出口，核心 §3 / §4.4）：物品先装配成装置，**持有至少一台设备**是 `redeem`（开盒 / 兑现）与 `socket`（镶嵌 / 装模块）的**链首校验**（§5.7）。**逻辑执行者不变**——开盒仍归 `GachaService.redeem()`（01）、池子数据仍只由 `PoolService`（05）写，**设备只是前置条件**（§2）。

| 职责 | 内容 |
|---|---|
| 定义装置 | `DeviceDef`：成本 + 品质 + 条件 + 互斥 + 标签 + 解锁标记。**效果类型 / 目标 / 系数（效果族）已作废**，替代形状未裁决（§11 04-L） |
| **硬门槛（★ v0.16）** | **没有设备，既不能开盒也不能装模块**——`redeem` / `socket` 的**链首先校验"已有一台设备"**；无设备 ⇒ **响亮拒绝 `no_device`、不消耗任何一次寿命、状态逐项不变**（§5.7）。**判定归本系统，落点归 01 / 05**（§8） |
| **开局发放（★ v0.16）** | **新游戏初始化时发放一台基础装置**（**品质 1 的基础款**，形态沿用 §4 既有定义，见 §1.1）——**否则开局死锁**（开盒需设备 → 设备由物品制造 → 物品来自开盒）。**定义归本系统；发放与落盘不归本系统**（§1.1） |
| 管理位次 | 槽位 `device_slot` 是**每套系常量**：构造时注入并冻结、运行时不可变、**不提供任何扩容接口**（P7 / C4）。**原"数量随套系品质取值"（D4）已作废** ⇒ 该字段**存废与语义待重定义**（核心 §15 **D22** / §11 **04-O**；本文只读并冻结注入值） |
| 装配 / 拆卸 | 装配**销毁物品实例**（`ItemService.consume(instance_ids)`，原子）；拆卸按原 `cost` 逐条 `floor(amount × 0.5)` **返还 50%**——返还**创建新实例**（**新 UUID**、`source = { kind = &"refund" }`；`serial = 0` 由 02 内部置位，**`serial` 不是 `grant` 的参数**）；**拆卸前须通过空间预检：返还装不下则整个拆卸被拒绝**（裁决 17）（R10，核心 D8；实例语义见 §5.3） |
| 承载镶嵌 | 由本系统**发起**模块的镶嵌 / 拆卸调用（`PoolService.socket()` / `unsocket()`）——**池子数据的唯一写入方仍是 `PoolService`**，本系统只是**工具路径**（§3 / §5.6 / §8）；**v0.16 起它还多一层身份：镶嵌的硬门槛**（§5.7 / §1） |
| 品质梯度 | 作为内容释放载体之一（R11 / D13），高阶装置由里程碑任务释放 |
| 归因条目 | 每个已装配装置应有可读的归因 / 展示条目（P2）；**装置自身在 ρ 里的贡献度量随效果族作废而待定**（§11 04-L） |

**服务循环的哪一步：** "使用物品"（核心 §1.1）——装置是"同一份物品，用掉还是留下当工具"里的**留下**；**v0.16 起它同时是"开盒"这一步的前置条件**（没有设备 ⇒ 循环的第一步就走不动）。

### 1.1 开局状态：必须已有一台基础装置（★ v0.16）

- **开局发放**：**新游戏初始化时，玩家必须已经持有一台基础装置**——**品质 1 的基础款**。**形态完全沿用本文件既有的装置定义**（§4 的 `DeviceDef` / `DeviceCost` / `DeviceCondition` / `DeviceLoadout`，**不新增任何字段、不新增机制**）；`[补充]` **它是一件普通的内容配置装置（`.tres`）**，本文只写死"**开局必须已有一件这样的装置**"——**它的 `id` / `display_name` / `cost` / `condition` / `tags` 的具体取值由内容配置给出，本条不发明任何数值**（R11：新增装置必须能纯配置产出，§5.5）。
- **为什么必须是"开局就有"**：设备是**硬门槛**（§5.7）⇒ 没有设备就**既不能开盒也不能装模块**；而设备由物品制造、物品来自开盒 ⇒ **不发这一台就是开局死锁**（§1 / `01-gacha.md` §5.10）。
- **归属（本系统只定义，不发放、不落盘）**：**装置的定义归本系统**；**发放（初始化时把它交给玩家）与落盘不归本系统**。⚠️ **交付路径在现有文档中尚未统一**：`01-gacha.md` §5.10 写"**发放与落盘归 03 / 10**"，而 `03-task.md` §8 写"**03 只发盒子、不发设备（设备归 04 / 10）**"，`10-progression.md` §11 **Q20** 登记了**存档目前没有任何装置条目**（是否新增 `devices` 块、`schema_version` 是否递增、载入缺设备时"报错"还是"补发"——**三项待裁**）。⇒ **本条只写死"开局必须已有一台基础装置"这一事实，交付路径不作单方面指定**；本系统**不实现发放、不落盘、不持装置清单**。
- **这一台够用，且是"可回滚的默认"**：**设备是通用耐用工具**——**不绑定盒子、不限制服务次数、不消耗、不损耗**（核心 §15 **D21 已裁决**）⇒ **开局那台永远够用、死锁被消除**；回滚路径 = 判定入口改为带 `box_id` 的形式（§11 **04-M** / **04-N**）。
- **教学含义（只登记，节奏归核心 §11）**：**开局就有一台** ⇒ 装置**在教学第一步就必须被展示**（否则玩家根本开不了盒），**不再是"30 min 才引入的可选配件"**。

## 2. 不负责什么（边界）

| 不属于本系统 | 归属 |
|---|---|
| 任务需求向量（`TaskDef`）的结构与匹配 | 见 `03-task.md` |
| ρ / M̄ / D̄ / B / σ 的**计算口径**与归因汇总 | 见 `07-economy-rho.md` |
| **池子数据**（某个盒子的池子状态、镶嵌位、排除 / 提升 / 损耗）——本系统只**发起**镶嵌调用 | 见 `05-module-pool.md`（`PoolService` 是**唯一写入方**；没有"该套系的池子"这个对象） |
| 物品的类别 / 品质定义、**持有量（派生值）与物品实例列表** | 见 `02-item.md`（`ItemService` 是实例列表的**唯一写入方**） |
| 六面板渲染、展开入口、实时联动 | 见 `08-ui-panels.md` |
| **槽位数的语义与存废**（原为随 `series_quality` 取值；该项随 D4 作废而悬空，**语义待重定义**） | 见 `01-gacha.md`（`SeriesDef` 归属）；本文只读并冻结注入值。**待裁项 = 核心 §15 D22 / §11 04-O** |
| 里程碑解锁的发放逻辑 | 见 `10-progression.md`（本文只消费 `unlock_flag`） |

**硬边界：** 本系统**不写池子数据**——`PoolService.socket()`（05）是池子数据的**唯一写入方**，本系统只是**触发 / 承载镶嵌动作的工具路径**（§3 术语纪律 / §8 铁律 7）。装置**永不**触碰概率与抽取，也**不读**池子（原"只读池子、仅用于 `cross_end` 判定"随 `cross_end` 作废，见 §5.4 / 核心 §16.10）。

**★ v0.16 追加：设备不写任何池子数据、不参与抽样——它只作为前置条件**（§5.7）。`roll(evaluation, seed)` 的签名与入参、`PoolState` 的写入权、`EvalService` 的分工**一字不动**：**设备不进 `PoolState`、不进 `EvalResult`、不参与抽样**，也不改变任何概率。**无设备时两侧入口被拒绝，是"校验"，不是"设备参与了逻辑"。**

## 3. 核心概念与术语

术语一律使用 `README.md` §5 的中文名 + 代码名，不自造同义词。

| 中文名 | 代码名 | 本文用法 |
|---|---|---|
| 装置 | `Device` | **开盒与装模块的前置条件 / 入口工具**（**v0.16 硬门槛：没有设备，既不能开盒也不能装模块**，§1 / §5.7）。一件可装配的**装模块工具**（**不再有"作用端"**） |
| 槽位 | `device_slot` | 数量为**每套系常量**：注入后冻结、同一套系内恒定、运行时不可变（**语义待重定义**——核心 §15 **D22** / §11 **04-O**；v0.6 起不再固定为 4） |
| 镶嵌 | `socket` | 把模块写进**某个盒子**的第 `slot` 位——**动作由本系统发起，数据写入归 `PoolService`**（§5.6 / §8） |
| 引擎 | `engine` | 物品出口之一：装配为装置 / 模块 |
| 物品 | `Item` | 装置素材来源（消耗规则见 §5.5） |
| **物品实例** | `ItemInstance` | 装配时被**销毁**的那个物品个体；拆卸返还时**新建**（见 §5.3）；实例列表归 02 |
| **实例 id** | `instance_id` | **UUIDv4，全局唯一**；装配消耗按它指定实例，**返还实例的 UUID 全新**（原实例已销毁，不可恢复） |
| **收藏编号** | `serial` | **返还实例一律 `serial = 0`**——上游裁决：只有开盒产出才分配收藏编号；**它是实例字段，不是 `grant` 的参数**，由 02 内部置位（§5.3） |
| **物品品质** | `quality` | 1–5 序数，见 `02-item.md`；`DeviceDef.cost[].quality` 用的是它 |
| **套系品质** | `series_quality` | 核心 §4.1.1 的套系分级，决定镶嵌位数（`05`）与常规物品数；由里程碑解锁。**原"决定装置槽位数"已作废**（§11 D4） |
| **池子** / 池子状态 | `Pool` / `PoolState` | **某一个盒子**的池子当前状态（= 该盒 `Box.item_pool` + `Box.modules` 的派生结果，**不入档**）；本系统**不读、不写、不缓存** |
| 闭环收益率 | `rho` / ρ | 装置**自身不再直接进入 ρ**（效果族作废）；其影响只经"镶嵌的模块"间接体现，口径见 `07` |

**术语纪律 —— "品质"有两个含义，本文必须分辨：** **物品品质** = `quality`（1–5 序数，见 `02-item.md`）；**套系品质** = `series_quality`（核心 §4.1.1）。本文出现装置的**"品质梯度"**（§1 / §5.5 / D13 / R11）时，指的是**后者所在的这套品质体系**——"按品质梯度释放内容"的节奏，**不是**物品等级：装置自身的档位是 `DeviceDef.quality`（4 档枚举），`DeviceDef.cost[].quality` 才是物品品质。

**术语纪律 —— 镶嵌动作归设备系统触发、数据写入归 `PoolService`：** 本系统是**镶嵌 / 拆卸模块动作的发起方**（工具路径），`PoolService.socket()` / `unsocket()`（05 §4）是**池子数据的唯一写入方**。因此本系统**不构造池子读写路径**、**不缓存池子状态**、**不求值概率 / 占比**；发起调用时必须显式给出 `box_id`（动作作用在**某一个盒子**上），但本系统**不持有**任何池子快照。（原纪律"读池子必须带 `box_id`、装配时求值一次并冻结"服务于 `cross_end`，**已随之作废**。）

**已作废名词（一句话）：** `convert_end`（作用端）／ `apply_end` ／ `CrossEndCondition` / `cross_end` ／ `DeviceEffect` ／ `get_modifiers()` ／ `get_loss_reduction_pp()` ／ `DeviceLoadout.cross_end_frozen` ——**转化端机制的名词整族作废**（核心 §16.10）。`DeviceLoadout` 作为**旧"修正载荷"容器**的含义随之作废，**暂时只表示"每套系的槽位状态"**（名称暂留的理由见 §4）。

**两套位次体系相互独立：** 装置占 `device_slot`（**每套系**常量，本文），模块占 `socket_slot`（数量 = **该盒的** `Box.item_pool.socket_count`——该盒获得时从 `SeriesDef.socket_count` **冻结进这个盒子**、**同一池（盒）内恒定**，见 `05-module-pool.md`）。二者互不占用、互不换算、互不提供扩容接口；装置**不能**被镶嵌进池子，模块**不能**被装入装置槽位（README §3 铁律 4 / 核心 §16.5 C4）。

**新增字段说明：** 本文出现 `[补充]` 标记的字段均为核心文档已命名能力在 GDScript 层的落地形状，**不引入新机制**；**装置的效果族（作用端 / 目标 / 强度）已作废**，其替代形状未裁决（§11 04-L），本轮不发明。

## 5. 规则与公式

### 5.1 效果语义与系数方向【已作废】

原四类 `EffectType`（降 `D̄` / 提 `B` / 降转化损耗 / 降需求品质下限）、`coefficient` 单位与合法 `TargetScope` **整族作废**：它们**全部是转化端修正**，而装置已退出转化端（核心 §16.10）——装置不再输出任何修正量。**替代形状未裁决（§11 04-L），不得以任何形式复活。**

### 5.2 叠加规则【已作废】

随 §5.1 一并作废：相加 / 同组取最大 / 汇总 `clamp` 都是为**效果族封顶**而设的机制（P7 的功率封顶推论），装置不再有效果可叠 ⇒ **失去对象**。§6 中对应的上限旋钮一并作废。

### 5.3 装配与拆卸（可逆但昂贵，D8 / R10）

**v0.8：装配与拆卸作用的对象是「物品实例」，不是「计数」**——这是本系统在物品实例化模型下唯一改变的形态，**数值规则（50% / 逐条 `floor`）一字不动**。

```
装配：校验（槽位 / 解锁 / 互斥 / 条件）
      → 挑选实例：按 cost 逐条在 (category, quality) 命中集内挑 amount 个实例
        （挑选顺序沿用 02/03 的精神：最低合格品质优先，同品质内 acquired_at 升序）
      → ItemService.consume(instance_ids, &"engine")   # 销毁实例，**原子：全有或全无**
      → 写入该槽位 → 槽位状态更新并落盘（归 10）；架上面板刷新（P2）
        # 装配只消耗、不产出 ⇒ **不做空间预检**（核心 §4.7 边界 2）
        # ★ v0.15：原"触发 07 重算 → 归因与 ρ 刷新"半句已作废——装置不再给 07 提供修正量

拆卸：校验槽位非空 → 按 cost 逐条计算返还量 floor(amount × 0.5)
      → ★ **空间预检（在事务之前，先查再动）**：Σ(返还实例的 ItemDef.size) ≤ 仓库剩余空间？
          ├─ 否 → **拒绝整个拆卸操作**：返回失败 + 可读错误（还缺多少空间）
          │       ★ 拆卸不执行——槽位不变、**原实例不销毁**、**不创建任何返还实例**（逐项不变）
          └─ 是 → 继续
      → item_id = ItemService.resolve_item_id(category, quality)   # ★ 反查接口归 02，不得自己拼字符串
      → ItemService.grant(item_id, { kind = &"refund" })            # ★ 新建实例，新 UUID
        # ★ serial 不是 grant 的参数：第三位是幂等键 instance_id；返还实例的 serial = 0 由 02 内部置位
      → 槽位置 null → 面板刷新

替换：**一次 ItemService.transact() 调用**（02 提供的单次事务原语）内 = 拆卸（含 50% 返还）+ 装配，
      ★ 空间预检同样放在**事务之前**：返还装不下则**整体拒绝**，槽位与实例列表逐项不变；
      不是"多次 consume / grant 调用拼起来"；任一失败则物品侧事务整体回滚
      （**回滚必须撤销本次已创建的全部返还实例**：数量与实例列表逐项回到事务前）
```

- **返还率 50% 是全局常量**（核心 D8），不可被配置或装置修改，也不提供上调接口。
- **消耗是销毁实例**：装配消耗经 `ItemService.consume(instance_ids)` 落地，**不做任何 `count -= n` 的计数扣减**；实例列表的唯一写入方是 02（README §2.1），装置只发起请求。
- **原子性**：一次装配的全部 `DeviceCost` 条目必须在**同一事务**内全部成功；任一条目实例不足即**整体失败、实例列表完全不变**（对应 02 的 R-M6 原子扣减）。因为一次装配涉及**多次实例销毁**（替换则还叠加多次实例创建），**失败面比计数模型更大**，所以"同一事务"是硬要求而非实现细节。
- **⚠️ 返还的是新实例，不是原实例——原实例在装配时已销毁。**
  - "返还 50%" 在实例模型下**不是把实例改回来**，而是**创建新实例**：`ItemService.grant(item_id, { kind = &"refund" })`，**UUID 全新**；
  - **⚠️ `serial` 不是 `grant` 的参数**：正确签名是 `grant(item_id: StringName, source: Dictionary = {}, instance_id: String = "")`（02 §4.3）——第三位是**幂等键 `instance_id`**，**不是 `serial`**。把 `serial = 0` 写进第三位，会让**所有拆卸返还共享同一个幂等键 `0`**，于是**第二次返还起被幂等逻辑吞掉，玩家只拿得回一次**——**这是会直接吃掉玩家资产的 bug，本文档禁止出现这种写法**；
  - **`source` 是开放字典、`kind` 必填**（核心 v0.9）：返还写 `source = { kind = &"refund" }`；**不得把 `value` 直接写成一个 `StringName`**（旧写法把 `source` 当成字符串传，类型错误——`source` 的合法类型是 `Dictionary`）。`serial = 0` 由 02 按"非开盒来源"**内部置位**（02 §5.6），装置侧**不传、不写、不参与**；
  - **原 `instance_id` 不可能恢复**——它已在装配时被销毁，且核心 §4.2.2 明确"已消耗的实例不保留历史"（只持久化现存实例）；
  - **`serial = 0`**（上游裁决：**只有开盒产出才分配收藏编号**）。返还实例在叙事上**不等于"你原来那一个"**，也不占用收藏编号序列；
  - 因此"返还 50%"是**数量意义上的 50%**，不是**个体意义上的复原**；数量规则**不变**，仍按**原有的逐条 `floor(amount × 0.5)`**（见下条）。
- **返还的 `item_id` 一律经 02 的 `resolve_item_id(category, quality)` 反查**（上游裁决 9）：装配成本是两维需求（**`DeviceCost` 保持两维**，裁决 5），而返还必须落到具体 `item_id`；**该映射的唯一性由配置校验器强制**（一个 `(category, quality)` 只允许对应一个 `item_id`，配置期不合法即报错）。装置侧**不得**自己构造 id 字符串（不得拼 `"<category>_<quality>"`），也**不得**从已销毁的实例读回 `item_id`——反查接口归 02，装置只调用（§11 / **04-F**）。
- **⚠️ 拆卸返还装不下 → 拒绝整个拆卸操作**（上游**裁决 17**）：产出溢出按**操作性质**分叉——
  - **被动产出（开盒）**：放不下 → **进邮件**（`location = mail`，产出永不丢失，核心 §4.7）；
  - **主动操作（转化 / 拆卸返还）**：放不下 → **拒绝整个操作**。理由是**主动操作不能反噬**：它销毁源实例腾出空间，产出的新实例却进邮件，就变成**净损失可用持有**，与"转化是燃料路径的预处理"的立意直接冲突；拆卸同理——玩家主动拆，返还却进邮件，等于**拆了个寂寞**。
  - **因此拆卸必须做空间预检，且预检在事务之前**（**先查再动**）：`Σ(返还实例的 ItemDef.size) > 仓库剩余空间` ⇒ **返回失败**并给出可读错误（缺多少空间），**槽位不变、原实例不销毁、不创建任何返还实例**（逐项不变）。**禁止"先销毁 / 先 `grant`，发现放不下再靠回滚"**——那会让玩家在一次被拒绝的操作里看到自己的东西消失过。
  - **装配侧仍不做空间预检**：它只消耗不产出（核心 §4.7 边界 2），不会因仓库满而失败。
- **邮件实例不可用于装配**（核心 §4.7 边界 1 / §14.2 铁律 9）：`count()` 只统计 `location == warehouse` 的实例，**邮件里的实例不是可用持有**，不可用于装配装置；因此挑选天然只落在仓库内实例上。**这是 02 的口径**——装置侧**不得自行读 `location` 或自行统计**（那会造出第二个事实来源）。**守恒口径以全部实例（含邮件）为准**（裁决 12）：`count()` 只是**带 `location` 过滤的查询**，**不得**把它写进任何守恒等式（"仓库 Σcount == 差值"这类写法是错的）。
- **消耗类操作不检查空间**（核心 §4.7 边界 2）：装配只消耗不产出，不因仓库满而失败；**装置侧唯一的空间分支就是拆卸的返还预检**（见上条），装配路径**不实现"空间不足"分支**。
- **不承诺跨系统原子性**（裁决 13）：`ItemService.transact()` **只覆盖物品侧**（实例的销毁与创建），**不**包含槽位等装置侧状态，也**不**跨 04 / 05 组事务。装置侧状态在物品事务成功后写入；其后的失败由装置侧自行回退或自愈，**不得**要求物品侧回滚（本文档任何"跨系统回滚"的说法都以此为准）。
- **逐条向下取整**：每 `DeviceCost` 条目返还 `floor(amount * 0.5)`，余数**不**累加到其它条目——保证返还量只与消耗量有关，与操作顺序无关（守恒可测，见 T2）。`[补充]` 取整与"替换 = 单事务"核心只规定"可拆、返还 50%"，此处补落地细节以保证确定性。
- 拆卸**不会**降低装置品质、不消耗额外费用；"昂贵"仅体现为 50% 净损失。
- 装配 / 拆卸 / 替换**都不改变**任何套系的槽位数；切换套系只是取用另一个套系的冻结值（见 T1 / T1b）。

### 5.4 跨端非线性组合（装置 × 模块）【整节作废】

**作废理由：装置退出转化端后，"装置在转化端 × 模块在开盒端"这个前提不成立**——装置不再产生任何 ρ 修正，也就**没有"两端相乘"可言**（核心 §16.10）。原节的 `CrossEndCondition` / `required_module_tag` / `min_pool_ratio` / `bonus_multiplier` / "装配时刻对指定盒子求值一次并冻结进 `DeviceLoadout`"**一并作废**（§4 / §11 04-H / 04-I）。**不得**据本节实现任何跨端加成、也不得为它读池子。

### 5.5 素材消耗与品质梯度

- 装置**只能**由物品装配而成：成本是 `cost` 向量（类别 + 品质 + 数量），在装配瞬间**销毁对应实例**（`ItemService.consume(instance_ids)`，原子，见 §5.3）；物品侧的状态变化见 `02-item.md`。**可消耗的只有仓库内实例**——邮件实例不参与挑选，也不计入 `count()`（§5.3 与核心 §4.7）。
- **实例化带来的形态差异只有一处**：装配**销毁实例**、拆卸**新建实例**（新 UUID、`serial = 0`）；**`cost` 的数值、返还率 50% 与逐条 `floor` 取整规则全部不变**。
- **品质梯度只改变量，不改变机制**：`COMMON → RARE → EPIC → MYTHIC` 的差异现在只体现在 `cost` 上；**原"体现在 `effects[].coefficient` 上、且效果类型集合完全相同"已随效果族作废**（§5.1 / §11 04-A）。
- **术语（见 §3）：** 本条与标题里的"品质梯度"指 `DeviceDef.quality` 与内容释放节奏，属 `series_quality` 所在的品质体系；`DeviceDef.cost[].quality` 才是物品品质 `quality`（1–5）。
- 新增装置**必须能纯配置产出**（写一个 `.tres` 即可，不改代码）——这是 R11 的核心对策，也是核心 §14.3 的硬要求。
- 高阶装置的 `unlock_flag` 由里程碑任务释放（见 `10-progression.md`），是 D13 节奏的载体之一。

### 5.6 镶嵌动作与寿命预算（★ v0.15 本轮唯一新增的实质规则）

- **动作的发起方是本系统，数据的写入方是 `PoolService`**：镶嵌由本系统发起 `PoolService.socket(state, box_id, module_id, slot)`（05 §4）；**`PoolService` 是池子数据的唯一写入方**，本系统只是**工具路径**（§3 术语纪律 / §8）。
- **每次成功镶嵌消耗该盒一次使用**：`Box.uses_remaining -= 1`（核心 §4.1 的**总寿命预算** `k`，按该盒所属套系品质在发放时初始化：**品质 1→10、2→15、3→20、4→25**，存活范围 **10–25**）。★ **别把预算与位数混成一个数**：**镶嵌位数仍是 `item_pool.socket_count` = 2/3/4/5**（随套系品质）——**预算远大于位数**（用户口径："盲盒的使用次数**远远超过**镶嵌的次数"）⇒ **装满镶嵌位烧不光预算**。
- **`unsocket` 不退还次数（现行规则，核心 §15 D20② 已裁决）**：**拆卸零成本**——不扣寿命，但**已消耗掉的那一次寿命不返还**（`uses_remaining` 逐项不变）；物品侧照旧**返还 50% 材料**。★ **"退还"（寿命次数）与"返还"（物品材料）是两件事，不得混写**。理由 = **配置是沉没成本**，与"**模块是消耗品、拆卸只返还 50% 材料、模块本体不回收**"**同一设计意图**（核心 §3.3 / §4.5 / §16.5）。
- **替换也是镶嵌 ⇒ "换掉谁"不再可以随意试错**：同一个盒子内**位数恒定、不能扩容** ⇒ **不存在"再装一个"这个选项，只有"换掉谁"**；而 **替换 = 拆卸 + 重新镶嵌** ⇒（拆卸不退那一次）**每替换一个位子额外 −1 `uses_remaining`**——**每次替换都要从该盒的寿命预算里再扣 1 次**，该位子历史累计花掉 **2 次**（原装 1 + 新装 1；再换一次即 3 次）。预算 10–25、位数 2–5 ⇒ **每个盒子大约能承受 5–20 次替换**，但**每换一次都更接近"归零即摧毁"**。因此 **`m` = 该盒历史累计的镶嵌次数（含替换），只在"从不替换"时才受位数封顶**（位数封的是**同时占用**的位子数）。
- **归零即摧毁**：`uses_remaining` 扣到 **0** ⇒ **该盒连同它的 `item_pool` 与 `modules` 立即被摧毁**（核心 §4.1 / §4.6；摧毁动作的执行方不在本系统，§2 边界）。
- **"次数归零 ⇒ 摧毁"这条规则本身仍然成立，哪怕这个盒子从未兑现过**：归零**只能由"镶嵌（含替换）+ 兑现累计到 0"触发**——**不是**靠"装满位子"（**从不替换时** `m` 才受位数封顶：那时 `m ≤ 2/3/4/5`，而 `k` = 10–25，**装满位子烧不光预算**）。★ **但"未开即毁"仍然可达**：**替换使 `m` 不再受位数封顶**（位数只封"同时占用"的位子数），**每替换一个位子额外 −1** ⇒ **反复替换可以把 `d = k − m` 一路压到 0**（预算 10–25、位数 2–5 ⇒ **每盒大约能承受 5–20 次替换**），盒子**从未兑现就被摧毁**。**这是设计上的真实决策风险，不是缺陷**。**不得**把它实现成"寿命不足，所以禁止镶嵌 / 替换"的**前置拦截**：预算是**配额**，不是**准入条件**（核心 §4.1.1 / §15 D20 的推荐实测路径）。
- **预算口径（与核心一致，本文不重述）**：`m + d == k`——装 `m` 个模块、开 `d` 次，**共用同一份预算**；`m = 0 ⇒ d = k`，`m = k ⇒ d = 0`。模块成本摊薄口径 `N̄ = M̄ − C/d`（`d = k − m`）归 `07` / 核心 §15 D17。★ **经济连带（只登记三句，本文不展开）**：①**不替换时 `m` 受位数封顶（`≤ 2/3/4/5`）⇒ 那时摊薄倍数是 `d = 8–20`**（品质 1 是 10−2、品质 4 是 25−5）；**替换越多 `d` 越小，`d = 0` 即"未开即毁"**（那时该盒已被摧毁、`C/d` 无定义）；②**D17 的标定基线位移更严重**——`C/d` 相比"预算 = 位数"的旧基线**又降了约 5 倍**，**若沿用 v0.10 的旧标定 ⇒ P7 唯一的跨池锚点实质归零**；③**`C/k` 与 `C/(k − m)` 的数值差距现在很小**（`k` = 10–25 vs `k − m` = 8–20，**同一量级**）——用哪一个对结论影响不大，但**口径必须唯一**（本文一律写 `C/d`）。
- **D20 的状态（本文不选边）**：**②已裁决 = 拆卸不退还** ⇒ 落地为**上文"`unsocket` 不退还次数"与"替换额外 −1"两条规则**（又见 §7 / §8 / §9 / T8 ④）；**③迁移中 `uses_remaining` 缺键取什么值仍待裁**（取 `0` ⇒ 老档盒子全部被摧毁；取品质初始值 ⇒ 白送寿命）——归 `10` 的 Q19 与核心 §15；**①** 摊薄口径已定为 `C/d`（见上条）。**本系统、测试与实现都不得自行选边 ③。**
- **寿命预算本身不在本系统**：`uses_remaining` 的字段定义、初始化与"归零摧毁"流程见核心 §4.1 / §4.6（执行方不在本系统，§2 边界）；本文只声明"镶嵌要花掉该盒一次使用"这一条**动作语义**。

### 5.7 设备硬门槛与无设备时的失败语义（★ v0.16 裁决）

- **硬门槛**：**没有设备，既不能开盒也不能装模块**——`GachaService.redeem()`（开盒 / 兑现）与 `PoolService.socket()`（镶嵌 / 装模块）**在链首先校验"已有一台设备"**（§1 / 核心 §4.4 / `01-gacha.md` §5.10）。
- **判定归本系统、执行者不变**：判定由本系统给出——`[补充]` **建议形状 `DeviceService.has_device() -> bool`**，**无参：持有至少一台即可**（与 `01` §5.10 的"判定无参"一致；核心 §15 **D21** 已裁决"通用 + 不消耗"）。`[补充]` 理由：核心只规定"无设备必须被拒绝"、未规定判定接口的形状，故给出最小形状以便落地——**不引入新机制、不新增字段**。**本系统不替代任何执行者**：开盒仍归 01、池子数据仍只由 05 写（§2）。
- **响亮拒绝（写死）**：无设备时**返回明确原因码 `no_device`**（与 `bad_rarity` 同级登记、并列交付 08 渲染）；**不得静默失败**、**不得**用"先扣后补"之类的实现（核心 §4.4 / `01` §5.10）。

| 被拒绝的入口 | 谁执行 | 结果 |
|---|---|---|
| `GachaService.redeem()`（开盒 / 兑现） | 01（本文只提供判定） | `ok == false` + `reason == &"no_device"` |
| `PoolService.socket()`（镶嵌 / 装模块） | 05（本文只提供判定） | `ok == false` + `reason == &"no_device"` |

- **原子且绝不消耗寿命（写死）**：被拒绝的那次调用**逐项不变**——**`uses_remaining` 连一次都不扣**、`item_pool` / `modules` 逐项不变、**实例列表逐项不变**、**存档断点上不留任何中间态**（与"校验失败不扣次数"同一条纪律）。
- **禁止的写法**：**不得**"先扣一次寿命再校验设备"、**不得**"扣了再补回来"、**不得**把无设备的调用静默当成已消耗。
- **这不是"拦截"**：门槛是**前置条件**（**没有工具就没法动手**），不是对玩家决策的防御性拒绝——**它与 §5.6 里被明文禁止的"寿命不足 ⇒ 禁止镶嵌"完全是两件事**：后者是**发明规则**，前者是**规则本身**。

## 7. 流程 / 状态机

```
                 equip(def, slot)                  unequip(slot) / replace
   ┌─────────┐ ──────────────────────▶ ┌───────────┐ ──────────────────▶ ┌─────────┐
   │  EMPTY  │                         │ EQUIPPED  │                      │ EMPTY   │
   └─────────┘ ◀────────────────────── └───────────┘ ◀────────────────── └─────────┘
                    拆卸（返还 50%）                    拆卸（返还 50%）
                              replace = unequip + equip（单事务）
```

| 状态 | 含义 | 可执行操作 |
|---|---|---|
| `EMPTY` | 槽位为空 | `equip` |
| `EQUIPPED` | 槽位有装置（**它的作用待定**，§11 04-L） | `unequip` / `replace` |

**每次状态迁移后必须更新的（P2）：**
1. 该套系槽位状态更新并落盘（归 10）；
2. 架上面板刷新（§9 / `08-ui-panels.md`）。
   ★ **原"每次迁移触发 `07` 重算 `D̄` / `B` / ρ、归因里写『装置 C02：−0.18（转化端·降 `D̄` 20%）』"已作废**——装置不再给 07 提供修正量（§16.10）；归因面板还剩什么条目见 §11 04-L。

**镶嵌 / 拆卸模块（模块侧动作，由本系统发起；§5.6）：**

```
前置：**已有一台设备**（硬门槛，§5.7）——无设备 ⇒ 本次调用被拒绝（`no_device`），**不进入下述任何一步**
镶嵌：PoolService.socket(state, box_id, module_id, slot) 成功
      → Box.uses_remaining -= 1
      → 归零（== 0）⇒ 该盒连同 item_pool / modules 立即被摧毁
             ⚠️ 归零由"镶嵌（**含替换**）+ 兑现累计到 0"触发：**装满位子烧不光预算**（10–25 ≫ 2/3/4/5），
                但**反复替换可以**（每替换一个位子额外 −1，§5.6）；**不得**实现成"寿命不足 ⇒ 禁止镶嵌 / 替换"的前置拦截
拆卸：PoolService.unsocket(state, box_id, slot)
      → **不退还**镶嵌时消耗的那一次（核心 §15 D20② 已裁决）：uses_remaining 逐项不变，只返还 50% 材料
替换：replace_device = 拆卸（不退还）+ 重新镶嵌 ⇒ **该位子净扣 1 次寿命**（该位子历史累计 2 次）
```

**开盒（`GachaService.redeem()`）走同一条前置**：**无设备 ⇒ `no_device`、不消耗那一次寿命**，盒子连同它的池子与 `modules` **原样留着**（落点归 01，本文只提供判定；`01-gacha.md` §5.10）——**即使盒子 `uses_remaining == 1`，被拒绝的兑现也不得把它摧毁**。

**池子数据的变化由 `PoolService` 负责**：模块镶嵌 / 拆卸改变**某一个盒子**的池子占比（**不影响同套系的其他盒子**），池子派生量的重算走 05 / 07 的既有链路（README §2.2）。本系统**不订阅池子事件、不缓存池子状态、不持有池子快照**（§3 术语纪律）。

```gdscript
func has_device() -> bool                         # ★ v0.16 硬门槛判定：无参（持有至少一台即可，核心 §15 D21）；false ⇒ 01 / 05 的入口返回 no_device（§5.7）
func slot_count() -> int                          # 返回本套系注入并冻结的槽位数（构造时取自 SeriesDef.device_slot_count），非全局常数
func get_loadout(series_id: StringName) -> DeviceLoadout   # [补充] 按套系取用其冻结的槽位配置；理由：槽位数是"每套系常量"，必须能按套系取值
func get_slots() -> Array[DeviceDef]              # 只读副本
func equip_device(def_id: StringName, slot_index: int) -> EquipResult
func unequip_device(slot_index: int) -> RefundResult
func replace_device(def_id: StringName, slot_index: int) -> EquipResult
                                                  # 替换 = 拆卸（返还 50%）+ 装配，一次 ItemService.transact()（§5.3）
                                                  # ★ v0.15：原 `box_id` 参数已删除——它是为 cross_end 求值而设的（§5.4）

# 镶嵌动作（由本系统发起，数据写入归 05；§5.6）
# → PoolService.socket(state, box_id, module_id, slot)   # 成功一次 ⇒ Box.uses_remaining -= 1
#                                                         # 归零 ⇒ 该盒连同 item_pool / modules 被摧毁
# → PoolService.unsocket(state, box_id, slot)             # 不退还那一次（核心 §15 D20② 已裁决）；替换 = 拆 + 装 ⇒ 再 −1
# 本系统不自建池子读写路径、不缓存池子状态（§3 术语纪律 / 铁律 7）
```

**铁律：** 槽位数量是**每套系常量**（README §3.4）；`equip_device` 的 `slot_index` 越界即返回失败，**不得**扩容，也不得因越界而"顺带"写入 `SeriesDef`。

**铁律（v0.8 实例化）：**
1. `equip_device` 的**实例销毁必须原子**——全部 `cost` 条目要么全成功，要么实例列表完全不变；
2. `unequip_device` 的返还**必须经 `ItemService.grant` 新建实例**——装置侧**不得**持有任何"原实例引用"，**不得**尝试复用或复原原 `instance_id`，**不得**自行生成 UUID（UUID 生成归 02）；
3. `replace_device` 必须是**一次 `ItemService.transact()` 调用**（02 提供的单次事务原语）——在同一事务内完成"拆卸（新建返还实例）+ 装配（销毁实例）"，**不得用多次 `consume` / `grant` 调用拼装**；任一失败**物品侧事务整体回滚**，包含撤销刚 `grant` 的返还实例（见 §5.3 与 T2）。**空间预检在事务之前**：返还装不下则**整体拒绝**（裁决 17）；
4. `unequip_device` 的**空间预检必须先于任何状态变更**——`Σ(返还实例的 ItemDef.size) > 仓库剩余空间` ⇒ 返回失败并给出可读错误，**槽位不变、原实例不销毁、不创建返还实例**；**禁止先销毁或先 `grant` 再靠回滚补救**（裁决 17）；
5. `get_slots()` / `get_loadout()` 等只读接口**不触碰实例列表**、不缓存池子状态。
6. **不承诺跨系统原子性**（裁决 13）：`transact()` **只覆盖物品侧**；装置侧槽位状态不在其中，**不得**要求物品事务覆盖它或让它回滚。
7. **★ v0.15：池子数据只能经 `PoolService` 写入。** 本系统的镶嵌 / 拆卸动作**只能**调用 `PoolService.socket()` / `unsocket()`（05 §4）——**不得**自建写池子的路径、**不得**直接改概率或 `Box.modules`、**不得**缓存池子状态 / 持有池子快照，也**不得**在别处复制一份"当前权重"。（原铁律 7 的"读池子必须带 `box_id`、装配时求值一次并冻结"服务于 `cross_end`，**已随之作废**。）
8. **★ v0.16：设备是硬门槛。** 无设备时**不得**放行 `redeem` / `socket`，**也不得**用"先扣寿命再补回来"的方式绕过（§5.7）；判定**无参**（**持有至少一台即可**，核心 §15 **D21**）；**本系统不持装置清单、不发放、不落盘**（§1.1）。
