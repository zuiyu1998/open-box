# 04 · 设备系统

- 上游：`../core-design.md` **v0.18（设备系统负责三件事：开启盲盒 / 镶嵌模块 / 设备升级；开盒消耗**原石**；§4.4 / §4.8 / §15 D23 / D24 / §16.13）**；更早沿革见核心 §16（§16.10 / §16.11 / §16.12）
- 依赖系统：`01-gacha.md`（**两个动作的执行者与唯一写入方**：`GachaService.redeem()` / `redeem_batch()`、`PoolService.socket()` / `unsocket()`；**开盒原石成本的基准 `SeriesDef.gem_cost` 归 01 的内容配置**）、`02-item.md`（**资源（货币类）的账**：原石余额的唯一写入方是 `ItemService`）、`10-progression.md`（**开局那台的发放事实 + 存档布局**）、`08-ui-panels.md`（呈现）
- 被依赖：`01-gacha.md`（本系统是"开盒 / 镶嵌"两个动作的**入口发起方**，并向它传入本次开盒的原石成本）、`08-ui-panels.md`（架上 / 原石读数 / 升级入口 / 各禁用态）、`10-progression.md`（设备 id 与等级事实）

> **v0.19 裁决（用户）：① 镶嵌模块需要消耗成本，**成本由模块的成本字段决定**（"模块有一个字段表示要消耗的**金币**数"）；② 该成本与"每次镶嵌 −1 寿命"**并列**；③ **拆卸什么都不返还**；④ **开局再发一笔金币**。**
> ⇒ **设备系统的三件事的成本现在是**：**开盒** = 该盒 1 次寿命 ＋ **原石**；**镶嵌（含替换）** = 该盒 1 次寿命 ＋ **该模块的 `gold_cost`（金币）**；**升级** = **原石**。
> - **★ 这是宪法级改动的落点**：**模块不再消耗任何物品** ⇒ **物品的唯一出口是"交付任务"**（核心 §3 / §16.14）——**旧口径"燃料还是引擎"已作废**（`04` 不是它的承载者，但**本文件不再写"模块素材 / 物品成本 / 返还 50% 材料"这类表述**）。
> - **原石管开盒 / 升级，金币管镶嵌**（两种资源各管一头）：**镶嵌不花原石、开盒不花金币**。
> - **拆卸不再产出任何实例** ⇒ **它也不再需要空间预检**（旧口径"返还 50% 材料、放不下则拒绝"整条作废，核心 §15 D8）。
>
> **v0.18 说明（原石与升级，仍在生效）**：①**开启盲盒需要原石**（与金币同级的资源）；②**设备可以升级** ⇒ 设备系统负责**三件事**：**① 开启盲盒**（**消耗该盒 1 次寿命 + 消耗原石**；**并受设备等级的套系门控**）；**② 镶嵌模块**（**v0.19：+ 消耗该模块的金币成本**）；**③ 设备升级**（消耗原石）。
> **与 v0.17 的关系（逐条，不得混读）**
> - **v0.17 的"只负责两件事"由本次裁决扩为三件**——升级是**新增的第三件**。★ **这不是把 v0.17 推翻**：v0.17 确立的是"**设备系统只做与设备相关的动作，不碰池子数据、不产修正量**"，本条**沿用**它。
> - **制造装置仍然删除**：**"升级"≠"制造"**——装置来源仍是**开局发放 / 缺键补发**这一条（§5.5 墓碑不变）。
> - **品质档位 / 条件 / 互斥 / 标签 / 解锁 / 归因条目仍然删除**。★ **`level`（设备等级）不是品质档位**：它是**设备的成长刻度**，只影响**①开盒的原石折扣 ②可开的套系品质上限**——**不碰镶嵌位数、不碰池子功率、不碰寿命数值**。
> - **红线一字不动**：**P7 / C4 的功率面**（镶嵌位恒为 `SeriesDef.socket_count`、同一池内不可扩容）**不受设备等级影响**；升级是**效率轴 + 准入轴**，不是功率轴。
> - **★ D21 的"可回滚的默认"被触发**：等级门控让"能不能开**这个**盒子"依赖**盒子**（它的套系品质）⇒ **判定入口从无参改带盒子上下文**（`has_device()` → `can_open(state, box)`）——**这正是 v0.16 预写的回滚点**（§5.6）。
> - **代价（已登记）**：①**开盒不再免费** ⇒ 原石成为**节奏闸门**（核心 §12 **R16**）；②**升级是"攒资源即可推进"的轴** ⇒ 它的准入是否需要**内容门控**仍待裁（§11 **04-R**）。

## 1. 这个系统负责什么

| 职责 | 内容 |
|---|---|
| **① 开启盲盒（入口）** | `DeviceService.redeem()` / `redeem_batch()`：**链首校验"有一台设备" + "该设备等级足以开这个盒子" + "原石够"** ⇒ 通过后**把本次成本交给 01** 并调用它的执行入口（§5.1 / §5.2 / §8）。**开盒的抽样、产出、寿命扣减仍全归 01** |
| **② 镶嵌模块（入口）** | `DeviceService.socket()` / `DeviceService.replace()`：校验"有一台设备" ＋ **金币够（该模块的 `gold_cost`）** ⇒ 调 `PoolService.socket()`（替换 = 先 `unsocket` 再 `socket`，§5.3）。**池子数据的写入归 01**；**镶嵌不受设备等级约束**；★ **v0.19：金币的扣除归 `02`**（`transact` 的 `currency` op，`kind = &"gold"`） |
| **③ 设备升级（新动作）** | `DeviceService.upgrade_device()`：**消耗原石**、等级 +1、上限 = 该装置的等级曲线长度（§5.4）。**升级不消耗设备本体**（D21 不变）、不产生任何实例 / 池子变更 |
| **硬门槛判定** | **两份判定、同一个数据源**：`has_device()`（无参，**镶嵌**用）与 `can_open(state, box)`（带盒子，**开盒**用；含等级门控）（§5.6 / §5.7） |
| **开局那台（内容 + id）** | `DeviceDef`（身份 + 展示 + **等级曲线**，§4）+ `STARTING_DEVICE_ID` + **开局那笔原石**（§1.2） |
| **不再有的职责** | **制造装置** ／ 品质档位 ／ 条件 ／ 互斥 ／ 标签 ／ 解锁 ／ 任何数值修正 ／ 归因条目 —— 逐条墓碑见 §5.5 |

**服务循环的哪一步：** 核心 §1.1 的"**开盲盒**"（本系统是它的入口，且**替它收原石**）与"**使用物品**"（镶嵌的入口）。**它本身不是出口**：核心 §3 的"引擎"出口**只剩模块**（§5.5）。

**它不是可选修正层：** 不产出任何量——`D̄` / `B` / ρ / `headline` / `attribution` 与它无关（`07-economy-rho.md` 那一侧只登记、不取数；**原石对闭环的影响在 `07` 登记，不在本系统的公式里**）。

### 1.1 开局状态之一：一台基础装置（保留 v0.16 / v0.17）

- **开局发放**：**新游戏初始化时，玩家必须已经持有一台基础装置**（核心 §4.4）。它是 `DeviceDef` 的一个实例（§4），**开局等级 = 1**（**等级 1 的曲线由内容配置给出**）。
- **开局那台的 `id` 常量（㉜）**：`STARTING_DEVICE_ID = &"dev_basic_q1"`（定义在 `src/devices/device_constants.gd`；**新游戏初始化路径读它，不在调用处硬编码字面量**）。★ id 里的 `q1` **只是命名**——**设备没有品质档位**（`DeviceDef.quality` 已删除，§5.5）；**等级 `level` 是另一回事**（§4）。
- **为什么必须开局就有**：设备是**硬门槛**（§5.7），而**装置没有第二个来源**（**制造已删除**）⇒ **不发放这一台，玩家就永远是 0 台**，于是**既不能开盒也不能装模块**。
- **★ 硬约束（切片必须测）**：**开局那台的等级 1 必须足以开切片里的那一个套系**（否则**开局直接死锁**：唯一的套系开不了、而升级又需要开盒产出）——见 §10 **T15 ③**。
- **归属（唯一口径，㉜；归属一律写成"层"）**：**`10`（新游戏初始化路径 + 存档层）负责写入"持有一台基础装置（含等级）"与"开局那笔原石"这两个事实，并负责落盘与读回**（`devices` / `resources` 入档；**缺键 ⇒ 补发**；**档存在但为空 ⇒ 报错拒绝载入**）；**`04` 只定义 `DeviceDef` / 等级曲线 / 开局那台的 `id` 常量，并提供三个入口**，**不发放、不写档、不持任何玩家状态**；**`01` 执行两个动作，并保留兜底校验**；**`02` 是原石余额的唯一写入方**；**`03` 只发原石（不涉及设备）**。

### 1.2 开局状态之二：两笔资源（★ v0.18 立原石 / v0.19 补金币）

- **开局必须同时发放资源**：**① 一笔原石**（否则**第一个盒子开不了** ⇒ 开局死锁：开盒要原石，而原石的来源是任务，任务又要先开盒产出物品）；**②★ v0.19：一笔金币**（否则**第一个模块装不上** ⇒ **中心机制的第一次体验被闸门挡住**——严格说不是死锁，但**教学上是不可接受的**）。
- **形态 = 资源（货币类）的余额**（归 `02`，§5.2 / §10）：**不入物品实例列表、不占仓库、不进邮件**。
- **数额由内容配置给出（🔧，切片标定）**，**硬约束**：**原石 ≥ 开第一个盒子所需**、**金币 ≥ 装第一个模块所需**（按开局设备等级 1 的折扣算）——见 §10 **T13 ③** / **T16**。
- **教学含义**：第 0–5 min 玩家的资源读数是"**一台设备 + 一笔原石 + 一笔金币 + 一个盒子**"（核心 §11 已改）。

## 3. 核心概念与术语

术语一律使用 `README.md` §5 的中文名 + 代码名，不自造同义词。

| 中文名 | 代码名 | 本文用法 |
|---|---|---|
| 装置 / 设备（运行态） | `Device` | 玩家持有的那一台：`device_id` + **`level`（等级）** |
| 装置定义（蓝图） | `DeviceDef` | 身份 + 展示 + **等级曲线 `levels`**（§4） |
| **原石** ★ | `gem` | **资源（货币类）**，与"金币"同级的一类东西；**开盒与升级的入场费**。**不是物品**：不占仓库、不进邮件、不分配 `serial`、不进物品守恒等式（§5.2 / §10） |
| **资源（货币类）** ★ | `Currency` / `CurrencyDef` | 无实例的持有：**一个计数器就是余额**；余额的账归 `02`（`ItemService` 唯一写入方） |
| **设备等级** ★ | `level` | 设备的成长刻度（1 起、连续、有上限）；**只影响**①开盒原石折扣 ②可开套系品质上限（§4 / §5.4） |
| **升级** ★ | `upgrade_device` | **消耗原石换一级**的动作（§5.4）——**不是制造**：装置本体不消耗、不可离开玩家（D21） |
| **原石成本** ★ | `gem_cost` | 本次开盒要花的原石：**基准（该盒套系）× 设备等级折扣**，一律 `floori`（§5.2） |
| 开盒（兑现） | `redeem` | **本系统的入口动作之一**：校验门槛 ⇒ 把成本交给 `01`（§5.1） |
| 镶嵌 | `socket` | 把模块写进**某个盒子**的第 `slot` 位——**动作由本系统发起，数据写入归 `PoolService`**（§5.3） |
| **替换** | `replace` | **替换 = 拆卸 + 重新镶嵌**——**本文件与核心 §3.3 的唯一定义**。★ **"装置替换"一词不得使用**（装置无槽位、不可装配） |
| 硬门槛 / 无设备 | `has_device()` / `no_device` | **镶嵌侧**的判定（无参）与原因码（§5.6 / §5.7） |
| **等级门控** ★ | `can_open()` / `device_level_low` | **开盒侧**的判定（带盒子）与原因码：该设备等级**开不了这个套系**（§5.6） |
| **原石不足** ★ | `currency_insufficient` | 原石余额 < 本次成本（开盒）或 < 升级价（升级）——**响亮拒绝**（§5.1 / §5.4） |
| 引擎 | `engine` | 物品出口之一：**制造模块**（**"造装置"仍不在出口里**，§5.5） |
| 套系品质 | `series_quality` | 决定**盒子的镶嵌位数**（`01`）与寿命预算（`01`）；**本系统只把它当作等级门控的比较对象**（§5.6） |

**术语纪律 —— "品质"有两个含义，本文必须分辨：** **物品品质 `quality`**（1–5 序数，`02-item.md`）与 **套系品质 `series_quality`**（核心 §4.1.1）。**设备侧现在有"等级 `level`"，它既不是物品品质、也不是套系品质、更不是已删除的"装置品质档位"**（§5.5）：等级是**设备的成长刻度**，其效果只有两条（§5.4）。

**术语纪律 —— 动作归本系统发起、数据写入归 `PoolService` / `ItemService`：** 本系统是**镶嵌动作的发起方**（工具路径），`PoolService.socket()` / `unsocket()`（`01`）是**池子数据的唯一写入方**；**原石的余额账归 `ItemService`（02）**，本系统**只发起扣减**、**不自行增减余额、不缓存余额**。

**位次体系只有一套：** **设备侧没有任何位子结构**（不绑定盒子、不限制次数，D21）⇒ 本文不涉及"两套位次"的对照。**盒子的镶嵌位** `socket_slot` = **该盒的** `Box.item_pool.socket_count`（该盒获得时从 `SeriesDef.socket_count` **冻结进这个盒子**、**同一池（盒）内恒定**，见 `01-gacha.md`）；**装置不能被镶嵌进池子**这条纪律不变（README §3 铁律 4）。

**已作废名词（一句话）：** `DeviceCost` ／ `DeviceCondition` ／ `DeviceEffect` ／ `stack_group` ／ `CrossEndCondition` ／ `cross_end` ／ `DeviceLoadout` ／ `device_slot_count` ／ `get_modifiers()` ／ `get_loss_reduction_pp()` ／ `device_loss_reduction` —— **整族已作废**（v0.15 作废效果族与跨端、v0.16 删除槽位、v0.17 删除成本 / 品质 / 条件 / 互斥 / 标签 / 解锁，逐条见 §5.5）。


## 5. 规则与公式

### 5.1 职责一：开启盲盒（入口 + 校验顺序）

- **入口签名（§8）**：`redeem(state, box, seed_override)` ／ `redeem_batch(state, boxes, k, seed_overrides)`。
- **★ 校验顺序（写死，不得调换）**——**全部在事务之前**，任一失败 ⇒ **响亮拒绝 + 逐项不变**（**不扣原石、不扣寿命、不推进 `draw_index`**）：

| # | 校验 | 失败原因码 |
|---|---|---|
| ① | **有一台设备**（§5.7） | `no_device` |
| ② | **该设备等级能开这个盒子**（该盒套系品质 ≤ 等级曲线的 `unlock_series_quality_max`，§5.6） | `device_level_low` |
| ③ | 01 的既有校验（盒子存在 / 寿命 > 0 / 套系可解析 / 分布自洽） | `box_not_found` / `uses_exhausted` / … |
| ④ | **原石余额 ≥ 本次成本**（§5.2） | `currency_insufficient` |

- **本系统只做"校验 + 计价 + 转发"**：它**不构造 `PoolEvaluation`**、**不调 `roll()`**、**不碰实例**、**不改 `uses_remaining`**、**不自行改原石余额**；**01 的职责链只多了一个入参（成本）**（§8 铁律 1）。
- **批量兑现 `redeem_batch`**：**先整批预校验**（含①②④：**等级按各自盒子的套系品质逐盒判定**、**原石按整批总成本判定**）⇒ 不通过则**整批拒绝**、一次寿命都不消耗；`k_batch` 的口径仍归 `01`。
- **纯函数层不动**：`roll(evaluation, seed)` 的签名与入参不因设备、也不因原石而变；**设备与原石都不进 `PoolState`、不进 `EvalResult`、不参与抽样**。

### 5.2 原石成本：口径、折扣与扣除边界

- **成本公式（唯一口径，整数）**：
  ```
  gem_cost(box, device) = floori( SeriesDef.gem_cost(该盒套系) × open_cost_bp(device.level) / 10000 )
  ```
  - **基准 `SeriesDef.gem_cost` 归 `01` 的套系内容配置**（按套系品质取值，🔧 标定）；
  - **折扣 `open_cost_bp` 归本系统的等级曲线**（§4）；
  - **一律 `floori`**（与 `02` / `06` 的取整纪律一致）；**结果恒 ≥ 0**（`open_cost_bp = 0` ⇒ **免费**，那是最高等级的合法取值）。
- **★ 原石扣除与实例产出必须同一次物品侧事务**：`01` 在提交段调用
  `ItemService.transact([{ op = &"currency", kind = &"gem", delta = -gem_cost }, { op = &"grant", … }])`
  （**抽中 `void` 时只有第一项**）⇒ **不存在"扣了原石却没给物品"的中间态**，也不存在"给了物品却没扣原石"。
  - **理由**：开盒是**付费动作**；付费动作的两半若分两次提交，任一半失败都会留下**玩家看得见的坏账**——这正是 `02` 设立 `transact()` 要防的形状（`02-item.md` §5.11）。
  - **寿命扣减排在事务成功之后**（`01` 的既有顺序：**校验失败不扣寿命**；跨系统原子性**不承诺**，README §3 铁律 12）。
- **余额的唯一写入方是 `02`**：本系统**不自行 `-=`**、**不缓存余额**；不足判定读 `ItemService.currency_balance(&"gem")`（只读）。
- **原石不是物品**：**不占仓库、不进邮件、无 `serial`、不进物品守恒等式**（守恒式只覆盖**物品实例**；资源的账由 `02` 单列）。

### 5.3 职责二：镶嵌模块（★ v0.19：成本 = 该模块的金币）

- **两种形态，都是"镶嵌"**：`socket(state, box_id, module_id, slot)`（空位）与 `replace(state, box_id, module_id, slot)`（**替换 = 拆卸 + 重新镶嵌**；本系统按序调 `PoolService.unsocket()` 与 `PoolService.socket()`，**不做隐式覆盖**）。
- **★ 成本（唯一口径）**：**该盒 1 次寿命（归 `01`）＋ 该模块的金币成本**（`ModuleDef.gold_cost`，**数额完全由模块的字段决定**）——**扣金币归 `02`**（一次 `transact([{ op = &"currency", kind = &"gold", delta = -gold_cost }])`；**与"扣寿命"并列，不是替代**）。
  - **校验链首**：**余额 ≥ `gold_cost`**，否则**响亮拒绝 `currency_insufficient`**（**不扣金币、不扣寿命、不改池子、不写 `modules`**）。
  - **替换也照付**：**替换 = 拆卸 + 重新镶嵌** ⇒ **再付一次新模块的金币 + 再扣 1 次寿命**；**旧模块的金币不返还**（§5.5 / 核心 §15 D8）。
- **★ v0.19：镶嵌不再消耗任何物品** ⇒ **`04` 侧不再有"模块素材 / 物品成本 / 制造消耗"这类路径**（旧口径已作废，核心 §16.14）。
- **单独拆卸（拆掉不装）不是本系统的动作** ⇒ **本系统不提供 `unsocket` 入口**：它的入口归 `01`，**不受设备门槛约束**（§5.8），**且现在什么都不返还**（无金币、无实例 ⇒ **也不需要空间预检**）。
- **本系统不构造池子读写路径、不缓存池子状态、不自行求值、不自行改余额**（`PoolService` 与 `ItemService` 各是唯一写入方）。
- **`box_id` 一律 `String`**；**镶嵌不花原石、也不看设备等级**（等级的两个效果都只作用于**开盒**，§5.4）。

### 5.4 职责三：设备升级（★ v0.18 新增）

- **入口**：`upgrade_device(state, device_id) -> { ok, reason }`（§8）——**一次调用升一级**。
- **价格**：`levels[level].upgrade_cost_gems`（**升到该级的价格**；等级 1 为 0）。**消耗的是原石**，经 `ItemService.transact([{ op = &"currency", kind = &"gem", delta = -price }])` **一次事务**扣除。
- **效果（升级后立刻生效，下一次开盒即用新档）**：①**`open_cost_bp` 生效** ⇒ 开盒的原石成本下降；②**`unlock_series_quality_max` 生效** ⇒ 能开的套系品质上限提高。
- **上限**：`level == levels.size()` ⇒ 拒绝 `device_max_level`（**没有"溢出升级"、没有第二套上限字段**）。
- **失败语义（写死）**：`no_device`（没有这台）/ `currency_insufficient`（原石不够，**余额与等级逐项不变**）/ `device_max_level`（已满级）。**失败一律不改任何状态**。
- **★ 升级不消耗设备本体**：D21 的"**不消耗、不损耗、不可离开玩家**"**原样成立**（升级只改 `level` 一个整数）——**"升级"与"制造"是两件事**（§5.5）。
- **升级不产生任何实例 / 池子 / 寿命变更**：**不发放物品、不改 `modules`、不改 `uses_remaining`**（它是**资源 → 准入/效率**的兑换）。
- **★ 与 P7 的关系（必须写清）**：升级**不是功率成长**——**它不增加镶嵌位数、不降低 40% 损耗、不提高寿命预算、不改池子功率**。它改变的是**开盒的价格**与**开盒的准入**。⇒ **P7 / C4 的功率面一字不动**；但"**攒原石就能升级**"仍是一条**非内容门控的推进轴**，其准入是否需要里程碑门控**仍待裁**（§11 **04-R**）。

| **`condition`（`DeviceCondition`）** | 条件门控的**客体**（镶嵌权限 / 成本）不存在（04-L 已关闭，§11） | **无人承担**。⚠️ **等级门控 ≠ 条件**：门控只比较"**该盒套系品质 vs 该设备等级的上限**"（§5.6），**不接受任务标签 / 已完成次数一类的条件** |

| **效果族残余**（`DeviceEffect` / `stack_group` / `cross_end` / `get_modifiers()` 一族） | v0.15 已作废（装置退出转化端）；**设备对镶嵌没有额外作用**（§11 **04-L** 已关闭） | **无人承担** |

### 5.6 两份判定：`has_device()` 与 `can_open()`（★ v0.18：回滚点被触发）

- **`has_device(state) -> bool`**（**无参**）：**"持有至少一台设备"**——**镶嵌侧**的判定（§5.3 的链首）。语义不变（D21）。
- **`can_open(state, box) -> bool`**（**带盒子**）：**"有一台设备，且它的等级能开这个盒子"**——**开盒侧**的判定。判定内容 = **存在一台设备，其 `unlock_series_quality_max(level) ≥ 该盒套系的 `series_quality``**（§5.1 ②）。
- **★ 这正是 D21 预写的回滚路径**：v0.16 把"通用 + 不绑定盒子"标为**可回滚的默认**，写明"**若将来改为'设备绑定盒子 / 有服务上限'，只需把判定入口改成带 `box_id` 的形式**"——**等级门控就是那种改动**（它让判定必须知道**是哪个盒子**）。⇒ **判定实现仍只有一处**（`DeviceService` 的两个查询函数，共用同一份 `devices` 数据）。
- **两份判定的数据源是同一份**：`state.devices`（`Array[Device]`）。**不得**在 UI 层或别处复制"有没有设备 / 等级够不够"的算术。
- **纯查询**：两个函数都无副作用、不写任何状态（T7）。
- **批量开盒**：`can_open` 对**每个盒子**分别判定（§5.1）；**不得**实现成"有一个能开的就放行整批"。

### 5.7 设备硬门槛与无设备时的失败语义

- **硬门槛**：**没有设备，既不能开盒也不能装模块**——本系统的三个入口**链首先校验"已有一台设备"**（§5.6）。
- **响亮拒绝（写死）**：`no_device`（与 `bad_rarity` 同级登记、并列交付 `08` 渲染）；**不得静默失败**、**不得**用"先扣后补"之类的实现。★ **v0.19：资源不足统一用一枚码 `currency_insufficient`**——**币种由动作决定**（**开盒 / 升级 ⇒ 原石 `gem`；镶嵌 ⇒ 金币 `gold`**）；**不再按币种各造一个码**（v0.18 的 `gem_insufficient` 是它的前身，已更名）。

| 被拒绝的入口 | 谁拒绝 | 结果 |
|---|---|---|
| `DeviceService.redeem()` / `redeem_batch()`（开盒 / 兑现） | **`04` 的入口**（`01` 侧用**同一枚码、同一份判定**兜底） | `ok == false` + `reason ∈ { &"no_device", &"device_level_low", &"gem_insufficient" }` |
| `DeviceService.socket()` / `replace()`（镶嵌 / 装模块） | **`04` 的入口**（`01` 侧同样兜底） | `ok == false` + `reason == &"no_device"` |
| `DeviceService.upgrade_device()`（升级） | **`04` 的入口**（无下层） | `ok == false` + `reason ∈ { &"no_device", &"gem_insufficient", &"device_max_level" }` |

- **原子且绝不消耗（写死）**：被拒绝的那次调用**逐项不变**——**原石余额连 1 点都不扣**、**`uses_remaining` 连一次都不扣**、`item_pool` / `modules` / **实例列表** / **设备等级**逐项不变、**存档断点上不留任何中间态**。
- **禁止的写法**：**不得**"先扣原石 / 先扣寿命再校验"、**不得**"扣了再补回来"、**不得**把被拒的调用静默当成已消费。
- **这不是"拦截"**：它们是**前置条件**（**没有工具就没法动手、付不起就不能买**），不是对玩家决策的防御性拒绝。

### 5.8 门槛与等级门控的范围：不得加宽、也不得挪作他用

- **"必须先有设备"只摆在「开盒」与「装模块」两个动作上**（v0.16 裁定⑪，沿用）。（写死这一句的理由：否则实现者很容易把门槛加宽成"**没有装置就什么都干不了**"。）
- **★ 等级门控只作用于「开盒」**：**镶嵌不因等级被拒**、**拆卸（`01` 侧）不因等级被拒**、**查看 / 试算（`08` 的沙盒）不因等级被拒**。
- **升级本身不受等级门控**（否则会形成"升不上去也开不了"的死结）：**只看原石够不够 + 是否满级**。
- **门槛与门控都不得挪用**：它们**不是**获取路径、**不是**难度旋钮、**不是**产出加成。

### 5.9 镶嵌的寿命语义归 `01`（本文只点名归属）

**每次成功镶嵌消耗该盒一次寿命、归零即摧毁、拆卸不退还那一次、替换额外多消耗一次**——这些都是 **盒子的规则**（核心 §4.1 / `01-gacha.md`）：**寿命的数值、不变式与三段式口径一律见 `01` 与核心，本文不复述**（README §2 引用纪律）。**开盒同样消耗该盒 1 次寿命**（`01`），**且现在还要多付原石**（§5.2）——**"寿命"与"原石"是两个独立的成本，不得混写**。

**本文只写死两条边界：**
1. **本系统的三个入口不得改变这些语义**——它们只做"校验 + 计价 + 转发"，**转发前后 `uses_remaining` / `item_pool` / `modules` / 实例列表逐项相等**（T11 ②；被拒绝时的"逐项不变"见 T9 ②）；
2. **寿命是配额、不是准入条件**：**不得**因为"寿命不足"而拒绝镶嵌 / 替换（那是发明规则；归零是**计数器**的事）。

### 5.10 资源的边界（★ v0.18 新增）

- **原石是"资源（货币类）"**（与金币同级的一类东西）：**一个计数器就是余额**，**没有实例、没有 UUID、没有 `serial`、没有 `location`**。
- **它不可用于**：交付任务（任务需求是**物品**向量）、镶嵌 / 替换（那些要**模块**）、转化（转化是**物品**之间的操作）、丢弃（丢弃只针对仓库实例）。
- **它的账归 `02`**：余额的唯一写入方是 `ItemService`（发放 = `grant_currency`，扣除 = `transact` 的 `currency` op）；**守恒等式（`02` §10.5）只覆盖物品实例**，资源**单列**，**不得**把资源混进物品计数。
- **本系统只消耗它**（开盒 + 升级），**发放归 `03` / `10`**（§2 边界 / §1.2）。

## 7. 流程 / 状态机

**本文件有效的流程是三个动作（开盒 / 镶嵌 / 升级），前两个都以"已有一台设备"为链首**：

```
开盒（兑现）：
  前置：① 有一台设备（否则 `no_device`）② 该设备等级能开这个盒子（否则 `device_level_low`）
        → 无设备 / 等级不足 ⇒ 本次调用被拒绝，**不进入下述任何一步**
  DeviceService.redeem(state, box, seed_override)          ← 本系统（校验 + 计价）
      → 算出 gem_cost（§5.2）→ 余额不足 ⇒ `currency_insufficient`（不扣任何东西）
      → GachaService.redeem(state, box, gem_cost, seed_override)   ← 01 执行：
            求该盒当前分布 → roll() → **一次 ItemService.transact([扣 gem_cost, grant 实例])**
            （抽中 void ⇒ 事务里只有"扣原石"这一项）→ 扣 1 次寿命（归零即摧毁该盒）
升级（设备自身）：
  DeviceService.upgrade_device(state, device_id)
      → 满级 ⇒ `device_max_level`；原石不足 ⇒ `currency_insufficient`
      → ItemService.transact([{ op = &"currency", kind = &"gem", delta = -price }])
      → device.level += 1（**新档立刻生效**：下一次开盒用新的折扣与准入）
镶嵌（装模块）：
  前置：**已有一台设备**（无设备 ⇒ `no_device`；**不看等级**）
  空位：DeviceService.socket(...) → PoolService.socket(state, box_id, module_id, slot)      ← 01 执行
  已占用：DeviceService.replace(...) → PoolService.unsocket(...) → PoolService.socket(...)   ← 01 执行
  ★ 镶嵌 **不消耗原石**（用户裁决）
拆卸（拆掉不装，**不经本系统**）：
  PoolService.unsocket(state, box_id, slot)                ← 01 的入口；**不受设备门槛、也不受等级门控**
```

**池子数据的变化由 `PoolService` 负责**；**原石余额的变化由 `ItemService` 负责**；本系统**不订阅事件、不缓存任何一份派生状态、不持有池子快照、不持有余额副本**（§3 术语纪律）。

**寿命与原石是两个独立的成本**（§5.9）：开盒 = `−1 寿命 − gem_cost 原石`；镶嵌 = `−1 寿命`；升级 = `−price 原石`。

```gdscript
func redeem(state: GameState, box: Box, seed_override: int = -1) -> GachaResult

## ★ 职责二：镶嵌模块 —— 校验（有设备）⇒ 转发 PoolService
func socket(state: GameState, box_id: String, module_id: StringName, slot: int) -> Dictionary
func replace(state: GameState, box_id: String, module_id: StringName, slot: int) -> Dictionary

# ⚠️ 本系统**不提供**：制造装置、装置侧位子的任何查询、单独拆卸的入口（归 01）、任何扩容路径。
```

**铁律：**
1. **本层只做"校验 + 计价 + 转发"**：不构造求值、不调 `roll()`、不写实例、不改寿命、**不改原石余额**；**`01` 的两层入口与 `PoolService` 的分工只多一个成本入参，其余一字不动**。
2. **池子数据只能经 `PoolService` 写入**；**原石余额只能经 `ItemService` 写入**。
3. **判定只有一处实现**（`has_device` / `can_open`，§5.6）：**不得**在 UI 层或别处复制"有没有设备 / 等级够不够 / 原石够不够"的算术。
4. **本系统不持玩家状态、不发放、不落盘**：`devices`（含 `level`）与原石余额的写入与存档归 `10` / `02`。
5. **不承诺跨系统原子性**（README §3 铁律 12）：**物品侧**（原石 + 实例）由 `ItemService.transact()` 保证；**寿命**在事务之后由 `01` 扣——**这三者的顺序写死在 §5.2**。
6. **设备是硬门槛**：无设备时**不得**放行 `redeem` / `socket`，**也不得**用"先扣再补"的方式绕过；**等级门控只作用于开盒**（§5.8）。
7. **升级不得触碰功率面**：**不得**让等级影响镶嵌位数、损耗率、寿命预算、池子权重（§5.4 / P7 / C4）。

| 测试者**攒着原石不开盒**，或反过来"**原石多到从不看余额**" | 原石闸门**过紧**或**过松**（R16）——前者让核心动作（开盒）被卡住，后者让闸门形同虚设 | 调 `SeriesDef.gem_cost` 与任务的原石奖励（**D24 的标定**）；**不得**用"降低开盒频率以外的手段"（如暗改概率）来补偿（P1） |
| 测试者**从不升级**（"不如多开一盒"） | 升级的**回本口径不成立**：升级价 vs 省下的原石 + 新准入的价值 | 先调 `upgrade_cost_gems` 与折扣曲线；**不得**给等级加功率奖励（那是重开 P7） |
| 测试者**抱怨"花了原石却抽到 `void`"** | 付费动作与"零价值结果"的情绪冲突（**这是 v0.18 的新风险**） | 走 **04-S**（§11）的处置：**保留"不丢失 / 可预期"的呈现**（事前下界提示 + 不把 `void` 说成失败，`09` 同载），**不得**因此取消 `void` 或暗改概率 |
| 实现里出现"装置品质 / 装置槽位 / 装置耐久 / 用原石买镶嵌位" | 死概念复活或越过 P7 红线（§5.5 / §8 铁律 7） | 按 **T12 / T14 ⑤** 断言之；**不得**用"删掉断言"来消 FAIL |
| 测试者问"设备怎么升级到能开 XX 套系"却找不到入口 | 升级入口埋太深（R12 同类） | 架上设备区直给入口 + 等级不足的置灰态直达升级（§9） |

| **04-P** ✅（**v0.17 已裁决**） | **"通用耐用"之后制造端还剩什么？** | **已裁决：制造端清零**（`DeviceCost` / 制造动作删除）；**v0.18 只加"升级"，不加"制造"** | `engine` 出口只剩模块 |
