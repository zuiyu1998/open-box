### 2.1 四条最容易打架的边界（重点）

| 争点 | 归属裁决 |
|---|---|
| **"池子的概率"归谁算？** | **状态**归 05（`PoolService` 是唯一写入方），**求值**归 07（`EvalService` 是唯一读出方）。01 只消费结果，自己不算。 |
| **盲盒封面那两个数字归谁算？** | **07 产出 `headline`**，08 只渲染。08 **不得**在 UI 层另算（核心文档 §6.4 的工程保证） |
| **"被排除的物品"在演出中由谁过滤？** | 05 提供池子状态，09 依状态过滤展示；**01 的 roll() 只按池子状态抽样，不做展示判断** |
| **`ItemDef` 归谁？** | **归 02**。v0.6 时它归 01，是因为那时它还叫"款"、属于池子概念；v0.7 合并后它承载 `category`/`quality`/`value`，**已是物品定义**。01 的 `SeriesDef` 只**引用** `ItemDef`，不定义它 |
| **物品实例列表归谁？** | **归 02**（`ItemService` 是唯一写入方）。03/04/05/06 只能经 `ItemService.consume/grant` 改它，**不得自行维护持有量副本** |
| **ρ 的定义归谁？** | 07 拥有定义与口径；03/04/05/06 只提供输入量，不得各自解释 ρ |

### 2.2 共享代码路径（跨系统铁律）

> `EvalService`（07）与 `GachaService`（01）**必须共享同一套池子求值路径**。
> "显示的分布"和"实际抽取用的分布"必须是同一份代码算出来的。这是 P1（一切可查可算）的工程保证，也是本作头号 bug 源。

## 3. 跨系统铁律（所有文档都必须遵守）

1. **纯函数**：`EvalService`、`GachaService` 不依赖节点，可在无头模式跑单测；给定 `(state, series, seed)` 输出完全确定。
2. **单一写入入口**：池子状态只允许 `PoolService` 改；**物品实例列表只允许 `ItemService` 改**（v0.8）；任务进度等各自也只有一个写入方。**任何系统都不得自行维护持有量副本。**
3. **单一计算源**：六个面板、试算、兑现对照全部共用 `EvalService`。
4. **常量不变量（v0.6 修订）**：镶嵌位数与装置槽位数是**每套系的常量**——从 `SeriesDef` 读取后运行时不可变，**不提供任何在同一套系内增加它们的接口**（P7）。不同套系可以不同，这是合法的内容成长轴。
5. **五条红线必须有回归测试守护**：
   - C1 常规物品概率和 + `void_prob` ≤ 98%
   - C2 排除损耗率符合配置（40% 蒸发）
   - C3 隐藏物品概率恒为 2%
   - C4 `pool_state.socket_count` 恒等于 `SeriesDef.socket_count`
   - **C6（v0.6 新增）任何合法 `PoolState` 下可产出常规物品数 ≥ 3**
6. **数据驱动**：新模块、新装置、新任务应可**纯配置产出**，不改代码（R11 的核心对策）。
7. **不得暗改概率**：任何"按玩家进度动态调权"的设计一律否决（P1）。
8. **物品实例不变量（v0.8，三条都必须有回归测试守护）**：
   - 每个实例必须带 `instance_id`（**UUIDv4**）；
   - **发放必须幂等**——同一 `instance_id` 重复发放**不得**产生第二个实例；
   - **`count` 一律为派生值**（由实例列表数出并缓存），**不得作为独立存储字段**。
   （核心 §14.2 铁律 8。Godot **没有**内置 UUID，`ResourceUID.create_id()` 返回的 `uid://` 串不是 UUID。）
9. **只持久化现存实例（v0.8）**：已消耗的实例不留历史——审计由开箱日志承担（它已记录 `seed` + `pool_snapshot`）。
   未遵守会让存档体积无谓膨胀：每实例约 120 B，5000 实例 ≈ 600 KB。
10. **仓库与邮件是同一实例列表的两个位置（v0.9，核心 §4.7 / 铁律 9）**：
    - **`count()` 只统计 `location == warehouse`**；邮件实例**不计入可用持有**，不可用于交付/装配/镶嵌/转化；
    - **领取只改 `location`**——不创建实例、不重分配 `serial`、不重跑幂等判定；
    - **被动产出（开盒）放不下 → 进邮件**；**主动操作（转化/拆卸返还）放不下 → 拒绝整个操作**（v0.9 裁决 17，理由：否则转化会反噬、净损失可用持有）；
    - **必须有"主动丢弃"路径**（裁决 16）——否则仓库满会形成死局：领不出邮件 → 交不了任务 → 拿不到盒子 → 仓库仍然满。
    - ★ **`kind` 与 `location` 是两件事，不得互相改写**（v0.9 裁决 18）：
      `kind` 是**来源事实**（`gacha`/`convert`/`refund`/`mail`/`migrate`/`unlock`），`location` 是**当前位置**（`warehouse`/`mail`）。
      **产出溢出只写 `location = mail`，绝不改写 `kind`**——否则"来自哪个盒子 / 哪次转化"会丢失，与 §4.7 的邮件溯源展示要求冲突。
      `&"mail"` 是**保留值**（语义为"从邮件直接发放，系统补偿类"），切片内无调用方。
    - ★ **领取是部分成功而非整体拒绝**（v0.9 裁决 19）：按 `acquired_at` 升序（同秒按 `instance_id` 字典序）逐件判定，"能领多少领多少"，返回实际领取清单。
      理由：邮件里的东西**已经是玩家的**（产出瞬间已建实例、已有 UUID 与 `serial`），领取只是搬家；整体拒绝等于"没地方放就什么都不给你"，把**空间问题变成惩罚**，反而放大 R14。
      代价：UI 必须回报"已领取 M / 还剩 K 件"，**不得**表述为"一键领完"。
    - ★ **容量变化绝不得把已入库实例挤出仓库**（v0.9）：否则"持有"会变成**可被回溯撤销**的量。
11. **守恒等式以"全部实例"为准（v0.9 裁决 12）**：`total_granted − total_consumed == Σ 全部实例`（**含邮件**）。
    `count()` 只是**带 `location` 过滤的查询**，**不得让位置概念污染守恒式**。
12. **不承诺跨系统原子性（v0.9 裁决 13）**：`transact()` 只覆盖**物品侧**；Box 发放与解锁各靠**自己的幂等键** + 重放恢复。
    **单人游戏不需要分布式事务。**

## 4. 文档模板

每份系统文档必须使用以下章节顺序与标题。

```markdown
# NN · 系统名

- 上游：`../core-design.md` **v0.9** ／ `README.md`
- 依赖系统：…
- 被依赖：…

## 1. 这个系统负责什么
## 2. 不负责什么（边界）
## 3. 核心概念与术语
## 4. 数据结构（GDScript Resource 字段定义）
## 5. 规则与公式
## 6. 参数表（推荐值 + 调参旋钮标记）
## 7. 流程 / 状态机
## 8. 与其它系统的接口
## 9. UI 需求
## 10. 测试点与验收标准
## 11. 待定项
```

**要求：**
- 篇幅 **150–600 行 markdown** 为常规区间。超过 600 行需在文首一句话说明理由。
  （篇幅区间修订历次记录：原定 150–300 → 上调至 400 → **600**。（历次：150–300 → 400 → 550 → 600）
   **上限是我拍的，内容才是有价值的**，故历次都是上调区间而非压缩文档。
  v0.9 的触发点很具体：`02-item.md` 承载整个持有模型 + 实例生命周期 + 仓库邮件，448 行时已顶到旧上限。
  真正要防的是空洞注水，不是篇幅。）
- 数据结构用真实 GDScript 字段定义（`@export`），能在 Godot 4.5 里直接用。
- 参数表必须标注**推荐值**，并用 🔧 标记哪些是**调参旋钮**。
- 测试点必须包含**红线测试**（§3.5）与**失败信号**。
- 中文写作，代码标识符用英文。
- **文件编码统一 UTF-8 无 BOM、纯 LF 换行**（已全库校验通过）。

### 4.1 新增机制的处理规则

> **不得发明 `../core-design.md` 中不存在的新机制。**

## 5. 术语表

**所有文档必须使用下列中文名 + 代码名，不得自造同义词。**

| 中文名 | 代码名 | 说明 |
|---|---|---|
| 盲盒 | `Box` | 可囤积、未兑现的抽取机会 |
| 套系 | `Series` | 一个独立概率池：8 常规 + 1 隐藏 |
| 物品 | `Item` | **既是池中的一个可产出物，也是你积累的资源**（两个概念已合并） |
| 物品定义 | `ItemDef` | 一种物品的静态属性：`item_id`/`display_name`/`category`/`quality`/`value`/`is_hidden`。**归属 02**（01 的 `SeriesDef` 只引用） |
| 物品实例 | `ItemInstance` | 玩家实际持有的**一个**物品。**每个实例一个 UUID**（v0.8） |
| 实例 id | `instance_id` | **UUIDv4，全局唯一**，兼作**幂等键**（v0.8） |
| 收藏编号 | `serial` | **该玩家开出的第 N 个此物品**（v0.8，收藏叙事） |
| 溯源 | `source` | 实例来自哪个盒子：`{ series_id, box_seed, draw_index }`（v0.8） |
| 持有量 | `count` | **派生值**：由实例列表数出并缓存，**不是存储字段**（v0.8）。**只统计仓库内实例**（v0.9） |
| 物品大小 | `ItemDef.size` | 该物品占仓库多少空间；**同种物品大小相同**（v0.9） |
| 仓库 | `warehouse` | 实例的一个**位置**，有容量上限（v0.9） |
| 仓库容量 | `warehouse_capacity` | **抽象单位**；UI 换算为**占比**显示（v0.9） |
| 邮件 | `mail` | 另一个**位置**：被动产出放不下时的去处。**无上限、不过期**（v0.9） |
| 位置 | `location` | `warehouse` / `mail`，实例的一个字段（v0.9） |
| 素材 | —（非术语） | **角色描述**，指"某物品被用作装置/模块的原料"，**与 `燃料`/`引擎` 同类**。不是独立的资源概念 |
| 池子 | `Pool` | 某套系当前的概率分布状态 |
| 池子状态 | `PoolState` | 基础权重 + 模块编辑结果 |
| 类别 | `category` | 物品的种类维度 |
| 品质 | `quality` | 物品的等级维度，1–5 序数 |
| 物品价值 | `ItemDef.value` | 该物品的 TVU 价值 v，EV 计算的输入 |
| 任务 | `Task` | 需求 + 奖励；分常规与里程碑 |
| 套系品质 | `series_quality` | 决定该套系的**常规物品数、镶嵌位数、装置槽位数、物品品质区间**。由里程碑任务解锁 |
| 模块 | `Module` | 作用于**开盒端**，占镶嵌位 |
| 装置 | `Device` | 作用于**转化端**，占装置槽位 |
| 镶嵌 | `socket` | 把模块放入镶嵌位的动作 |
| 镶嵌位 | `socket_slot` | **数量由套系品质决定；同一套系内恒定、运行时不可变**（v0.6：不再固定为 3） |
| 槽位 | `device_slot` | **数量由套系品质决定；同一套系内恒定**（v0.6：不再固定为 4） |
| 排除 | `ban` | 令某个物品概率归零 |
| 提升 | `boost` | 提高某个物品概率，增量从其他常规物品按比例扣除 |
| 损耗 | `loss` | 排除释放的概率中蒸发的部分（40%） |
| 回收 | `recover` | 挽回蒸发概率的操作（第二切片） |
| 燃料 | `fuel` | 物品出口之一：交付任务被消耗 |
| 引擎 | `engine` | 物品出口之一：装配为装置/模块 |
| 开盒端 | `open_end` | ρ 的因子之一：M̄ |
| 转化端 | `convert_end` | ρ 的因子之一：D̄ / B |
| 闭环收益率 | `rho` / ρ | `(M̄ / D̄) × B` |
| 期望 | `ev` | 单池当前数学期望 |

### 6.1 ⚠️ 待回改上游：C1 与 C2 的内部矛盾

**核心设计书 §5.2 存在一处内部矛盾：**

| 条目 | 原文 |
|---|---|
| **C1** | 常规款概率之和**恒为 98%** |
| **C2** | 排除释放的概率仅 60% 可回收，**40% 蒸发** |

若 40% 真的消失且抽取分布仍需归一，则 C1 不成立；若归一化把那 40% 摊回其他款，则**损耗完全失效**，D6 这个主旋钮形同虚设。

**裁决（已在 `05-module-pool.md` §5.4 与 `07-economy-rho.md` §5.4 落地）：**

> 蒸发的概率**不消失**，而是落为一个显式的零价值结果 **`void`**。
> 即 `Σ probs(常规) + void_prob + 0.02(隐藏) == 1.0`。
> **C1 措辞需从"恒为 98%"改为"≤ 98%，差额为 `void_prob`"。**

**影响范围**：`01-gacha.md`（抽取需处理 `void` 结果）、`09-presentation.md`（演出需呈现 `void`）、`08-ui-panels.md`（直方图需画出 `void` 柱）、`10-progression.md`（存档需记录 `void_mass`）。

> ✅ **已回改上游（v0.6）**：核心设计书已新增 **§5.6「空洞 void」** 给出正式定义，C1 措辞已修订为"常规款概率之和 + `void_prob` 恒为 98%"。
> 本节保留作为该缺陷的历史记录与论证过程。
> ✅ **v0.7 复核**：术语合并（物资与款 → 物品）不触及概率与 `void` 的任何规则，**本节结论仍然成立**——`void` 依然是显式零价值结果，`void_prob` 的归属与求值路径不变。
