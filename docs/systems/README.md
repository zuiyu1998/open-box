# 《Open Box》系统文档索引

- 上游文档：`../core-design.md`（核心设计书 **v0.13**）——**唯一事实来源**
- 本文档的作用：定义**系统清单、所有权边界、文档模板、术语表**
- 状态：**v0.13 对应版本**
- 契约版本：**本契约对应核心设计书 v0.13**
  - v0.13 变更：**去除隐藏款**——每个套系**不再有"1 个隐藏物品"**，池中**全部物品都是常规物品**、**全部物品共分 100%**：`p_i = rarity_i / Σ rarity`（v0.12 的加权方式不变，**只是不再留出隐藏款的那 2%**）。**红线 C3 作废**（原为"隐藏物品概率恒 2%、免疫一切池子编辑"——**保护对象不存在了**）：**C3 的行号保留、不重编号**，以免牵动全库对 C4 / C6 的引用。**C1 的零和式随之变更**：由"常规物品之和 + `void_prob` == 98%"变为"**物品之和 + `void_prob` 恒为 100%**"（整数口径 `Σ weights_bp + void_mass_bp == 10000`）。**代码已同步**：`ItemDef.is_hidden` 与 `ItemPool.hidden_item` / `HIDDEN_TOTAL_BP` **全部删除**。**连带影响**：①**R2（编辑太强 ⇒ 全收集失去挑战）风险上升**——对策只剩 C2（40% 损耗）与 C6（≥3 可产出）；②**R15（去除保底后尾部无界）大幅缓解**——不再有"最难、且无法被编辑影响"的那一款，残留风险 = "抬缺口**很贵**"；③**终局变成"纯工程"的事**——每一款都受编辑影响，不再有"最后一个隐藏物品保留不可预测性"。**不变**：C2 / C4 / C5 / C6、P1–P7、40% 损耗与零和、`void`、无保底（v0.11）、池子逐盒一份（v0.10）、`weights_bp` 的整数口径与 ρ 公式（核心 §5.4 / §5.6 / §10 / §12 R2·R15 / §16.8）
  - v0.12 变更：**物品池产生概率按 `rarity` 加权**——`ItemDef` 新增 **`rarity: int`**（**权重**：**数值越大越常见**，"越稀有"就写得越小；**必须 ≥ 1**，`0` = 永不产出 = 配置错误）；`p_i = rarity_i / Σ rarity`，**全部 `rarity` 相等时退化为 v0.11 的"均等"**；**基础权重表不再是独立配置**（`base_weights` 由 `rarity` 归一化**派生**，消灭第二份事实来源）。新增决策 **D19 各物品的稀有度配置**（核心 §4.1 / §5.1 / §15 D19 / §16.7）
  - v0.11 变更：**去除保底系统**——删除"连续 8 次未出新物品则硬保底"，**一次抽取的概率就是公布的那个分布、不存在任何"必出"覆盖**；删除保底计数器（`pity_counters` 不存在、不入档，**抽取无状态**）；`void` 不再推进任何计数器；`roll()` 缩短为 `roll(evaluation, seed)`；`SeriesDef` 无保底参数、`game_state` 无保底计数。**正面理由**：保底是唯一一处"公布概率 ≠ 每抽概率"的地方，删掉后 **P1 在每一次抽取上都严格成立**；**代价**见核心 **R15 / D18**（全收集尾部无界）——**v0.13 起已大幅缓解**（见上一行）。**规则与数值其余部分一律不变**（**C2 / C4 / C5 / C6**、P1–P7、40% 损耗与零和、池子逐盒一份、`weights_bp`）——**C1 的零和式与 C3 的口径已由 v0.13 另行变更，见上一行**（核心 §4.1 / §5.4 / §5.6 / §9 铁律 1 / §12 R15 / §15 D18 / §16.6）
  - v0.10 变更：**池子随盒子走 + 结构澄清**——`Box` 下面挂着**两个并列字段**：**`item_pool`（物品池，生成数据的凭证，`roll()` 消费它）** 与 **`modules`（模块列表，镶嵌在该盒上；模块的唯一作用方式就是更改 `item_pool` 的状态）**；**模块不折进池子**，**池子的当前状态是二者的函数**（`PoolService` 唯一求值/写入，`EvalService` 唯一求值成概率 / EV / ρ），且这份状态是**派生值、不入档**（逐盒重建；核心已否决 `PoolState.socketed` 这种"模块在池子里"的形状）；**镶嵌位数 = 该盒所属套系品质对应的位数，在同一池（盒）内恒定**（C4 只改措辞）；`headline` / 池子面板 / ρ 以**选中的那个盒子**为准；**P7 已改写**（单池功率仍封顶于 N），**跨池复制则由模块的物品成本约束（D17）**；新增 **D17 单个模块的物品成本**（核心 §4.1.2 / §6.1 / §7 / §16.5）
  - v0.9 变更：**仓库容量与邮件系统**——`ItemDef.size`、实例加 `location`、被动产出溢出进邮件、主动操作空间不足则拒绝（核心 §4.2 / §4.7）
  - v0.8 变更：**物品实例化**——每个物品持有 `instance_id`（UUIDv4），`count` 变为派生值（核心 §4.2.1–4.2.3）
  - v0.7 变更：**「物资」与「款」合并为「物品」**（代码 `Item`）——`MaterialDef` 被 `ItemDef` 吸收、`star` 合并为 `quality`、产出映射字段删除；文件 `02-material.md` 改名 `02-item.md`

### 2.1 九条最容易打架的边界（重点）

| 争点 | 归属裁决 |
|---|---|
| **"池子的概率"归谁算？** | **求值**归 07（`EvalService` 是**唯一读出方**）；**数据归属与写入权见下两行**。01 只消费结果，自己不算。 |
| **`Box` 下面的两份池子数据归谁？** | **归 01（那个盒子）**：**`item_pool`（物品池，生成数据的凭证）与 `modules`（模块列表）都挂在那个盒子上**，且是**两个并列字段**——**模块不折进池子**。**05 只拥有编辑它们的规则与写入权**（`PoolService` 是**唯一写入方**）。这与"07 的 `EvalService` 是唯一读出方"是同一套风格：**数据归属 与 写入权/读出权 是两件事**，**不得**混写成"05 拥有池子状态"。因此**同套系的两个盒子可以有完全不同的池子**（v0.10，核心 §4.1.2）。 |
| **"池子的当前状态"是什么、归谁？** | 它是**派生值**：`f(item_pool 的基础数据, 该盒 modules)`——**由 05 的 `PoolService` 推导**（再由 07 求值成概率 / EV / ρ），**不是一份可存储的数据**（**不入档**，载入时逐盒重建）。**任何系统都不得把它当第二个事实来源**落盘，也不得在缓存键里省掉 `box_id`（核心 §4.1.2 / §14.2）。 |
| **`headline` / 池子面板 / ρ 以哪个池子为准？** | **以"选中的那个盒子"为准**（`selected_box`）：**选中态由 08 维护**，其余系统只读、不得自行改变它。05/07 一律按调用方**显式传入的 `box_id`** 求值（如 `get_pool_state(state, box_id)` / `compute(state, box_id)`）——**不再存在"这套系的期望"这种说法**（v0.10，核心 §4.1.2 / §6.1）。 |
| **盲盒封面那两个数字归谁算？** | **07 产出 `headline`**，08 只渲染。08 **不得**在 UI 层另算（核心文档 §6.4 的工程保证） |
| **"被排除的物品"在演出中由谁过滤？** | 05 提供池子状态，09 依状态过滤展示；**01 的 roll() 只按池子状态抽样，不做展示判断** |
| **`ItemDef` 归谁？** | **归 02**。v0.6 时它归 01，是因为那时它还叫"款"、属于池子概念；v0.7 合并后它承载 `category`/`quality`/`value`，**已是物品定义**。01 的 `SeriesDef` 只**引用** `ItemDef`，不定义它 |
| **物品实例列表归谁？** | **归 02**（`ItemService` 是唯一写入方）。03/04/05/06 只能经 `ItemService.consume/grant` 改它，**不得自行维护持有量副本** |
| **ρ 的定义归谁？** | 07 拥有定义与口径；03/04/05/06 只提供输入量，不得各自解释 ρ |

### 2.2 共享代码路径（跨系统铁律）

> `EvalService`（07）与 `GachaService`（01）**必须共享同一套池子求值路径**。
> "显示的分布"和"实际抽取用的分布"必须是同一份代码算出来的。这是 P1（一切可查可算）的工程保证，也是本作头号 bug 源。

## 3. 跨系统铁律（所有文档都必须遵守）

1. **纯函数**：`EvalService`、`GachaService` 不依赖节点，可在无头模式跑单测；给定 `(state, series, seed)` 输出完全确定。
2. **单一写入入口**：池子状态只允许 `PoolService` 改；**物品实例列表只允许 `ItemService` 改**（v0.8）；任务进度等各自也只有一个写入方。**任何系统都不得自行维护持有量副本。**
3. **单一计算源**：六个面板、试算、兑现对照全部共用 `EvalService`。
4. **常量不变量（v0.10 修订）**：**镶嵌位数是每个池子的常量**——由**该盒所属套系品质**决定（2/3/4/5），从 `SeriesDef.socket_count` 冻结进**该盒的 `item_pool.socket_count`**，**运行时不可变**，**不提供任何在同一池（同一盒子）内增加它的接口**（P7）；**装置槽位数仍是每套系常量**（`SeriesDef.device_slot_count`，从 `SeriesDef` 读取后运行时不可变）。不同套系可以不同，这是合法的内容成长轴。
   （v0.6 的旧口径是"两者都是每套系常量"；v0.10 只改镶嵌位这一半的口径，**规则本身未变**——核心 §5.2 C4 / §16.5。）
5. **五条红线必须有回归测试守护**：
   - C1 **物品概率之和 + `void_prob` 恒为 100%**（整数口径 `Σ weights_bp + void_mass_bp == 10000`。v0.13：**不再留出隐藏款的 2%**。**断言侧**：回归断言若写浮点，写法是 `≤ 1.0` **并注明 1e-6 取整容差**——**`≤` 只是断言形式、不是 C1 的陈述**；**精确性一律由上面的整数形态断言**）
   - C2 排除损耗率符合配置（40% 蒸发）
   - C3 ~~隐藏物品概率恒为 2%~~ **【v0.13 作废】**——隐藏款设定整体删除、**保护对象不存在**（核心 §5.4 / §16.8）；**行号保留、不重编号**，以免牵动全库对 C4 / C6 的引用
   - C4 **该盒的** `item_pool.socket_count` 恒等于**该盒所属** `SeriesDef.socket_count`，且该盒 `modules` 的**项数 ≤ 它**（`modules` 是变长列表；v0.10 口径：数据是每盒一份，因此断言的是"该盒的池子数据 vs 该盒的套系"）
   - **C6（v0.6 新增）任何合法 `PoolState` 下可产出常规物品数 ≥ 3**
6. **数据驱动**：新模块、新装置、新任务应可**纯配置产出**，不改代码（R11 的核心对策）。
7. **不得暗改概率**：任何"按玩家进度动态调权"的设计一律否决（P1）。
8. **物品实例不变量（v0.8，三条都必须有回归测试守护）**：
   - 每个实例必须带 `instance_id`（**UUIDv4**）；
   - **发放必须幂等**——同一 `instance_id` 重复发放**不得**产生第二个实例；
   - **`count` 一律为派生值**（由实例列表数出并缓存），**不得作为独立存储字段**。
   （核心 §14.2 铁律 8。Godot **没有**内置 UUID，`ResourceUID.create_id()` 返回的 `uid://` 串不是 UUID。）
9. **只持久化现存实例（v0.8）**：已消耗的实例不留历史——审计由开箱日志承担（它已记录 `seed` + `pool_snapshot`）。
   未遵守会让存档体积无谓膨胀：每实例约 120 B，5000 实例 ≈ 600 KB。
10. **仓库与邮件是同一实例列表的两个位置（v0.9，核心 §4.7 / 铁律 9）**：
    - **`count()` 只统计 `location == warehouse`**；邮件实例**不计入可用持有**，不可用于交付/装配/镶嵌/转化；
    - **领取只改 `location`**——不创建实例、不重分配 `serial`、不重跑幂等判定；
    - **被动产出（开盒）放不下 → 进邮件**；**主动操作（转化/拆卸返还）放不下 → 拒绝整个操作**（v0.9 裁决 17，理由：否则转化会反噬、净损失可用持有）；
    - **必须有"主动丢弃"路径**（裁决 16）——否则仓库满会形成死局：领不出邮件 → 交不了任务 → 拿不到盒子 → 仓库仍然满。
    - ★ **`kind` 与 `location` 是两件事，不得互相改写**（v0.9 裁决 18）：
      `kind` 是**来源事实**（`gacha`/`convert`/`refund`/`mail`/`migrate`/`unlock`），`location` 是**当前位置**（`warehouse`/`mail`）。
      **产出溢出只写 `location = mail`，绝不改写 `kind`**——否则"来自哪个盒子 / 哪次转化"会丢失，与 §4.7 的邮件溯源展示要求冲突。
      `&"mail"` 是**保留值**（语义为"从邮件直接发放，系统补偿类"），切片内无调用方。
    - ★ **领取是部分成功而非整体拒绝**（v0.9 裁决 19）：按 `acquired_at` 升序（同秒按 `instance_id` 字典序）逐件判定，"能领多少领多少"，返回实际领取清单。
      理由：邮件里的东西**已经是玩家的**（产出瞬间已建实例、已有 UUID 与 `serial`），领取只是搬家；整体拒绝等于"没地方放就什么都不给你"，把**空间问题变成惩罚**，反而放大 R14。
      代价：UI 必须回报"已领取 M / 还剩 K 件"，**不得**表述为"一键领完"。
    - ★ **容量变化绝不得把已入库实例挤出仓库**（v0.9）：否则"持有"会变成**可被回溯撤销**的量。
11. **守恒等式以"全部实例"为准（v0.9 裁决 12）**：`total_granted − total_consumed == Σ 全部实例`（**含邮件**）。
    `count()` 只是**带 `location` 过滤的查询**，**不得让位置概念污染守恒式**。
12. **不承诺跨系统原子性（v0.9 裁决 13）**：`transact()` 只覆盖**物品侧**；Box 发放与解锁各靠**自己的幂等键** + 重放恢复。
    **单人游戏不需要分布式事务。**
13. **模块一旦镶嵌即锁定进该盒子（v0.10）**：镶嵌后模块**进入该盒的 `modules` 列表**、属于**那个盒子**，**不得移到别的盒子**；**该盒施工台随之清空**——**配置下一个盒子需要新的模块**。**拆卸只能从盒子上拆**（即从该盒的 `modules` 里移除那一项编辑；盒子未兑现时）；**兑现后盒子连同它的 `modules` 一同消耗**。
    因此"把同一套配置复制到另一个盒子"**必须重新支付模块的物品成本**——这是 P7 被改写后仅存的那条否决项（核心 §7 / §16.5，数值由 **D17** 标定）。
    **★ 裁决（v0.10）：模块是消耗品——不存在"模块库存"。** 拆卸**只返还 50% 材料**，**模块本体不回到库存、也不可能被搬到别的盒子**；**不提供任何"模块仓库 / 回收再用"的接口**。
    理由（保留推演）：若模块本体可回收再用，同一个模块就能在多个盒子上**轮流使用**——"配置 N 个盒子需要 N × 位数个模块"当场失效、**D17 被归零**，而 D17 是 P7 改写后**唯一的跨池锚点**。
14. **模块不折进池子（v0.10 结构澄清）**：`Box` 下面是**两个并列的数据**——**`item_pool`（物品池，生成数据的凭证，`roll()` 消费它）** 与 **`modules`（模块列表）**。
    **池子的当前状态是二者的函数**（「`item_pool` 的基础数据 + 该盒 `modules` 的编辑效果」）：由 **05 的 `PoolService` 唯一写入**（它由这两份数据**推导**出池子的当前权重）、由 **07 的 `EvalService` 唯一求值**（权重 → 概率 / EV / ρ）。**二者不得混写**。
    这份状态是**派生值、不入档**（载入时逐盒重建）——**存档里不得存在"编辑后的权重"这第二个事实来源**。
    **否决**任何"把模块塞进池子自己的字段里"的形状（含 `PoolState.socketed`）。"换掉一个模块" = 换掉**一项作用于该池的编辑**，而**不是**"在池子里挖掉一块再补上"；**模块列表可以独立于池子被查看、替换与拆卸**。
15. **盲盒没有保底——公布的概率就是每抽概率（v0.11 核心契约）**：**一次抽取的概率就是公布的分布本身，不存在任何"必出"覆盖**；**抽取无状态**（`roll(evaluation, seed)`，入参里没有计数器、没有跨次累计的状态）；**`void` 不产出物品、仅消耗一个盲盒，也不推进任何东西**。**P1 因此在每一次抽取上都严格成立**——池子编辑是概率的**唯一**决定者（v0.11 之前，保底是唯一一处"显示的概率 ≠ 实际每抽概率"的地方）。
    **否决**：任何以"**隐式必出**"（暗改某次的权重、看不见的加速、未公布的补偿）形式复活保底的做法；将来若要缓解全收集尾部（核心 **R15**），新机制**必须是可公布、可查的**（P1 / P6），并走核心 **D18** 的决策路径。

> 从路径上看不出任何归属信息——与本文档"每个系统只拥有自己的数据"的边界契约正好相反。
> **按系统组织让路径本身承载所有权信息**：看到 `src/items/` 就知道这一坨全归 02。

### 6.1 C1 与 C2 的内部矛盾（✅ **已回改上游，v0.6**——本节保留为历史记录）

**核心设计书 §5.2 存在一处内部矛盾：**

| 条目 | 原文 |
|---|---|
| **C1** | 常规款概率之和**恒为 98%** |
| **C2** | 排除释放的概率仅 60% 可回收，**40% 蒸发** |

若 40% 真的消失且抽取分布仍需归一，则 C1 不成立；若归一化把那 40% 摊回其他款，则**损耗完全失效**，D6 这个主旋钮形同虚设。

**裁决（已在 `05-module-pool.md` §5.4 与 `07-economy-rho.md` §5.4 落地）：**

> 蒸发的概率**不消失**，而是落为一个显式的零价值结果 **`void`**。
> 即 **物品概率之和 + `void_prob` 恒为 100%**（**v0.13 现行式**；隐藏款删除前此式是 `Σ probs(常规) + void_prob + 0.02(隐藏) == 1.0`）。
> **C1 措辞需从"恒为 98%"改为"≤ 98%，差额为 `void_prob`"**（v0.6 的落地口径）；**v0.13 进一步改为"物品概率之和 + `void_prob` 恒为 100%"**——隐藏款的 2% 已并入全部物品。

**影响范围**：`01-gacha.md`（抽取需处理 `void` 结果）、`09-presentation.md`（演出需呈现 `void`）、`08-ui-panels.md`（直方图需画出 `void` 柱）、`10-progression.md`（存档需记录 `void_mass`）。

> ✅ **已回改上游（v0.6）**：核心设计书已新增 **§5.6「空洞 void」** 给出正式定义，C1 措辞已修订为"常规款概率之和 + `void_prob` 恒为 98%"。**v0.13：隐藏款删除后，现行 C1 是"物品概率之和 + `void_prob` 恒为 100%"**（整数口径 `Σ weights_bp + void_mass_bp == 10000`）——**本节里的"98%"是那段历史的记录，不是现行规则**（核心 §5.4 / §5.6 / §16.8）。
> 本节保留作为该缺陷的历史记录与论证过程。
> ✅ **v0.7 复核**：术语合并（物资与款 → 物品）不触及概率与 `void` 的任何规则，**本节结论仍然成立**——`void` 依然是显式零价值结果，`void_prob` 的归属与求值路径不变。
