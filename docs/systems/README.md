### 2.1 四条最容易打架的边界（重点）

| 争点 | 归属裁决 |
|---|---|
| **"池子的概率"归谁算？** | **状态**归 05（`PoolService` 是唯一写入方），**求值**归 07（`EvalService` 是唯一读出方）。01 只消费结果，自己不算。 |
| **盲盒封面那两个数字归谁算？** | **07 产出 `headline`**，08 只渲染。08 **不得**在 UI 层另算（核心文档 §6.4 的工程保证） |
| **"被排除的款"在演出中由谁过滤？** | 05 提供池子状态，09 依状态过滤展示；**01 的 roll() 只按池子状态抽样，不做展示判断** |
| **ρ 的定义归谁？** | 07 拥有定义与口径；03/04/05/06 只提供输入量，不得各自解释 ρ |

### 2.2 共享代码路径（跨系统铁律）

> `EvalService`（07）与 `GachaService`（01）**必须共享同一套池子求值路径**。
> "显示的分布"和"实际抽取用的分布"必须是同一份代码算出来的。这是 P1（一切可查可算）的工程保证，也是本作头号 bug 源。

## 3. 跨系统铁律（所有文档都必须遵守）

1. **纯函数**：`EvalService`、`GachaService` 不依赖节点，可在无头模式跑单测；给定 `(state, series, seed)` 输出完全确定。
2. **单一写入入口**：池子状态只允许 `PoolService` 改；物资、任务进度等各自也只有一个写入方。
3. **单一计算源**：六个面板、试算、兑现对照全部共用 `EvalService`。
4. **常量不变量（v0.6 修订）**：镶嵌位数与装置槽位数是**每套系的常量**——从 `SeriesDef` 读取后运行时不可变，**不提供任何在同一套系内增加它们的接口**（P7）。不同套系可以不同，这是合法的内容成长轴。
5. **五条红线必须有回归测试守护**：
   - C1 常规款概率和 + `void_prob` ≤ 98%
   - C2 排除损耗率符合配置（40% 蒸发）
   - C3 隐藏款概率恒为 2%
   - C4 `pool_state.socket_count` 恒等于 `SeriesDef.socket_count`
   - **C6（v0.6 新增）任何合法 `PoolState` 下可产出常规款数 ≥ 3**
6. **数据驱动**：新模块、新装置、新任务应可**纯配置产出**，不改代码（R11 的核心对策）。
7. **不得暗改概率**：任何"按玩家进度动态调权"的设计一律否决（P1）。

## 4. 文档模板

每份系统文档必须使用以下章节顺序与标题。

```markdown
# NN · 系统名

- 上游：`../core-design.md` **v0.6** ／ `README.md`
- 依赖系统：…
- 被依赖：…

## 1. 这个系统负责什么
## 2. 不负责什么（边界）
## 3. 核心概念与术语
## 4. 数据结构（GDScript Resource 字段定义）
## 5. 规则与公式
## 6. 参数表（推荐值 + 调参旋钮标记）
## 7. 流程 / 状态机
## 8. 与其它系统的接口
## 9. UI 需求
## 10. 测试点与验收标准
## 11. 待定项
```

**要求：**
- 篇幅 **150–400 行 markdown** 为常规区间。超过 400 行需在文首一句话说明理由。
  （篇幅区间修订：原定 150–300 行，实际交付后多数文档落在 300–400 行。**上限是我拍的，内容才是有价值的**，故上调区间而非压缩文档。真正要防的是空洞注水，不是篇幅。）
- 数据结构用真实 GDScript 字段定义（`@export`），能在 Godot 4.5 里直接用。
- 参数表必须标注**推荐值**，并用 🔧 标记哪些是**调参旋钮**。
- 测试点必须包含**红线测试**（§3.5）与**失败信号**。
- 中文写作，代码标识符用英文。
- **文件编码统一 UTF-8 无 BOM、纯 LF 换行**（已全库校验通过）。

### 4.1 新增机制的处理规则

> **不得发明 `../core-design.md` 中不存在的新机制。**

若为了落地必须补充实现细节（如具体字段名、边界条件、错误处理），**在文中用 `[补充]` 标记并一句话说明理由**。
系统文档的职责是**细化**既有设计，不是**扩张**设计。如果认为核心设计缺了什么，写进 §11 待定项，不要直接实现。

### 6.1 ⚠️ 待回改上游：C1 与 C2 的内部矛盾

**核心设计书 §5.2 存在一处内部矛盾：**

| 条目 | 原文 |
|---|---|
| **C1** | 常规款概率之和**恒为 98%** |
| **C2** | 排除释放的概率仅 60% 可回收，**40% 蒸发** |

若 40% 真的消失且抽取分布仍需归一，则 C1 不成立；若归一化把那 40% 摊回其他款，则**损耗完全失效**，D6 这个主旋钮形同虚设。

**裁决（已在 `05-module-pool.md` §5.4 与 `07-economy-rho.md` §5.4 落地）：**

> 蒸发的概率**不消失**，而是落为一个显式的零价值结果 **`void`**。
> 即 `Σ probs(常规) + void_prob + 0.02(隐藏) == 1.0`。
> **C1 措辞需从"恒为 98%"改为"≤ 98%，差额为 `void_prob`"。**

**影响范围**：`01-gacha.md`（抽取需处理 `void` 结果）、`09-presentation.md`（演出需呈现 `void`）、`08-ui-panels.md`（直方图需画出 `void` 柱）、`10-progression.md`（存档需记录 `void_mass`）。

> ✅ **已回改上游（v0.6）**：核心设计书已新增 **§5.6「空洞 void」** 给出正式定义，C1 措辞已修订为"常规款概率之和 + `void_prob` 恒为 98%"。
> 本节保留作为该缺陷的历史记录与论证过程。
