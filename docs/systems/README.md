`d` 修正**——一个盒子能开的次数由 ≤5 变成 **`d = k − m`**（**不替换时 ∈ 8–25**；**未配置时 `d = k` = 10–25**；**替换越多 `d` 越小**），"抬缺口很贵"被更强地削弱，但**仍无任何保证**（P1 严格性不变）。**装置（04）被重新定位为盲盒的入口工具**——**开启盲盒 + ## 2. 所有权边界（防重叠契约）

**每个系统只写自己"拥有"的数据与规则。引用他人的东西时，写"见 `xx-xxx.md`"，不要复述。**

> **★ 引用纪律（裁定⑲）：跨文档引用时，权威归属方给出数值，引用方只点名归属、不复述数值。**
> **判据（可原文引用）**：**核心可以点名某事实的归属，但不得复述其数值**。例：核心**不再写**「`schema_version` 仍 v5」，改写为「**不新增迁移步骤**（**存档版本号的数值与迁移步骤归 `10`**；本裁决**不改变版本号**）」。
> **理由**：**核心是宪法**——只回答"**这次改动要不要动存档结构**"；"**当前是几**"是 `10` 的**实现事实**，且会随切片推进而变；核心写死数值 ⇒ **下次升版就得回改宪法**。
> **本文档（索引）同样适用**：**不复制数值，只给指针**。（本文自己的"契约版本 v0.14 / v0.16"写法**保留**——那是索引自己的版本观。）**★ 路径写法（㊿-quater）**：**跨目录引用写"仓库根相对"路径**（`docs/systems/NN-x.md`）；**`docs/systems/` 内部互引写裸文件名 + 节号**（如 `07-economy-rho.md` §2），**不必**加 `docs/systems/` 前缀。**理由**：全库曾**三种写法并存**（`systems/…` 只在"相对 `docs/`"这一种解释下成立；裸文件名简洁；`docs/systems/…` 在任何文件里都无歧义）⇒ **统一约定优先于检查器兼容**（**不在 gate 里加兼容层**）；**核心的 L168 / L390 / L701 三处已按本条统一为 `docs/systems/…`**。**边界**：本条约的是**路径引用**处；**"提到某文档"（不给出可点开的路径）处允许裸名、不强制加前缀**（核心 L1112 那种属此类）。
>
> **★ 维护纪律（v0.16 起，全库通用；事故条款）**
> **① 不得用"删掉检查器所指的内容"来消 FAIL。** 门禁（`tools/check_docs.ps1`）报 FAIL 时，**允许的动作只有两种**：**改检查器**（并留负测试）或**按裁定改文档**；**"把出问题的那句话删掉"不在其中**——**检查器指出的往往正是应当保留的墓碑 / 引用**（实例：曾把 `D22` 的撤销记录当成"禁用串为 0"的成绩删掉，见核心 §15 的 `D22` 行）。
> **②「门禁全绿」不能证明"裁定被遵守"。** 为过门禁做的任何改动，**必须回头逐条核对"这些改动是否越过了裁定划的边界"**——**绿灯是检查器的结论，不是合规的证明**（同一实例：`D22` 三处被删后 gate 反而更绿）。
> **③「上游口径」的数字不得由引用方自行改动。** 凡标注为"**上游口径 / 未含 X**"的数字（记账类，如 `10` §6 的落盘开销估算），**引用方不得自行改动**；**要修正必须报裁定**。只是"记账方式"的，**保留原样**。
> **④ 迁移条款里的字段名保持"当时的样子"，不得按现行形状回改。** 回改等于**伪造历史**，会让"当年到底存了什么"永远查不出来；**同名不同物时加限定句、不改名**（实例：`10` §7.4 的 v1 → v2 条款里那个 `pool_snapshot` = v1 档的旧形态）。

## 3. 跨系统铁律（所有文档都必须遵守）

1. **纯函数**：`EvalService`、`GachaService` 不依赖节点，可在无头模式跑单测；给定 `(state, series, seed)` 输出完全确定。
2. **单一写入入口**：池子状态只允许 `PoolService` 改；**物品实例列表只允许 `ItemService` 改**（v0.8）；**★ v0.18：资源余额（原石）也只允许 `ItemService` 改**（发放 `grant_currency` / 扣除 `transact` 的 `currency` op）。任务进度等各自也只有一个写入方。**任何系统都不得自行维护持有量副本。**
3. **单一计算源**：六个面板、试算、兑现对照全部共用 `EvalService`。
4. **常量不变量（v0.10 修订）**：**镶嵌位数是每个池子的常量**——由**该盒所属套系品质**决定（2/3/4/5），从 `SeriesDef.socket_count` 冻结进**该盒的 `item_pool.socket_count`**，**运行时不可变**，**不提供任何在同一池（同一盒子）内增加它的接口**（P7）。**装置没有槽位**（**v0.16：该字段与相关引用整族删除**——装置只是"开盒 / 装模块的工具"，**不带修正、不绑定盒子、不限制次数** ⇒ **槽位没有对象**）。不同套系可以不同，这是合法的内容成长轴。
   （v0.6 的旧口径是"两者都是每套系常量"；v0.10 只改镶嵌位这一半的口径，**规则本身未变**——核心 §5.2 C4 / §16.5。**v0.17 追加**：**设备侧既不设位子、也不设档位与成本**——`DeviceDef` 只剩身份与展示，`04` 的职责只有"开盒 + 镶嵌"两个入口，§2 边界表与 `04-device.md` 同载。）
5. **五条红线必须有回归测试守护**：
   - C1 **物品概率之和 + `void_prob` 恒为 100%**（整数口径 `Σ weights_bp + void_mass_bp == 10000`。v0.13：**不再留出隐藏款的 2%**。**断言侧**：回归断言若写浮点，写法是 `≤ 1.0` **并注明 1e-6 取整容差**——**`≤` 只是断言形式、不是 C1 的陈述**；**精确性一律由上面的整数形态断言**）
   - C2 排除损耗率符合配置（40% 蒸发）
   - C3 ~~隐藏物品概率恒为 2%~~ **【v0.13 作废】**——隐藏款设定整体删除、**保护对象不存在**（核心 §5.4 / §16.8）；**行号保留、不重编号**，以免牵动全库对 C4 / C6 的引用
   - C4 **该盒的** `item_pool.socket_count` 恒等于**该盒所属** `SeriesDef.socket_count`，且该盒 `modules` 的**项数 ≤ 它**（`modules` 是变长列表；v0.10 口径：数据是每盒一份，因此断言的是"该盒的池子数据 vs 该盒的套系"）
   - **C6（v0.6 新增）任何合法 `PoolState` 下可产出常规物品数 ≥ 3**
6. **数据驱动**：新模块、新任务应可**纯配置产出**，不改代码（R11 的核心对策）。**★ v0.18：装置也在"纯配置"范围内**——`DeviceDef` 的 `.tres`（含**等级曲线**：可开套系品质上限 + 开盒原石折扣 + 升级价）**不需要改代码**；**装置的内容量 = 等级曲线这一条**（**v0.17 曾把它清零，v0.18 恢复**），**但"装置数"仍为 0**（只有开局那一台、没有获取路径）⇒ **长期内容量主力仍是模块规格 × 任务结构 × 物品类别**（核心 §14.3 / §16.12 / §16.13）。**原石（货币）同样是纯配置**：加一种货币 = 加一个 `CurrencyDef` 的 `.tres`。
7. **不得暗改概率**：任何"按玩家进度动态调权"的设计一律否决（P1）。
8. **物品实例不变量（v0.8，三条都必须有回归测试守护）**：
   - 每个实例必须带 `instance_id`（**UUIDv4**）；
   - **发放必须幂等**——同一 `instance_id` 重复发放**不得**产生第二个实例；
   - **`count` 一律为派生值**（由实例列表数出并缓存），**不得作为独立存储字段**。
   （核心 §14.2 铁律 8。Godot **没有**内置 UUID，`ResourceUID.create_id()` 返回的 `uid://` 串不是 UUID。）
9. **只持久化现存实例（v0.8）**：已消耗的实例不留历史——审计由开箱日志承担（它已记录 `seed` + `pool_snapshot`）。
   未遵守会让存档体积无谓膨胀：每实例约 120 B，5000 实例 ≈ 600 KB。
10. **仓库与邮件是同一实例列表的两个位置（v0.9，核心 §4.7 / 铁律 9）**：
    - **`count()` 只统计 `location == warehouse`**；邮件实例**不计入可用持有**，不可用于交付/装配/镶嵌/转化；
    - **领取只改 `location`**——不创建实例、不重分配 `serial`、不重跑幂等判定；
    - **被动产出（开盒）放不下 → 进邮件**；**主动操作（转化/拆卸返还）放不下 → 拒绝整个操作**（v0.9 裁决 17，理由：否则转化会反噬、净损失可用持有）；
    - **必须有"主动丢弃"路径**（裁决 16）——否则仓库满会形成死局：领不出邮件 → 交不了任务 → 拿不到盒子 → 仓库仍然满。
    - ★ **`kind` 与 `location` 是两件事，不得互相改写**（v0.9 裁决 18）：
      `kind` 是**来源事实**（`gacha`/`convert`/`refund`/`mail`/`migrate`/`unlock`），`location` 是**当前位置**（`warehouse`/`mail`）。
      **产出溢出只写 `location = mail`，绝不改写 `kind`**——否则"来自哪个盒子 / 哪次转化"会丢失，与 §4.7 的邮件溯源展示要求冲突。
      `&"mail"` 是**保留值**（语义为"从邮件直接发放，系统补偿类"），切片内无调用方。
    - ★ **领取是部分成功而非整体拒绝**（v0.9 裁决 19）：按 `acquired_at` 升序（同秒按 `instance_id` 字典序）逐件判定，"能领多少领多少"，返回实际领取清单。
      理由：邮件里的东西**已经是玩家的**（产出瞬间已建实例、已有 UUID 与 `serial`），领取只是搬家；整体拒绝等于"没地方放就什么都不给你"，把**空间问题变成惩罚**，反而放大 R14。
      代价：UI 必须回报"已领取 M / 还剩 K 件"，**不得**表述为"一键领完"。
    - ★ **容量变化绝不得把已入库实例挤出仓库**（v0.9）：否则"持有"会变成**可被回溯撤销**的量。
11. **守恒等式以"全部实例"为准（v0.9 裁决 12）**：`total_granted − total_consumed == Σ 全部实例`（**含邮件**）。
    `count()` 只是**带 `location` 过滤的查询**，**不得让位置概念污染守恒式**。
    ★ **v0.18：守恒等式只覆盖物品实例**——**资源（原石）单列一份账**（发放量 / 消耗量，核心 §4.8）：**不得**把资源计入这个等式、**也不得**与物品互相折算。
12. **不承诺跨系统原子性（v0.9 裁决 13）**：`transact()` 只覆盖**物品侧**；Box 发放与解锁各靠**自己的幂等键** + 重放恢复。
    **单人游戏不需要分布式事务。**
13. **模块一旦镶嵌即锁定进该盒子（v0.10；**v0.14 改寿命**）**：镶嵌后模块**进入该盒的 `modules` 列表**、属于**那个盒子**，**不得移到别的盒子**；**该盒施工台随之清空**——**配置下一个盒子需要新的模块**。**拆卸只能从盒子上拆**（即从该盒的 `modules` 里移除那一项编辑）；**v0.14：模块留到盒子被摧毁**——盒子**被摧毁前**一直挂在**该盒**上、**可编辑可拆卸**（**两次兑现之间也能改**），**归零即盒子被摧毁（连同 `modules`）**（**"兑现后随盒子一同消耗"已作废**；**"没开过就被配光"不能再靠"装满位子"达成**，**但"从未兑现就被摧毁"整体仍可达**——**替换不占新位子、但计入 `m`** ⇒ **反复换上换下可把 `m` 推到 `k`** ⇒ **`d = 0`（合法路径）**；**"归零只看计数器"仍成立、与是否兑现过无关**，核心 §4.1 / §4.6 / §16.9）。
    **★ 分账（唯一权威写法）**：**镶嵌（含替换）与兑现共用同一份预算 `k`**——不变式 **`镶嵌总次数 + 兑现次数 + 剩余 == k`**；**装满位子后剩下的 `d = k − 位数`（8 / 12 / 16 / 20）必须在"替换"与"开盒"之间分账** ⇒ **每替换一次就少开一次盒**——"**换掉谁**"的价格是**一次开盒机会**。**⚠️ 防误用**：**8 / 12 / 16 / 20 只在"位子已装满"前提下成立**（**不得抄成"每盒可替换次数"常量**）；**`k − 1` 那条属退化玩法——不单独写规则、不得写成断言**；**禁写任何"范围口径"**（"每盒能替换 N 次"式的区间说法一律不得出现）。
    因此"把同一套配置复制到另一个盒子"**必须重新支付模块的物品成本**——这是 P7 被改写后仅存的那条否决项（核心 §7 / §16.5，数值由 **D17** 标定）。
    **★ 裁决（v0.10）：模块是消耗品——不存在"模块库存"。** 拆卸**只返还 50% 材料**，**模块本体不回到库存、也不可能被搬到别的盒子**；**不提供任何"模块仓库 / 回收再用"的接口**。
    **★ 裁决（v0.16）：拆卸（`unsocket`）不退还那一次寿命。** **替换 = 拆卸 + 重新镶嵌**——**拆卸零成本、不退那一次** ⇒ **每替换一个位子额外消耗 1 次寿命**（**该位子历史累计 2 次**：原装 1 + 新装 1）。**理由是"配置是沉没成本"**，与上一条（模块是消耗品 / 拆卸只返还 50% 材料 / 模块本体不回收）**同一设计意图** ⇒ **"换掉谁"不再可以随意试错**（**每次替换都更接近"归零即摧毁"**；核心 §4.1 / §15 **D20（整条已关闭）**）。
    理由（保留推演）：若模块本体可回收再用，同一个模块就能在多个盒子上**轮流使用**——"配置 N 个盒子需要 N × 位数个模块"当场失效、**D17 被归零**，而 D17 是 P7 改写后**唯一的跨池锚点**。
14. **模块不折进池子（v0.10 结构澄清）**：`Box` 下面是**两个并列的数据**——**`item_pool`（物品池，生成数据的凭证，`roll()` 消费它）** 与 **`modules`（模块列表）**。
    **池子的当前状态是二者的函数**（「`item_pool` 的基础数据 + 该盒 `modules` 的编辑效果」）：由 **01 的 `PoolService` 唯一写入**（它由这两份数据**推导**出池子的当前权重）、由 **07 的 `EvalService` 唯一求值**（权重 → 概率 / EV / ρ）。**二者不得混写**。
    这份状态是**派生值、不入档**（载入时逐盒重建）——**存档里不得存在"编辑后的权重"这第二个事实来源**。
    **否决**任何"把模块塞进池子自己的字段里"的形状（含 `PoolState.socketed`）。"换掉一个模块" = 换掉**一项作用于该池的编辑**，而**不是**"在池子里挖掉一块再补上"；**模块列表可以独立于池子被查看、替换与拆卸**。
13. **★ v0.19：模块的成本是「金币」，不是物品。** `ModuleDef.gold_cost` 是**唯一的价格来源**（**镶嵌按它扣金币**，`02` 的 `currency` op）；**模块不消耗任何物品**、**拆卸什么都不返还**（核心 §4.5 / §15 **D8** / §16.14）。**任何"模块消耗物品 / 拆卸返还材料 / 模块库存"的实现都是回归缺陷**（`engine` tag 与 `consume_by_filter` 已失去调用方，墓碑见 `02-item.md` §5.7）。
14. **★ v0.18：开盒要花原石**（`SeriesDef.gem_cost` × 设备等级折扣）；**设备有等级**（准入 + 折扣），**升级消耗原石**（核心 §4.4 / §15 D23 / D24）。
15. **盲盒没有保底——公布的概率就是每抽概率（v0.11 核心契约）**：**一次抽取的概率就是公布的分布本身，不存在任何"必出"覆盖**；**抽取无状态**（`roll(evaluation, seed)`，入参里没有计数器、没有跨次累计的状态）；**`void` 不产出物品、仅消耗一次使用（v0.14：兑现与"镶嵌一个模块"共用该盒的总寿命预算各 −1，**归零即盒子被摧毁**——不再是"仅消耗一个盲盒"），也不推进任何东西**。**P1 因此在每一次抽取上都严格成立**——池子编辑是概率的**唯一**决定者（v0.11 之前，保底是唯一一处"显示的概率 ≠ 实际每抽概率"的地方）。
    **否决**：任何以"**隐式必出**"（暗改某次的权重、看不见的加速、未公布的补偿）形式复活保底的做法；将来若要缓解全收集尾部（核心 **R15**），新机制**必须是可公布、可查的**（P1 / P6），并走核心 **D18** 的决策路径。

> **按系统组织让路径本身承载所有权信息**：看到 `src/items/` 就知道这一坨全归 02。

### 6.1 C1 与 C2 的内部矛盾（✅ **已回改上游，v0.6**——本节保留为历史记录）

**核心设计书 §5.2 存在一处内部矛盾：**

| 条目 | 原文 |
|---|---|
| **C1** | 常规款概率之和**恒为 98%** |
| **C2** | 排除释放的概率仅 60% 可回收，**40% 蒸发** |

若 40% 真的消失且抽取分布仍需归一，则 C1 不成立；若归一化把那 40% 摊回其他款，则**损耗完全失效**，D6 这个主旋钮形同虚设。

**裁决（已在 `01-gacha.md` §5.2.2 与 `07-economy-rho.md` §5.4 落地）：**

> 蒸发的概率**不消失**，而是落为一个显式的零价值结果 **`void`**。
> 即 **物品概率之和 + `void_prob` 恒为 100%**（**v0.13 现行式**；隐藏款删除前此式是 `Σ probs(常规) + void_prob + 0.02(隐藏) == 1.0`）。
> **C1 措辞需从"恒为 98%"改为"≤ 98%，差额为 `void_prob`"**（v0.6 的落地口径）；**v0.13 进一步改为"物品概率之和 + `void_prob` 恒为 100%"**——隐藏款的 2% 已并入全部物品。

**影响范围**：`01-gacha.md`（抽取需处理 `void` 结果）、`09-presentation.md`（演出需呈现 `void`）、`08-ui-panels.md`（直方图需画出 `void` 柱）、`10-progression.md`（存档需记录 `void_mass`）。

> ✅ **已回改上游（v0.6）**：核心设计书已新增 **§5.6「空洞 void」** 给出正式定义，C1 措辞已修订为"常规款概率之和 + `void_prob` 恒为 98%"。**v0.13：隐藏款删除后，现行 C1 是"物品概率之和 + `void_prob` 恒为 100%"**（整数口径 `Σ weights_bp + void_mass_bp == 10000`）——**本节里的"98%"是那段历史的记录，不是现行规则**（核心 §5.4 / §5.6 / §16.8）。
> 本节保留作为该缺陷的历史记录与论证过程。
> ✅ **v0.7 复核**：术语合并（物资与款 → 物品）不触及概率与 `void` 的任何规则，**本节结论仍然成立**——`void` 依然是显式零价值结果，`void_prob` 的归属与求值路径不变。
