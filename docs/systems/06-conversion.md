## 1. 这个系统负责什么

**转化解决盲盒的根本矛盾：随机产出 vs 确定性需求。**

盲盒产出的是**随机类别**，任务需求的是**确定类别**（需求向量的定义见 `03-task.md`）。没有转化，玩家会因为「开出来的一直不是我需要的那一类」而卡死——这不是难度，是系统缺陷。转化的职责就是给这条裂缝补一个**有代价、可计算、可归因**的出口：**把不对口的燃料，改造成对口的燃料。**

三条定位：

1. **它服务循环的「使用物品」这一步**（核心 §1.1）。转化是玩家在"使用物品"上的第三个动作，因此合规于 P3，也**增加**了这一步的深度。
2. **它不构成第三个物品出口。** 核心 §3 的二元取舍（燃料 / 引擎）不变：转化产出的仍是物品，最终仍要交付任务或作为装置/模块素材，出口裁决权归 `03-task.md` / `04-device.md` / `05-module-pool.md`。转化是**燃料路径的预处理**，不是并行的第三条路。
3. **它在教学曲线上必须最早、最简**（核心 §11）：15–30 min 引入，**早于装置**（30 min–1 h）。因此转化必须在**一个数字**内被理解，且**不依赖任何外部修正**即可使用（**v0.14：转化也没有任何可被调优的路径**——损耗固定 30%，见文首 v0.14 说明）。

## 5. 规则与公式

### 5.1 结算链（唯一公式）

```
conversion_loss = conversion_loss_base          # v0.14：固定 30%，无修正项、无下限、不 clamp

ratio     = v(source) × (1 − conversion_loss) / v(target)
count_out = floori(count_in × ratio)          # 一律向下取整，禁止向上

value_in  = count_in  × v(source)
value_out = count_out × v(target)
```

- `v()` 的**口径归 07**（见 `07-economy-rho.md`）；本文档只决定它的**用法**：先乘 `(1 − conversion_loss)`，再按目标单位取整。
- `[v0.8]` **`count_in` / `count_out` 的物理含义已由"计数增减"变为"实例个数"**：`count_in` = 本次**销毁的源实例个数**，`count_out` = 本次**创建的新实例个数**。**公式与"一律向下取整"的规则一字未改**——它本来就是按个数算的，实例模型只是把这个"个数"变成了**具体的个体集合**（§5.3）。
- **`conversion_loss` 恒为 0.30**（无修正项、无下限、不服从任何输入；v0.14 起**玩家侧没有任何可调路径**）。15–30 min 的引入点因此**不涉及任何"修正 / 可降低"概念**——它只有一个数字。
- [补充] **一次转化只接受同一「类别 × 品质」的单一源物品。** 理由：教学曲线上 15–30 min 必须简单直观，多源混合会引入心算负担（R5 / P6）。`[v0.8]` 该约束照旧，只是"单一源物品"现在读作"**单一 `(category, quality)` 分组内的实例**"（§5.3 的挑选规则）。
- [补充] **`count_out < 1` 时拒绝提交**，并返回 `min_count_in = ceili(v(target) / (v(source) × (1 − conversion_loss)))`。理由：核心未定义整数结算的边界，必须避免"提交后什么都没得到"。

### 5.2 品质折算规则

- `source_quality == target_quality`：**跨类别平移**，首切片唯一形态（核心 §13.1）。
- `source_quality != target_quality`：**品质折算**，由表项显式配置，公式不变（`v()` 已含品质维度）。
- **硬约束（套利封印的前提）：表项不得附带任何奖励倍率。** 换算收益只能来自 `v()` 的比例，不得出现"向上折算额外送 1 个"之类的加成。
- 品质向上折算（多个低品质 → 一个高品质）**不保证收益**，它是否划算完全由 `v()` 的曲线形状决定；`v()` 若超线性，则该表项是**内容设计**而非数值缺陷，必须走 §10 的套利环测试逐一验证。品质折算表项的释放节奏见 §11。

### 5.3 守恒要求、实例的销毁与创建、唯一写入入口

**守恒三断言**（每次结算必须全部成立，进入 §10 测试）：

```
(1) value_out ≤ value_in × (1 − conversion_loss)          # 不凭空产生
(2) remainder_value < v(target)                            # 取整残余上界
(3) value_in − value_out = value_in × conversion_loss + remainder_value   # 变化可加总
```

`[v0.8]` 三断言的**口径一字未改**，只把"计数"落到实例上：`value_in = Σ v(被销毁的源实例)`、`value_out = Σ v(新创建的实例)`。

**v0.8：转化是"销毁源实例 → 创建新实例"，不再是"扣计数、加计数"。`[v0.9]` 两个动作合并为一次事务调用（上游裁决 2），且产出放不下时整笔拒绝（裁决 17）。**

```
res = ItemService.transact([
  { op = &"consume", instance_ids = source_instance_ids, tag = &"convert" },
  { op = &"grant",   item_id = target_item_id,
    source = { kind = &"convert", from_instance_ids = [...], conversion_def_id = "<table_id>/<entry_id>" } },
                                     # 新实例、**新 UUID**；serial 由 02 分配（kind != &"gacha" ⇒ serial = 0，02 §5.6）
                                     # 共 count_out 条 grant op（02 的 grant 一次只创建 1 个实例）
])                                     # -> { ok, reason, consumed, granted, mailed }（02 §5.11）
# 放不下（空间不足）→ ok == false, reason == &"no_space" → **整笔不生效**：
#   consumed == []、granted == []、mailed == []，实例列表逐位回到转化前（裁决 17）
```

- **一次调用 = 一次提交（上游裁决 2）。** 销毁与创建**不得**拆成两次 API 调用再"拼起来"（v0.8 的 `consume` + `grant` 两步写法**作废**）——拆开就重新引入了"源已销毁、目标没创建"的失败形态（下方硬约束 / §10 T10）。`consume` op 的 `instance_ids` 是**逐个实例 id**（02 的 `grant` 一次只创建 1 个实例），因此 `count_out` 个目标实例对应 **`count_out` 条 `grant` op**，全部写在**同一次 `transact`** 里。
- **空间不足 ⇒ 拒绝整个转化（上游裁决 17，核心 §4.7）**：转化是**主动操作**，产出的新实例**不进邮件**——02 在事务内判定容量，放不下则**整笔事务失败**（`reason == &"no_space"`），**源实例不销毁、目标实例不创建、实例列表逐位不变**。06 **不判定空间**（不读 `warehouse_capacity` / `size`、不写 `location`、不生成邮件条目），只把该 `reason` 呈现给玩家。
  `[补充]` **预览的已知边界**：`quote()` 是纯函数、不做容量判定（判定点唯一在 02），因此存在"预览 `ok == true`、提交被 02 拒绝"的**唯一合法例外**。为把它讲清楚，§9.2 要求 UI **原样呈现该拒绝**；预告所需的容量口径由 02 的只读 **`warehouse_usage()`**（`{ used, capacity, ratio }`，`02-item.md` §4.3 / §5.9）提供，**呈现归 08，06 不自算容量、也不把 `used + size <= capacity` 写进任何 06 的代码**（§10 T14 / `02-item.md` §10.6）。
- **源必须是仓库内实例。** `source_instance_ids` 只能从 `location == warehouse` 的实例里挑选——**邮件实例不可作为转化源**（核心 §4.7 边界 1 / §14.2 铁律 9），02 的 `consume` 对非仓库 id 直接返回 `reason == &"not_in_warehouse"`；该只读查询归 02（§5.3 挑选规则）。

- **源实例的挑选**：本文档的转化**一次只接受同一「类别 × 品质」的单一源**（§5.1），因此挑选只发生在这一组内。`[补充]` 顺序固定为 **`acquired_at` 升序**（同一时刻按 `instance_id` 字典序兜底）——与核心 §4.2.3 对任务侧的裁决同精神（**先入先出**），也与 02 的 `query()` 顺序一致（`02-item.md` §5.5：quality 升序 → `acquired_at` 升序 → `instance_id` 字典序；本组品质恒定，故前两键即退化为 `acquired_at` 升序）。**实现归 02**（实例列表的唯一写入方，README §2.1）。
- **新实例的 `source` 必须记"由转化产生"，而不是"开盒"。** 取值约定（**判别键沿用 02 已定的 `kind`**）：

```
source = {
  kind              = &"convert",                    # 判别键（**必填**）：本次入库不是开盒（02 §4.2 的取值域）
  from_instance_ids = [<被销毁的源 instance_id> …],   # [扩展键·**已获上游授权**] 溯源：它由谁换来
  conversion_def_id = &"<ConversionDef.table_id>/<entry_id>",   # [扩展键·**已获上游授权**] 由哪条表项换来
}
```

  - 对应地，**开盒**产出的实例是 `{ kind = &"gacha", series_id, box_seed, draw_index }`（02 §4.2：三键 + 02 补的 `kind`）。**两套键集不同，靠 `kind` 判别。**
  - ⚠️ **`kind = &"convert"` 是 02 已实现的取值**（`02-item.md` §4.2 的 `source` 表 + §5.8 来源清单），**本文档不再另提 `origin` 键名**（该提案作废，避免与 02/04/05 已有的 `kind` 冲突）。
  - ✅ **`from_instance_ids` / `conversion_def_id` 已获上游授权**（裁决 3/4/7：`source` 是**开放字典**、`kind` **必填**，取值域 `gacha` / `convert` / `refund` / `mail` / `migrate` / `unlock`）。键名沿用 02 已定的 `kind`，**扩展键与 `kind` 同处一个字典**；§11 C8 已关闭，v0.8 稿的"退化实现（只写 `kind`）"**不再需要**。
- **`serial = 0`（上游裁决）：转化产生的新实例不分配收藏编号。** 理由：`serial` 的定义是"**该玩家开出的第 N 个此物品**"（核心 §4.2.1）——转化产出**没有被开出**，因此它没有编号；`serial = 0` 显式表示"**非开盒来源**"，与开盒实例的 `serial ≥ 1` 天然可区分。`[补充]` 由此推出：`serial = 0` 的实例**不得**推进图鉴进度与套系完成度——图鉴只由**开盒产出**登记（本文档 §8 与 `10-progression.md`；该口径的最终措辞归 10）。

- **`grant` 的第三参（`instance_id`）正常路径不传。** 02 的签名是 `grant(item_id, source := {}, instance_id := "")`，第三参**只在重放**（存档重放 / 日志补发）时用于命中幂等（02 §4.2 / §4.3）；转化产出的实例身份必须是**全新 UUID**（§10 T11），因此本文档**不传**该参数，由 02 生成。
- **原子性（v0.8 重点强调，v0.9 由事务原语承载）：销毁与创建必须在同一事务内；失败则整体回滚（源实例不销毁、目标实例不创建）。**

- v0.7 的转化在计数模型下只改两个键，失败面小；v0.8 跨了两次 API 调用（`consume` + `grant`），因此**"源已销毁、目标没创建"成为新的失败形态**——那等于凭空吃掉玩家的物品。`[v0.9]` **上游裁决 2 已把这两步收敛为一次 `ItemService.transact(ops)` 调用**（见上方代码块），失败面回到"一次提交"的粒度。硬约束：
  1. 销毁与创建必须在**同一次 `transact()` 调用**里提交：任一 op 失败 → 全部回滚，实例列表**逐位回到转化前**；**不得**用两次调用拼合（拆开即本约束失效）；
  2. 取整与校验必须在 **SETTLE** 阶段完成（§7），**不得**先销毁再算；
  3. 回滚后**不得**留下任何"半成品实例"（已生成 UUID 但未入库的实例必须一并作废）；
  4. 该约束进 §10 的 **T10** 测试（创建失败时源实例仍在），并在 v0.9 强化为"**只允许一次 `transact()` 调用**"。

- **转化是唯一允许改变「玩家持有类别分布」的后天入口。** 物品进入持有只有两个来源：**开盒**（见 `01-gacha.md` / `09-presentation.md`）与**转化**（本文档）；`category` 是 `ItemDef` 的不可变属性（见 `02-item.md`），物品**不得原地换类别**，只能"销毁源 + 创建目标"。`[v0.8]` 这句话至此从一句设计约束变成**数据结构上的事实**：源与新实例是**两个不同的 `instance_id`**，原地换类别在结构上不可能。
- [补充] **`quote()` 与 `convert()` 必须共用同一函数体**，UI 预览值与实际结算值必须逐位相等。理由：把 README §2.2「显示的分布＝实际用的分布」这条铁律复用到转化，防止第二处"显示与实际不一致"的 bug 源。`[v0.8]` 预览的 `source_instance_ids` 与实际销毁的集合也必须逐位相等（否则"显示的代价"与"实际代价"是两个不同的实例集）。
- [补充] **拒绝即零副作用**：任何 `ok == false` 的路径都不得写入**实例列表**（原子性）。理由：核心未定义结算失败时的状态边界。`[v0.9]` **`no_space` 同属此列**——空间不足是"整笔不做"，**不是**"产出改道进邮件"（裁决 17）：源实例仍在、目标实例不存在，实例列表逐位可变前（§10 T14）。
- **残余即已声明损耗。** `remainder_value` 不得静默消失：它是第 (3) 条的一部分，进归因（P2）。`[v0.8]` 残余的产生方式不变——`floori` 少创建的就是残余，**不是"少销毁"**（源实例按 `count_in` 全部销毁）。

### 5.4 套利环封印（由公式保证，由测试守护）

对转化表上任意**有向闭路** `k` 步：

```
Π ratio_k = (1 − conversion_loss)^k ≤ 0.9^k < 1
```

`[v0.8]` **措辞更新（公式与数值一字未改）**：`ratio` 现在是"**创建的新实例个数 ÷ 被销毁的源实例个数**"，`floori` 读作"**创建 `floori(...)` 个新实例**"。由于计数是一一数实例得出的（核心 §4.2.2），**实例化不改变本节的任何一步推导**：`Π ratio_k`、`0.9^k` 与 `< 1` 的结论原样成立。

闭路上每次折算的 `v(source)/v(target)` 逐项相消（回到同一「类别 × 品质」），因此只要满足：**(a) 每条边 `conversion_loss > 0`**（**v0.14：它就是固定 30%，恒 > 0**；原文的"`≥ conversion_loss_floor`"随该下限字段一并删除）、**(b) 结算永远 `floori`**、**(c) 表项无奖励倍率**、**(d) 不自动生成反向表项**，A→B→A **在数学上不可能净赚**。品质折算不破坏该结论。

- [补充] **反向表项必须显式配置，不自动生成。** 理由：配置期自动补反向边是意外制造 `ratio ≥ 1` 环的主要途径。
- **表连通性约束（由核心 §10.3 推出）：** 转化表**不得完全连通**。若任意类别两两可达，`category` 维度失效，任务需求的摩擦（§10.3 后期唯一压力来源）被消掉，R1/R5 同时触发。首切片推荐 2 类别 2 条有向边。
- `[v0.8]` **实例化对套利环的唯一影响是"把代价落到具体个体上"**：闭路上的每一跳都要销毁一批实例、再创建另一批实例，`source` 被改写为"由转化产生"（§5.3）。这条**不改变** `Π ratio_k < 1` 的证明（它是纯比例论证），但给 T3 增加了一条可观测的旁证：**绕行一圈后，起始的 `instance_id` 一个都不会剩下**——净赚若发生，不可能来自"同一个实例又回来了"。

## 7. 流程 / 状态机

```
IDLE
 └─▶ SELECT_SOURCE   选源：类别 + 品质 + 可用实例数（读 02 的实例快照，按 (category, quality) 聚合出派生计数；
                      `[v0.9]` **只含仓库内实例**——邮件实例不可作为源，核心 §4.7 边界 1）
      └─▶ SELECT_TARGET  选目标：仅列出转化表中存在的**出边**
           └─▶ PREVIEW     quote() 实时报价：ratio / count_in / count_out / conversion_loss
                ├─ ok == false ─▶ REJECTED（显示 min_count_in 或"不可转化"）─▶ IDLE
                └─ ok == true  ─▶ CONFIRM ─▶ SETTLE ─▶ COMMIT ─▶ RESULT ─▶ IDLE
```

- **SETTLE** 纯函数，输出 `ConversionQuote` + `ConversionLogEntry`。`[v0.8]` **源实例的挑选也在此冻结**：`quote().source_instance_ids` 一经产出即确定，COMMIT 必须原样使用，**不得重新挑选**（§5.3）。
- **COMMIT** 是本文档的**唯一写入入口**：`ConversionService.convert()` 是唯一被允许提交跨类别物品变更的函数。`[v0.8]` 它通过 02 的唯一物品写入接口提交；`[v0.9]` **收敛为一次 `ItemService.transact(ops)` 调用**（销毁 op + 创建 op，上游裁决 2）——`ok == false` 时**实例列表逐位不变**（§5.3）。**空间判定在 02 的事务内完成，06 不介入**：空间不足 → `reason == &"no_space"` → **整个转化被拒绝**（源不销毁、目标不创建，**产出不进邮件**，裁决 17 / 核心 §4.7）。
- **原子性**：SETTLE 与 COMMIT 必须成对成功。`[v0.8]` **且 COMMIT 内部的两步（销毁 / 创建）也必须成对成功**——`[v0.9]` 二者在**同一次 `transact()` 调用**内，任一步失败则实例列表**逐位回到转化前**，不存在"源没了、目标没到"的中间态（§5.3 / §10 T10）。
- **不在流程内做需求匹配**：缺口提示由任务面板提供（见 `03-task.md` / `08-ui-panels.md`）。
- **教学介入点**：15–30 min。此阶段 UI 只暴露 SELECT → PREVIEW → CONFIRM，`conversion_loss` **恒为 30%**，且**全流程（不只引入阶段）都不出现任何"可降低 / 可优化 / 可修正"字样**——转化端没有可调路径（v0.14；装置已退出转化端，核心 §4.4）。

## 9. UI 需求

### 9.1 归属裁决（明确）

> **转化不新增第七个常驻面板。** 核心 §8.1 明确只有六面板；新增面板会稀释"界面即玩法"的预算，也与 R3（池子编辑变成第二个工作台）同型。

- **入口与呈现规格**：内嵌于**任务面板**（核心 §8.1「任务面板 = '使用物品'的工作台」）——在缺口高亮旁提供转化入口。该入口的形态、位置与展开规格归 **08**。
- **操作场景**：钻取到独立工作台场景 `scenes/workbench/conversion.tscn`（核心 §14.1 已列出 `scenes/workbench/ # 转化`）。本文档只声明必需信息元素，布局规格归 08。
- 一句话：**数据与结算归 06，呈现归 08，入口寄生在任务面板，操作落在 workbench 场景。**

### 9.2 必需信息元素（08 负责渲染）

- 源：类别 / 品质 / **可用实例数**（来自 02，是**派生计数**——UI 上的数字不变，来源由存储字段变成了数实例）。`[v0.9]` 该数字**只含仓库内实例**：**邮件实例不可作为转化源**，因此不得计入可利用量（核心 §4.7 边界 1）
- 目标：类别 / 品质（**只列出转化表中存在的出边**，无出边的目标不显示）
- `[v0.9]` **空间不足 ⇒ 整个转化被拒绝**（裁决 17）：预览报的是"将**新建** `count_out` 个新实例"，而**放不下时这笔转化根本不会发生**——**不是**"产出改道进邮件"。UI 必须**原样呈现** 02 返回的 `no_space` 拒绝（说明"空间不足，本次转化未执行：源实例未销毁、新实例未创建"），**不得**让玩家以为东西进了邮件、也**不得**承诺"转化后仓库里会多出 N 件"
- **折算比 `ratio`**：15–30 min 教学阶段**唯一需要展示的数字**
- 本次将销毁 `count_in` 个源实例 / 创建 `count_out` 个新实例（实时预览，P6）
- `conversion_loss` 的**单一数字展示**（引入时恒为 30%）
- 不足时显示 `min_count_in`；`ok == false` 时禁用提交

### 9.3 禁止项

- **禁止一键最优配置**：只提供试算，不提供自动决策（D12：一键最优直接关系 R1）。
- **禁止在 15–30 min 引入时展示概率、ρ、方差或"损耗叠加"**——前 15 分钟不需要理解概率（核心 §11）。
- **禁止把 `v()` 的计算结果在 UI 层另算**（P1 / 铁律 3 的精神：显示值必须来自同一计算源）。

### 失败信号（对齐核心 §13.4）

- **测试者从不使用转化，遇到缺口只会等下一个盲盒** → 转化不可达或入口埋太深（同 R12 型问题）。
- **测试者把转化当"万能兑换机"，不再看任务需求结构** → 表连通性过强，`category` 维度已失效（T7 应先失败）。
- **测试者在 15–30 min 的引入点就追问"损耗率和 ρ 什么关系"** → 转化不够直观，需简化而非补充说明。
- **测试者反复尝试 A→B→A 套利** → 损耗不可见/提示不足；**若真的净赚，按 T3 严重 bug 处理**。
- **测试者抱怨"按了转化却什么都没拿到"** → `min_count_in` 提示缺失（T9）。
- `[v0.8]` **测试者说转化产出的物品"算我收集到了"** → `serial == 0` 未生效或图鉴误登记（T12 应先失败）。
- `[v0.8]` **测试者说转化后"东西少了两份"** → 事务原子性破裂（源已销毁、目标未创建），按 T10 严重 bug 处理。
- `[v0.9]` **测试者在仓库将满时按了转化，却说不清"为什么没反应 / 东西去哪了"** → `no_space` 的拒绝未被呈现（§9.2 / T14）。注意要**同时**排除相反的错误认知：**产出不会进邮件**（那是开盒的路径，主动操作只拒绝，裁决 17）。
