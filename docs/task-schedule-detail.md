## 2. 每周固定节律

| 时点 | 动作 |
|---|---|
| 周一上午 | 定本周目标（**只写 3 条**）；确认前置是否真的完成 |
| 每日收工 | 跑一遍红线回归（**不跑不提交**） |
| 周三 | 中途检查：本周目标是否仍可达？不可达就砍范围，不砍验收 |
| 周五下午 | **验收 + 记录**：本周交付物对照验收标准逐条打勾；记录踩到的坑 |
| 每阶段末 | 门禁评审（§3.4 / §4.3 / §5.15 / …），未过不进入下一阶段 |

> **铁律：红线回归每日必跑。** 它守护的是"显示的分布 == 抽取用的分布"，这是本作头号 bug 源，
> 而且症状是"玩家所有施工失去可信度"——这种 bug 一旦漏进去，后面所有数值调参都是在错误的地基上做。

### 4.3 M1 门禁 —— **本项目的第一个决策点**

**通过（满足 ≥2 条）→ 进入 P2：**
- [ ] 测试者在**无人引导**下主动讨论"这个要不要留"
- [ ] 测试者能在 2 分钟内说出 ρ 的主要贡献来源
- [ ] 出现囤积行为
- [ ] 连续调整装配 ≥3 次而不觉得烦

**不通过（任一出现）→ 停止并重设计，不要继续投 P2：**
- ❌ 物资**全部**用掉，从不考虑装配 → **燃料/引擎取舍不成立，中心机制已死**
- ❌ 物资**全部**留下，从不完成任务 → 循环张力不成立
- ❌ 测试者问"这些数字是干嘛的" → 默认层信息设计失败
- ❌ 10 分钟内就把池子编到接近必出 → C6 或 C2 未生效（先查代码，不是调参）

> **M1 是全排期性价比最高的一关：6.5 人日，可能省下 40 人日。**

## 10. 为什么 P0 与 P3 不可并行

### P0 不可并行
`EvalService` 与 `GachaService` **必须共享同一套 `evaluate_pool()` 路径**（核心 §5.6 工程约束）。
把这段拆给两个人写，是**破坏 P1 最可靠的方式**——它会直接产出"显示的分布 ≠ 抽取用的分布"，
而这是本作头号 bug 源，症状是"玩家所有施工失去可信度"。

### P3 不可并行
调参需要**同一套判断标准与连续的手感记忆**。两个人各调一半，等于用两把尺子量同一个东西。
