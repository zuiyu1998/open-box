# 《Open Box》核心设计书

- 版本：**v0.4（新增池子编辑系统：盲盒期望可被模块改写）**
- 历史版本：`docs/archive/core-design-v0.1.md` ~ `v0.3.md`
- 引擎：Godot 4.5（Forward+）
- 已定前提：**纯单人** / **纯游戏内货币，无数值付费** / 社交**留接口不实现**

> **v0.4 说明**
> v0.3 里"引擎"这条路只有"装置 +10%"这类数值手段，太薄。
> v0.4 新增**池子编辑系统**：玩家用模块**排除**某些款不再产出、**提升**某些款的概率。
> 于是**盲盒的期望不再是套系的固定属性，而是玩家可施工的对象**——"做大数学期望"至此成为字面意义上的操作。
>
> **术语确认：** 本节按"模块可**改写/覆盖**基础概率结构"理解；"提升某些物品的概率"按"概率"理解。若原意不同请纠正。

## 1. 核心循环（宪法）

```
   ┌────────────────────────────────────────────────────────┐
   │                                                        │
   ▼                                                        │
开盲盒 ──▶ 获取物资 ──▶ 使用物资 ──▶ 完成任务 ──▶ 获取盲盒 ──┘
   ▲                        │                              │
   │                        ├──▶ 燃料：交付任务             │
   │                        └──▶ 引擎：造装置 / 造模块 ─────┤
   │                                     │                 │
   └───────── 模块编辑盲盒池 ◀───────────┘                 │
                                                           │
                          最终完成全收集 ◀─────────────────┘
```

**这条循环是设计宪法。** 任何新系统必须先回答"它服务循环的哪一步"，否则不做。

### 1.1 循环各步的情绪与职责

| 步骤 | 情绪 | 玩家在做什么 | 系统职责 |
|---|---|---|---|
| **开盲盒** | 悬念、揭示 | 兑现未知 | 演出、概率、**池子状态** |
| **获取物资** | 收获、入库 | 清点战利品 | 物资分级、图鉴 |
| **使用物资** | **决策** ★ | **唯一的能动性所在** | 任务分配、装置、**模块** |
| **完成任务** | 目标达成、验证 | 推进度 | 任务需求与奖励 |
| **获取盲盒** | 期待积攒 | 囤积下一次悬念 | 闭环闭合 |
| **全收集** | 终局成就感 | — | 长线终端目标 |

### 1.2 最重要的一条洞察

**整条循环上，玩家能动性只集中在"使用物资"这一步。**

- 开盲盒是随机的（无决策）
- 获取物资是被动的（无决策）
- 完成任务是执行（无决策）
- 只有**使用物资**有选择。

**推论：本作的全部玩法深度必须堆在"使用物资"上。** 其余各步的职责是**制造压力**（让这一步的选择有重量），而不是抢戏。

这条推论否决了一类设计：任何让"开盲盒"本身变成策略博弈的方案，都是在给无决策的步骤加深度。**注意区分**——"开盲盒"不是决策点，但**"编辑盲盒的池子"是**，因为它发生在"使用物资"这一步（用物资造模块）。§5 的池子编辑因此是合规的，而 v0.2 的"开盒端算子装配工作台"不是。

## 2. 主数值：闭环收益率 ρ

### 2.1 定义

```
开 1 个盲盒      → 平均产出 M̄ 单位物资
完成 1 个任务    → 消耗 D̄ 单位物资，奖励 B 个盲盒

闭环收益率  ρ = ( M̄ / D̄ ) × B
```

| ρ | 含义 | 玩家体感 |
|---|---|---|
| ρ < 1 | 循环衰减 | 我在亏，需要外部补给 |
| ρ = 1 | 自持 | 勉强转得动 |
| ρ > 1 | 循环增殖 | **滚起来了** |

### 2.2 ρ 就是"盲盒的数学期望"

> **每投入 1 个盲盒，最终平均能回收多少个盲盒。**

这是整条链的期望。**做大 ρ 就是这个游戏的全部玩法。**

### 2.3 ρ 的分解（归因面板的内容）

```
ρ  =   M̄ / D̄   ×   B
      └──┬──┘     └┬┘
      开盒端      转化端
        │           │
      M̄ = Σ(pᵢ × vᵢ) × 池子修正
        │           │
     ▲ 模块        ▲ 装置
   （编辑 pᵢ）   （降低 D̄、提高 B）
```

| 端 | 施工工具 | 手段 | 特征 |
|---|---|---|---|
| **开盒端**（M̄） | **模块** | 排除/提升池中款式的概率 | 改变分布形状，高方差 |
| **转化端**（D̄ / B） | **装置** | 降低任务消耗、提高任务奖励、减少转化损耗 | 线性数值，低方差 |

**两个施工工具，一一对应两个端。** 归因面板要做的事因此非常明确：把 ρ 拆成这两项，并逐项列出贡献者。

## 3. 核心决策：燃料还是引擎

"使用物资"要成为有重量的决策点，物资必须面对一个**永久性的取舍**：

> **同一份物资，用掉它完成任务（燃料），还是留下它改造循环（引擎）？**

| 出口 | 形态 | 代价 | 收益 |
|---|---|---|---|
| **燃料** | 交付给任务 | 物资被消耗 | 立即换来盲盒，推进循环 |
| **引擎 · 装置** | 装配 | 物资永久占用槽位 | 提升**转化端**效率（降 D̄、提 B） |
| **引擎 · 模块** | 装配 | 物资永久占用槽位 | 编辑**开盒端**池子（排除 / 提升） |

### 3.1 为什么这是本作的中心机制

1. **它是循环上唯一有真实代价的选择。** 用掉就没了，代价永久且不可撤销。
2. **它复刻了实体盲盒最真实的心理——舍不得拆。** 摆在架上的盒子比拆开的盒子更让人惦记。
3. **它天然制造了收集与推进的根本矛盾。** 想全收集就得留着；留着就不能拿去完成任务；不完成任务就没有新盲盒。**这个矛盾是循环自带的，不需要额外系统。**
4. **它让"全收集"和"做大 ρ"互相拉扯**，而不是各走各的。

### 3.2 二级决策：投开盒端还是转化端

确定要造引擎之后，还要选**投哪一端**：

- 投**开盒端**（模块）→ 改变分布形状，追求高上限、高方差
- 投**转化端**（装置）→ 稳扎稳打，低方差、可预测

这构成第二层取舍，是防"最优解收敛"的第一道防线。

### 3.3 设计约束

- 装配**必须可逆但昂贵**（可拆，返还 50%），否则玩家会因害怕误操作而不敢决策。
- 装配信息（装了什么、放弃了什么）必须在**每次面临选择时可见**。
- 槽位必须有**硬上限**，否则后期所有物资都会被留下，"燃料/引擎"的取舍自然消失。

## 4. 系统骨架

### 4.1 盲盒（Box）

- 每个套系**独立概率池**：8 常规 + 1 隐藏。
- 隐藏款基础概率 2%；常规款均等（合计 98%）；未拥有款权重 ×1.5；连续 8 次未出新款则硬保底。
- **概率与池子当前状态公示界面属于核心玩法范围，不是可选项**（P1）。
- 盲盒**可以囤积**：何时兑现是决策（见 §4.6）。

### 4.2 物资（Material）

| 属性 | 作用 |
|---|---|
| **类别** | 决定能满足哪类任务需求 |
| **品质** | 决定任务贡献度、作为装置/模块素材时的强度 |
| **数量** | 可堆叠；重复款即数量增加 |

物资的两个出口（互斥）：

```
物资 ──┬──▶ 交付给任务（被消耗，推进循环）
       └──▶ 装配为装置 / 模块（永久占用槽位，改造循环）
```

### 4.3 任务（Task）

- 任务有**需求**（某类别/某品质的物资若干）与**奖励**（盲盒、券、槽位）。
- 两类任务，职责不同：
  - **常规任务**：循环引擎，可重复，盲盒回流的主要来源。
  - **里程碑任务**：一次性，解锁新套系、新物资类别、新槽位。
- **任务需求随进度变宽**（后期要求更分散、更稀有的类别）。
  这是自然摩擦：ρ 会因需求分散而下滑，玩家必须持续提升 ρ 才能维持进度。**用需求结构提供长期压力，而不是靠调低概率**（见 R5）。

### 4.4 装置（Device）

作用点在**转化端**，永久生效，占用槽位。

| 效果示例 |
|---|
| 「任务物资消耗 −10%」 |
| 「转化损耗 −15%」 |
| 「完成任务额外 +1 盒」 |
| 「任务需求品质下限 −1」 |

### 4.5 模块（Module）

作用点在**开盒端**，编辑池子，永久生效，占用槽位。**详见 §5。**

### 4.6 兑现时机（Timing）

盲盒可囤积，于是产生一个纯涌现的决策：

> 「现在开」还是「等我 ρ 或池子再好一点再开」？

由此自然形成一种资源配置玩法：**用低价值套系刷模块素材，把高价值套系的盒子攒到池子编辑成型后再开。**

不需要任何新系统，只需保留"盒子可囤积"这一条规则。

## 5. 池子编辑系统

### 5.1 核心命题

> **盲盒的期望不是套系的固定属性，而是玩家可以施工的对象。**

每个套系的池子对玩家开放三种操作，全部通过模块实现：

| 操作 | 效果 | 代价 |
|---|---|---|
| **排除（Ban）** | 指定款概率归零，不再产出 | 释放的概率仅 **60% 可回收**，40% 蒸发 |
| **提升（Boost）** | 指定款概率 ×N | 增量**必须从其他常规款按比例扣除** |
| **回收（Recover）** | 把蒸发掉的概率挽回一部分 | 需要更高级模块，占槽位 |

### 5.2 硬约束（缺一不可）

| # | 约束 | 理由 |
|---|---|---|
| **C1** | **零和**：常规款概率之和恒为 98% | 提升必须从别处抢，取舍才真实 |
| **C2** | **损耗**：排除释放的概率仅 60% 可回收，40% 蒸发 | 若无损耗，排除就是免费午餐，玩家会把池子收敛到必出缺口款，系统当即崩坏 |
| **C3** | **隐藏款免疫**：不可排除、不可提升、不可被回收波及，概率恒为 2% | **见 §5.4，这条是红线** |
| **C4** | **槽位有限**：模块占用与装置同一槽位池 | 保持"燃料/引擎"取舍的强度 |
| **C5** | **排除数量上限**：随进度增长 | 防止后期池子被清空成单一款 |
| **C6** | **编辑全程可见且可归因**：池子当前分布必须实时公示 | P1 + P2 |

### 5.3 由此产生的核心张力（本系统的设计价值所在）

**提升缺口款，会摊薄任务物资款。** 推进全收集与推进循环，抢的是**同一份概率预算**。

| 玩家想做的事 | 池子编辑动作 | 副作用 |
|---|---|---|
| 推进全收集 | 排除已集齐款、提升缺口款 | 任务物资产出下降，ρ 下滑 |
| 推进循环 | 排除无用款、提升任务物资款 | 缺口款更难出，收集停滞 |

这条张力不是硬塞的，**它从零和约束里自己长出来**。而且它正好落在"使用物资"这一步——与 P3 完全一致。

**同时它让"排除"的代价可以被精确计算**：排除某款 = 放弃它转化出的任务物资（可算），换取概率集中（可算）。代价明确、可归因，符合 P2。

### 5.4 隐藏款必须免疫编辑（红线）

**若隐藏款可被编辑，玩家就能把池子收敛到必出它，"盲盒"的悬念当场死亡。**

因此：
- 隐藏款概率恒为 2%，**免疫排除、免疫提升、免疫回收波及**；
- 隐藏款另配**独立保底**（开满 N 次必出），兜住挫败，但保底只保证"会出"，不保证"何时出"。

于是终局结构是：**常规款靠池子编辑工程化收敛，最后一个隐藏款保留不可预测性。**

这是"工程 + 最后一点运气"，也是这个品类最后不能放弃的尊严。

### 5.5 终局落点

全收集收官阶段的玩法变得非常清晰：**把池子一步步编辑到只剩缺口款。**

玩家不是"抽到的"，而是**把概率编辑到接近 100%**。这正是"我算赢了它"这个终局情感的字面兑现，也是"从赌徒到庄家"这条线的终点。

## 6. 设计支柱

支柱必须有**否决权**。

### P1 · 一切概率、池子状态与期望可见可算
概率、权重、保底计数、**当前池子分布**、M̄、D̄、B、ρ——全部对玩家公开。
**否决：** 任何暗改概率、动态调权、"根据玩家进度悄悄调爆率"的设计。概率是玩家的施工材料，材料必须是真的。

### P2 · 每一次 ρ 的上升都必须可归因
必须能逐项读到「模块 A：+0.42（开盒端·排除3款）／ 装置 B：+0.11（转化端）／ 池子损耗：−0.08」。
**否决：** 任何只显示总数的数值呈现方式。

### P3 · 深度只堆在"使用物资"上
**否决：** 任何在开盒、获取、完成这几步上增加策略博弈、而"使用物资"仍无选择的方案。
**合规示例：** 池子编辑发生在"使用物资"（造模块），合规。

### P4 · 单次悬念不可消除
可优化的是分布，不是结果。
**否决：** 透视、预知、下次必出某款；**隐藏款可被编辑**（§5.4）。
（保底是分布层规则，不是结果层预测，二者不可混同。）

### P5 · 重复与过剩永远不是空手
重复物资是装置与模块的原料。
**否决：** 任何会产生"我什么都没得到"的开箱结果。

### P6 · 玩家的时间用于决策，不是用于算数
提供试算 / 沙盒，试错成本趋近于零。**池子编辑必须有实时预览**，否则玩家无法评估 40% 损耗意味着什么。
**否决：** 任何要求玩家手算或外部查表才能决策的机制。

## 7. 方差：第二条轴

**这是防止"最优解收敛"的第二道防线。**

ρ 不是唯一目标。方差 σ 是**独立的第二条轴**，必须**显式显示**（数字 + 分布直方图）。

| 构筑方向 | 玩家类型 | 手段 |
|---|---|---|
| **ρ 最大** | 长期主义者 | 模块集中概率、容忍高方差 |
| **σ 最小** | 稳健派 | 装置堆保底与抬下限 |
| **定向获取** | 收集派 | 模块提升缺口款，牺牲 ρ |

三者**互相冲突**，因此**不存在唯一最优解**。

规格要求：
1. 方差是**一等公民数值**，不是隐藏属性。
2. **分布直方图是本作最重要的单个 UI**：它同时呈现"编辑前的形状"和"编辑后的形状"，让玩家**亲眼看到自己把分布捏成了另一个形状**。

**第三道防线是场景约束随机化**：每批任务附带 1 条环境约束（禁用某类模块 / 加成某类物资），使当前最优配置随场景漂移。

## 8. 可视化是玩法本体

**美术与 UI 预算的重心在"ρ、池子分布与归因的可视化"，不在开箱特效。**

### 五个必备面板

| 面板 | 内容 | 为什么是玩法 |
|---|---|---|
| **循环面板** | ρ、M̄、D̄、B，以及循环箭头上的实时流量 | 没有它就没有"做大 ρ"这个动作 |
| **池子面板** ★ | 当前分布、已排除款、已提升款、损耗量 | **模块的编辑台，本作最核心的画面** |
| **归因面板** | ρ 的两因子分解、逐模块/装置贡献、编辑前后对比 | 决策的唯一依据（P2） |
| **架上面板** | 已囤积未开盒、已装配装置与模块、槽位占用 | "燃料还是引擎"的决策现场 |
| **任务面板** | 需求向量 vs 持有物资向量、缺口高亮 | "使用物资"的工作台 |

### 试算 / 沙盒（P6）

装配模块前**实时预览**：池子分布如何变化、ρ 如何变化、40% 损耗吃掉多少。
**没有实时预览的池子编辑是不可用的**——玩家无法凭空评估概率操作。

## 9. 开箱演出

演出规格沿用 v0.1 的四段式（摇盒 → 破封 → 分级预告 → 揭晓入库，总时长 4.5–7s，上限 15s，可跳过），定位为**循环的第一步**。

**§5 给演出新增了一条要求：**
> 开箱时，被玩家**排除**的款不应出现在演出里，被**提升**的款应有可感知的视觉倾向（例如池子里该款的"份量"更重、摇盒音效不同）。

理由：如果池子编辑在演出中不可感知，玩家会觉得自己的施工没有落地。**演出的职责是让玩家看到自己的池子在起作用。**

**工程铁律（不变，且更重要）：**

> 1. `GachaService.roll(series_id, pool_state, seed) -> Result` 是**纯函数**，输入是**当前池子状态**而非套系基础配置。
> 2. `EvalService.compute(state) -> {rho, m_bar, d_bar, b, sigma, pool_distribution, attribution}` 也是**纯函数**。
> 3. **五个面板、试算、兑现对照全部共用 `EvalService`**，绝不允许各自实现。
> 4. `EvalService` 与 `GachaService` **必须共享同一套池子求值路径**——"显示的分布"和"实际抽取用的分布"必须是同一份代码算出来的。这是 P1 的工程保证，也是本作最容易出 bug 的地方（**池子编辑引入了第二份可变状态，一旦两处不同步，玩家的所有施工都不再可信**）。
> 5. 池子状态变更必须**走单一入口**（`PoolService.apply(module)`），禁止任何地方直接改概率。

## 10. 全收集：终局

### 10.1 终局情感

全收集的收尾不是"我终于抽到了"，而是 **"我算赢了它"**。

常规款靠池子编辑工程化收敛，隐藏款保留最后一点运气但有保底兜底。**全收集是玩家工程能力的证明。**

### 10.2 终局结构

| 阶段 | ρ | 玩家体感 | 池子状态 | 收集状态 |
|---|---|---|---|---|
| 开局 | < 1 | 花一个少一个，紧张 | 原始池 | 零星几款 |
| 破局 | ≈ 1 | 勉强转得动 | 首次排除无用款 | 首个套系过半 |
| 起飞 | 1–3 | **滚起来了** | 模块开始集中概率 | 快速补全前期套系 |
| 工程期 | 3–10 | 我在设计这个池子 | 池子按目标塑形 | 长尾款显形 |
| 收官 | 10+ | 碾压 | **池子收敛到只剩缺口款** | 集齐（隐藏款除外） |

### 10.3 后期摩擦的来源

后期摩擦**必须来自需求结构**（任务越来越需要分散、稀有的物资类别），而不是调低概率。这条是硬的：**用低概率撑时长会直接摧毁 P1 与"可信的未知"。**

## 11. 教学曲线

ρ 与池子编辑都是多参数概念，门槛高于"开盲盒收集"。**这是本设计最大的用户层代价，必须用教学设计补偿。**

| 阶段 | 引入内容 | 玩家此刻理解的事 |
|---|---|---|
| 0–10 min | 只有开盒 + 交付 + 显示 ρ | "原来这游戏有个循环" |
| 10–30 min | 引入**转化** | "我能把没用的换成有用的" |
| 30 min–1 h | 引入**装置**（只有转化端） | "物资可以留着变强，而不是用掉" |
| 1–2 h | 引入**模块·排除**（单一操作，无损耗概念） | "我能让某些款不再出现" |
| 2–3 h | 引入**模块·提升 + 40% 损耗** | "编辑池子有代价" |
| 3 h+ | 方差轴、场景约束、多套系 | "我要在两条轴之间取舍" |

**第一小时只暴露一个维度。**
**"燃料还是引擎"必须在 30 分钟内出现**——它是本作的灵魂，不能埋太深。
**40% 损耗这个概念要单独教**，它是池子编辑全部重量的来源，教不会玩家就会觉得系统在骗他。

## 12. 风险与对策

| # | 风险 | 后果 | 对策 |
|---|---|---|---|
| **R1** | **"使用物资"退化为唯一解**（最大风险） | 深度消失，循环变成点击流水线 | §3 燃料/引擎永久取舍；§3.2 二级取舍；§7 三轴冲突 + 场景约束；槽位硬上限 |
| **R2** | **池子编辑太强，全收集失去挑战** | 收官阶段变成无脑收敛，游戏提前结束 | C1 零和 + C2 40% 损耗 + C4 槽位有限 + C5 排除上限 + **C3 隐藏款免疫** |
| **R3** | **池子编辑变成第二个工作台，抢走中心机制的注意力** | "燃料还是引擎"的简洁取舍被淹没 | 模块种类要少、效果要直观；模块与装置**共用槽位**，强制二选一 |
| **R4** | **池子状态与显示不同步**（技术性但致命） | 玩家所有施工失去可信度，等于暗改概率 | §9 铁律 4/5：单一求值路径 + 单一变更入口 + 回归测试 |
| **R5** | 物资种类爆炸，超出心算能力 | 玩家放弃规划，改成乱点 | P6 试算 / 沙盒；任务面板用需求向量 vs 持有向量对照，而非列表 |
| **R6** | ρ 起飞后循环失去张力 | 后期变成无脑挂机 | §10.3 需求结构提供摩擦；每个数量级解锁新套系与新物资类别 |
| **R7** | 数字膨胀但体验空洞 | ρ 从 1e3 到 1e6，玩家毫无感觉 | ρ 必须绑定**可感知产出**（真的开出更多更好的东西）；每个数量级要有新的可感知内容 |
| **R8** | 无付费导致肝度失控 | 靠调低概率撑时长，毁掉 P1 | 用**内容量**而非低概率提供长期目标；隐藏款 2% 不随进度衰减 |
| **R9** | 用户层收窄 | 目标用户从"休闲收集玩家"变为"系统思考型玩家" | **接受这个取舍并据此外宣**；用 §11 尽量扩大入口 |
| **R10** | 装配误操作的恐惧让玩家不敢决策 | 中心机制被主动回避 | §3.3 可逆但昂贵；选择点必须显示"放弃了什么" |

**R1、R2、R3 是本轮新增机制带来的三个核心风险。** R2 是池子编辑的内在风险（太强 → 崩），R3 是它的外在风险（太复杂 → 抢戏），两者需要相反方向的对策，**调参空间很窄，切片必须专门测**。

## 13. 垂直切片范围

**切片目标：验证"使用物资"这一步好不好玩，并验证池子编辑的强度是否可控。**

要回答的问题：
1. 玩家拿到物资时，**会不会真的犹豫**"用掉还是留着"？（§3）
2. 玩家能否在 2 分钟内说出自己 ρ 的主要来源？（P2）
3. ρ 从 0.8 涨到 2.4 时，**有没有爽感**？
4. **玩家能否理解 40% 损耗的含义**，并据此做出取舍？（§11）
5. **玩家会不会把池子编辑到过强**，让收集失去挑战？（R2）
6. 池子编辑有没有淹没"燃料还是引擎"这个中心机制？（R3）

### 13.1 做

- [ ] **`EvalService`：纯函数计算 ρ / M̄ / D̄ / B / σ / 池子分布 / 逐项归因**（一切的地基）
- [ ] **`PoolService`：池子状态的唯一变更入口**（§9 铁律 5）
- [ ] **循环 / 池子 / 归因 / 架上 / 任务 五个面板**
- [ ] 1 个套系：8 常规 + 1 隐藏
- [ ] **2 类物资**（类别 × 品质两维），足够支撑转化与任务需求
- [ ] **任务系统**：3 个可重复常规任务 + 1 个里程碑任务，需求向量化
- [ ] **燃料/引擎取舍**（中心机制，必须最早实现）
- [ ] 装置：两端各至少 2 个，含 1 组跨端非线性组合；共用槽位池（4 槽）
- [ ] **模块：排除 + 提升 + 40% 损耗 + 零和约束 + 隐藏款免疫**（C1–C3）
- [ ] **池子分布实时预览**（P6，不可省）
- [ ] **转化系统**：带损耗，损耗率可被装置影响
- [ ] 试算 / 沙盒
- [ ] 分布直方图（编辑前后对比，§7）
- [ ] 兑现链条：开盒 → 四段式演出 → **被排除款不出现、被提升款有视觉倾向** → 产出对 ρ 的影响提示
- [ ] 盲盒囤积 + 兑现时机选择
- [ ] 概率与池子状态公示界面
- [ ] **手动设定 ρ 曲线做手感测试**（不接真实经济，先验证爽感）
- [ ] 存档 + 全数据驱动配置（含池子状态）
- [ ] 开箱日志（seed + 池子快照 + 结果，可复现）

### 13.2 不做

- 成品美术与音效（占位资源）
- 社交、排行榜、交换（仅预留接口）
- 第 2 个及以后的套系
- 里程碑任务链、成就系统
- **回收（Recover）类模块**（留到第二切片）
- 剧情、角色养成
- 本地化、设置菜单、手柄适配
- 付费、广告、任何变现

### 13.3 切片成功判据

任一成立即继续：
- 测试者在**无人引导**的情况下，主动讨论"这个要不要留"；
- 测试者能说出自己 ρ 的主要贡献来源；
- 测试者表现出"等我把池子编好再开这批盒子"的囤积行为；
- 测试者在被排除款与缺口款之间做出**有意识的取舍**；
- 测试者连续调整装配 ≥3 次而不觉得烦。

### 13.4 切片失败信号（要正视）

- 测试者把物资**全部**用掉，从不考虑装配 → 中心机制不成立；
- 测试者把物资**全部**留下，从不完成任务 → 循环张力不成立；
- 测试者问"这些数字是干嘛的" → §11 教学失败；
- **测试者在 10 分钟内就把池子编辑到接近必出，此后不再关心开箱** → R2 失控，损耗率与槽位上限需要重调；
- **测试者完全忽略池子面板，只玩排除** → R3 成立，池子编辑需要缩减而非保留。

## 14. 技术骨架（Godot 4.5）

### 14.1 目录结构

```
res://
  autoload/
    game_state.gd         # 运行时状态（物资、装置、模块、任务、囤积盲盒、保底计数）
    pool_service.gd       # ★ 池子状态的唯一变更入口：apply(module)
    eval_service.gd       # ★ 纯函数：state -> {rho, m_bar, d_bar, b, sigma, pool_distribution, attribution}
    gacha_service.gd      # ★ 纯函数：roll(series_id, pool_state, seed) -> Result
    task_service.gd       # 任务需求匹配与结算
    save_service.gd       # user:// 存档（JSON）
  data/
    defs/
      material_def.gd     # extends Resource：类别、品质、堆叠规则
      device_def.gd       # extends Resource：作用端、目标、系数、条件、互斥
      module_def.gd       # extends Resource：编辑操作类型、目标、强度、损耗率
      task_def.gd         # extends Resource：需求向量、奖励、可重复性
      series_def.gd       # extends Resource：基础权重表、隐藏款参数、保底参数
    series/
      series_01.tres
  scenes/
    panels/               # 循环 / 池子 / 归因 / 架上 / 任务
    loadout/              # 装置与模块装配工作台 + 实时预览
    workbench/            # 转化
    gacha/                # 兑现演出（四段式，独立可测）
    collection/           # 图鉴 / 套系进度
  ui/
  tests/
```

### 14.2 工程铁律

1. **`EvalService` 与 `GachaService` 都是纯函数、不依赖节点**，可在无头模式跑单测。给定 `(state, series, seed)`，输出必须完全确定。
2. **池子状态只允许通过 `PoolService.apply(module)` 变更。** 禁止任何地方直接改概率。这是本作头号 bug 源。
3. `EvalService` 与 `GachaService` **共享同一套池子求值路径**——"显示的分布"和"实际抽取用的分布"必须是同一份代码算出来的。
4. 五个面板、试算、兑现对照**全部共用 `EvalService`**。
5. **池子编辑必须写回归测试**：给定一组模块，`PoolService` 的输出分布必须满足 C1（和恒为 98%）、C2（损耗率）、C3（隐藏款恒为 2%）。这三条是设计红线，必须由测试守护，不能靠人工检查。
6. 存档记录每次兑现的 `{ seed, series_id, pool_snapshot, state_snapshot, item_id, star }`，四个用途：开箱日志、可复现凭据、玩家信任基础（P1）、归因回归测试的数据源。

### 14.3 数据驱动

- 内容用自定义 `Resource`（`.tres`）：`MaterialDef` / `DeviceDef` / `ModuleDef` / `TaskDef` / `SeriesDef`。
- **模块与装置参数必须完全数据化**（作用端、操作类型、目标、强度、损耗率、条件、互斥标记）。新模块、新装置、新任务应可纯配置产出，不改代码。
- 长期内容量 = 模块数 × 装置数 × 任务结构数 × 物资类别数。如果每个都要写代码，内容永远做不够。

## 17. 一句话总结

**盲盒的期望不是定数，是玩家手里的一个可编辑的池子。**
每份物资都在问同一个问题——**用掉它推进循环，还是留下它改造循环**——
而玩家对池子的每一次编辑，都是在收集速度与循环效率之间，亲手划下一条线。
